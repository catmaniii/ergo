# 语音回复由运行时跟着回合决定和合成：agent 写口语总结，没写先追问一次，再兜底截

规格第 22 节：用户发语音时 agent 用语音回复，"是否用语音、什么算'长'由运行时判定和兜底，不只靠提示词"；回复长的由 agent 写一段口语总结来合成，详细内容照常发文字。32 号票要定的是：这件事挂在哪里、agent 和运行时各做什么、兜底怎么做、界面上文字和语音的关系。第一版评审后用户（2026-10-08）又定了两条：语音这一轮不流式显示、短回复合成好只出语音；没写总结时先追问 agent 一次，再兜底。

## 决定

- **运行时跟着回合做**（`voice/voice-reply.ts`）：跟着会话频道上的回合事件（`turn_start`、agent 的消息、`turn_end`）走。这一轮开始时输入是用户的语音（有参考音色），就建出 agent 语音对象（`replying`）；一轮完成时看这一轮处理的用户消息里最后一条是不是语音，是就把这一轮 agent 发出的文字定成口语稿、排队经 audio.cpp 合成。
- **agent 写口语总结**：回复长、或有代码表格链接这类念不出来的内容时，用 `spoken_summary` 工具写一段口语总结。写不写都不影响"用不用语音"——那由运行时按用户的输入定；什么算长也由运行时按字数估。
- **没写先追问一次，还是没写才兜底截**：回复长、agent 这一轮没写总结时，运行时追问它一次（"给刚才的回复写一段适合听的口语总结，用 spoken_summary"）。这一次不算新回复：没有 `turn_start` / `turn_end`，它说的话不进会话、不流式推送，工具照常经守卫（调用记录照常进会话），用量照常记账。追问后还是没写，运行时取回复开头念得完的几句，加一句"详细内容我发在聊天里了"。守护进程里没有不经 pi 的模型调用（ADR-0011 的后果之一），兜底也不破这个例。
- **追问是 `AgentSession` 的一个通用钩子，口语总结工具走装配**：会话在追加 `turn_end` 之后同一刻问 `voiceReplies.followUp(会话, 输入)`，有追问就在处理下一条输入之前交给子进程（宿主协议不变，就是一条 `user_input`）。口语总结工具不由会话类塞进去，而是和别的代为执行的工具一样由各处的装配放进去（秘书、任务维护者起草和执行、项目维护者各段；执行时在 `executionSetup` 一处），所以 `MaintainerAssembly.hostTools`、守卫的工具包、固定上下文里的工具清单都是真实的那一份。
- **agent 的语音是自己的对象和事件**（`AgentVoiceRecord`、`agent_voice`、消息里的 `tts_audio` part），不和用户语音的 `VoiceRecord` 合成一个联合类型：两者的生命周期（识别 / 回复、追问、合成）、字段、素材和删除的规矩都不一样，混在一起要改遍 31 号票已有的每个读者。概念上它们都是"语音消息"（CONTEXT.md），界面上用同一个气泡；共用的只是版本、一次一条的队列、开着只留一条的说明这几件小工具（`voice/shared.ts`）和前端的按版本归并。
- **界面上（用户定）**：语音这一轮不流式显示回复，只有"正在回复…"（agent 语音对象记着这一轮开始的序号，那之后 agent 的消息先不显示文字）；回合结束后，短回复（整段合成）合成中显示"正在合成语音…"，合成好只出语音气泡，文字收进语音里（长按"转文字"展开）；长回复（口语总结）的文字和附件照常显示，合成好再加气泡；没合成出来的照常显示文字，带一条说明。事件日志、agent 的会话里文字原样都在。往上翻、重连补发同一套规则。
- **失败一律退回只发文字**：合成之后不论哪一步出错（服务没开、忙、出错、超时、回的不是 WAV、存不进媒体库、参考音色被删了）都走同一个失败处理。服务忙（503）不等超时，说明里写"语音服务忙"。
- **合成可以重做**：只是一次 HTTP 调用，守护进程在合成途中停了，重启后还在"合成中"的重做一遍，不进 23 号票的"中断不确定"；在追问的直接兜底；还在回复的记成没用语音（那条输入由会话标成中断）。

## Considered Options

- **全靠提示词**（系统提示里写"用户发语音时回复要短、像说话"，把 agent 的整段回复都合成）：规格明确不要；而且长回复、带代码的回复念出来没法听。
- **没写总结时直接兜底截，不追问**（第一版的做法）：省一次模型调用和等待，但兜底的总结只是回复的开头，概括得不好。用户定先追问一次。
- **追问作为一条运行时通知、再起一轮**：总结一定是 agent 写的，但那条通知和 agent 的回答会出现在聊天里，还占一个回合。所以追问不算回合、它说的不进会话。
- **守护进程直接调模型概括**：ADR-0011 去掉大模型修正时说过的麻烦（出错时正文可能带出 key、短句里模型容易去"回答"原文）这里一样有，而且会是守护进程里唯一一处不经 pi 的模型调用。
- **在 `AgentSession` 里收回复、在回合结束时直接合成**：知道得最准，但要往秘书、维护者共用的会话类里加一块和它的职责无关的逻辑。会话类只加两个钩子（输入后面的说明、回合后的追问），判定和合成都跟着事件走。
- **口语总结工具由会话类统一追加**（第一版的做法）：一处就够，但装配记下的工具清单和实际给子进程的不一样，子 agent 收窄、固定上下文的工具清单都会看错。
- **语音这一轮照常流式显示、整段合成时文字也照常显示**：最省事，但"转文字"就成了重复，和用户"agent 的语音不默认展开文字"、"短回复合成好只出语音"的要求不符。

## Consequences

- 判定看的是"这一轮处理的用户消息里最后一条"：运行时的通知引起的一轮（任务执行中的阶段通知、审批结果）不用语音，哪怕用户上一句是语音；31 号票里重新识别成功后交给 agent 的通知例外，它就是用户的语音（31 号票导出 `isVoiceRetryNotice`）。这一轮开始时只看交给 agent 的那条输入（插话要到回合结束才知道），所以插话改变了结论时：开始是语音、最后一句是文字的，前端在回合结束后补显示文字；开始不是语音、插话是语音的，这一轮照常流式显示，回合结束后照样合成。
- 一轮只回一条语音（幂等键 `agent-voice:<输入的消息 id>`），合成一次一条（显卡和 drama 共用）。合成在 agent 处理下一条输入时照常进行，语音消息可能排在下一轮的回复后面。追问在下一条输入之前，所以用户紧接着说的话要等追问完才交给 agent。
- 短回复要等合成完才能听到也看到：服务冷启动时可能等几十秒（合成中有提示，失败了文字回来）。
- 前端的时间线（完整视图）按 agent 语音对象收起文字：`timelineItems` 依赖 `UiState.agentVoices`，往上翻时这一页的语音对象跟着历史分页一起取回。
