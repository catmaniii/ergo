# 关注类别设置以配置区的文件为真相，事件只做同步；已确认任务的调严在确认时连规则快照

规格第 9 节："关注类别注册表是数据，放在数据目录的配置区，agent 写不到"；"改完后下一次判定就按新设置走"；用户自己加的类别"随时可以改规则、改处置或删除"。03 号票定了文件 `config/watch-categories.json` 和它的格式，守卫每次判定现读。26 号票要做设置页、要让别的前端跟着变，还要定下全局设置改了以后，正在执行的任务怎么办。二狗别处的约定是"事件日志是唯一真相"（ADR-0006 是素材的例外），所以这里要说清楚：

## 决定

- **文件是关注类别设置的真相**。守卫、任务模块、快速动作每次现读它（经 `watch-categories/` 的 `WatchCategoryService.current()`）；设置页的修改先写文件（临时文件再改名），再在关注类别频道追加一条 `watch_category_settings` 事件，事件里是设置的完整样子，给前端同步、留个记录。
- **文件和最后一条事件不一样时，以文件为准补一条事件**（`by: "system"`、`change.op: "file"`）：启动时、用户手改过文件、文件被改坏了。坏了时事件里带上问题，表格沿用上一次有效的设置，设置页据此提示、给出修复（恢复成上一次有效的，或恢复默认；坏文件另存一份），待我处理里放一条事项，修好后自动归档。不从事件反写文件：用户手改的就是他要的。
- **已确认的任务：生效处置 = 当前全局设置和确认时快照的本任务设置取最严**（评审后定，取代第一版的"本任务的调严只记处置、跟着全局走"）。确认计划时，本任务调严过的全局自定义类别连同当时的名字和规则写进计划（`snapshotWatchCategories`），本任务新加的类别本来就带规则；守卫拿到的本任务设置是单独的类型 `TaskWatchSettings`。于是全局后来调严照样生效（判定时取最严），全局调松、改规则或删除放松不了已确认的任务；没调严的全局类别不快照，跟着全局走（调松也跟着松）。设置页删除或调松一个仍被进行中任务快照着的类别时，事件里记下有几个任务（`heldByTasks`），界面提示"N 个进行中的任务仍按确认时的设置检查"。
- **自定义类别的 id 不重用**：全局的是 `c-<n>`，n 取用过的最大号（事件里、当前文件里、计划里）加一；本任务的类别用单独的命名空间 `<任务 id>-c<n>`，和全局的不会撞。快照下来的全局类别保留原 id，和全局同 id 的那份各按各的规则匹配，一同命中时取最严。

## Considered Options

- **事件日志是真相、文件是派生**（启动时、每次修改后按事件重写文件）：和别处一致，备份、恢复也只看事件日志。但用户手改文件会被悄悄覆盖；文件坏了时也说不清该信谁。03 号票已经让守卫直接读文件，用户也知道这个文件在哪。
- **设置只存在事件日志里，不要文件**：违反规格"注册表放在配置区"；事件日志所在的数据库区用户没法手改、示例配置也没法给。
- **本任务的调严只记处置，规则和存废跟着全局走**（26 号票第一版，`customOverrides`）：全局删了类别或改了规则，任务里的调严跟着失效。用户确认计划时看到的是"这个任务里它是永不"，事后在设置页的一次删除就把已确认的约束放松了，没有任何提示。评审定为不可接受。
- **把全部全局类别都在确认时快照**：已确认的任务彻底不受全局改动影响。但全局调严也不再生效，用户在设置页收紧一个类别，正在跑的任务却照旧，和"改完后下一次判定就按新设置走"不符。

## Consequences

- 读设置可能顺带追加事件和待我处理事项（同步）：`current()` 不是纯读，调它的地方不能在事件存储的事务里（现有的调用方都在事务外：守卫的 `guard_request`、代为执行的工具、卡片动作的 `run`）。
- 备份里的设置是配置区的那份文件（备份按文件快照），事件只是记录；恢复后启动时以文件为准补一条事件。
- 13 号票执行任务时，判定用现取的全局设置（`daemon.watchCategories.current()`）加确认时算一次的 `toGuardPlan`；`GuardPlan` 不必跟着全局设置重算。14 号票的计划变更要照样在确认变更时快照。
- 全局设置里删掉的类别可能还活在已确认的计划里；设置页只在删除、调松时报个数，计划卡和任务详情里能看到本任务的类别。
