# 关注类别设置以配置区的文件为真相，事件只做同步；本任务对全局类别的调严只记处置

规格第 9 节："关注类别注册表是数据，放在数据目录的配置区，agent 写不到"；"改完后下一次判定就按新设置走"；用户自己加的类别"随时可以改规则、改处置或删除"。03 号票定了文件 `config/watch-categories.json` 和它的格式，守卫每次判定现读。26 号票要做设置页、要让别的前端跟着变，还要让正在执行的任务跟着全局设置走。二狗别处的约定是"事件日志是唯一真相"（ADR-0006 是素材的例外），所以这里要说清楚：

## 决定

- **文件是关注类别设置的真相**。守卫、任务模块、快速动作每次现读它（经 `watch-categories/` 的 `WatchCategoryService.current()`）；设置页的修改先写文件（临时文件再改名），再在关注类别频道追加一条 `watch_category_settings` 事件，事件里是设置的完整样子，给前端同步、留个记录。
- **文件和最后一条事件不一样时，以文件为准补一条事件**（`by: "system"`、`change.op: "file"`）：启动时、用户手改过文件、文件被改坏了。坏了时事件里带上问题，表格沿用上一次有效的设置，设置页据此提示、给出修复（恢复成上一次有效的，或恢复默认；坏文件另存一份）。不从事件反写文件：用户手改的就是他要的。
- **计划里本任务对全局类别的调严只记处置，不抄规则**：内置类别进 `builtin`，全局自定义类别进 `customOverrides`（守卫的设置里新加的一项，只在计划里出现）。判定时规则从当时的全局设置里取，所以全局改了规则就按新规则匹配，删了就不再命中；本任务新加的类别（带规则的）只存在计划里，不受全局改动影响。同一个自定义类别 id 的几份和调严一律取最严。
- **自定义类别的 id 不重用**：`c-<n>`，n 按建过的个数往上数，删掉的 id 不再分配，计划里对旧类别的调严不会落到新类别上。

## Considered Options

- **事件日志是真相、文件是派生**（启动时、每次修改后按事件重写文件）：和别处一致，备份、恢复也只看事件日志。但用户手改文件会被悄悄覆盖；文件坏了时也说不清该信谁。03 号票已经让守卫直接读文件，用户也知道这个文件在哪。
- **设置只存在事件日志里，不要文件**：违反规格"注册表放在配置区"。配置区是受保护区域，agent 用任何方式都写不进去；事件日志所在的数据库区同样受保护，但用户没法手改、示例配置也没法给。
- **计划里把全局自定义类别连规则一起抄一份**（12 号票的 `toGuardPlan` 原来这样做）：执行中的任务和全局设置脱节，用户在设置里删了类别，任务里照样命中，和规格"已确认的计划里，来自全局的那部分跟着全局走"不符；而且同一个 id 两份都命中时，守卫只认先到的那份处置，调严白调。

## Consequences

- 读设置可能顺带追加事件（同步）：`current()` 不是纯读，调它的地方不能在事件存储的事务里（现有的调用方都在事务外：守卫的 `guard_request`、代为执行的工具、卡片动作的 `run`）。
- 备份里的设置是配置区的那份文件（备份按文件快照），事件只是记录；恢复后启动时以文件为准补一条事件。
- 13 号票执行任务时，判定用现取的全局设置（`daemon.watchCategories.current()`）加确认时算一次的 `toGuardPlan`；`GuardPlan` 不必跟着全局设置重算。
