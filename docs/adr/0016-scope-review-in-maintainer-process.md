# 范围审视在维护者自己的子进程里另开一次调用；范围记录以守护进程的事件为准，项目档案里的文件是投影

规格第 10 节：范围审视有两个时点（维护者会话压缩时、每张工单结束时），对照立项书、任务计划和用户给过的授权（包括用户在会话里直接说的话），用户授权过的记为范围变更、写进项目档案，没授权的记为越界、在待我处理放一条不推送的通知；`before_agent_start` 把最近 5 条范围记录拼到维护者系统提示末尾。守护进程不跑模型（ADR-0002），审视的模型调用要放在某个子进程里；每张工单是一段新的 pi 会话（ADR-0012），旧段里的 `appendEntry` 新段拿不到。18 号票定成：

- **审视在维护者自己的子进程里，会话之外另开一次调用**：装配参数带审视用的模型（便宜模型）、审视的说明（那次调用的系统提示）、对照物和近期范围记录（宿主协议 9 的 `scopeReview`）。子进程用同一个 `ModelRuntime` 的 `completeSimple` 调审视的模型，不写进维护者的会话；用量另报一条（`purpose: "scope_review"`）。压缩时在 `session_before_compact` 里审视要压缩掉的消息；工单结束时守护进程送 `scope_review`，子进程审视会话里还没审视过的部分（上次压缩留下的和之后的）。两种结果都 `appendEntry` 进会话（副本）并以 `scope_review_result` 报回。
- **审视的说明、对照物和近期范围记录都由守护进程写好交给子进程**（照秘书压缩指令的先例，运行时封装层不写业务文字）：拉起时进装配，对照物和近期范围记录之后变了在下一条输入之前、要审视时送 `scope_context`。子进程不回头问守护进程；`before_agent_start` 拼的就是它手里最新的那段。对照物里有用户在审批卡上批准过的调用（算授权过）。
- **审视的输出是约定的 JSON**（`{"records":[{"kind","summary","detail?","basis?"}]}`），取不出就报原因、不记；不用工具调用约束输出（不是每个 provider 都能强制调用某个工具）。
- **范围记录以守护进程的事件为准**：每条一个 `scope_record` 事件（项目维护者的在项目列表频道，不属于项目的任务的在任务看板频道，前端整条补发），同一事务里维护者会话频道上一条同种类的 `timeline_record`（时间线标出），越界另有一条待我处理的通知。项目档案的 `scope-records.md`（不属于项目的任务：任务产出区里的同名文件）是事件的投影：追加之后往文件里添，启动时按记录号补上没写进去的。
- **工单结束的审视在子进程退出之前做，且和工单的结束同一事务**：派单器在写回检查通过之后（或者催写回到了次数时）先要审视，结果回来才让这一段和工单结束；子进程审视时排在后面的命令（含闲置退出的 `exit`）等它，会话这一侧在审视做着时拿着 agent 管家的 `holdAwake`（管家只认"拿着不闲置退出"，不认得范围审视）。子进程已经不在了（闲置退出、守护进程重启）就按这一段的装配再拉起一个来审视。会话这一侧的协调（送给哪个子进程、等结果、超时、对照物送没送过）单独放在 `conversation/scope-reviews.ts`，`AgentSession` 只在几处接上它。
- **范围记录记着审视看到的用户原话从哪来**（`sources`：对照物里的消息和审批卡上的批准、会话里交给维护者的输入）：彻底删除其中一条时，记着它的范围记录连同时间线记录、越界通知一起改写（改写函数表的"引用"），再追加一条改写后的新版本让页面和文件换掉；会话文件里审视结果的副本有彻底删除就整个换掉。

## Consequences

- 审视用的是维护者自己的凭据和子进程名额，不另起进程；审视的用量自然记在维护者当时所属的名下（工单段是任务），不算进阶段预算。
- 每张工单结束多一次模型调用、晚一点结束；审视出错（模型出错、回复不合约定、子进程中途退出、超时）不卡工单：照常结束，会话里一条说明、这次不记范围记录。
- 维护者看到的"近期范围记录"是守护进程保存的，不靠会话里的 `appendEntry`：换了工单分段、重置维护者之后也在；会话文件里的那份只是副本。
- 对话段（用户直接和维护者聊）只在压缩时审视，结束时不审视；重置维护者时直接结束的工单段不强行审视，时间线上如实记"重置时这段没做范围审视"。
- 范围记录里可能引着用户的原话：删除项目时随项目改写；彻底删除时按 `sources` 连带改写——审视的模型原样引了还是转述了不去辨认，凡是看到过那条消息、那次批准的记录都改（宁可多改，摘要、说明、依据换成删除标记，记录本身和种类、归属留着）。工单内容里转述的用户的话（16 号票）删不掉，如实写进 `PURGE_LIMITS`。
- 以后换掉 pi 时，新的运行时也要支持：会话之外另开一次模型调用并拿到用量、压缩之前拿到要压缩的消息、每条输入之前改系统提示（契约测试 `scope-review.contract.test.ts` 守着）。

## Considered Options

- **守护进程自己调审视的模型**：违反"守护进程只当管家、不跑模型"（ADR-0002），凭据和调用超时也要在守护进程里另管一套。
- **为审视另拉一个一次性子进程**（照评审子 agent）：压缩时要审视的是维护者会话里正要被压缩掉的消息，只有维护者的子进程手里有；工单结束时另拉一个也要把这段对话交过去，绕过"会话文件的形状只在子进程那一层认"（ADR-0004）。
- **审视的调用走维护者会话本身**（让维护者自己审视自己）：会写进会话、占上下文，还会改变维护者的行为；规格要的是另开一次、不进会话。
- **子进程每条输入之前向守护进程要近期范围记录**（请求 / 回复）：多一个往返和超时处理；守护进程本来就知道什么时候变了，推过去更简单。
- **范围记录只放在维护者会话频道上（时间线记录）**：会话频道打开时只补发最近一页，简版项目页拿不全；所以另在项目列表、看板频道上各记一条。
- **文件为准**：维护者也能写项目档案，文件可能被改坏；事件日志是唯一真相（规格第 2 节），文件只是给人和维护者读的投影。
- **彻底删除时按文字比对找引了原话的范围记录**：模型转述的找不到，阈值也说不清；记下审视看到了哪些、凡是看到过的都改，结果确定。
- **让审视的模型在依据里标出引了哪几条**：靠模型守约，漏标就留下原话。
