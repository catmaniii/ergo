# 工具包一变就在两次模型调用之间停下、按新装配接着同一个会话；MCP 服务进程归守护进程管

规格第 20、21 节：工具包（skill、MCP、bash、联网）一变就立即生效——用户批准或直接改、维护者自己增减 skill 之后，守护进程等维护者做完手头这一步，就重启子进程、按新工具包重新装配会话、从会话文件接着干；MCP 服务进程由守护进程拉起、放进 Job 对象、按登记注入凭据，agent 经守护进程转发调用、碰不到凭据，它们不在 LSM 登记。27 号票定成：

- **"做完手头这一步"是宿主协议里的一个命令**：宿主协议 10 加 `yield` 和回合结局 `yielded`。子进程那一层（ADR-0004）包一层 pi 的 `agent.finishTurn`：收到 `yield` 之后，这一轮模型那一步调了工具、工具结果都回来了（下一次模型调用之前），就让回合在这里结束（`{ action: "end" }`），报 `turn_end` 的结局 `yielded`；模型那一步已经不再调用工具（在写最后的回复）时照常结束。停下时排着、还没送进上下文的插话由子进程清掉队列并扣除，不算收下，守护进程照样留在队里。
- **守护进程这一层是 `AgentSession.reassemble(notice)`**：忙时发 `yield`，回合以 `yielded` 结束后停掉子进程、马上按新装配拉起（同一个会话名），就绪后把"工具包已变更：……"作为一条用户输入交过去，原来那条输入仍算在处理中，接着的这一轮结束时才记成处理完；闲着时停掉子进程，下次有输入再拉起；休眠时什么都不停。后两种情况"工具包已变更"跟在下一条输入后面作上下文消息。谁的工具包变了、要不要重新装配由拉起它的模块判断（任务维护者看计划里的工具包，项目维护者看项目的工具包，16 号票的 `RESHAPING_CHANGES` 加上 `toolkit_changed`）。
- **换工具包接着同一个会话**：skill 只经宿主协议的 `skillPaths`（pi 的 `noSkills: true` 加 `additionalSkillPaths`），工具白名单照工具包（有 skill 时一定含 `read`）；pi 打开已有的会话、发现系统提示或工具变了，记一条系统消息（新的系统提示，加了、去掉了哪些工具）。第一阶段的 deepseek-flash 不认会话中途的系统消息，pi 发给它时把更新后的系统提示放回开头、工具列表整份重发，所以那一次的提示词前缀缓存失效——规格说的"接受的代价"。
- **MCP 服务进程是守护进程的子进程，每个 MCP 一个 Job 对象**：按需拉起（会话装配时在后台拉起拿参数说明，或者第一次调用时），经一个闸门进程先进 Job 再起服务进程（`process/gated-spawn.ts`，和带类型的 bash 工具共用同一个闸门）；Job 设成句柄关闭即结束，守护进程被杀时随之结束。不放进 agent 管家的 Job：那里按"从活着的 agent 走不到"回收孤儿，会误杀服务进程。服务进程的环境是系统变量白名单加登记里写的变量，凭据写成 `{ "fromEnv": "变量名" }`，从守护进程的环境里取（由 LSM 注入守护进程），agent 子进程和它起的进程的环境里没有；注入的凭据值在服务进程的输出进守护进程日志、工具结果交给 agent 和写进事件日志之前都擦掉。守护进程里是一个只实现 `initialize`、`tools/list`、`tools/call`、取消通知的 JSON-RPC stdio 客户端，不引入 MCP SDK。
- **会话里的 MCP 工具是守护进程代为执行的工具**：名字 `mcp__<MCP 名>__<工具名>`，在守卫的工具注册表里按登记的类别、底线、参数规则、"只读或幂等"判（来源 `mcp`）；登记里不写联网标记的按要联网算，联网开关关着时会话里没有它们，调用也硬拒绝。
- **守卫用此刻的工具包，不用拉起时的**：每次判定把拉起时的守卫视角收窄到现在的工具包（去掉的 bash、联网、MCP 就用不到），正在等审批的调用被批准时也重判。子进程要等做完手头这一步才重启，这期间同一步里剩下的调用、等审批的调用不能按旧工具包放行。

## Consequences

- 宿主协议升到 10：守护进程和子进程要一起升级（握手时版本不同就拒绝，ADR-0004 的规矩）。
- 每次重新装配都让一次模型调用的前缀缓存失效：工具包频繁地改（比如维护者连着增减 skill）会多花 token，这是规格接受的代价。
- 范围审视（18 号票）在做时不换装配：子进程还要交审视的结果。审视兑现之后再重启子进程、接着干。
- 以后换掉 pi 时，新的运行时也要支持"在两次模型调用之间结束回合"和"同一个会话换一套系统提示和工具接着"。
- 正在等一个很长的工具调用（比如等用户批准）时，会话里的工具要等这一步结束、重新装配之后才换；守卫的判定不等：收窄之后的下一次判定、被批准时的重判就按新工具包。扩大的要等重新装配才用得到。
- 停下、重新拉起的这段时间这个维护者算忙；`yield` 发出后这一轮自己正常结束的，和闲着时一样处理。
- MCP 服务进程是守护进程的子进程，不是服务：不在 LSM 登记，不对外监听；守护进程停止时一起结束。服务进程自己起的孙进程也在它的 Job 里。
- 凭据要在 LSM 的守护进程登记里配环境变量，登记文件（配置区）里只写变量名；缺了照样拉起，日志里写明缺了哪些。

## Considered Options

- **直接中断（abort）当前回合再重新拉起**：会话文件里会留下做了一半的回合，要走 23 号票被杀后的那套恢复；而且正在执行的工具调用会被打断。等这一步做完再停就没有这些问题。
- **不重启子进程、在会话里热换工具**：pi 的工具白名单和 skill 都是装配会话时给的，热换要改 pi 的内部状态，越过 ADR-0004 的边界；重新拉起、接着同一个会话文件更简单，也是规格写的做法。
- **MCP 服务进程放进 agent 管家的 Job**：Job 里的孤儿回收会把"不是 agent 后代"的服务进程当孤儿结束；分开放也让每个 MCP 能单独重起。
- **用 MCP 官方 SDK**：只用到四个消息，自己写的客户端几十行，少一个依赖，也好控制超时和取消。
- **MCP 服务进程在 LSM 登记**：它们只是守护进程的工具，跟着守护进程起停；在 LSM 登记要用户多管一批服务，凭据也会散到多处。
