# 语音识别放在守护进程这一侧：按需拉起的 Python 进程，不是 agent

规格第 22 节：用户的语音上传完成后，"守护进程用 faster-whisper 识别出文字"，"识别是运行时自动做的"；第 21 节定了 faster-whisper 跑在"守护进程按需拉起的 Python 识别进程"里。二狗别处的子进程都是 agent（ADR-0002），经 agent 管家拉起、占名额、过守卫。31 号票要定的是：识别进程算不算 agent，归不归 agent 管家管。

## 决定

- **识别进程不是 agent**：守护进程直接拉起 Python（`voice/recognizer.ts` + `recognizer.py`），不经 agent 管家、不占子进程名额、不经守卫（它不调工具，只读媒体库里的一个文件、回一段 JSON）。它放进自己的 Job 对象（不放 agent 管家那个：那里按"从活着的 agent 子进程走不到"回收孤儿），环境照 agent 子进程的系统变量白名单（没有守护进程的密钥），模型只从本机缓存加载、不联网（`HF_HUB_OFFLINE=1`）。
- **识别出的文字就是 faster-whisper 的结果，第一阶段不用大模型修正**（用户 2026-10-08 定）。用户发的语音，识别出的文字默认显示在气泡下方，这段文字就算用户对识别结果的确认，所以语音转写和打的字一样参与快速动作的"点明"判定。
- `startDaemon` 上留了替换口（`recognizerCommand`），测试一律换成假的识别进程（`test/fixtures/fake-recognizer.mjs`），不加载真模型、不占显卡。

## Considered Options

- **识别进程放进 agent 管家的 Job**：少建一个 Job。但孤儿回收会把它当成孤儿结束（和 28 号票的带类型 bash 工具同一个原因）。
- **识别进程常驻**：省掉冷启动（实测多约 4 秒）。但 large-v3 在显卡上占约 2.1 GB 显存，和语音合成（audio.cpp，约 7.3 GB）同时在 12 GB 的显卡上，常驻挤占显存；所以用时拉起、闲置退出。
- **识别完再让大模型（DeepSeek）保守修正**（原规格）：能改掉同音字、补上标点。31 号票做过一版（守护进程直接调 DeepSeek 的接口，改动太大就不用），评审时发现两类麻烦：出错时接口返回的正文可能带出 key 的片段，要另外脱敏；短句里大模型容易去"回答"原文，"像不像修正"的判断很难做稳。用户看过之后决定去掉：气泡下直接显示识别文字、由用户自己看一眼，比多一层可能改坏的修正更可靠。以后要加回来，修正得在交给 agent 之前、由运行时确定地做，而且不能让它的结果绕过用户看到的那段文字。

## Consequences

- 识别进程不受 agent 的资源限制（子进程上限、闲置退出、超时）管，有它自己的：一次一条、闲置 `voice.recognizer.idleMinutes` 退出；一次识别最多等多久按语音时长和设备算（`voice.recognizer.timeout`：余量 + 冷启动 + 时长 × 每秒语音最多等几秒，显卡、CPU 各一个），超时结束这个进程、这条记成失败，后面排队的输入不再等它。
- agent 收到的、素材里存的、气泡下显示的是同一段文字（faster-whisper 识别出的），没有"哪份文字算数"的问题。识别错了的，用户看得见；agent 照着错的文字理解，代价由用户一眼确认来兜。
- 守护进程里仍然没有不经 pi 的模型调用。
