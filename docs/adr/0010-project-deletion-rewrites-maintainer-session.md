# 删除项目：二次确认放在待我处理；先停维护者、复查、再改写事件、最后删文件；属于项目的原话都改写，用户本人的话作为素材留着

规格第 11 节：删除只能从已归档发起，要二次确认；删除时删掉项目档案和维护者会话，但用户在里面说过的话作为素材保留（用户故事 93、131）。第 15 节：事件日志不可修改，例外只有两个——彻底删除（改写成删除标记，ADR-0008），和删除项目时改写该项目维护者会话及立项书的原话（结构字段和状态保留，用户说过的话照样作为素材保留；规格在 15 号票评审后补上了第二个）。维护者会话在二狗里有两份：pi 的会话文件（会话区 `sessions/<维护者>`）和事件日志里的会话频道 `maintainer:<维护者>`（消息、回合、工具调用记录）。项目的原话还散在别处：立项书（`charters` 频道的事件和立项书卡）、这个维护者的审批（审批请求、审批卡、审批决定）和效果日志、待我处理里属于项目的事项。15 号票评审后定成：

- **二次确认是待我处理里的一条通知**：项目页上的"删除"（`project_action` 的 `delete`）只在已归档时可用，不马上删，往待我处理放一条 `project_delete` 通知（"确认删除" / "不删了"，带项目编号），同一个项目已有没处理的就用它。
- **顺序**（`projects/deletion.ts`）：
  1. 先停维护者：马上不再接输入、之后来的输入也不唤起它，等子进程退出（内存里的原文随之没了）；
  2. 复查：停下来的这段时间里用户取消了归档（或者项目已经不在了）就整个中止，什么都不删，维护者恢复成能唤起；
  3. 没变就在同一个事务里追加项目的 `deleted`、改写属于项目的事件（见下）；
  4. 最后删项目档案目录和会话区里维护者的会话文件（pi 的会话文件整个删掉，不逐条改写）。到这一步项目已经删了，不再回头。
- **改写，不删行**：和彻底删除走同一个口子（`EventStore.appendBatch(events, { purge })`），事件日志的行、频道、序号、类型、时间都在，只换负载（规格第 15 节的第二个例外，机制和第一个一样）；派生视图整体重放，提交后 `wal_checkpoint(TRUNCATE)`，连接开着 `secure_delete`，原文不留在 WAL 和空闲页里。
  - 维护者会话频道上的事件整条换成 `DeletedEventPayload`（消息留下 id 和时间）；
  - 立项书正文、维护者的审批和效果日志、待我处理里属于项目的事项：用记忆模块的改写函数表（`memory/rewriters.ts`）按事件类型字段级改写，原话换成删除标记，状态不变（立项书卡还是已处理、审批还是已批准、二次确认还是"确认删除"）。为此登记了 `charter_submitted`、`approval_requested`、`inbox_item` 的改写函数，`charter_decided` 的改写函数和立项书卡、审批卡的 `purge` 连立项书正文、参数摘要一起换掉；
  - 改写过的卡片追加一个改写后的新版本（开着的页面据此换掉手里的卡）。
- **用户本人的话不删，系统记下的内部记录随项目删**（66 号票改；用户 2026-10-10 定分界）：用户本人说过的话（在维护者会话里的发言、投喂的材料、记忆命令）在素材库里，本人的原文另有一份不可修改的副本（ADR-0006）——它们是用户的记忆，不按项目删：删项目不写它们的墓碑，素材模块不把它们当"忘掉"，以后从事件日志重建素材时这些话从原文副本补回；维护者会话不追加 `messages_purged`（66 号票起秘书、跨项目任务的维护者会话里读过这个项目的调用有，见下一条，里面没有素材 id）。这个项目的内部任务由系统自动记下的素材（ADR-0023：内部任务的结局、计划和审批的决定、验收、提问卡的回答、建议卡被关掉……，`memory/internal-records.ts` 认）随项目照彻底删除的口径删：同一事务记一条彻底删除的 `memory_command`（出处 `{ kind: "project_deletion", projectId }`，它不产生"显式记忆命令"素材——不是用户下的命令），素材模块据此删掉素材和索引、记下墓碑，重建时不回来；它们的原始事件大多已经随项目整条换成标记，没换的照彻底删除改写（`purgePlan` 的 `skip`：上面已经改写了的不改第二遍）。外部工作目录（绑定的外部路径）不动。
- **项目之外读过这个项目的调用**（66 号票补；用户 2026-10-09 定：秘书会话里读过这个项目档案的调用，返回内容一起抹掉，秘书当时据此说的话不改；评审后主会话定跨项目任务自己的维护者读到的一起补）：秘书会话里的、涉及多个项目的任务自己的维护者和评审子 agent 的调用没有这个项目的归属，按"读的是不是这个项目的东西"找——读项目档案的工具按返回开头写的项目编号认（名字会被新项目重用，编号不回收）；别的按调用碰到的路径（调用时守卫规范化过的、完整参数里写死的绝对路径）和项目档案、工作目录有包含关系，任一方向都算（读了上级目录、递归扫到项目里也算），写的路径和真实路径都比，经符号链接、目录联接读到的也算，通配符先展开、展不开的按通配符之前的那段目录。找到的照彻底删除的口径在同一事务里字段级改写：完整内容、效果日志、执行记录、会话里的工具调用记录，调用本身、工具名、结局留着；完整内容另记 `purgedBy: "project_deletion"`，详情页写"已随项目删除"（删除项目时改写的完整内容都这样记，过了保留期清掉的说明一起去掉）。这些调用所在的会话（秘书、跨项目任务的维护者）追加 `messages_purged`（改写后的工具调用记录和这几次调用的 id），前端据此换掉手里的记录，agent 据此改写会话文件里这几次调用的参数和返回（同 ADR-0008：等手头这一条处理完、停下、改写、接着拉起）。认不出、清不掉的（环境变量拼出的路径、`python -c` 这类看不透的命令、pi 的 bash 输出太长时另存的临时文件、据此说过的话、备份）照彻底删除的写法如实写在删除的二次确认上（`PROJECT_DELETE_LIMITS`）。还是"删除项目时的改写"这个例外，口子不变（`appendBatch` 的 `purge`）。

- **删除任务照这个做法**（186 号票，用户 2026-10-20 定"任务能删除，连会话和工作目录一起删"；`tasks/deletion.ts`）：不用二次确认事项，网页上确认一次（看板卡的菜单、任务详情的"⋯"、多选），秘书的快速动作 `delete_task` 总要在卡上确认。顺序照上面：先停（没结束的照现有的取消走；维护者停稳手头这一轮再停掉、不再唤起；子 agent 停下、等交回的说明落盘）→ 复查（又开始做了就中止，维护者恢复）→ 同一事务追加任务的 `deleted`、改写属于它的事件 → 最后删维护者和子 agent 的会话目录、工作目录 `outputs/<任务>`。改写的范围是项目删除里"一个维护者"那一份缩到一个任务：任务自己的记录（看板上的任务事件、现在生效的计划、任务书和计划、并行、触发登记——和删项目时的内部任务共用，279 号票起是任务、子 agent、触发底座各自的删除参与方），它自己的维护者会话（整条标记；由项目的维护者做的不碰），它的卡片和维护者、子 agent 的审批卡（整条标记；别人会话里的提问卡、建议卡、快速动作卡、工单卡、归档清单不动），审批、效果日志、执行记录、完整内容、范围记录（字段级），待我处理里它的事项（改写并删掉）。素材照 66 号票的分界：从这些被改写的事件采到的系统记录随任务彻底删（记忆命令的出处 `task_deletion`），用户本人的话留着。**能不能删照项目的规矩**：项目还在时属于项目的东西由项目管——项目内部任务、转为项目了的、由项目的维护者做的单项目任务都不能单独删（项目删掉了的可以，会话已经随项目删过了），项目在用的运营任务写明到项目里改运营方案。和删项目一样不动的：消耗的账、秘书会话里据此说过的话和读过的产出（删项目时找"项目之外读过这个项目的调用"那一套没有搬过来：秘书读任务产出的调用、做完时转告的结果都留着，确认框写明"秘书那边说过的话不改"）、涉及多个项目的任务派到各项目的工单（项目的记录）、备份。
- **删除范围改由"删除参与方"登记表决定**（279 号票，方案 C，用户 2026-10-25 定；`deletion/participants.ts`）：删项目、删任务、移除插件时连数据删（211 号票）走同一张表，拥有属于项目 / 任务 / 插件的事件的模块各自登记怎么找、怎么改写（整条标记、换成给出的负载、按改写函数表字段级改写，卡片整张标记或字段级改写加新版本），删除代码只管先停、复查、提交、删文件。上面列的改写范围和做法不变，只是写在各自的模块里；没登记改写函数的事件类型照旧整个拒删。

## Consequences

- 删掉的项目的维护者会话频道上永远留着一串"已删除"标记（只有序号、时间、消息 id）。前端靠项目列表频道上的 `deleted` 把项目和它的会话从界面上拿掉；有人再订阅这个频道，只拿到标记。
- 项目列表频道上的项目事件（名字、一句话目标）不改写：它们是项目列表的历史，不是会话里的原话。
- 任务转为项目的，维护者会话里转之前的任务对话也一起删掉（是同一个会话）。原任务的看板事件不动；首个建设任务的说明不写立项书正文（只说"见项目档案里的立项书"），所以看板上没有立项书正文。
- 待我处理事项的改写没有追加新版本（事项的更新只能改标题这类状态，正文改不了）：开着的页面要重新同步才看到删除标记。
- 备份快照里仍有删除前的一份，随快照轮换消失（同 ADR-0008）。
- 以后在维护者会话频道上加新的事件类型，不用为删项目登记改写函数（整条换成标记）；属于项目的别的事件类型（以后的工单、定时作业……）要登记改写函数并加进 `deletion.ts` 的范围，否则删除时整个被拒。279 号票起不用改 `deletion.ts`：在拥有它的模块里登记一个删除参与方认领它（字段级改写的照旧要登记改写函数，没登记的整个拒删）。

## Considered Options

- **删掉整个频道的行**（15 号票第一版，`appendBatch` 加 `dropChannels`）：最干净，但删行是比改写更重的一种口子（事件日志里连"这里曾经有过什么"都没了），彻底删除也不这么做；频道序号从 1 重来，带着旧序号的前端要重新同步。
- **只删会话文件和项目档案，事件留着**：不碰事件日志，但用户在维护者会话里的原话、立项书正文还在 `ergo.db` 里，前端订阅得到，算不上"删掉"。
- **先删文件、再改写事件**（15 号票第一版的顺序）：中途出错会留下"项目档案没了、项目还在"的半截状态；改写事件之后再删文件，最坏是"项目删了、档案目录还留着"（不再有东西用到它，日志里有记录，可以手动清）。
- **在项目页上弹窗确认**：原型这么画的；但规格把要用户拍板的事都放进待我处理，弹窗关了就没了，也留不下"谁在什么时候确认删的"。
