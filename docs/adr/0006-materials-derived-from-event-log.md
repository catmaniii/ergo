# 素材是事件日志的派生：memory.db 能整个重建，删除也要记进事件日志

规格第 15 节要求素材"由守护进程从事件日志确定性地产生"，08 号票的验收标准又要求"清空 `memory.db` 后从事件日志重建，得到相同的素材"。08 号票据此把 `memory.db` 做成**事件日志的派生**，和 `ergou.db` 里的派生视图同一个性质，只是放在单独的库里、由素材模块自己维护：

- 素材模块订阅事件存储，按登记的采集规则（`materials/capture.ts`）从事件产生素材；采到事件日志的哪一条（全局序号）和素材写在 `memory.db` 的同一个事务里。停着时追加的事件，启动时补采。
- **素材 id 由事件算出来**：`mat-` 加 sha256（频道、频道内序号、事件时间、采集规则的名字、第几条）的前 24 位。不用全局序号：`ergou.db` 换成更早的版本（比如只恢复了它）时，新事件会重用旧的全局序号，撞上已有素材的 id。
- **一条事件一条素材**（一条消息、一次反应），信封里带切段，每个切段有自己的来源等级；信封的来源等级是"这件事是谁做的、谁说的"。
- **原文副本是 `memory.db` 之外唯一的素材数据**：本人切段的原文存成素材区 `originals/<年-月>/<素材 id>-s<切段>-<哈希前 12 位>.txt`，只读、"不存在才创建"。重建时同一条素材落到同一个文件，不重复写。文件名里带着素材 id，所以**素材 id 的算法定了就不能改**（改了旧文件就成了没人认领的孤儿）。

## Consequences

- **`memory.db` 丢了、坏了、表结构要大改，都可以删掉重来**：启动时从事件日志重采一遍，向量在后台重算。备份（11 号票）照样备份它，只是为了恢复得快。
- **删除必须进事件日志**（21 号票）：只在 `memory.db` 里删掉一条素材，下次重建它会回来。
  - "忘掉"、"别推断"、按会话或时间段删除，要先追加一条事件（比如"素材被忘掉"，带素材 id 或范围），再由素材模块把这类事件当作采集规则处理：删掉素材和它的原文副本、或者打上"不参与推断"的标记。重建时这条事件排在原始事件后面，结果一样。
  - "彻底删除"把事件日志里的原文改写成删除标记（第 15 节唯一的例外），重建时原始事件已经没有原文，自然采不出来；同样要删掉已有的素材和原文副本。
- **素材 id 的算法、采集规则的名字定了不改**：改了相当于换了一批素材（重建时 id 全变，原文副本另起一批文件）。采集规则要改行为，就在同一个名字下改（重建后按新规则），或者另起一个名字。
- **采集规则必须是确定性的**：只看事件本身，不读时钟、不读会变的派生视图。需要的信息放进事件负载（比如 08 号票给 `card_dismissed` 加了用户的说明 `note`）。
- **项目删除（15 号票）**：维护者会话的事件如果从事件日志里删掉，已有的素材和原文副本仍在；但之后再重建 `memory.db`，这部分素材就没了，只剩原文副本文件。要么删项目时不动事件日志里用户的发言，要么接受这一点。

## Considered Options

- **`memory.db` 是独立的真相、不能重建**：素材写进去就只在那里。删除简单（直接删），但"清空后重建得到相同的素材"做不到，`memory.db` 坏了也没有退路；素材和事件日志之间要另外保证一致。
- **素材 id 用全局序号**（`mat-<全局序号>`）：短、好读。但只恢复 `ergou.db` 时会撞 id，`INSERT OR IGNORE` 会悄悄吞掉新素材。
- **一个切段一条素材**：来源等级在信封上只有一个值，按来源筛最直接。但一条消息被拆成几条素材，"忘掉这句话"要按事件把几条一起删，检索结果也缺上下文；记忆子地图定的是"每条消息、每次反应各一条"。
