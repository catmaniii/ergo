# ADR-0030 推理图谱由记忆管理员维护，一律经唯一写入口写入

状态：已定（用户 2026-10-24）

> 329 号票（2026-10-27）起，结论的状态和传播改按 [ADR-0032](0032-memory-reasoning-rules.md)（已验证 / 猜测 / 撤回、"待复核"改成复核标记、身份不再改、依据变了怎么往下传）：下面第 2 条"依据被改或被删时转成待复核""前提里有拿不准的事实降成假设"、第 5 条"不合格的结论转待复核"，以及"实现"里讲这几处的段落，以 ADR-0032 为准。

## 背景

- 词表原来写"唯一写者"，意思不清，实际有两个地方在写推理图谱：每晚整理里引擎调模型出假设、判证据、往上抽；记忆管理员在白天直接改结论。
- 263 号票查出这样会打架：管理员直接改库，下一次整理计分又把它改回去。
- 维护推理图谱要做判断（出什么假设、哪个解释占上风、能不能往上抽），只有大模型做得了，纯规则做不到。所以"只让引擎写"不对。

## 决定

1. **判断归记忆管理员**（大模型）。每晚整理就是管理员的夜班：出假设、判证据、往上抽、复核都算它做的；白天它记下用户的表态、改结论、提顺口问。
2. **写只有一个入口**：一组受检查的写操作，管理员也一样只能经它写。写入口按推理图谱的规矩检查（记忆系统自己的一份，见下面"实现"），不合格的拒掉，并说明哪里不合格：
   - 结论写明前提和推法（演绎、归纳、溯因）、支持和反对的证据；
   - 引用的证据必须真实存在；
   - 按推法封顶把握，往上抽要过结构门槛；
   - 依据被改或被删时，依赖它的结论转成待复核，不悄悄留着；
   - 不留悬空的结论；
   - 前提里有拿不准的事实，推出来的只能是假设（未验证的猜测），不能是结论：写的时候自动降成假设写进去、写明为什么，不报错不拒写；冲突解决再升回结论，事实被推翻跟着推翻（用户 2026-10-27 定，326 号票）。
3. **管理员的权限分档**：
   - **直接做**（过写入口的检查就行）：从素材抽事实、提假设、挂支持或反对的证据、提追问和顺口问的问题、把可疑结论标成待复核、记下用户的表态；
   - **要有证据**（检查会核）：判一条结论成立或推翻、往上抽成需求和价值观；
   - **要用户确认**：推翻用户亲口说过或确认过的结论、在敏感类别（健康、情绪、财务、人际关系）上下推断、"忘掉"和"彻底删除"（只由用户发起）；
   - **永远不做**：改原话、删素材、编造证据。
4. **别的角色**：秘书只读，用户对秘书说"这个不对"，由秘书转给管理员去记；维护者只按授权的记忆范围读，不写。
5. **留痕和验收**：每次写入记下谁写的（夜班、管理员、用户的表态）、推法、依据、原因，记忆页能看到；每晚整理完把推理图谱整张查一遍（记忆系统自己的图谱自检），不合格的结论转待复核并写进整理报告。

## 后果

- 词表的"唯一写者"改成"唯一写入口"；"记忆管理者""做梦阶段"统一成"记忆管理员""每晚整理"。
- 要做的：写入口的检查、权限分档、留痕、每晚校验（267 号票）。现有的写操作要逐个收进写入口。

## 实现（267 号票，2026-10-25）

- **写入口**：@ergo/memory 的 `ReasoningWriteGate`（`packages/memory/src/rg/write-gate.ts`；326 号票前包名是 memory-lab），引擎打开时建好（`engine.gate`）。证据、事实、结论、关联、推断、追问、预测只能在一次 `gate.write({ op, actor, via, reason }, fn)` 里写；写完按这一次留下的修订查一遍，不合格整次回滚，抛 `ReasoningWriteRefused` 逐条说明哪里不合格。第 2 条的五样检查对应 `premise`、`exists`、`confidence_cap` 和 `lift_threshold`、`dependents`、`dangling`；另有 `evidence_backed`、`user_confirm`、`sensitive`、`never`、`permission`。细节见 [记忆架构](../memory-architecture.md) 第 7.10 节。
- **收进来的写路径**：每晚整理的每一步（明说的结论、提假设、撤组、追问、判状态、联动、往上抽、写回、对抗复核、预测）、记忆管理员记下用户的表态（`recordClaimVerdict`）、问题箱（出问题、过期、判回答；264 号票的顺口问：记问过、跳过和回避信号、"别问这个"、回答回写，记"经秘书顺口问"——记问过算管理员白天提顺口问，回答和跳过是用户的表态，"别问这个"是用户发起；271 号票起规则认不出的回答由管理员每晚整理时判：判成在答的回写记"用户的表态 · 经记忆管理员夜里判"，没答的跳过、拿不准的那一笔是夜班）、删除登记的忘掉 / 彻底删除 / 别推断 / 敏感类别、素材入库和抽事实。源码里除了存储和写入口没有别处直接写这几张表，有静态检查守着。
- **权限分档**：第 3 条照做。"要用户确认"的几样现在的做法是**只由用户发起**（用户的表态、记忆删除卡、设置页、经管理员转达的忘掉），夜班和管理员自己下的写入口直接拒；给管理员出确认卡、让它代问用户的那条路还没做。管理员的 `forget_material` 照 242 号票是"用户说了才调"，记成"用户发起 · 经记忆管理员"。
- **别的角色**：秘书的简报和问记忆那一份引擎、记忆页那一份引擎的写入口开成只读，写一律拒；维护者没有记忆工具。
- **留痕**：`rg.db` 新表 `rg_writes`（只追加）：谁写的（夜班、记忆管理员、用户的表态、用户发起）、经谁转达、写操作、推法、依据、原因、留下的修订；记忆页的修订列表显示是谁写的。
- **每晚校验**：整理完由图谱自检（`packages/memory/src/rg/graph-check.ts` 的 `checkReasoningGraph`，经 `graphSelfCheck`）把整张推理图谱查一遍：读得出来、字段合格，引用都在，依赖不绕圈，成立的结论压着的前提都还成立；不合格的结论转待复核，写进整理报告和整理记录。
  - 326 号票（2026-10-26）起是记忆系统自己的 TypeScript，跑在守护进程里，不再起 Python、不再读本机的东西，所以没有"本机缺什么就跳过"这回事。第 2 条的检查和它是同一份规矩："引用存在、前提还在、依据还成立"的判断写在 `rg/graph-rules.ts`，写入口每次写只查这一次改到的，图谱自检查整张图（旧数据、没经写入口进来的坏数据也查到），另加只有看整张图才查得了的"不绕圈"；字段合格用的是存储写入前那一份 `domain/validate.ts`。
  - 拿不准的前提（用户 2026-10-27 定）：写入口每次写先把碰过的、前提里（顺着推断往上找）有拿不准事实的结论降成假设（`graph-rules.ts` 的 `contestedPremises`），修订和留痕写明为什么；图谱自检把前提后来才变成拿不准的结论降成假设，记成改动、不算不合格。事实拿不准不算"依据不成立"；被纠正、撤回才算，压在上面的转待复核、当晚重判，只靠它撑着的撤掉。冲突解决、事实回到成立，明说的那条在每晚整理"跟着事实走"那一步升回结论；推断出来的断言本来就是假设，没有升成结论这条路。被新值取代的事实算还成立（观点变了，旧值在它的有效期里是对的）。
- **依赖链不设深度上限**：第 2 条"依赖它的结论转成待复核，不悄悄留着"照做——失效传播、标待复核一路传到底，写入口沿依赖查也不设层数（原来的 6 层上限取消，主会话 2026-10-25 按这份决定定）。
- 实体和交互策略没收进写入口（策略另有用户确认）。
