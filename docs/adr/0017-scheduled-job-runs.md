# 定时作业的一次运行：属于项目的是一张不属于任务的工单，不属于项目的交给作业自己的维护者；结局看这一轮，开始了才占名额，授权随计划卡确认

规格第 8、11、12、13 节：定时作业通过任务建，计划确认后登记；到点时属于项目的作业作为一张工单交给项目的维护者，不属于项目的交给"作业自己的维护者"；每次运行占一个全局并发名额；失败要记、连续失败 3 次自动暂停。规格没说作业自己的维护者是谁、一次运行算什么、什么叫失败。19 号票定成（评审后按用户的决定改过名额和授权两条）：

- **属于项目的：一张没有所属任务的工单**。工单按来源区分成联合类型，这一支是 `JobRunWorkOrder`：来源 `scheduled_job`（"定时作业"）、种类 `run`，没有任务，带 `scheduledJobId`、`runId`。派单、排队、一次只做一件、开段、写回检查、已归档退回、工单结束时的范围审视全照 16、18 号票（ADR-0012），定时作业模块只调 `dispatchRun` / `finishRun` / `dropRun`。运行的段里没有提问（`ask_clarification`）：没有任务可以挡，用户也不在场；做不了就报失败。
- **不属于项目的：每个作业一个自己的维护者 `jm-N`**（`j-N` 的），会话频道 `maintainer:jm-N`，接着同一个 pi 会话（前几次运行的经验留在会话里），工作目录是建它的任务的产出目录。一次运行是一条带作业身份的通知。不复用建它的任务的维护者：任务结束、归档以后它的维护者不该再被唤起，任务的会话也不该混进每天的运行。
- **结局看这一轮**：维护者处理完这次运行的那条输入（属于项目的是工单结束），正常结束算成功；它用 `fail_job_run` 报了原因、这一轮出错或被中止、有一步等不到批准被拦下或要交给用户亲手做，算失败。**停机打断的那次记为"中断"**，不重做，也不算进连续失败（不然几次重启就把作业自动暂停了）。还排着时作业被暂停、取消，这次记为"没运行"。不另设"验收"：作业没有阶段和验收方式，规格只要求记成功失败。
- **授权随计划卡确认**（2026-10-08 用户定）：作业定义在计划卡上列出每次运行要的授权项（和阶段的授权项同一种写法），用户说的限制编成时序规则，随计划卡一起确认、登记在作业上。作业在就一直有效，不按 7 天续期；暂停、取消作业即收回。运行时守卫按作业的授权判：作业的授权项、时序规则、本任务的关注类别，属于项目的工具包再和项目的取交集；超出的照常先问用户。守卫核心为此多了"带着授权的会话段"：按任务的那一套判，但效果日志、规则和次数只看这一段会话（每次运行一段），调用不属于任何任务。
- **名额在运行真正开始时才占**（用户定）：一次运行从真正开始（作业自己的维护者收到通知；属于项目的工单开始）到结束占一个全局执行名额，和执行中的任务共用 `tasks.maxRunning`；属于项目的到点就派出工单，在项目的队列里排着不占名额，排到了、又有名额才开始。谁占着名额只在一处数（`tasks/slots.ts`），名额空出来时依次叫执行控制器、派单器、定时作业。同一个作业上一次还没跑完的，这一次跳过（只把下一次往后算）。

## Consequences

- 作业自己的维护者的会话会越来越长，靠 pi 的压缩；它的用量按作业身份记在作业名下（24 号票），不算系统开销。每次运行按这一次重新拉起子进程（守卫的会话段跟着换），会话照样接着。
- 运行工单在项目的队列里排着不占名额，所以项目队首是排队中任务的执行工单、后面排着运行时不会卡死；代价是派出的运行工单排到了也可能因为名额满了再等一会儿（派单器在名额空出来时再看一遍）。
- 授权和作业绑在一起：用户确认一次，之后每天的运行都不再问授权内的事；要收回就暂停或取消作业。作业的授权不进 14 号票的续期，也没有"到期"。
- 失败只有维护者自己说、这一轮没正常结束、有一步没做成几种；它说"做完了"但其实没做好，记成成功。以后要更严，可以给作业加验收（比如脚本），这是另一张票。
- 守护进程停着期间错过的触发只补跑一次；停机时正在跑的那次记为中断，不重做，避免一天跑两次。

## Considered Options

- **不属于项目的作业交给建它的任务的维护者**：任务结束、归档后还要唤起它，任务详情里的会话会混进每天的运行；任务的维护者装配带着任务的阶段工具和授权，和作业对不上。
- **不属于项目的作业也走工单**：工单是"项目的维护者一次只做一件"的排队单位，没有项目就没有队列可排；作业自己的维护者只做这一个作业，用不上。
- **每次运行派一个新的子 agent**：没有连续的会话，前几次运行学到的（数据源在哪、简报的格式）每次都要重来；用量和活动状态也分散到一堆临时 id 上。
- **一次运行要验收才算成功**：作业定义里没有验收方式，规格也只说"失败"；加验收要改计划的结构（12 号票的作业定义），留给以后。
- **授权按聊天的处置判**（第一轮的做法）：每天的运行里对外发送都要问，用户不在场时就做不成；评审时用户定成随计划卡确认。
- **属于项目的从派单起就占名额**（第一轮的做法）：能卡死——队首是等名额的执行工单，名额被后面排着的运行占满，谁也开始不了。
