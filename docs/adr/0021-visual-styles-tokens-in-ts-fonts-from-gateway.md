# 视觉风格的 token 写在风格清单（TS）里、构建时生成样式；字体随构建产物由守护进程提供

规格第 19 节"外观"：多套视觉风格在设置里选、按设备记住，每套都有浅色深色、和明暗正交；风格只换皮；字体由二狗自己提供，不请求外部 CDN。39 号票搭底座，之后 40–42、46–51 号票并行各加一套。定成：

- **一套风格 = 一组 token + 限定在这套风格下的规则**。token（颜色、字体、字号阶、圆角、阴影、间距密度、边框）写在 `packages/web/src/visual-styles/<id>/style.ts` 里，是 TS 数据，不是手写的 CSS 变量；规则写在同目录的 `style.css`，每条以 `:root[data-style="<id>"]` 开头。风格清单 `index.ts` 一套一行。
- **构建插件把清单变成样式**（`packages/web/build/visual-styles-plugin.ts`）：生成一份 token 样式表（经典挂在 `:root`，每套风格写全全部 token 挂在 `[data-style="<id>"]` 上），按清单顺序接上各套的 `style.css`；同一个插件把每套风格的地址栏颜色、字体样式表的地址填进 `index.html` 的内联脚本，打开页面时在页面脚本之前就挂好 `data-style`，不闪。
- **"经典"就是原来的样式**：`src/styles/` 那几份只用 `var(--token)`，经典的 token 值和原来写死的一样（截图逐像素比对过）。别的风格没写的 token 沿用经典的。
- **字体随构建产物走、由守护进程提供**：风格声明要用的 fontsource 包（npm 上按 unicode-range 切好片的 woff2，OFL 等许可）；构建时只把 woff2 和许可证拷进 `dist/fonts/<包>@<版本>/`，生成 `dist/fonts/<风格 id>.css`。字体不内联进单文件的页面。网关按 `/fonts/` 原样提供（只认 .css、.woff2、.txt），外网端口上和别的地址一样要设备凭证；woff2 的目录带版本号，长期缓存。页面只给现在这套风格挂字体样式表。

## Consequences

- 颜色、地址栏颜色、设置里的预览、对比度测试都从同一份 TS 数据来：对比度测试直接 import 风格清单，以后加的风格自动算进去；地址栏颜色不用在内联脚本、页面脚本、样式里各抄一份。
- 改 token 要重新构建才看得到（开发服务器会因为配置引用的文件变了自己重启）；样式里看不到 token 的值，要去 `style.ts` 找。
- 加一套风格只动它自己的目录、清单里的一行（和 import 一行）；要字体的再加一个 devDependency，`packages/web/package.json` 和 `package-lock.json` 跟着变。几张票并行加风格时，冲突在清单那几行，要字体的还有这两个文件（变基时重新 `npm install` 生成锁文件）。
- token 里字体分正文、标题、数字三个，实色块（主按钮、危险按钮）的底和当字用的强调色分开：只用在标题或数字上的展示字体、深色下要亮的字和要暗的底，都不用改共享代码。每套风格的 `style.css` 由测试扫一遍，每条规则都得以 `:root[data-style="<id>"]` 开头。
- 新加 token 要在 `tokens.ts` 加名字、在经典里给一个和原来一样的值；页面样式不能再写死颜色、圆角、阴影。
- 构建产物多了 `dist/fonts/`（净白格栅的 Noto Sans SC 可变字体约 4.3 MB，一个页面实际下一两成）。守护进程只是按目录提供文件，不知道有哪些风格。
- 设置里每套风格浅色、深色两张预览（用户 2026-10-09 加），**现场渲染**：容器挂 `data-style`、`data-theme`（"每套风格的 token 也挂在 `[data-style]` 上"，容器的 `color-scheme` 按 `data-theme` 定），场景放在容器的 shadow root 里，用页面样式表复制的一份，把每套风格规则开头的 `:root[data-style="<id>"]` 换成 `:host([data-style="<id>"])`（`src/visual-styles/preview.ts`）。这套风格的规则在它的预览里生效，页面现在那套风格的规则进不了 shadow root；场景最外层先 `all: initial`，页面挂在根元素、body 上的可继承属性也不会经容器继承进来（token 是自定义属性，照样继承）。代价：风格规则的开头在根元素上只能再加属性、往下接只能是空格或 `> body`（测试扫）；页面样式表在内存里多一份（第一次画预览时做一次，所有预览共用）。预览的字体另出一份只收预览里那几个字的 `dist/fonts/preview.css`，打开设置只多下一两片。

## Considered Options

- **token 直接写在每套风格的 CSS 里**（`[data-style="grid"] { --bg: light-dark(…) }`）：写起来最直接，但地址栏颜色（内联脚本要在样式加载前用）、对比度测试、预览都要再从 CSS 里解析一遍或者另抄一份；放弃。
- **运行时用 JS 把 token 写到根元素上**：要等页面脚本，打开页面会闪；内联脚本里也得带上全部 token。放弃。
- **字体从 Google Fonts 等 CDN 取**（设计稿就是这么写的）：手机经 tailnet 时可能连不上，也把使用情况透露给第三方；规格不许。
- **字体内联进单文件页面**（base64）：每次打开页面都要带着几 MB，选别的风格的人也要下；放弃。
- **守护进程直接从 `node_modules` 里的字体包提供**：守护进程得知道哪些风格用哪些包，加一套风格就要改守护进程；拷进构建产物后守护进程只认一个目录。
- **预览在构建时生成图片**：构建里要跑浏览器截图，图片还得内联进页面或另外提供，风格一改就要重出；放弃。
- **预览直接在容器里套规则**（不用 shadow root）：要让页面那套风格的规则不漏进别的风格的预览，每条规则末尾得加 `:not(.style-preview *)`，这种带空格的 `:not()` Chrome 105 以前不认、会丢掉整条规则（`cssTarget` 还照顾 Chrome 94 档的老 WebView），规则还得每条写两遍；放弃。
- **预览用 iframe**：每张都要整份重新解析页面样式，二十多张开销大；shadow root 能共用一份解析好的样式表。
