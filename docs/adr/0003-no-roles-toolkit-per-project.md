# 不设"角色"，维护者的能力按项目或任务配一个工具包

二狗不设"角色"，也就是不设"工程师、研究员、写作"这类工种，没有角色卡，也没有角色经验。每个维护者的能力，由它所属的项目或任务配置的**工具包**决定。工具包包括：
- 哪些 skill；
- 哪些外部工具（MCP）；
- 能不能用 bash；
- 能不能联网。

工具包怎样定、怎样改：
- **初始配置**：立项时写在立项书里，发起任务时写在计划卡上。由维护者提议，用户确认。
- **skill 的增减**：维护者可以自己做，记进时间线。skill 只是说明书，不增加权限。
- **能力的增加**：开 bash、加外部工具、开联网，算扩大授权，要用户批准。

"只做本领域的事"改成软约束，叫**范围审视**：
- **什么时候做**：每次压缩会话时、每张工单结束时。
- **怎么做**：另开一次模型调用，对照立项书和用户给过的授权，检查维护者做了哪些范围外的事。
- **结果怎么处理**：
  - 用户授权过的，记为"范围变更"，写进项目档案；
  - 没授权的，记为"越界"，写进维护者的系统提示，并给用户一条不推送的通知。

真正的硬闸仍是守卫的关注类别：越出项目目录、对外发送这类操作，照常拦下或先问用户。

用户的理由是：有时候用户本人会在授权的基础上，让维护者先去做别的事，所以范围必须能被突破，不能被工具权限卡死。

## Considered Options

- **维护者挂一个主角色**：
  - 做法：维护者是"座位"，角色是"工种"。会话里只注册角色允许的工具，再和项目权限取交集；越界的请求，用一个"越界退回"工具退回。
  - 放弃的原因：用户不要角色这层设定；而且硬性的领域边界和"范围要能突破"相冲突。
- **再设一个只管不干的独立项目经理**：调研表明，"不动手"只写在提示词里会失效，必须靠工具权限卡住。现在的做法是，跨项目任务的维护者用一个固定的工具包（读项目档案、派工单、汇总回执），改不了任何项目。
- 调研依据：`docs/research/04-multi-agent-teams.md`。

## Consequences

- **不做**：角色库、角色管理页、角色经验的提炼和审批，「起步角色目录」票关闭。
- **经验按项目沉淀**：经验存在项目档案里，不自动提炼。用户要求时，用 `reasoning-graph`（推理图谱）skill 沉淀领域知识。
- **固定工具包**：评审子 agent 用只读的固定工具包；跨项目任务的维护者用上面那个固定工具包。
- **框架自带哪些 skill**，第二阶段再定（地图待定项「内置 skill 库」）。
- **技术接法**：
  - 范围审视挂在 pi 的 `session_before_compact` 钩子上，结果用 `appendEntry` 持久化，再通过 `before_agent_start` 拼到系统提示的末尾。压缩不频繁，所以不会常常打穿前缀缓存。
  - 每张工单结束时，由运行时触发一次同样的审视。
