# ADR-0041 授权的文件夹进守卫：只放开读，真实路径说了算

状态：已定（用户 2026-11-01 提需求，主会话定"先做成读"；355 号票）

## 背景

- 用户："我电脑上的文件，二狗可以访问授权的文件夹中的文件，不需要再找我授权。"
- 授权的文件夹（138 号票）以前只划定"找文件"的范围，和权限无关：`CONTEXT.md` 写着"不限制秘书读别处的文件"。读工作目录外的文件都落入"越出项目目录"（对话里先问，任务里要写进计划）。
- 对话审批开着、流程任务的计划比对开着时，这一条每次都打断用户。
- 守卫的判定是纯函数，判定函数不能自己读文件，名单和真实路径都要调用方给。

## 决定

1. **只放开读。** 写、删、覆盖照原来的规矩，要放开由用户另说。
2. **判定规则**（`guard/judge.ts`，名单由调用方判定前现读、作为 `GuardInput.authorizedFolders` 交进去，改了下一次调用就生效）。一个路径参数算读授权的文件夹，要同时满足：
   - 参数登记成 `read`，工具是文件工具的读、列、搜，或 bash 拆出来的读、列、搜、复制的来源；
   - 目标的**真实路径**（调用方现取的环境事实）在授权的文件夹里；取不到真实路径的不算；
   - 目标和真实路径都不在数据目录、受保护区域里，也不是密钥文件（`guard/secret-files.ts`）和备用数据流。
3. **这些路径参数登记成读，但不算：**
   - 跑脚本（`run_script`）：可做的不止是读；
   - git（`git_status_diff`）：仓库的配置（`core.fsmonitor`、外部 diff 这些）能让它跑命令；
   - `cd`、`pushd`：之后不带路径的命令（`make`、`npm run`）都在那里跑，守卫看不全，Claude Code 的 Bash 还会把目录留到下一次调用；
   - 只读程序之外的程序的路径参数（`pytest x.py`、`go run x.go`、`npm run foo x`）：拆的时候按"读"补上，但程序拿它做什么守卫不知道，多半是跑它；
   - `awk -f`、`sed -f`：读进来当程序跑；
   - 拿到了守卫看不见的输入的（`curl -K` 的配置文件能再写网址和数据，管道喂给它的）；
   - bash 里写着 `..` 的路径：守卫按字面解析，Git Bash 却先走符号链接再走 `..`；
   - 展不开的通配符（`**`、太多）：看不全会读到什么；
   - MCP 和代为执行的工具：可做的不止是读。
   这些都和没授权时判得一模一样。测试按"有没有授权判出来完全一样"锁住（`test/guard/authorized-folders.test.ts`）。
4. **整个数据目录都不算授权的范围，不只是密钥区和受保护区域。** 把它的上级授权了，密钥区照样拒绝，配置区、数据库区、程序目录、别的项目档案、日志和会话记录照原来的规矩判。
5. **流程任务**：不用把授权的文件夹写进计划。第一道判定不落入类别；计划比对（`guard/plan-monitor.ts`）在第一道判出 `authorizedRead`（整次调用都只是看、至少读了一处授权的文件夹、没命中任何类别）时不算计划外、超范围。步骤先后、审查时剔除的对象照旧。照搬的 planguard 引擎不动。
6. **运行时**：pi 没有自己的权限，守卫就是闸口。Claude Code 自己也管权限：传只读规则 `Read(//d/照片/**)`（`allowedTools`），不传 `additionalDirectories`（那个连写也放开了）。规则是拉起时的那一份，下一次起进程才跟上；判定本来每次现读，运行时再要问人时走 `canUseTool`，守卫放行过的直接放行。守卫的钩子在规则之前，规则放不开守卫拦下的。
7. **设置单独一页**（`#/more/authorized-folders`，数据与设备组，排在数据源后面），是内核的页面，浏览插件停用时也在。页面写清后果：所有 agent 都能读，读到的内容会发给模型服务，不要授权放密钥的文件夹。

## 后果

- 读授权的文件夹不再打断用户，所有 agent 一样，定时运行不会因为它算部分完成。
- 授权的范围比以前大了：以前只影响找文件，现在影响判定。任何 agent 自己都改不了这份名单（138 号票的规矩不变）。
- **已知的限制：**
  - 整目录搜索（`grep -r`）会读到目录里的密钥文件，守卫只认路径参数，认不出来，"读过密钥之后不许往外送"也算不上它。这和工作目录里的整目录搜索一样，所以页面上写"不要授权放密钥的文件夹"；
  - `awk`、`sed` 这类程序的脚本里写着的路径（`print > "x"`、`w x`）守卫本来就看不见，读授权的文件夹里的文件时也一样。这不是这次放开的，工作目录里的读今天就是这样；
  - 用 `cd` 进去再读的还是要问（或者在对话审批关着时按原来的规矩放行）。上下文块告诉 agent 用完整路径读。

## 考虑过的

- **读写都放开**：用户原话是"访问"，但写、删放开的后果大得多，主会话定先做成读。
- **按写的路径比、不看真实路径**：符号链接、目录联接、8.3 短名都能绕出去。
- **授权里的密钥文件也放开**：用户授权的是文件夹，不是说里面的密钥可以发给模型服务。照旧。
- **只挡密钥区和受保护区域、数据目录别的地方放开**：日志、会话记录、别的项目档案里可能有读过的密钥和别人的东西。把用户目录授权了就全放开了，太容易发生。
- **给 Claude Code 传 `additionalDirectories`**：能放开读，也连写一起放开（比如自动接受改文件的模式）。写虽然还要过守卫，但没必要多开一道。
