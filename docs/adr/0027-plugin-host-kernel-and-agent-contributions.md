# 功能做成插件：守护进程里自建插件宿主，借 Cordis 的规矩不引入 Cordis；agent 那一侧只留一个通用桥接扩展

用户 2026-10-17 提出"把二狗整个系统插件化"：界面、记忆、项目、任务都做成插件，点名参考 DeepSeek harness 底层的 Cordis；也问能不能在 pi 上"给 agent 装一个记忆插件"。调研见 [调研 19](../research/19-plugin-architecture-cordis-pi.md)。

主会话出了架构评审，用户同意按建议做（2026-10-17："同意按你的想法做吧"）：

- **分内核和插件**：
  - 内核：事件日志、任务执行连同守卫、宿主协议、网关，所有插件都依赖它们，不做成插件；
  - 插件：提醒、日历、语音、配对、记忆（素材）、运营态项目这些功能模块。
- **守护进程里自建插件宿主**：
  - 插件声明自己依赖什么，宿主按依赖排顺序装；
  - 插件经宿主做的每一次注册（卡片类型、彻底删除的改写函数、素材来源、快速动作、内部作业、派生视图……）都返回撤销函数，记在这个插件名下，停用时倒着撤；
  - 组合根 `daemon.ts` 只管装内核、按清单装插件。
- **借 Cordis 的三条规矩，不引入 Cordis 本身**：
  - 每次注册都能撤销，并记在插件名下；
  - 依赖靠声明，到齐才启动；
  - 网页用类型化插槽，插件之间不互相 import（网页这一条以后做）。
- **agent 那一侧**：
  - 插件经一条"agent 贡献"缝提供工具、每轮的上下文块、钩子订阅，守护进程当数据经宿主协议下发；
  - 子进程里只有一个通用桥接扩展，把它们翻译给 pi；
  - 功能本身（比如记忆的整理、做梦、管理页、记忆范围的强制）一律在守护进程的插件里，不做成 pi 扩展。
- **两个适配器做实这条缝**：迁一个现成的叶子模块"提醒"，再把"素材与记忆"做成插件；二期的记忆系统在这个插件里长出来。
- **顺序**：协议从封闭联合改成由插件登记、网页插槽，等这两个插件跑通再做。

## Considered Options

- **直接引入 Cordis 当守护进程的插件宿主**：能白得撤销记账、`inject` 依赖、热重载。不选的原因：
  - Cordis 4.x 还是 RC，README 写着 API 不稳定，实际只有一个主维护者；
  - 它最大的用户 dsh 也是把源码复制进仓库、自己打了 24 条补丁在用；
  - Windows 下热重载最近才修；
  - 4.x 的 `inject` 列的全是必需依赖，可选依赖没有明确写法；
  - 最根本的：Cordis 只管一个进程里的插件，二狗是每个 agent 一个子进程（ADR-0002），进程边界那一半还得自己做。

  等 Cordis 4.0 正式版，再拿自建的插件接口对照评估要不要换。
- **功能做成 pi 的扩展**（"给 pi agent 装一个记忆插件"）。不选的原因：
  - pi 的扩展跑在每个 agent 的子进程里，跟着会话生灭；
  - 单个扩展不能卸载，工具注册了撤不掉；
  - 没有往网页加东西的口子；
  - 跨 agent 的整理、做梦、管理界面、单一写者都只能在守护进程里。
- **整个换成 dsh 那样 agent 跑在宿主进程里**：要推翻 ADR-0002（每个 agent 一个子进程：崩溃隔离、Job 对象清理、限额）。不选。

## Consequences

- 插件停用后，它写过的事件还在日志里。投影能撤，事件不能撤。停用的插件留下的事件由谁解释、还能不能彻底删除（ADR-0008），插件宿主的票里要定。
- 每加一种 agent 侧的钩子，原来要给宿主协议升版本；改成"通用贡献清单"之后，新插件不用再改协议、不用改子进程。代价是桥接扩展要能处理通用的工具、上下文块、钩子三类，pi 升级时只改它（ADR-0001 的合同测试照旧当闸门）。
- 记忆简报照现在的做法作为消息追加进会话（"模型看到的都要记下来"），不改用 pi 的 `context` 事件（只对单次请求生效、不落盘）。
- 测试可以只起"内核 + 某几个插件"；同时要有走真实装配路径的测试（dsh 的复盘 0001：手挂插件的单元测试全过、上线即崩）。

## 网页插槽怎么做的（193 号票，2026-10-20）

两个插件（126 提醒、129 素材与记忆）跑通之后做了网页这一条。照 dsh 的网页插件（调研 19 §3.7.2），不引入 Cordis：

- **一个功能插件两半，同名**：守护进程里的插件（上面）加网页里的网页插件（`packages/web/src/plugins/<插件>/`），一起启停。守护进程在插件频道上推临时事件 `plugin_status`（清单里每个插件在运行、停用了、没装上，带原因；订阅时补推，运行中停用、换了语言再推），网页按它装、停自己的网页插件；还没收到（原型、旧的守护进程）当作全开。
- **网页插件宿主**（`plugins/host.ts`）照守护进程那边借同样的规矩：插件经 `ctx.register(插槽, 条目)` 往类型化插槽里放东西，每次登记都返回撤销函数、记在插件名下，停用时倒着撤，停了再登记报错。插槽是编译期的一张表（`plugins/slots.ts`）：页面和路由（导航项、"更多"里的入口）、设置分节、对话里的条目（按会话条目的种类）、详情（按详情的种类）、卡片（按卡片类型）、看板条目和菜单项、日历。秘书页标题旁的小部件没做（没有插件要用）。
- **数据契约照守护进程那边**：插件在定义里写明拥有哪些位置（`owns`，不管开没开都认得），停用的插件拥有的位置核心画占位——页面写"X插件没启用"，聊天、待办、看板里以前的条目显示"（X插件没启用，这条内容暂时看不到）"，不报错、不崩。会话条目的推导（比如 187 号票的"回忆了 N 条记忆"怎么切段）留在状态层，只看协议里的数据，插件停用时照样推出来、再换成占位。
- **插件之间不互相 import**：插件只 import 网页核心的公开接口（宿主经 `plugins/api.ts`，状态层经 `state/index.ts`，别的核心模块照常），核心不 import 插件，插件清单只在 `plugins/manifest.ts` 一处列、只由组合根 `App.tsx` 引；扫 import 的测试检查。
- **构建时打包，不运行时加载**（调研 19 §8.4 第 15 条要单独定的）：网页插件跟网页一起构建，守护进程报的状况只决定装不装。运行时下发插件脚本要多管一套模块加载、缓存版本和热更新，现在只有自带的插件，用不上。
- **默认全开时界面一点不变**：搬之前、搬之后在原型里同样的几页（秘书页、记忆页、看板、日历、"更多"、设置，经典浅色 390 和 1280）存下 DOM 逐字比对，一样。
- **内核的保证不跟插件藏**：素材库和删除是内核的（129 号票），记忆页里的"成批删除"是内核的页面；记忆插件停用时记忆页不在了，设置里列出"删除素材"（`PageSlot.covers`：在用的插件页面里已经有的核心设置页，设置列表里不再列）。
- **走真实装配路径的测试**：守护进程主切面经组合根和插件清单起、停用只经数据目录配置，录下网页收到的事件流；网页这边原样交给状态层，再用真的插件清单建宿主装上，查各插槽和占位。


## 运行中停用、启用、移除（211 号票，2026-10-20）

用户 2026-10-20："设置界面里面要能查看当前加载了哪些插件，还有可以把它暂时禁用或者是移除。相当于是可以热插拔"。之前停用只能写配置、重启生效，运行中停用只给测试用、停了不能再启用。现在设置里多一页"插件"，运行中停用、启用、移除马上生效：

- **是热插拔，不是热重载代码**：插件都是自带的、跟着守护进程和网页一起构建（上面"构建时打包，不运行时加载"），"移除"不卸载代码，只是停用、收进"已移除"、能装回。运行时下发、加载插件代码照旧不做。
- **宿主管装和停，设置那一层写配置**：插件宿主多了 `enable`（启用它连同它要的、没开的，按依赖排顺序装配、启动；因为它没开而没装上的启用着的插件跟着装上）和 `remove`（停用、记成移除了）；运行中停用时依赖方一起停，都记成"停用了"（不是"没装上"），一起写进 `plugins.disabled`，重启后不算降级。移除的写进 `plugins.removed`。每次装配是新的一次：登记、生命周期从空的开始，上一次的 ctx 照样不能再登记。
- **派生视图运行中补齐**：停着时它没看到的事件（追加的、彻底删除改写的）启用时要补。事件存储多了 `attachView`：建表、整表清空、按事件日志补一遍（登记了频道的只读那几个），和打开事件存储时一样，在同一个事务、同一段同步代码里，不会漏掉中间追加的。素材库也一样能在运行中又开始采集（记忆插件运行中启用、装回：从停下的采集位置补采）。
- **正在跑的一轮不崩**：agent 手里的工具清单是拉起时给的，停用后秘书这一条处理完才按新的贡献重新装配。宿主把插件给 agent 的工具包一层：这一次装配停了以后再调，回"X插件没启用：现在用不了 <工具>"（isError），不做。
- **连数据一起彻底删除（用户 2026-10-20 定）**：
  - 删什么由插件在数据契约里写明（`removal.declare`）：它拥有的事件、要按现有改写函数只改字段的事件、它拥有的卡片类型、待我处理里属于它的通知、它自己的文件，外加给人看的"删哪些""删不掉的"（设置里的确认框列出，默认不勾，勾了再确认一次）。
  - 走 ADR-0008 的同一个口子：同一个事务里改写、追加待我处理里删掉的事项和一条删除记录（插件频道上的落盘事件 `plugin_data_purged`，只写插件名、什么时候、删了几条和它拥有的类型，不带内容），派生视图整体重放，提交后做 WAL 检查点。这个插件自己停着的视图也一起重放（215 号票补上：之前只重放在用的视图，停着的表里留着原话到装回时）。
  - **它拥有的事件整条换成"已删除"标记**，不像彻底删除素材那样只换带原话的字段：ADR-0008 的"不改坏状态"说的是还在用的状态（审批、卡片），插件都移除了，它的状态不用留。
  - **提醒**：全部提醒事件、提醒卡的每个版本、待我处理里提醒的通知（提醒视图随之是空的）；删不掉的写明两处——秘书会话里提到过的提醒内容、备份快照里的一份。提醒卡没有"关掉"这个动作，不会有由提醒采成的素材。
  - **记忆（选 A：只删记忆插件自己的）**："记住"的命令里的内容（用现有的改写函数）、建议卡和提问卡长期没处理的记录（`card_stale`）、记忆删除卡的每个版本。**素材库不动**：`memory.db` 和原文副本是内核素材库的、派生的（ADR-0006，删了也会按事件日志重建回来），本人的话留原文副本是用户的数据承诺，和记忆插件开不开无关；确认框写明"素材属于内核，要删请去 记忆 · 素材 的成批删除"。**删除类的记忆命令不碰**：它们是"这些素材被删了"的记录，改写了重建时被删的素材会回来（ADR-0008）。
  - 考虑过、没选：记忆连素材库一起删（等于"成批删除 · 全部 · 彻底删除"，用户说过的每句话在会话和会话文件里都改写成"已删除"，太重，而且素材属于内核）；记忆不给"连数据删"这个勾（用户要的是能选）。

## 日历拆成插件（213 号票，2026-10-20）

用户 2026-10-20："把内置浏览器和网页工具，日历和语音这三个拆成插件，其他都不拆"。日历是第三个插件（现在的插件：提醒 126、记忆 129、日历 213）：

- **拆的**：守护进程里按天合起提醒和定时作业的日历服务（`calendar/`）、网关里按月取的那个请求；网页里的日历页、主导航和"更多"里的日历入口（`plugins/calendar/`）。**不拆的**：工作日历服务、工作日判定（设置 · 工作日规则、协议包的纯函数），定时作业本身——定时作业的时间规则要用，留在内核，日历插件停用时照常。
- **提醒是可选依赖**（`wants`，第一次在真插件上用到）：提醒在就排在它后面装、每次现取；提醒停用时日历照常显示工作日和定时作业，只是没有提醒那一栏，也不连带停日历。
- **不拥有数据**：日历只是合起来看的视图，没有数据契约；211 号票的"连数据删"对它是空的，设置里移除时不出那个勾选。
- **内核替插件接请求**：网关的 `GET /api/calendar` 留在内核，经插件宿主新加的 `active(服务名)` 现取日历的服务，插件没在运行时回"日历插件没启用"（插件没启用的现有说法）。没有另做"插件登记 HTTP 接口"，等真有插件要自己的接口再说。
- **地址不变**：日历 35 号票起就在主导航上、地址是 `#/calendar`，不在 `#/more` 下面。网页插件的页面插槽多了一项"自己的地址"（`route`）：导航、"更多"里点了去那里，收进"更多"时也是整页；地址的拆拼还在核心的路由，核心按它画插件的页面，插件停用时那个地址写"日历插件没启用"，核心里去那一页的链接（工作日规则里的"日历"、待办里到点的提醒的"去看看"）不出。
- **开着时一模一样**：搬之前、搬之后在原型里同样的几页（秘书页、日历的月、某一天、下个月，"更多"、设置、工作日规则、外观、待办、记忆，经典 390 和 1280；连同停用提醒插件时）存下 DOM 逐字比对，除了设置 · 插件多了日历那一块，都一样。

## 语音拆成插件（214 号票，2026-10-20）

用户 2026-10-20："把内置浏览器和网页工具，日历和语音这三个拆成插件，其他都不拆"。语音是插件清单里的又一个（提醒 126、记忆 129、日历 213、语音 214）：识别、合成、agent 用语音回复、参考音色、预热、Debug 的语音组在插件里；对外只有 `voice/api.ts` 的服务 `VOICE`（`VoiceApi`），内核和别的插件现取，取不到就是停用了。开着时 31 到 210 号票的语音规矩全照旧。

- **语音对象的视图、投影、改写、素材来源留在内核**（`voice-records/`），不随插件停：语音 part 换成识别出的文字是会话的数据契约，历史分页、交给 agent 的输入、输入队列停用时都要读；而且插件停着的视图在彻底删除时不重放（上面"停用的插件留下的事件"），语音事件里有原话，留着旧的就删不干净。插件的数据契约里登记素材来源、改写函数、`voiceIntake` / `retryVoice` 请求和移除时删什么。
- **核心留的口子**：输入队列的挡板（"这条消息还要不要等"，插件按 208、210 号票的规矩回答；插件不在时内核的默认：还没识别完、只有语音的不交，带附件、卡片的照交、语音那段写"识别失败"，同 208 号票的失败）和挡板变了再看一眼队首；语音回复由插件在回合前后决定（会话现取，插件不在就不放行语音、不合成）；插件运行中停用、启用时秘书手头这一条处理完按新的装配（`spoken_summary`、`send_voice`、系统提示里的条件"语音"跟着变）。两个工具仍随会话的工具一起给（不改工具的先后），没有改成 agent 贡献。
- **停用时**：识别进程停掉、合成不再调用；网页上没有按住说话、没有自动播放，设置 · 语音不列；历史里的语音气泡照样显示文字，录音、合成好的音频照样能听（媒体接口，只是读文件）。启用回来排队、识别中的接着识别（同守护进程重启）；停用期间照交了"识别失败"的那条识别出来，另交一条带转写的通知。
- **连数据删**：录音、合成出的音频、语音事件里的文字（识别结果、送进 TTS 的原文换成删除标记，状态留着）、参考音色、待我处理里语音的说明。会话里转写成文字交给过二狗的那部分归会话，不删，确认框写明；素材库不动（素材属于内核）。
- **网页**：多了三个插槽——输入框的语音模式、后台部件（自动播放）、插件画的设置页；录音、播放的底层和语音气泡留在核心（网页上的悬浮按钮也用录音器，历史气泡停用时照样要画）。鸿蒙 App 的原生录音器不动，网页照插件状况决定用不用。
## 内置浏览器和网页工具拆成插件（212 号票，2026-10-20）

同一句话里的第一个（"把内置浏览器和网页工具，日历和语音这三个拆成插件"）。内置浏览器是第五个插件（现在的插件：提醒 126、记忆 129、日历 213、语音 214、内置浏览器 212，名字 `browsing`）：

- **拆的**：守护进程里浏览侧边栏的设备通路、秘书的八个网页工具（读网页、填框、找文件、看图、交文件、开网址、看能点的、点）、交文件的取件码和候选缩略图、网页候选卡、悬浮按钮上说话、"存进二狗的素材"、交给秘书的输入后面那段说明、系统提示里讲浏览的三段，联网搜索"算上内置浏览器"那一步（`browsing/`）；网页里的"浏览"页、浏览侧边栏、悬浮按钮和小气泡、挑图片窗口、网页候选卡（`plugins/browsing/`）。**不拆的**：授权的文件夹（秘书在聊天里也用，`folders/`）、132 号票的转发和应用内浏览器、联网搜索本身、App 原生浏览器那一层的接口和页面桥（`app/native-browser.ts`、`page-bridge/`：鸿蒙 App 构建时从这里打包页面桥）、"浏览"的设备设置和设置 · 浏览与填框。鸿蒙 App 一行不改。
- **agent 贡献多了"输入附注"**（`agent.notes`）：接在交给 agent 的那条输入正文后面的一段。原来写死在核心 `conversation/agent-input.ts` 里的"在网页上说的"那段说明改由浏览插件登记，核心不再 import 它。上下文块（唤起时、每轮输入时单独的一块）放不了：这段说明要贴着那条消息、只跟着从网页发来的那几条。
- **工具可以排在内核的后面**（`at: "end"`）：秘书的网页工具一直排在工具清单最后，拆出来以后照旧（默认的插件工具在内核的工具前面）。
- **内核的服务多了三个**（`localFolders`、`thumbnails`、`webSearch`；媒体库 `media`、数据目录 `layout` 和语音插件共用）：浏览插件要的都是内核已有的东西，组合根绑上。**语音插件是可选依赖**（`wants: [VOICE]`）：悬浮按钮上说话每次现取语音插件的识别，语音插件停用了浏览插件照常，说话回"语音插件没启用"。
- **数据契约**：网页候选卡、存进素材的网页（事件和素材都属于内核，素材来源和改写函数随插件登记，停用也登记）；"连数据删"删网页候选卡的每个版本和候选缩略图的缓存，存进素材的网页不删（素材属于内核）。
- **网页插件多了"页签"插槽**（`tabs`）：主导航里"浏览"的位置、地址、什么时候有（鸿蒙 App 里有原生浏览器时）还是核心定，整页、侧边栏模式那一页、主框架里挂一次的由插件给；宿主建的时候交给插件页面的连接和 HTTP（`ctx.page`），浏览插件第一次装上时接上 App 推过来的。停用时导航里没有"浏览"，地址和侧边栏模式写"内置浏览器插件没启用"。App 那边 `browserAttach` 了替主页面接外链收不回来：停用后它接住的外链网页交给系统浏览器打开。
- **记忆插件不用 `wants`**：它读存进来的网页只要一个纯函数（`savedPageOf`，在 `browsing/api.ts` 里），浏览插件停着时存进来的网页照样检索得到，用不着取服务。

## 输入上下文块可以异步、可以给回话带部分（266 号票，2026-10-25）

每条消息的记忆简报要先检索（本机 bge-m3，线上一条约 0.3 秒）再决定带不带，同步的 `text()` 放不下：

- **`when: "input"` 的 `text()` 可以交回 Promise**：会话把它和附件的准备一起等齐了才交这条输入，等的时间就是回话慢下来的时间，所以贡献方要自己设上限（记忆简报 3 秒，超了这一轮不带）；出错的那块当没有、记一行日志，别的块照拼。全是同步的照旧同步，`wake` 块照旧只能同步。
- **`input` 块可以给 `replyParts(message)`**：文字算好之后取一次，交回的 part 放进这一轮第一条回话（一条回话都没有就在这一轮结束前单独记一条 agent 消息）。记忆简报靠它把"带了哪几条、为什么"挂到回话上，网页画进"回忆了 N 条记忆"——不另造一种事件，也不进模型看到的上下文。
- **内核的服务多了一个**（`KERNEL.usage`，可选）：插件塞进上下文的估的 token 记进账本（`context_usage`，不进 token 合计），用量页单列。

## 运行时是插件贡献点，宿主协议是运行时的接缝（286 号票，2026-10-25）

用户 2026-10-25 要二狗能指挥本机的 Claude Code（issue 24），并追加："会话支持 Claude Code 这个事情要做成插件化，以后我要接入 Codex，也用同一个插件的方式来实现即可"。所以 agent 运行时成了插件宿主的一个贡献点，pi 照同一个接口登记：

- **一个运行时**（`runtime/runtimes.ts` 的 `AgentRuntime`）：id、给人看的名字、子进程入口、能力清单（共享协议包 `RUNTIME_OPERATIONS` 的每一项能不能做：插话、压缩、撤回、切分支、分支摘要、换模型写交接摘要、思考档位、斜杠命令转交、接管已有会话、彻底删除改写会话、做完这一步停下、范围审视、Remote Control）、可选模型和设置项、（可选）列本机能接管的会话。界面和守护进程按能力清单决定显示什么、走哪条路（一套界面几种运行时，取交集，没有的由二狗间接补或不显示）。
- **宿主协议是接缝，不改**：每个运行时是一个实现宿主协议的子进程入口，守护进程用 `process.execPath` 拉起它，每个会话一个（ADR-0002 照旧：名额、Job 对象、超时、闲置退出、孤儿回收不分运行时），收同一条"启动"、说同一套消息（ADR-0004）。守护进程、网页都只认宿主协议和二狗自己的事件，不知道下面是 pi 还是 Claude Code；Claude Code 的适配（Agent SDK、钩子、MCP）全在它的子进程里，就像 pi 只在 `agent-child/` 里（ADR-0001 的封装边界照旧）。
- **登记在数据契约里**（`ContractContext.runtimes`），不在装配时的 `ctx` 里：维护者的运行时属性（`Task.runtime`、`Project.runtime`，没写是 pi）存在事件里，插件停用、没装上、移除了也要认得它、写得出"X插件没启用"；能不能用跟着插件此刻在不在运行。pi 由组合根照同一个接口登记，不是插件、不能停用。
- **维护者多一个属性"运行时"**：项目的维护者照项目的（没写照转来的任务的），任务自己的、定时作业自己的维护者照它执行的那个任务的。agent 宿主按它给拉起请求带上运行时，agent 管家按登记表解析子进程入口。秘书、子 agent、评审照旧是 pi。
- **运行时插件停用时**（运行时闸门 `agent-host/runtime-gate.ts`）：用它的维护者不拉起，输入留在队里；有活拉不起时活动状态"等你"，说明写明哪个插件没启用（项目没有"等我"状态，项目转等我就是它的维护者"等你"）；执行中的任务转等我（新的等我原因"运行时没启用"，说明写明哪个插件，用户点"继续"没用）。正在做的那一轮做完才停（不中止，照"正在跑的一轮不崩"），做完子进程退出、不再拉起；执行中的任务也等那一轮做完才转等我，免得做到一半的调用被"任务不在执行中"拒掉。启用后接着：因为它在等我的任务接着执行（名额满了排队），排着的输入交给新拉起的子进程。
- **网页**：`GET /api/runtimes`（`RuntimesView`）列出登记了的运行时连同能力清单、能不能用。用 HTTP 不用插件频道上的推送：推送会多一条订阅时补推的临时事件，录下的事件流（`plugins-*.json`）就得重录。新建任务、项目时选运行时、⚙ 按运行时显示从 289 号票起（见文末）。

考虑过、没选：

- **运行时登记在装配时的 `ctx` 里（停用就撤）**：停用后登记表里没有它了，维护者记着的运行时写不出是哪个插件没启用，网页上也认不出任务用的是什么；要再在定义里静态写一份"我提供哪些运行时"，两处要对得上。
- **在守护进程里直接跑 Claude Code 的 SDK**（issue 24 第五节第 1 条）：省一层进程，但打破宿主协议这条接缝、出事拖垮二狗；用户选了每个会话一个子进程。
- **插件停用时马上中止维护者手头那一轮（照暂停）**：项目对话里那一轮的回话就丢了，用户得重说；做完再停没有这个损失，代价是执行中的任务要等那一轮做完才转等我。

Claude Code 照上面的贡献点做成插件 `claude-code`（`packages/daemon/src/claude-code/`）：数据契约里只登记运行时，装配什么都不做；子进程入口 `child/main.ts` 用 Agent SDK（`@anthropic-ai/claude-agent-sdk`，锁版本，只在子进程里引）的 `query()`（流式输入）驱动本机的 claude，把宿主协议翻成 SDK 调用、把 SDK 事件翻回宿主协议。用户 2026-10-25 的第 3 条决定（用 Claude Code 自己的配置，二狗的信息追加在末尾）落成：加载用户、项目、本地三层设置，系统提示用 Claude Code 自己的、二狗的追加在末尾且不录下（恢复的会话里当场生效）。宿主协议只加了一个可选字段（22：工具调用开始、结束带 `parentToolCallId`，子代理里的调用挂在调用它的 Agent 工具下面），pi 不用它。

## 运行时的工具调用都过二狗守卫（288 号票，2026-10-25）

issue 24 用户答复第 4 条：用 Claude Code 跑的维护者，每次工具调用都经二狗守卫、二狗这边全程留记录。守卫留在内核（上面"内核"一条），运行时只负责把调用交过来：

- **闸口在子进程里，用运行时自己的钩子**：Claude Code 是 SDK 的 `PreToolUse` 钩子（每次调用都过、子代理里的也过、在用户设置的放行规则之前），不用 `canUseTool`（它只在 Claude Code 自己本来就要问人时才叫，放行过的规则直接绕过，调研 32 第 4.2 节）。钩子里发宿主协议的 `guard_request`、等 `guard_reply`，判定原样翻成钩子的决定；守卫放行不给决定，Claude Code 自己的规则和权限模式照常（二狗的守卫是加的一道，不替掉它自己的）。
- **工具名映射在子进程里**：能对上二狗工具的（Bash → bash、Read → read……）映射过去，照二狗自己的工具判；原样的随 `guard_request.native` 交来，完整内容（ADR-0020）存原样的参数（`ToolCallDetail.nativeTool`，可选字段）。守护进程不认得 Claude 的工具名。
- **运行时自带、二狗没装配的工具由运行时登记**（`AgentRuntime.guardTools`，工具登记表的来源 `runtime`）：用这个运行时的维护者，agent 宿主把它们加进守卫的注册表，工具包不按白名单硬拒绝它们和没登记的（没登记的照"未登记的写操作"判）。单次调用的超时也由运行时声明（`AgentRuntime.toolTimeouts`，子代理不按单次超时算）。
- **运行时自己要问用户的，变成内核的卡片**：宿主协议 23 加 `ask_user` / `ask_user_reply`（选择题、计划批准），卡片类型 `runtime_question` 在内核（`conversation/runtime-questions.ts`），不随插件停用——停用时用它的维护者本来就不拉起，卡在这一轮结束时作废。

没选的：把 Claude Code 的工具名逐个登记进守卫、守护进程按它的参数判——守卫的规则（路径围栏、bash 拆开逐条判）就得为每个运行时各写一份；在守护进程里接 SDK 的钩子——ADR-0001 的封装边界不许，宿主协议是接缝。

考虑过、没选：

- **用 SDK 自带的 claude.exe**：版本和 SDK 锁死、不会对不上；但和用户终端里的不是同一个版本，接管、和 Remote Control 互转用的又是用户装的那个。选了先找本机装的、找不到才用自带的（294 号票真机验证时核对两边的版本能不能一起用）。
- **用量按每轮 `result` 的四段报**：那是一轮里主线几次模型调用加起来的，⚙ 的"上下文用量"按最近一次调用算会算大；选了每次模型调用报一条（流里 `message_start` 的输入、`message_delta` 的输出），`result` 只在流里没有逐次用量时兜底。

## 数据源是插件贡献点，导入文件夹和断开在内核（295 号票，2026-10-25）

用户 2026-10-25 问"数据源是不是也可以通过插件化的方式来接入，每一种数据源是一个插件"，issue 25 的六件事都按推荐定了（每种数据源一个插件、只产素材不产结论、量大的先整理成摘要、共用导入文件夹、统一外形和第一个数据源插件一起做）。这一张把统一外形和导入文件夹接通（用测试里的假数据源插件验证），296 起逐个接真的（Looki、Google 日历 / Gmail / 联系人、手机 App）：

- **"数据源"是第二个写在数据契约里的贡献点**（照运行时，`ContractContext.dataSources`，登记表 `data-sources/registry.ts`）：数据源的静态部分（id、名字、敏感类别、两种用法和默认、定期导入的时间、它导入的记录是哪几类事件、认导入文件夹里哪种文件）插件停用、没装上、移除了也认得——设置 · 数据源照样列出、写"X插件没启用"，断开并删照样删得掉、条数照样数得出；要插件在运行的（连接状态、填设置、同步、导入一个文件、断开时插件自己的清理、按需查的工具）写成函数，里面经 `ctx.active` 现取，内核只在插件在运行时叫。
- **两种用法由内核管开关**：按需查（秘书被问到时现查、不存）的工具由内核替数据源登记成一份 agent 贡献，只给按需查开着、插件在运行的（agent 贡献多了 `refresh()`：贡献给出的东西变了、不是登记撤销，也通知秘书重新装配）；导入（同步进来）开着、连着、登记了时间的挂内部作业 `data-source:<id>`。开关存在配置区的 `data-sources.json`，没改过照数据源登记的默认。
- **数据源只产素材、不产结论**：插件把拿进来的写成自己的事件、经 `ctx.materialSources.register` 采成素材（本章开头的素材来源，ADR-0006），不碰推理图谱（ADR-0030）、不直接写个人档案；证据性质按来源定、量大的先整理成摘要是各数据源插件的事（issue 25 第 2 节）。用到的敏感类别对上记忆的敏感类别开关（这一张给 `SensitiveCategory` 加了"位置"，和情绪、财务、关系一样是开关占位）。
- **密钥在密钥区、由守护进程直接读写**：数据源的 API Key、应用专用密码、私密地址在密钥区的 `data-sources/<id>.json`（不经 LSM 注入环境；模型 key 照旧），只经函数参数里的 `ctx.secrets` 给那一个数据源；出错原因里带着它的值，内核记下之前换成 `***`。
- **断开在内核**：先叫插件自己的清理，再删密钥区那一格；选"连已导入的一起删"走"删除参与方"登记表的新一种删除 `DATA_SOURCE_DELETION`（同删项目、删任务、移除插件）——它导入的记录和同步记录整条换成"已删除"标记，由这些记录采成的素材照彻底删除的口径删（记忆命令出处 `data_source`，不产生"显式记忆命令"素材），"已导入"里它的文件提交之后删掉。和移除插件时连数据删不同，这里**素材跟着删**：用户选的就是"连已导入的一起删"。
- **共用的导入文件夹是内核的一个小功能**（不是插件）：数据目录的 `imports/`，每分钟、文件夹一有变化、用户点"现在检查"时看一遍；认得的先挪进 `imports/imported/` 再交给数据源导入（同一个文件不会被导两次），导入出错挪回原地；认不出的、几个数据源都认的、插件没启用的、导入关着的、出错的留在原地并在数据源页提示。导入文件夹整个不进备份快照（`nonBackupEntries`：Takeout 这类导出可能几十 GB，导入后的数据已经在事件和素材里）。数据源页（`#/more/data-sources`）也在内核，网页插件要在一个数据源下面画设置（填 Key、测试连接）就登记新的网页插槽 `dataSources`。

- **设备交来的、外部日历**（299 号票补）：数据源多了 `push`（设备经网页交来，内核按数据源登记的 schema 查、按幂等键只收一次、记同步记录；算"导入"这种用法）和 `calendar`（交给日历插件显示的日程，内核服务 `KERNEL.externalCalendars` 转给日历插件，日历插件 `needs` 它）。"只产素材"不是"必须产素材"：通讯录挑的人走个人档案的候选（用户逐条确认才写进档案）、手机日历走日历插件，都不进素材；断开并删时别的模块里从这个数据源来的东西由那个模块登记删除参与方（个人档案的候选）。没选"日历插件自己登记一个外部日历贡献点"：数据源的服务建在插件之后、数据源本来就带着"插件在不在运行"，经数据源转一道最省，297 号票的 Google 日历同样走这条。
- **原始数据**（300 号票补）：数据源多了 `raw`（插件自己存储里的原始数据按天列出、能按天清掉，动作 `clear_raw`）。量大的（位置点、照片的时间地点）插件先按天整理成摘要再写事件、采成素材，原始的那一份不进事件日志（不然清不掉、删不干净），存在数据目录里插件自己的地方，用户能按天清；断开并删、移除插件连数据删时一起删。

考虑过、没选：

- **数据源登记在装配时的 `ctx` 里（停用就撤）**：停用的插件的数据源就从页面上消失了，用户没法在插件停用时断开并删掉它导入的；要再静态写一份"我导入了哪些事件"，两处要对得上。
- **在现有的"连数据删"（`removal.declare`）里加一节当外形**：那是移除插件时的一次性删除，没有连接状态、同步、两种用法这些常用的；断开数据源（插件还在）和移除插件是两回事。
- **导入文件夹做成一个"文件导入"插件**：数据源插件就得依赖它（`needs`），停了它所有手动导入的数据源一起失灵；它本身很小、不拥有数据，留在内核。
- **按需查的工具由插件自己经 `ctx.agent.tools` 登记、自己看开关**：每个插件都要写一遍"开关关了不给"，开关一变还得自己想办法让秘书重新装配；内核统一管更不容易漏。

## 选运行时、中途换运行时、斜杠命令转交（289 号票，2026-10-25）

- **中途换运行时 = 原来的写交接摘要 + 新的新开一段会话**（issue 24 的"和换模型一样"）：两个运行时的会话格式互不相认，没法接着同一段会话。宿主协议 24 加了命令 `write_handoff`（报 `handoff_written`），每个运行时都要实现，摘要由原来的那个写；会话里记一条"已换成 X"的分隔，新会话名跟着这条分隔，摘要作为新会话第一条输入的上下文。换在手头这一条做完之后（各种维护者一样，不照换模型"项目维护者等下一段会话"的规矩：运行时是用户明确要换的）；换完才把任务、项目的运行时写进事件。
- **选的模型和设置项经"启动"交给子进程**（宿主协议 24 的 `SessionAssembly.runtimeOptions`）：运行时自己的设置项（Claude Code 的权限模式、思考档位）只有它的子进程认，守护进程只核对值在它登记的列表里；默认"跟它自己的设置"不交。
- **斜杠命令在守护进程这一侧认**：用户发的以 `/` 开头的话，二狗自己的命令优先，其余对能转交的运行时原样当输入交出去（不加时间标记、不展开 skill）；能用的命令清单由子进程报回（`runtime_catalog`），只记在内存里。

考虑过、没选：

- **换运行时时把旧会话的记录翻译给新的运行时**：要读写对方内部的会话格式（Claude Code 的记录二狗不读不改，287 号票），也装不下对方的工具调用；摘要够接着做。
- **斜杠命令交给子进程自己判断**：子进程不知道二狗自己的命令（`/流程`、`/任务`），两边会各认一半；放在守护进程这一侧一处判断。

## 第一个真的数据源插件 Google：日程走 299 号票的 calendar()、定期导入可以每隔几分钟（297 号票，2026-10-25）

Google 日历走"私密 iCal 地址"（调研 37、39），事件按 issue 25 第 3 节直接给日历插件显示、不进素材，秘书被问到安排时现查。几样取舍：

- **日程交给日历插件用 299 号票定的那条路**：数据源的 `calendar(range, ctx)`，内核经 `KERNEL.externalCalendars` 只问在运行的数据源、补上数据源和它的名字，日历插件按月取时列出（协议的 `CalendarExternalEntry`）。Google 在它上面只用到已有的 `calendar`（哪个日历：用户起的名字，没有用日历自己的）；重复事件在 Google 这边按问的那一段展开（只展开 `[from, to)`），日历插件拿到的已经是一次一次的日程。断开以后没有地址了就不给（和手机日历一样），停用插件时内核不问它。
- **日程的数据归 Google 插件**：每个 VEVENT 写成自己的事件（内部频道 `google`，只写新的、变了的、没了的），"共几条"用 299 号票的 `count`（按最后一版数）；数据源断开并删、移除 Google 插件连数据删时跟着删。
- **定期导入可以每隔几分钟**：内部作业的时间表多了 `IntervalSchedule`（`{ kind: "every", minutes }`，从上一次跑完往后数、错过了开机补一次），提醒那一套规则不动（提醒不会每隔几分钟响）。每隔几分钟的数据源同步什么都没变（新进来 0 条、没出错、上一条记下的也没出错）的那次**不记同步记录**——每 30 分钟一条会把事件日志撑大、数据源页每次现读也越来越慢；只在内存里记着，页面上照样显示"上次同步"，重启后显示最后记下的那次。内部作业自己的"跑过了"照记（一个作业一行的视图，开机补跑靠它）。
- **数据源外形补的几样**：`usages.import.destination`（导入的东西去哪，不写是整理成素材）、`syncOnConnect`（连上以后马上同步一次）、`status()` 的 `note`（提示，不算出错："日历插件没启用"）和 `items`（下面的几样：几个日历）；填设置没过的原因在已经连着时也写出来。

考虑过、没选：

- **外部日历另起一张登记表**（297 号票先做过一版：内核一张登记表，带来日程的插件在 `setup` 里登记来源，变了在活动状态频道推临时事件、日历页重新取）：299 号票先合进 main 定了 `calendar()` 这条路，合并时改用它，不两套并存。代价是日历页开着时，同步来的变化要换月或重新打开才看到（手机日历也是这样）；要实时再给数据源同步加通知。
- **每次同步都记同步记录**（295 号票的老规矩）：一年一万多条只为写"上次同步"，不值；有变化、出错、恢复的照记，看得出发生过什么。
- **加 npm 依赖解析 iCal**（ical.js、node-ical 这类）：要的只是 VEVENT、全天、TZID、RRULE 常用的那几项、EXDATE、RECURRENCE-ID，几百行自己写得完，时区换算用 Node 自带的 Intl，不多一个依赖。
## Looki 插件：接外部接口的数据源（296 号票，2026-10-25）

照上一节的外形接真的：插件 `looki` 在数据契约里登记数据源 `looki`、两条采集规则、改写函数和"连数据删"，装配只提供一个服务（接 Looki 官方的只读开放接口），数据源的函数一行一个经 `ctx.active` 现取它。几处取舍：

- **接口地址写死在插件里、用户只选区域**（中国区 `open.looki.tech` / 海外 `open.looki.ai`），不让填地址：Key 只会发给这两个地址；测试连接直接拿 Key 调所选区域的 `/me` 一步判断（没照官方 Skill 先去 `open.looki.ai` 做不带 Key 的地址检查：地址本来写死，中国区也不必依赖海外那台）。测试用的假接口经插件工厂 `createLookiPlugin(options)` 换地址，主切面经 `extraPlugins` 换掉清单里的同名插件（照 Claude Code 插件）。
- **连接状态只在内存里**：Key 不认了、限速了在插件服务里记着，`status` 不调接口；重启后先当连着，下一次同步、按需查碰到了再标（数据源页上"上次同步出错"的原因一直在）。区域、打码的账号和 Key 存在密钥区同一格里（断开时一起删）。
- **只导入到昨天为止**：当天的时刻还在变，每晚整理也不读当天的数据源素材；定期导入定在 02:30，赶在 03:00 的整理之前。今天的事由按需查现查。
- **AI 日记当"别人写给你的"、只进检索**：它是 Looki 的 AI 写的，不是用户做的事，也和当天的时刻说的是同一件事；全文只进检索，按条标情绪、健康（默认这两类不推断）。照片视频不进素材库，也不交给秘书链接（一小时就失效）。
- **"连数据删"删记录和密钥区里那一格**：素材属于内核照旧不删（要连素材一起删，先在设置 · 数据源里断开并选"连已导入的一起删"）。
- **存一份到本地是插件自己的事，内核只多给三样通用的口子**（307 号票）：照片、日记、vlog 下载到用户选的文件夹（默认「文档」下的 Looki），设置在配置区、按 Looki id 去重的索引在数据目录里，都归插件（移除并连数据删时删设置和索引，文件是用户的档案、不删）；它们不是"导入的记录"，不进素材、不进 `records`，所以断开并删不碰。内核为它加的是任何数据源都能用的：`status()` 带插件那一块要的数据 `panel`（原样交给网页，内核不看）、断开时要说的一句 `disconnectNote`、本机文件夹 `localFolder` 加数据源动作 `open`（和导入文件夹同一个"在电脑上打开"）。没另开插件自己的 HTTP 接口：设置、补存走填设置（`values.archive`），和 Google 加删日历同一条路。

## 插件要的外部组件可以没装（315 号票，2026-10-27）

开源后 Claude Code 的 Agent SDK（Anthropic 自己的许可）不随二狗分发，改成可选依赖。插件定义多一个 `missing()`：它要的外部组件没装时交回给人看的一句（没装什么、怎么装），装着是 `undefined`。

- **宿主每次装配之前问一次**：没装的不装配，记成没装上（原因是那一句），依赖它的也不装；数据契约照常登记（维护者记着的运行时照样认得）。
- **给人看的**：设置 · 插件里状况写"没装"、下面是那一句（`PluginInfo.missing`），装好之前启用不了（`cannotEnable` 也是那一句）；运行时不能用的原因写那一句而不是"X插件没启用"（`RuntimeOwner.missing`）。停用、移除之后照旧写"没启用"。
- **装好以后**点启用就装上（因为它没装上而没装的跟着装上），不用重启；重启也一样。
- **只找、不加载**：Claude Code 插件按 Node 的解析规则找 SDK 在不在（`claude-code/sdk-installed.ts`），SDK 照旧只在子进程里引；这是边界测试里写明的唯一例外。以后 323 号票的组件下载做好后，"怎么装"那一句换成一键装。
