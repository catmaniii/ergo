# 工具调用完整内容的保留期和总量上限：到期的改写成只剩摘要（事件日志第三个例外，单开 expireContent），不重放视图、不马上做检查点

53 号票起每次工具调用的完整参数和返回都另存一份，放在事件日志守护进程内部频道 `tool_calls` 上的 `tool_call_detail` 事件里（ADR-0020），没有上限，也不过期。65 号票要给它定保留期和总量上限，用户 2026-10-09 定：保留 90 天、总量上限 2 GB（到了从最旧的清），每天凌晨清一次就够；设置里给"现在就清理"按钮（点之前确认），只清已到期或超上限的。清掉的只是完整内容，工具调用记录、要点、效果记录、时间线照旧；还被用着的不清。规格第 15 节随之把"事件日志不可修改"的例外从两个改成三个。定成：

- **改写成只剩摘要，不删行**：到期的 `tool_call_detail` 事件，负载换成只剩摘要的样子（`clearedDetail`：`args` 是参数摘要、`result` 是结果摘要，和聊天里工具调用记录的摘要同一写法；去掉截断说明；记下 `cleared: { reason: "expired" | "over_limit", at }`），工具、结局、归属、时间、图片说明不变。行、频道、序号、类型、时间都在，频道内序号照旧连续；详情接口照样回 200，前端看到 `cleared` 就和没存完整内容一样退回摘要，注明为什么；效果记录照旧按调用 id 从效果日志里找。
- **事件存储单开一个口子 `expireContent`，只改得了登记过的事件类型**：彻底删除和删除项目共用 `appendBatch` 的 `purge`（ADR-0008、ADR-0010）。保留期清理另开 `EventStore.expireContent(rewrites: ExpiredContent[])`：拥有这类事件的模块在自己的派生视图上登记 `contentExpiry: { eventType, expired }`（一类只能登记一次，现在只有 `tool_call_detail`），别的类型一律拒绝、整组回滚，免得被当成通用的改写口子。同一事务改写、没有这条事件时整组回滚、不通知订阅者，这些和彻底删除一样；**不同的是不重放派生视图**——只去掉内容，不改别的视图归并出的东西，而完整内容可能上 GB，每天整体重放一遍太重；登记它的视图在 `expired` 里更新自己记着的大小、样子，和 `apply` 归并换过的负载结果一致（整体重建后对得上）。
- **不马上做 WAL 检查点**：彻底删除提交后做 `wal_checkpoint(TRUNCATE)`，是为了原话不留在 WAL 里。保留期清理没有这个要求，而 `TRUNCATE` 要等所有读者读完——每晚备份的 `VACUUM INTO` 在工作线程里一直占着读，每批都要等满 `busy_timeout`（5 秒），电脑睡醒后备份和清理一起补跑时事件循环会被反复卡住。交给 SQLite 自己的自动检查点（PASSIVE，不等读者）。测试里另一个连接开着读事务时改写照样马上回来。
- **挑哪些**（`detail-retention.ts` 的 `planCleanup`，纯函数）：先是存下（调用结束时）超过保留期的；清完总量还超过上限的，从最旧的起往后挑到上限以内（按清掉之后一个字节不剩估，清完重新算，还超就再挑：宁可少清，不多清）。总量按负载 JSON 的 UTF-8 字节算，清掉后剩下的摘要也算。
- **还被用着的不清**：归属没结束的任务（流程也是任务）的调用；待办里还在（没删、没归档）的事项引用到的调用——哪些卡片、通知会引用调用、怎么找到那次调用，登记在 `CALL_REFERENCES` 一张表里（审批卡、快速动作卡、"交给我做"、"中断不确定"），新加的卡片、通知要引用调用就在表里加一行；外加还没决定的审批（卡被归档了也算）。不用了以后下一次照样清。
- **怎么跑**：内部作业 `tool_call_detail_retention` 每天 04:15（错过了开机后补一次，异步，不挡启动）；设置里的"现在就清理"按同样的规则马上清一次，同一时间只跑一次。一批最多 100 条一个事务，批与批之间让出事件循环。每跑一次写一行日志。
- **派生视图 `tool_call_details` 加列**：存下的时间、大小、任务、`state`（`full` / `cleared` / `purged`）。53 号票建的表没有这几列（都要从负载算，ALTER 加列补不上），启动时删表重建，`create` 返回 `"refill"`，由事件存储把事件日志分批过一遍这个视图补回来（彻底删除过的只剩删除标记，补不回原文）。

## Consequences

- 事件日志不可修改的例外有三个（规格第 15 节）。第三个不重放视图，所以只能用在"去掉内容、不改别的视图归并结果"的改写上；以后别的事件要做保留期清理，得同样保证这一条，在自己的视图上登记 `contentExpiry`。
- 清掉的旧内容可能在 WAL 里多留一阵，直到 SQLite 的自动检查点把它写回库文件；数据库文件不会因为清掉而变小（空闲页留着给后来的写入用，`secure_delete` 把它们清零），设置里显示的是完整内容本身占多大。每晚的快照用 `VACUUM INTO`，清掉的部分不再进新快照；旧快照里照旧有，随快照的保留规则过期。
- 清掉之后完整内容找不回来；"现在就清理"点之前确认，确认框里说清楚清掉几次、大约多大、找不回来。
- 效果日志（`effect_recorded`）里写文件这类调用的参数是原样存的（含写进去的全文），不在这份完整内容里，不受保留期管（票里写明效果记录不受影响）；它的体积另算。
- 总量上限是每天查一次，两次之间可以超出一天的增量（用户定的）。

## Considered Options

- **删掉这些事件的行**：频道内序号就不连续了（规格第 2、4 节要求连续），备份、补发、按序号读都假设它连续；行删掉后详情接口也没法说"过了保留期"，只能 404。
- **走彻底删除的口子（`appendBatch` 的 `purge`）**：每次都整体重放所有派生视图，整个事件日志（含上 GB 的完整内容）读一遍、每个视图重建一遍，每天跑太重；还会在每批后做要等读者的检查点。
- **一个不限事件类型的通用改写口子**：容易被当成"随便改负载"的后门用掉；按事件类型登记，一眼看得到谁能用。
- **每批或整轮清完做一次 `TRUNCATE` 检查点**：要等读者，和备份撞上就卡 5 秒；清掉的又不是要马上抹掉的原话。
- **完整内容另存到事件日志之外（一张表或一组文件），过期直接删**：ADR-0020 已经比过，备份、恢复、彻底删除都围着事件日志转，另起一份存储要把这些各做一遍；这张票只管保留期，不改存法。
- **"现在就清理"清掉全部（除了还被用着的）**：用户定了只清已到期或超上限的。
