# 每个 agent 跑在自己的子进程里，守护进程只当管家

二狗的每个 agent（秘书、各个维护者、子 agent）各占一个子进程：有活时常驻，闲下来就退出，下次被唤起时从磁盘上的会话接着跑。守护进程自己不跑模型，只负责以下几件事：
- 启停子进程；
- 守卫审批；
- 事件日志；
- 派单器和调度器；
- 给前端提供界面和事件流。

子进程之间不直接通信。agent 之间的往来（工单、回执）一律经过守护进程。

选它有三个原因：
- **隔离故障**：一个维护者卡死、内存爆掉或崩溃，不会拖垮秘书。
- **天然分开每个项目的配置**：每个项目的工作目录、密钥和工具包都不一样，在进程层面分开最自然。
- **绕开全局单例**：pi 的全局单例（设置、认证、模型注册表）在同进程多会话下会不会互相干扰，从来没有验证过。换成每个 agent 一个进程，这个问题直接不存在了。

## Considered Options

- **同一进程多会话**（守护进程里开多个 `createAgentSession()`）：
  - 好处：最简单，agent 之间互相调用就是函数调用。
  - 坏处：一个 agent 出事会拖垮全部；全局单例的问题没有验证过。
  - drama_maker 的设计稿原本选的也是它，评审时以同样的理由放弃了。
- **每轮对话起一个子进程**（drama_maker 的实际做法：`pi -p --mode json --session-id`，跑完一轮就退出）：
  - 好处：隔离得好。
  - 坏处：每轮都要冷启动；等审批这类跨轮次的状态挂不住；它的子 agent 结果回不到父会话。
- 调研依据：drama_maker 的源码和踩坑记录（「运行时架构」的讨论记录），以及 `docs/research/10-pi-layer-mapping.md`。

## Consequences

- **要写守护进程和子进程之间的通信层**。开工后的第一个 spike 先验证 pi 官方的 RPC 模式（stdin/stdout JSON）；不合适的话，就在子进程里用 SDK 加自定义 IPC。不管哪种，都包在 ADR-0001 的 `runtime/` 封装层里。
- **照 drama_maker 的教训，这些都要做**：
  - 每次启动子进程都显式注入 API key 和环境变量（被 LSM 拉起时拿不到用户级环境），并剥掉不该给的密钥；
  - 每次调用都有超时，子进程数量设上限，没人管的进程要回收；
  - 子 agent 的结果必须回到父会话；
  - 进行中的回合要写盘。
- **子进程要能被一起清理**：所有子进程和它们的孙进程都放进二狗自建、不允许脱离的 Job 对象。守护进程被 LSM 重启时，Job 对象会把它们一起清掉，再按「运行时架构」的混合恢复规则续上。
- **守卫的判定集中在守护进程里**：
  - 子进程里的 pi 扩展在 `tool_call` 钩子里，把每次调用送给守护进程，再按守护进程的判定放行或拦截。
  - 关注类别、授权项、时序规则用到的历史，只有一份，都在守护进程里，agent 改不到。
  - 扩展代码放在框架目录里，路径围栏不允许 agent 写这个目录。
- **资源**：每个活跃的 agent 多占约 100–150 MB 内存（估计值），唤起时有大约 1 秒的启动开销。本机有 32 GB 内存，可以接受。
