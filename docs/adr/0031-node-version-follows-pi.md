# ADR-0031 二狗的 Node 大版本跟着 pi 走

状态：已定（用户 2026-10-26）

## 背景

- 二狗打包、运行用一份专用的 Node（不用 PATH 上的；开源后安装包自带 Node）。项目服务也用这一份（324 号票：命令开头的 `node` 换成二狗自己那份）。
- 二狗的 agent 核心是 pi（ADR-0001）。pi 跑在二狗的这份 Node 上，联网、流式输出都在 pi 里，是二狗里对 Node 版本最敏感的部分。
- pi 只在 Node 22 上测：它的 `.github/workflows/ci.yml` 写 `node-version: 22`，官方安装脚本没有合适的 Node 时装 `nodejs.org/dist/latest-v22.x`；npm 包要求 Node ≥ 22.19（0.75.0 起）。pi 的更新日志里修过好几处只在 Node 24、26 上出的问题（Node 26.0 下压缩响应解析失败、Node 26 流式请求空闲五分钟超时、Node 24.19+ / 26 下 `node --watch` 的 worker 消息），都在联网这一层，二狗的假模型测试测不到。
- 2026-10-26 试过把二狗换到 Node 26：全量测试也过。但"打包的 Node 比 pi 测的新"意味着 pi 在没测过的 Node 上的问题会先落在用二狗的人身上，要另外花成本兜（两个版本都测、真模型联网检查、给 pi 报问题或打补丁）。

## 决定

1. **二狗打包、运行、测试用的 Node 大版本跟 pi 一样**：pi 的自动测试和安装脚本用哪个大版本，我们就用哪个，取那条线的最新补丁（现在是 22，v22.23.4）。
2. **pi 升级我们就跟着升；pi 不升，我们照旧用。** 不自己往前跑。
3. **升级 pi 时核对**：看 pi 的 `ci.yml` 里的 `node-version` 和安装脚本里的 `latest-v<大版本>.x` 变没变；变了就跟着换大版本、跑全量。
4. `engines` 写 pi 的最低要求（现在 ≥ 22.19）。开源后的安装参数只放行测过的版本（默认 pi 那条线），用户上报问题时带上 Node 和 pi 的版本。

## 后果

- pi 在没测过的 Node 上出问题这一类麻烦没有了；我们不用两套版本都测，也不用每年自己决定换哪个大版本。
- 用不上新版 Node 的改进（比如 `node:sqlite` 更成熟）；二狗自己的代码要能在 pi 那条线上跑（现在没有障碍：二狗在 Node 22 上跑了几个月）。
- **停止维护时**：Node 22 到 2027-04-30 停止维护。按用户的话"pi 不升级我们就继续用"，不自动替 pi 往前走；2027-01 前后提醒用户看一眼 pi 有没有动、要不要例外。
- 用 Bun 编译的 pi 单文件版和这里无关（二狗用的是 pi 的 npm 包）。
