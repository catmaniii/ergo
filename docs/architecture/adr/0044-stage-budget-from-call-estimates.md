# ADR-0044 阶段预算：负责人只估次数，token 预算由运行时按实测算

状态：已定（"每次差那么多，说明你估计有问题"是用户指出的，下面是实现时的取舍）

## 背景

真模型闭环试验里预算控制一次停了 28 次，用户要点 27 次"追加预算继续"，¥4.45 里约 ¥1.00 是空转。查下来是三件事叠在一起：

- 用量把缓存命中也全算进去。上下文 15 万时一次调用就记 15 万，实际只花约 ¥0.01。
- 负责人在计划里写 token 数，但它不知道上下文多大，只能猜。试验里阶段预算写 4 万到 11 万，实际差到 150 倍。
- 超预算停下后连 `complete_stage` 都被拒，通知还一条叫醒一轮。

光改用量算法不够：`pm-1` 440 次调用平均每次缓存命中 12.8 万、没命中 2900、输出 720，按新算法每次约记 1.6 万，写 4 万的阶段 3 次就超了。用量约等于调用次数乘上下文大小，负责人只能判断前者。

## 决定

1. **用量**：没命中缓存的输入 + 输出 + 命中缓存的十分之一（`BUDGET_CACHE_HIT_DIVISOR`，只有一处）。只有预算用这个数，账本、消耗页还是真实的 token 和钱。
2. **负责人只估工具调用次数**（`budget.toolCalls`）。它写了 `tokens`、`tokenEstimate` 也不作数，交来时就清掉。老计划存着的照旧能读。
3. **token 预算由运行时算**：阶段开始时算好记在阶段上（`TaskStage.budget`）：次数 × 校准比例 × 单次计量。追加预算继续、确认加预算的计划变更都重算一份，用量从那时起算。
4. **单次计量**：这个 agent 最近 20 次调用的实测平均，和按最近一次上下文估的（上下文的十分之一 + 3000），取大的。一次都没调用过时假定上下文 2 万。
5. **校准**：阶段验收时记下估的和实际的次数。同一个任务的后续阶段按前面的合计比例放大，限制在 1 到 5 倍，只放大不缩小。负责人写后面的阶段、提计划变更时看得到"估 X 次，实际 Y 次"。
6. **停下**：超预算的这一支只放行 `complete_stage`、`propose_plan_change`（流程是 `report_step`），别的都拒绝并写清楚因为什么、等什么。连着被拒 5 次中止手头这一轮。
7. **通知**：排着的说明进展、这一支停下、接着做，状态变了就作废出队；只有这些时模型不会被拉起。超预算停下、没别的能做时不发通知。

## 不选的

- **按钱算预算**：明确不做。自定义模型没有单价，钱不能当判定依据；卡片上的钱只是附带的粗估。
- **继续让负责人写 token、只给它上下文大小当依据**：它得自己做乘法，每次起草都要重新说明算法，上下文还在涨。次数是它真能判断的，乘法交给运行时。
- **工具调用次数预算不变、只去掉 token 预算**：大上下文的模型调用很贵，只看次数看不出单次涨起来的情况（子 agent、压缩都不算工具调用）。
- **出队时再判过时（改 AgentSession）**：作废放在状态变化的那个事务里（`dropQueued`），AgentSession 不用懂任务的状态。

## 后果

- 进行中的任务不迁移：已经开始的阶段没有 `TaskStage.budget`，还按计划里写的数比，下一次判定就按新的用量算法。用过"追加预算继续"的阶段，老的起算点比新算法的数大，这一段用量先算成 0，是偏松的。
- 估的次数写 0 的阶段没有运行时预算（不判超预算）。
- 单次计量取自整个 agent 的最近调用，项目负责人跨任务时也算在一起。这正是想要的：上下文是 agent 的，不是任务的。
- 拒绝模型工具调用的话写得长，模型能读到全文；界面上的调用记录是截短的摘要。
