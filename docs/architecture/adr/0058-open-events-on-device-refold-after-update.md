# ADR-0058 网页换了一版之后再打开：本机存事件、重新折一遍、只补增量；WebSocket 压缩

状态：已定（"回来刷新时增量刷新、不要把完整的历史发过来"是用户 2026-11-09 提的；本机存事件、换版本时重新折、WebSocket 加 permessage-deflate 是 452 号票推荐的做法，其余是实现时定的）。修订 [ADR-0048](0048-open-snapshot-on-device-batch-catch-up.md) 的"网页版本对不上就不用、从头补"。**修订（2026-11-09，456）：** 冷补发只发最新的——守护进程冷补发、页面本机存的事件都按同一份规则合并掉被后来的事件整份盖掉的旧记录，见下面"修订：冷补发只发最新的"一节。

## 背景

- ADR-0048 的本机快照存的是状态层折出来的结果，按网页版本（构建产物的哈希）认：版本一变整份作废，从头补。用户一天部署好几次（11-01 以来 129 次合并里 48 次改了 `packages/web/src/state`，按状态层代码的哈希认也一样常作废），所以手机放久了切回来、页面自己刷新（450 的场景 E）几乎每次都是冷打开。
- 冷打开时守护进程对会话频道只补最近一页，别的频道从第一条起全部补。用户那台 2026-11-09 只读数过：一打开就订阅的频道里会话以外的约 1.66 万条、21 MB（看板 6836 条 / 15.1 MB、卡片 996 条 / 3.1 MB、待办 985、活动状态 3521、已读位置 3527……），一天还长约 560 条、0.7 MB；秘书会话最近一页只有 73 条、42 KB。450 的复现里（合成数据，约 1.1 万条、10 MB）切回来要 11～13 秒内容才回来。

## 决定

1. **本机除了快照，再存一份事件本身**（`app/open-snapshot.ts`、`app/open-snapshot-idb.ts`；哪些频道存见 `state/open-snapshot.ts` 的 `keepsOpenEvents`）。
   - 和快照同一个 IndexedDB 表：快照在键 `latest`，事件一条一个键 `[频道, 序号]`（数组键排在字符串后面、按频道和序号排好，删一个频道是删一段键）。不升库的版本：开着的旧版本页面照样读写它的 `latest`，不会被升级挡住。
   - **会话频道不存。** 秘书会话、负责人的会话冷打开时本来就只补最近一页（更早的经 HTTP 往上翻），换了一版时这几个频道游标给 0、从守护进程再要一次最近一页（很小），本机不用照"最近一页 + 往上翻"的规矩修剪，也不会和冷打开的那一页对不上。别的频道（卡片、待办、看板、活动状态、设备、项目、工作日历、关注类别、名字、语言、已读位置、插件……）冷打开时是全部补的，原样存下。临时事件不存。
   - **和快照一起写，一个事务。** 连接交给状态层的每一样先给它记一下（`note`）；写快照时把记下的、序号不大于快照游标的那部分事件一起加上，记一个"各频道到哪一条为止是全的"（`through`，和快照的游标相同）。一个频道只认从 1 起一条不缺的那一段（守护进程每个频道的序号从 1 起、连着；用户那台每个频道都是），接不上的不算进去。写不进去不抛错，事件留到下次写（攒得太多就这次打开不再存事件）。
2. **打开时**（读快照最多 1.5 秒，换了一版要读事件另给 5 秒）：
   - **同一版**：照旧用快照马上画出来，订阅带快照的游标。快照的游标和存的事件对不上（比如只存了快照）时这次打开不存事件、把存着的删掉，等下一次冷打开重新存。
   - **换了一版、或者快照格式变了，协议版本没变**：快照不用，读出存着的事件，按订阅的先后（和守护进程冷补发一样）当补发的帧一次交给新版本的状态层重新折一遍（`refoldInput`），等于本机自己做一次"从头补"；再带着事件的游标订阅（会话频道是 0），守护进程只补增量和会话最近一页。读出来某个频道不全（别的标签页从头补时删掉了一段）就不用这个频道，它的游标给 0，第一次写时先删掉它存着的。
   - **协议版本变了**（事件的样子可能变了）、什么都不能用：全删，从头补。
   - 订阅回 `resync` 的频道：清掉它存着的事件，从头补发的从 1 记起。
   - 设备被吊销、回到配对页：快照和事件全删（手机上不留个人数据），之后这个页面上不再存。
3. **本机重折加增量必须和守护进程冷补发折出来的一模一样。** `test/state/open-snapshot.test.ts` 用 54 份录下的真实事件流和照用户量级编的数据，各频道存到 0、1/3、1/2、4/5、全部几处，"本机重折 + 增量"和"冷补发"折出来的快照、游标逐项相等；`test/open-snapshot-page.test.ts` 在真 Chrome 里：换了一版后再打开只补增量，补完存下的快照和一台新设备冷打开存下的一样。
4. **守护进程的 WebSocket 加 permessage-deflate**（`gateway/gateway.ts`）：冷打开、新设备第一次打开仍要全量，经隧道的字节少很多。同一条连接共用压缩上下文（一帧帧事件的 JSON 很像，合成数据压到原来的 4%，内容换成随机汉字也有 32%）；窗口 2^13、memLevel 7，每条连接压缩那头约 100 KB 内存（比默认的约 300 KB 小，压缩比差几个百分点）；短于 128 字的帧（回执、空订阅的响应）不压。ws 的 `threshold` 只在不共用上下文时管用，所以小帧是发的时候按帧挑的（`send(text, { compress })`）。不提这个扩展的客户端照常不压。Chromium 内核的浏览器握手时都会提；鸿蒙 ArkWeb 是 Chromium 内核，按理也会提，没在真机上看过。
5. Debug 工具集"打开时补了多少"那行多一种说法："网页换了一版：用本机存的 N 条事件重算，只补增量"。

## 后果

- 量过（452 号票的实现记录有整张表；合成数据约 1.2 万条、11 MB，CPU 降速 4 倍，页面和 /ws 一起限速）：换了一版之后再打开（包括 450 的场景 E：手机切回前台才知道、整页刷新），补完画好在 4 Mbps / 200 ms 下从 25.4～25.7 秒降到 3.4～3.7 秒，10 Mbps / 100 ms 下从 10.8～11.2 秒降到 2.0～2.4 秒，和同一版热打开（3.3 / 1.8 秒）差不多；只补 599 帧 / 515 KB（以前 11,959 帧 / 11.0 MB），剩下的大头是重新下 1 MB 的页面。新设备第一次打开线上字节 12.1 MB → 1.47 MB，补完 26.2 → 5.4 秒（4 Mbps）。换了一版的那次打开主线程多了读 IndexedDB（约 90 毫秒）和重折（约 250 毫秒，和冷打开那一次折一样），长任务最长 250～390 毫秒。
- 手机上多存了一份个人数据：会话以外那几个频道的全部历史事件（包括被后来的事件覆盖掉的旧版本），比快照大（用户那台约 21 MB，一天长约 0.7 MB）。和快照一样只在这台手机的浏览器存储里，吊销、回到配对页时删；没打开过的被偷的手机上会一直留着，直到被打开。
- 本机存的事件只增不减，重折的时间跟着长（用户那台现在 1.66 万条；一个月后约 3.3 万条）。（456 起不再是这样：本机存的按冷补发同一份规则合并，大小保持在"这时冷补发会发的那些"，见下面的修订。）
- 冷打开（新设备、协议变了、浏览器数据被清）要补的条数没变，只是线上字节少了。新设备第一次打开那次写进 IndexedDB 的一万多条事件是一次写的（一个事务）。
- 状态层的归并照旧要求：同一个频道里的事件按序号归并，不同频道之间的先后不该影响结果（冷补发是一个频道一个频道补的，本机重折加增量的跨频道先后和它不同）。新加跨频道的归并（比如按别的频道里的东西删）时要照 `pluginDataPurged` 那样按时间比，不按到达的先后；`test/state/open-snapshot.test.ts` 的等价测试会红。

## Considered Options

- **按状态层代码的哈希认快照**：状态层改得太勤（11-01 以来 48 / 129 次合并），作废得还是太多。
- **会话频道也存事件、照"最近一页"修剪**：本机要按守护进程的 `firstReplayAfter`、`replayPins` 那一套修剪，修剪出来的那一页和冷打开的对不上就会走样；会话最近一页本来就小（用户那台 42 KB），换版本时再要一次更简单。
- **一条事件一个键 vs 按频道打包成块**：块读写的对象少，但追加要重写最后一块、合并要管；一条一个键追加只是 put，重新同步是删一段键，同一条存两遍是覆盖（几个标签页同时写也不会乱），读的时候查 1..through 一条不缺就行。量下来一万多条读一次是几百毫秒的级别（见票的记录）。
- **守护进程冷补发时按频道合并旧事件**：冷打开也能少一个数量级，但要逐个事件类型对齐前端的归并（返工记录、定时作业的运行记录、项目删除的连带……都不是"留最后一条"），还要和本机存的事件（只认一条不缺）配合。另开票（456 做了，见下面的修订）。
- **WebSocket 不共用上下文、按 ws 的 threshold 压**：压缩比差很多（合成数据 42%～66%，共用上下文 4%～32%）。

## 修订：冷补发只发最新的（2026-11-09，456）

用户看了 452 量的真实库构成之后说"第一只发最新的"。会话以外一打开就订阅的频道里，大半是同一件事被后来的事件整份盖掉的旧记录：用户那台 11-09 只读数过，16,628 条 / 20.7 MB 里，看板的用量合计 6,069 条只对应 36 个归属、任务 573 条只对应 49 个任务、已读位置 3,554 条只要最后一条……

**决定**

1. **合并规则写成一份，守护进程和网页共用**：协议包的 `replay-compaction.ts`。每条事件说它"认领"哪几样（键 + 名次），同一个键只留赢家（名次最大，一样大留先到的）；一条事件赢下任何一样就留，"照留"的不管输赢都留；每个频道的最后一条总在（页面的游标照旧是最后一条的序号）。只去掉事件、不改事件，留下的照原来的先后。规则按事件类型写成一张表（`REPLAY_COMPACTION_RULES`），逐个对齐状态层 `ui-state.ts` 的归并：
   - 后来的整份替换前面的：用量合计（按归属）、活动状态（按 agent）、工单、范围记录、计划（按任务）、提醒、设备、待办、项目、任务（按 id），工作日历、关注类别、名字、语言（全局一份）——留最后一条；
   - 卡片按版本：留版本最大的（一样大留先到的，前端后到的不认）；已读位置按会话留位置最靠后的（前端只往后挪）；
   - 定时作业：每个作业留最后一条，另外每次运行（`run.runId`）留最后说到它的那条（前端 `jobRuns` 按运行攒）；看板上最后一条提醒或定时作业事件总留着（日历的 `changedAt.board` 是它的序号）；
   - 不是"留最后一条"的照真实的归并：返工（`change: rework`）每条都留（前端攒返工记录）；任务、项目的删除照留（连带拿掉计划、返工记录、负责人会话，项目还连带内部任务、工单、范围记录——留着删除那一条，连带的照样发生，不去推连带）；待办、设备删了的整条不留（只有这个频道管它们）；"已删除"标记（前端忽略的）不留；
   - 不合并：快速动作卡（它每一版都改会话里对应的操作记录，"这一版有结果说明就换、没有就留着上一版的"，只留最后一版可能不一样）、移除插件连数据删的记录（跨频道按时间删）、前端不归并的三类（回避信号、提问卡的回答）、会话频道上的、守护进程内部频道上的，以及不在表里的（以后新加的、插件自己的）。
   - 协议包的测试查表是齐的：协议里每个落盘事件类型都要写一条（按什么合并，或者明说不合并），新加一个不写就红。规则一改要把 `REPLAY_COMPACTION_VERSION` 加一（页面按旧规则合并过的事件可能缺了新规则要的，认出来不是这一版就不用、从头补）。
2. **守护进程冷补发用它**（`gateway/gateway.ts` 的订阅）：游标为 0、或者订阅回 `resync` 的会话以外的频道补合并后的；游标大于 0 的增量照旧一条不少；会话频道照旧"最近一页"。存着的事件一条不删、不改（`token_totals` 每次模型调用落一条完整合计的写法也不动）。合并的开销是在原来就要读的那一遍（`store.read`）上多扫一遍：照用户量级编的数据约 5 毫秒（读要约 100 毫秒），不缓存。
3. **页面本机存的事件也用它**（`app/open-snapshot.ts`）：每个频道记着合并到哪儿（`ChannelCompaction`：最后一条、照留的、每一样的赢家，能存成 JSON），和快照一起存；新来的事件接着往里加，被盖掉的那几条在同一次写里删掉（`EventWrite.remove`）。所以本机存的就是"这时冷补发会发的那些"。读的时候一个频道只认"合并后该留的那几条一条不缺"（不再要求从 1 起一条不缺：合并过的本来有洞）；缺了的频道只从头补它（合并过的，很快）；该留的以外还存着的（别的标签页留下的）下次写删掉。记事件时：从头补的频道（游标 0、重新同步）补发里的洞都认（守护进程合并掉的），别的地方出了洞（不该有）这个频道这次打开不再往下记。452 存的整段（格式 1）照样认：读出来先合并、只交合并后的去重折，第一次写删掉被盖掉的、记成格式 2——这一版上线后手机不用为了换格式再冷补一次。
4. **锁住"合并后 = 全量"**（`test/state/open-snapshot.test.ts`）：54 份录下的事件流、照用户量级编的数据、专门编的删除连带 / 返工 / 卡片版本 / 定时作业运行 / 已读位置往回 / 重新同步，"全量冷补发"和"合并后冷补发"折出来的整份状态逐项相等，"本机存到 0、1/4、1/3、1/2、2/3、4/5、全部几处合并后重折 + 增量"折出来的快照、游标也相等；重新同步时手里已经有别的（负责人会话开着）也一样。真 Chrome 的页面测试：新设备冷打开、换了一版再打开存下的快照和守护进程全补时一模一样。

**后果**

- 用户那台（11-09 只读数，只数条数和字节）：冷打开会话以外的频道从 16,628 条 / 20.7 MB 降到 1,317 条 / 3.0 MB（看板 14.8 MB → 0.6 MB）；本机存的事件跟着从约 21 MB 降到约 3 MB，以后只随"有多少件事"长，不随"改了多少次"长。复现（照真实库构成编的 1.7 万条、CPU 降速 4 倍、页面和 /ws 一起限速；整张表在 456 号票的实现记录里）：新设备第一次打开补完画好 4 Mbps / 200 ms 下 6.5 → 4.2 秒（守护进程不压缩时 42.3 → 9.7 秒），10 Mbps / 100 ms 下 4.9 → 2.5 秒，帧 17,227 → 1,505；换了一版再打开 3.7 → 3.4 秒（10 Mbps：2.1 → 1.7 秒），重折的从 1.7 万条变成 1,400 条，主线程最长的长任务 420 → 90 毫秒左右。
- 两边会走样的风险换成了测试：前端以后改一个类型的归并、合并规则没跟着改，等价测试会红（录下的事件流、编的专门用例）；新加落盘事件类型不写规则，规则表的测试会红。规则拿不准的一律不合并。
- 跨频道的先后照旧要求不依赖到达的先后（上面"后果"最后一条）。实现时发现一处现成的（452 起就有、和合并无关）：快速动作卡更新会话里的操作记录（`withOperationsOf`）只在记录已经在手里时才改，本机重折时卡片频道先折、会话后补，没做成的快速动作（卡上"没做成：…"、记录里是原话）重折出来的操作记录说明和冷打开的不一样；守护进程给的卡片结果说明一般和记录的一样，所以只在没做成时看得出来。456 一起修了：时间线上加操作记录时手里已经有它的快速动作卡，就照卡片现在的版本换一遍（`withRecord`，和卡片后到时 `withOperationsOf` 换的一样），哪个频道先到都一样；`test/state/open-snapshot.test.ts` 加了一份没做成的快速动作的数据锁住"重折 = 冷打开"。
- 合并后的冷补发中间有洞：页面以外直接订阅 `/ws` 的程序（测试的模拟前端）从 0 订阅时收到的也是合并后的。
