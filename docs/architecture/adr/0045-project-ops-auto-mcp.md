# ADR-0045 项目转入使用时自动转成 MCP：真的 stdio 进程，登记算出来不写文件

状态：已定（"项目开发完成自动转运营、转 MCP 接入二狗使用"是需求，下面是实现时的取舍）

## 背景

项目对外的接口写在运营接口清单 `ops.json` 里，格式就是 MCP 的 `tools/list` 加几样，转入使用时验收、登记，带版本号（ADR-0028）。但只有秘书用得上：`project_ops` 一个工具列出、看说明、调用。别的项目、任务的负责人要用，得手写一个 stdio 程序转发，再用 `request_mcp_change` 登记（出卡）、`request_toolkit_change` 进工具包。喜欢手搓工具的人，这段转发每个项目都要写一遍。

## 决定

1. **真的 MCP，不是内部假装。** 二狗带一个 stdio 程序（`project-ops/mcp-bridge-main.ts`），说 `initialize`、`ping`、`tools/list`、`tools/call`，工具清单和调用都经本机端口问守护进程，到 `project_ops` 同一段执行逻辑（`prepareArgs`、`runOp`、记录）。它和用户写的 MCP 一样由 `mcp/client.ts` 经闸门拉起、进 Job 对象、过守卫，Claude Code 负责人也经原来那条路拿到。
2. **登记是算出来的，不写进 `config/mcp.json`。** `createMcpService` 的 `computed` 每次现读时取"使用中、有已登记清单的项目"，和用户写的合起来。不会残留、不用同步，用户的文件一个字节都不动。项目不在使用中了就算不出来，MCP 跟着没有；工具包里残留的名字按现有的"找不到"处理。
3. **名字从项目编号生成，定了不变：** `project-<项目编号>`（`project-p-3`，`projectOpsMcpName`），符合 `MCP_NAME_PATTERN`。撞名时用户写的优先，自动的跳过并记一行日志。`request_mcp_change` 不能改、删自动的那条，也不能用 `project-p-` 开头的名字新加（用户自己写进 `mcp.json` 的不拦）。
4. **凭证照服务事件那一套（ADR-0043）：** `POST /api/project-ops-mcp` 只在本机端口开，外网端口 403，Bearer。一个项目一份，**只在内存里**：转发程序是守护进程的子进程，守护进程停了它们也没了，不用存。经登记的 `env`（`fromEnv`）注入，值放在 `computed` 给的那份环境里，不进守护进程自己的环境，`buildChildEnv` 也就不会把它给 agent。`redactorOf` 按注入的凭据擦工具结果、说明和日志；记 `project_op_called` 和时间线之前再擦一遍。项目不在使用中了凭证作废。
5. **守卫映射：** `kind: query` → `readOnlyOrIdempotent: true`；`network: false`（调的是本机）；`title`、`description`、`inputSchema` 从清单取。`risk` 仍然只记不做：写进工具说明给模型看，不接守卫。
6. **只转项目自己的操作。** 白送的通用操作（`builtin.ts`）不转，秘书的 `project_ops` 还有。名字不合 MCP 工具名规矩的操作（带点这类，清单的名字比 MCP 工具名宽）转不了，只有秘书能用，自检时写明；不改名，改了 `tools/call` 对不上。
7. **秘书不变。** 还是 `project_ops` 一个工具；`mcp_call` 调到自动转的 MCP 时指回 `project_ops`，免得一件事两条路、记两份。
8. **项目自己的负责人工具包里自动有它：** 算出来（`segmentToolkit` 加上 `ownMcp`），不写进项目的工具包。这样早就在使用中的项目升级后马上有，不用补事件，用户也去不掉。起草计划的那一段不带（那段本来就没有 MCP）。别的项目、任务走现有的 `request_toolkit_change`、计划的工具包，规矩不变。
9. **调用者写明。** 守护进程调的时候把 `agentId`、`toolCallId`、`inputMessageId` 放进 `tools/call` 的 `_meta["ergo/caller"]`（模型碰不到；只给自动转的 MCP，别的 MCP 是外面的程序，用不着知道）。转发程序只转工具名、参数和这一项，**别的 `_meta` 不转**，验收用的 `ergo/test` 走不到这条路。`project_op_called` 记 `by: "agent"`、`agentId`、称呼；时间线记在调用者自己的会话上。
10. **改了清单跟着变，不用重启。** 登记的内容变了，`mcp.ts` 的连接按登记的 JSON 比对，下次用到时换新的转发程序。登记了新版时让项目自己的负责人、工具包里配了它的负责人按新的工具重新装配（闲着的等下次唤起，不叫醒）。**调用只认登记着的那一版**，档案里新改的要 `check_ops` 过了才算，不像秘书那样用到时顺手验。
11. **自检不挡转入使用。** 登记了一版之后在后台真的拉一次转发程序做 `tools/list`，结果写进负责人时间线，失败只写原因。自检完收掉进程，第一次调用时再拉起：使用中的项目可能很多，别每个白占一个 Node 进程。

## Considered Options

- **进程内假装成 MCP（直接把操作做成宿主工具）：** 少一个进程，但 README 不能写"标准 MCP"，给会话另开一条路，守卫、Claude Code 的接法都要再走一遍；以后给外部客户端用也还要写这个程序。不要。
- **转入使用时写进 `mcp.json`：** 要同步（改清单、归档、删除都要写），写失败、用户手改就对不上；用户的文件被程序动。算出来的没有这些问题。
- **项目自己的 MCP 写进项目的工具包：** 工具包事件多一条、要补历史项目、用户能在页面上去掉，都不是想要的。
- **凭证放密钥区文件（照服务事件）：** 服务由服务管家拉起、会活过守护进程重启，所以要落文件；转发程序不会，内存里就够，少一个要清的文件。
- **一个守护进程一份凭证：** 一个项目的转发程序就能调别的项目的操作。一个项目一份。
- **MCP 调用也走"秘书用到时"那套自动验收：** 调一次工具可能等一轮验收（包括真跑测试），也不是调用方该等的。改了就 `check_ops`。
- **把风险标记接到守卫：** 不做，和 `project_ops` 一样只记不做。

## Consequences

- 登记的 `tools` 不经 `mcp.json` 的 schema 校验（说明长度这类上限不适用），工具名按同样的规矩筛。
- 转发程序只是转话，守护进程停着时它也没了；中途连不上时 `tools/list` 回 JSON-RPC 的错，`tools/call` 回 `isError` 的结果，不崩。
- 跟负责人说一句（`ergo` 绑 `tell_maintainer`）经 MCP 调时不走秘书转达那条路：那条路是"用户的话"，别的 agent 说的不能算。放一条写明来路的通知。
- 触发一次运行（`run_now`）在运行记录里仍写"秘书"触发的（触发底座只有这一种说法）；是谁调的看 `project_op_called`。
- `mcp.json` 写坏时用户写的一个也不用，自动转的照样在。
- 项目删掉之后，别的 agent 会话时间线上那条"调了项目 X 的操作"不会被改写，和秘书会话里那条一样；operations 频道上的事件照旧随项目删除。

## 以后

这个 stdio 程序不依赖二狗的代码，以后可以直接配给外部客户端（用户自己的 Claude Code、Cursor）。这一期只接二狗内部：外部客户端要的配置和认证（凭证现在只在内存里）另做。
