# 语音回复由运行时跟着回合决定和合成：agent 写口语总结，没写先追问一次，再兜底截

用户发语音时 agent 用语音回复，是否用语音、什么算"长"由运行时判定和兜底，不只靠提示词；回复长的由 agent 写一段口语总结来合成，详细内容照常发文字。要定的是：这件事挂在哪里、agent 和运行时各做什么、兜底怎么做、界面上文字和语音的关系。第一版评审后用户（2026-10-08）又定了两条：语音这一轮不流式显示、短回复合成好只出语音；没写总结时先追问 agent 一次，再兜底。

## 决定

- **运行时跟着回合做**（`voice/voice-reply.ts`）：跟着会话频道上的回合事件（`turn_start`、agent 的消息、`turn_end`）走。这一轮开始时输入是用户的语音（有参考音色），就建出 agent 语音对象（`replying`）；一轮完成时看这一轮处理的用户消息里最后一条是不是语音，是就把这一轮 agent 发出的文字定成口语稿、排队经 audio.cpp 合成。
- **agent 写口语总结**：回复长、或有代码表格链接这类念不出来的内容时，用 `spoken_summary` 工具写一段口语总结。写不写都不影响"用不用语音"——那由运行时按用户的输入定；什么算长也由运行时按字数估。
- **没写先追问一次，还是没写才兜底截**：回复长、agent 这一轮没写总结时，运行时追问它一次（"给刚才的回复写一段适合听的口语总结，用 spoken_summary"）。这一次不算新回复：没有 `turn_start` / `turn_end`，它说的话不进会话、不流式推送，工具照常经守卫（调用记录照常进会话），用量照常记账。追问后还是没写，运行时取回复开头念得完的几句，加一句"详细内容我发在聊天里了"。守护进程里没有不经 pi 的模型调用（ADR-0011 的后果之一），兜底也不破这个例。
- **追问是 `AgentSession` 的一个通用钩子，口语总结工具走装配**：会话在追加 `turn_end` 之后同一刻问 `voiceReplies.followUp(会话, 输入)`，有追问就在处理下一条输入之前交给子进程（宿主协议不变，就是一条 `user_input`）。口语总结工具不由会话类塞进去，而是和别的代为执行的工具一样由各处的装配放进去（秘书、任务负责人起草和执行、项目负责人各段；执行时在 `executionSetup` 一处），所以 `MaintainerAssembly.hostTools`、守卫的工具包、固定上下文里的工具清单都是真实的那一份。
- **agent 的语音是自己的对象和事件**（`AgentVoiceRecord`、`agent_voice`、消息里的 `tts_audio` part），不和用户语音的 `VoiceRecord` 合成一个联合类型：两者的生命周期（识别 / 回复、追问、合成）、字段、素材和删除的规矩都不一样，混在一起要改遍已有的每个读者。概念上它们都是"语音消息"（CONTEXT.md），界面上用同一个气泡；共用的只是版本、一次一条的队列、开着只留一条的说明这几件小工具（`voice/shared.ts`）和前端的按版本归并。
- **界面上**：语音这一轮不流式显示回复，只有"正在回复…"（agent 语音对象记着这一轮开始的序号，那之后 agent 的消息先不显示文字）；回合结束后，短回复（整段合成）合成中显示"正在合成语音…"，合成好只出语音气泡，文字收进语音里（长按"转文字"展开）；长回复（口语总结）的文字和附件照常显示，合成好再加气泡；没合成出来的照常显示文字，带一条说明。事件日志、agent 的会话里文字原样都在。往上翻、重连补发同一套规则。
- **失败一律退回只发文字**：合成之后不论哪一步出错（服务没开、忙、出错、超时、回的不是 WAV、存不进媒体库、参考音色被删了）都走同一个失败处理。服务忙（503）不等超时，说明里写"语音服务忙"。
- **合成可以重做**：只是一次 HTTP 调用，守护进程在合成途中停了，重启后还在"合成中"的重做一遍，不进"中断不确定"；在追问的直接兜底；还在回复的记成没用语音（那条输入由会话标成中断）。

## Considered Options

- **全靠提示词**（系统提示里写"用户发语音时回复要短、像说话"，把 agent 的整段回复都合成）：明确不要；而且长回复、带代码的回复念出来没法听。
- **没写总结时直接兜底截，不追问**（第一版的做法）：省一次模型调用和等待，但兜底的总结只是回复的开头，概括得不好。定下先追问一次。
- **追问作为一条运行时通知、再起一轮**：总结一定是 agent 写的，但那条通知和 agent 的回答会出现在聊天里，还占一个回合。所以追问不算回合、它说的不进会话。
- **守护进程直接调模型概括**：ADR-0011 去掉大模型修正时说过的麻烦（出错时正文可能带出 key、短句里模型容易去"回答"原文）这里一样有，而且会是守护进程里唯一一处不经 pi 的模型调用。
- **在 `AgentSession` 里收回复、在回合结束时直接合成**：知道得最准，但要往秘书、负责人共用的会话类里加一块和它的职责无关的逻辑。会话类只加两个钩子（输入后面的说明、回合后的追问），判定和合成都跟着事件走。
- **口语总结工具由会话类统一追加**（第一版的做法）：一处就够，但装配记下的工具清单和实际给子进程的不一样，子 agent 收窄、固定上下文的工具清单都会看错。
- **语音这一轮照常流式显示、整段合成时文字也照常显示**：最省事，但"转文字"就成了重复，和用户"agent 的语音不默认展开文字"、"短回复合成好只出语音"的要求不符。

## Consequences

- 判定看的是"这一轮处理的用户消息里最后一条"：运行时的通知引起的一轮（任务执行中的阶段通知、审批结果）不用语音，哪怕用户上一句是语音；里重新识别成功后交给 agent 的通知例外，它就是用户的语音（导出 `isVoiceRetryNotice`）。这一轮开始时只看交给 agent 的那条输入（插话要到回合结束才知道），所以插话改变了结论时：开始是语音、最后一句是文字的，前端在回合结束后补显示文字；开始不是语音、插话是语音的，这一轮照常流式显示，回合结束后照样合成。
- 一轮只回一条语音（幂等键 `agent-voice:<输入的消息 id>`），合成一次一条（显卡可能和别的程序共用）。合成在 agent 处理下一条输入时照常进行，语音消息可能排在下一轮的回复后面。追问在下一条输入之前，所以用户紧接着说的话要等追问完才交给 agent。
- 短回复要等合成完才能听到也看到：服务冷启动时可能等几十秒（合成中有提示，失败了文字回来）。
- 前端的时间线（完整视图）按 agent 语音对象收起文字：`timelineItems` 依赖 `UiState.agentVoices`，往上翻时这一页的语音对象跟着历史分页一起取回。

## 2026-10-11 补充

让 agent 在用户打字的那一轮也能用"发语音"工具（`send_voice`）发语音气泡。合成那一半和语音回复共用（`voice/voice-synthesis.ts`），上面的决定照旧适用于语音回复；工具发的语音在两处是例外：

- **"一轮只回一条语音"只管语音回复**：语音回复的幂等键还是 `agent-voice:<输入的消息 id>`，一轮最多一条；工具发的一次调用一条（幂等键 `agent-voice:tool:<工具调用 id>`），同一轮可以发几条，各是一个气泡。工具只在用户打字的那一轮能用——用户最后说的一句是语音（语音轮，有参考音色）时它直接交回"已经在合成了"，不多出一条，所以同一轮里不会同时有语音回复和工具发的语音。这一轮另写的文字收不收进气泡照这里的整段合成的判定，回合结束时定（`coversReply`），记在这一轮最后一条工具发的语音上。工具发的没合成出来时，会话里的说明只说这一条没发出去和原因，不说"这次只发文字"（同一轮后面可能还有发出去的）。
- **"语音消息可能排在下一轮的回复后面"对工具发的语音一般不成立**：工具等合成有了结局才把结果交回 agent，所以语音消息在这一轮里、在 agent 接下来写的话之前就出来了。例外是等太久：合成一次一条，前面还排着别的语音时，工具最多等 `SEND_VOICE_WAIT_MS`（5 分钟）就先交回"还在合成，合成好会自己出现"，这一轮照常往下走，这条语音就和语音回复一样，可能出现在这一轮结束之后、甚至下一轮的回复后面；回合结束时它还在合成的，照样按判定记下收不收这一轮的文字。前端"收着"这一轮文字只到下一轮开始为止。
- 合成可以重做照旧：守护进程被杀，工具发的语音重启后重做，不进"中断不确定"；agent 的会话里那次调用补的结果是"这条语音会自己补发出来，不要重发"。

## 2026-11-01 补充

任务、项目的负责人配了自己的角色和音色之后，它的进展用它自己的声音汇报，由秘书的聊天窗转发：秘书先开场，再接负责人的声音，两段合成一条。不增加打扰，只是换声音——开了自动播报的任务做完、开关开着的任务或项目的进展来信、用户打字或说话问进展这三种情况才这样发，开关关着又没人问的照旧是文字。项目照任务加了自动播报开关，默认关。

- **一条语音对象支持几个声音（`AgentVoiceRecord.parts`）**：每段有文字、参考音色、说话的人。`text` 还是连起来的那一份、`referenceVoice` 是第一段的，老的读者不用改；老记录和只有一段的没有 `parts`。没有另外发两条气泡：用户听到的是一条，转文字时分两段标名字。
- **声音由运行时定，模型只能说转述谁**：`send_voice` 的 `relay` 只有 `source`（通知里写的任务、项目编号）和 `text`（负责人那段的稿子），没有音色、agent 的参数。`source` 只认通知上记的（`MessageEnvelope.relaySources`，连同信上的发信人）：通知引起的一轮只认这条通知的；用户问的一轮认交给过秘书的通知。这一份单独存，不从通知的文字里认——信的原话也在文字里，写什么都不该影响声音。
- **没有信的任务不转述**：负责人那段"只转述信里有的"。用户问的任务、项目还没给秘书来过信或做完的通知时，工具交回"没有可转述的"，秘书用自己的声音说看板上的情况。
- **语音轮还是一条语音回复**：用户发语音问进展时不另建一条：秘书调 `send_voice`，运行时把两段记到这一轮上，回合结束时语音回复念它们（`mode: summary`，回复的文字照常显示）。
- **退回一条秘书的语音**：发信人没配音色、和秘书的一样、音色被删了（调用时查，合成前再查一次，排队时才被删的也算）都不分两段，文字连起来用秘书的声音念，不算失败。
- **中途失败**：第一段出了、第二段没出，照之前的算"只合成了一部分"，会话里的说明写清谁的话没念到和那段话，文字不丢；一段都没出来照旧是失败。重启重做照旧从第一段来，只发一条。

**Considered**：让模型直接写音色或 agent id（越过"声音由运行时定"，模型能冒用别人的声音）；发两条语音消息（气泡分开、自动播放要排队，和用户要的"合成一条"不符）；在通知的文字里认编号（信的原话能混进去）；用户问的那一轮不看有没有信（负责人那段没有依据，秘书只能编）。
