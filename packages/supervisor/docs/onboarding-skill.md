# 纳管 skill

这份文档是「把一个项目的服务纳管进来」的流程，人照着做、或者交给 coding agent 做都行。
这里不带现成的 skill 文件；想做成 agent 的 skill（比如 Claude Code 的 skill），按下面的流程写一份即可。

**装在哪**：全局（比如 `~/.claude/skills/`），不放在管理器的代码目录里——你需要在**别的项目**的会话里调用它。

**它做什么**（纳管是一次搬迁，不是一次登记——一个服务只能有一个管理者）：写注册表 + 摘除项目原有的自启入口 +
当场验证钩子闭环。三件事缺一件，纳管就是无效的。

**不走这个 skill 的一种情况**：接入的项目经接入协议替自己登记的「名下的服务」（link-protocol.md §7）。
那是新起的服务，没有要摘除的旧自启入口；起不起得来由「登记 → 启动 → 探活转绿」当场见分晓，起不来的原因推回给登记方；
没给停机命令的就是没有停机能力，停 / 重启要显式 force（管理器不替它伪造停机能力）。

## 流程

**1. 摸清现状**（skill 自己查，不问用户）
   - 项目里现有的启动/停止/重启脚本、README 里的启动说明
   - 服务监听的端口、是否有 `/health`
   - 项目现有的自启入口：`Get-ScheduledTask` 里指向本项目的任务、开机脚本、注册表 Run 项
   - 日志文件位置、需要的环境变量与密钥来源

**2. 确认钩子**（问用户，因为这是领域知识）
   - 有没有优雅停机的带内通道？停机前需要等什么？（比如要等 TTS 空闲，否则损坏 CUDA 上下文）
   - 启动有什么不能省的参数？（比如 uv 项目必须 `--no-sync`，否则手装的 torch 被当多余依赖删掉）
   - **如果项目没有 stop 钩子（很多项目都没有），这一步就要把它写出来**——
     这是纳管里最常见的实际工作量。

**3. 写注册表**：数据目录里的 `registry/services/<id>.yaml`（`lsm paths` 看数据目录在哪），按 `service-schema.md`。密钥只写来源，不写值。

**4. 当场验证闭环**（强制，不可跳过）
   ```
   stop → 等端口消失 → start → 等 probe 转绿 → 校验三元一致 → stop → start
   ```
   最后多一次 start 是为了把服务还原成你调用 skill 之前的状态。
   **验证前必须明确提示**：「这一步会重启该服务，确认吗」——纳管时它可能正在被你使用。
   验证通过才写 `onboarding.verifiedAt` 与 `verifiedHooks`；不通过就不落盘，先修钩子。

   之所以强制，是因为 stop 钩子是最少被使用、最容易写错、也最不可能被顺手发现的那个——
   不当场验证，你会在半夜服务挂了、点重启、发现钩子根本跑不通的时候才知道。

**5. 摘除旧入口**
   - `Unregister-ScheduledTask` 掉项目原有的自启任务，把任务名记进 `onboarding.removedScheduledTasks`
   - 改项目 README / CLAUDE.md：启动方式改为「由本地服务管理器托管」，避免半年后的你（或 agent）
     照着旧文档又建一个计划任务
   - 最危险的状态不是「没纳管」，而是「纳管了但旧任务还在跑」——两个 server 抢同一个端口，
     而 WebUI 上那盏绿灯不知道指的是哪一个

## 漂移检查（管理器的职责，不是 skill 的）

skill 只在你调用时才跑，兜不住漂移（服务清单集中在管理器这边的固有代价）。管理器在**每次启动失败时**自动比对并提示：
「这个 start 钩子上次成功是 3 周前，项目在那之后改过 `package.json` / 钩子脚本本身」。
比对依据是 `onboarding.verifiedAt` 与钩子脚本、依赖清单文件的 mtime。
