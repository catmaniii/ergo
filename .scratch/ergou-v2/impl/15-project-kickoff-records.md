## What to build

做完后，用户能把一件长期的事立成项目。立项有三个入口：在消息里明说或点"新建项目"；秘书给出"建议立项"卡（名字、一句话目标），用户点"立项"；把一个任务转为项目。点"立项"后项目立刻诞生（筹备中），维护者随之产生。用户进入"和维护者交流"，维护者和用户做立项问答，把规格、术语表、ADR 写进项目档案，最后交出立项书（范围、目标、首版要做到什么程度、项目类型是开发类还是其他、是否把工作目录绑定到一个外部路径）和它提议的工具包，作为立项书卡放进待我处理。开发类项目提议的工具包默认带 bash。立项书卡有两个按钮："确认并开工"（项目转建设中，同时发起首个建设任务）和"只确认，稍后开工"（留在筹备中，标"立项书已确认"）；不管点哪个，立项书里的项目类型和外部工作目录绑定在确认时即生效。任务转为项目时不新建维护者，原任务的维护者接着做立项问答，原任务以"已完成 · 已转为项目"结束。

项目档案是数据目录项目区里的一套最小文档：立项书、规格、术语表、ADR、进展、项目清单、范围记录，再加维护者会话；随数据目录备份，永不进外部仓库。工作目录默认在项目档案里面，立项书写明绑定外部路径的，确认后工作目录改到这个外部路径。项目状态机完整可用：首个建设任务完成后，项目自动从建设中进入使用中，不出卡、不等用户判定（不再区分"运营中"和"已完成"）；使用中 ⇄ 已停用，由用户停用、重新启用，已停用项目的维护者照常对话、接工单；放弃、归档、取消归档；删除只能从已归档发起并二次确认，删除时删掉项目档案和维护者会话，但用户在里面说过的话作为素材保留。除了首个建设任务完成这一次自动迁移，项目状态不随任务变，也不随服务在不在线变。

Web UI 上有项目列表（状态、进行中任务数）和简版项目页（状态、"和维护者交流"）。演示：faux provider 剧本走一遍"建议立项 → 立项 → 立项问答（开发类、绑定外部路径）→ 立项书卡'确认并开工'"，造出首个建设任务完成，项目自动转使用中，再停用、重新启用；再把另一个项目放弃到已归档、取消归档、再归档后删除。

## Acceptance criteria

- [x] 主切面：秘书调用"建议立项"工具只产生一张卡（名字、一句话目标）；用户点"立项"后项目以"筹备中"出现在项目列表频道，同时产生它的维护者；用户点"新建项目"时不经"是不是项目"的判断，直接由秘书收口出卡。
- [x] 主切面：用户在维护者会话里说话时唤起休眠的维护者；维护者能把规格、术语表、ADR 写进本项目的项目档案，写到项目档案和工作目录之外被守卫拒绝；它提交立项书（范围、目标、首版程度、项目类型、是否绑定外部工作目录及其路径）和提议的工具包后，待我处理出现由结构化数据生成的立项书卡；项目类型为开发类时，提议的工具包默认含 bash。
- [x] 主切面："确认并开工"后项目转建设中，并建出属于本项目的首个建设任务（规划中，出现在任务看板上），提议的工具包成为项目的工具包；"只确认，稍后开工"后项目留在筹备中，并标"立项书已确认"。两种确认都让立项书里的项目类型和外部工作目录绑定立即生效。
- [x] 主切面：新项目在数据目录的项目区建好最小文档集（立项书、规格、术语表、ADR、进展、项目清单、范围记录）和维护者会话；工作目录默认在项目档案里；立项书确认绑定外部路径后，维护者的文件工具围栏改为覆盖这个外部路径，备份不包含它。
- [x] 主切面：项目状态按第 11 节迁移，非法迁移被拒——筹备中 →（确认并开工）建设中；首个建设任务完成时自动由建设中 → 使用中，不出卡、不等用户判定；使用中 ⇄ 已停用（由用户停用、重新启用）；筹备中、建设中可放弃 → 已归档；使用中、已停用 →（只能用户手动）已归档；取消归档回到归档前的状态；删除只能从已归档发起，并要二次确认。除首个建设任务完成外，任务状态变化（包括之后其他任务的完成）不改变项目状态。
- [x] 主切面：已停用项目的维护者会话照常可以对话；已归档项目的维护者会话只读，用户在里面发话被拒并说明原因；删除项目后它的项目档案和维护者会话被删掉，但用户在该维护者会话里说过的话在素材库（含原文副本）里仍在。
- [x] 主切面：用户把任务转为项目后，项目诞生（筹备中），不新建维护者，原任务的维护者在同一会话里接着做立项问答；原任务以"已完成 · 已转为项目"结束，出现在看板的最近结束分组里。
- [x] 主切面：产生对应的素材事件——"建议立项"卡被关闭（回避信号）；立项书卡上的确认（用户对产出的反应）；用户在维护者会话里的发言。由 08 号票采集；若 08 尚未完成，至少事件类型和负载就绪。
- [x] Web UI：项目列表显示每个项目的状态和进行中任务数，有"新建项目"入口；简版项目页显示状态、项目类型和"和维护者交流"（进入共用的会话组件，已归档时只读），按当前状态给出放弃、停用、重新启用、归档、取消归档、删除这些入口；待我处理里能处理"建议立项"卡、立项书卡（显示项目类型和外部工作目录绑定）和删除的二次确认。前端状态层回放主切面录下的立项和状态迁移事件流，项目列表和项目页显示正确。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 2026-10-07 补充（05 号票评审后定）：项目档案里的文件被整体重写或删除前，运行时自动留一份旧版本（放在项目档案自己的历史区，随数据目录备份）；守卫判定时对项目档案的覆盖传 `backedUp: true` 环境事实，"删除或覆盖前须已备份或已提交"模板因此总是满足。本票实现这份自动留旧版本。

- 首个建设任务失败或取消时，项目留在建设中；用户可以再发起一个建设任务，或者放弃归档。首个建设任务完成时自动进入使用中，是"项目状态不随任务变"的唯一例外。

- **不在本票**：
  - 首个建设任务本票只建出来；由项目维护者起草计划和执行（单项目任务走工单）归 16。"首个建设任务完成 → 使用中"的触发在本票的测试里可以直接造出完成事件；本票给首个建设任务打上标记，只有它的完成会推动项目状态。
  - 停用时暂停本项目的定时作业、重新启用时恢复，以及项目页上列出本项目的定时作业及各自状态，归 19。项目自己的服务（项目页显示在不在线、停用时撤出 LSM、收回公网入口）是第二阶段。
  - 维护者会话分段（工单段、用户直接对话的"对话段"）、唤起时的固定上下文、每段结束检查进展文档写回和"上一段摘要"、重置维护者（入口在项目页）、发给已归档项目的工单直接退回、项目页的工单流水线归 16；本票的立项问答在 16 完成后就是一个对话段，本票先按一条会话实现。项目页的范围记录归 18；工具包的查看和修改归 27；项目列表上的活动状态小圆点归 25。秘书读项目档案的只读工具归 22。
- 第 11 节：项目状态不再区分"运营中"和"已完成"，首版做完一律进入使用中，没有运营判定卡，也没有"转运营"；项目有没有服务、定时作业不影响项目状态，只在项目页上显示。完整的项目规范模板是第二阶段，本票只建最小文档。
- 项目类型和外部工作目录由维护者在立项问答里问清、写进立项书，用户确认立项书即生效，不另设页面表单。开发类项目默认带 bash（第 9 节）在本票体现为提议的工具包默认含 bash；工具包的装配（noSkills + additionalSkillPaths）和项目页上的查看、修改归 27。
- 秘书收口时"提议记忆范围"（`CONTEXT.md` 的立项条目）第一阶段只占位。
- 立项问答是"grill-with-docs 式"的问答，靠维护者的系统提示；faux provider 下只测运行时一侧。
- 删除时保留用户原话依赖 08 号票的原文副本；08 未完成时至少断言删除项目不触碰事件日志里的用户发言事件。
- 对应用户故事：5、86–95。

## Comments

- 2026-10-08（实现，15 号票的 agent；评审后修改过一轮）：规格没写清、又必须定的地方，按最保守、最贴近规格的做法定了：
  - **删除项目**（ADR-0010，`projects/deletion.ts`）：二次确认是待我处理里的一条 `project_delete` 通知（"确认删除" / "不删了"），不是项目页上的弹窗。确认之后按"先停维护者 → 复查 → 同一事务追加 deleted 并改写事件 → 最后删项目档案和会话文件"的顺序做；停维护者期间用户取消了归档就整个中止、什么都不删，维护者恢复成能唤起。维护者会话频道上的事件和彻底删除一样改写成"已删除"标记（同一个机制，不删行；规格第 15 节已把它列为事件日志可改写的第二个例外）；立项书正文（`charters` 频道的事件和立项书卡）、该维护者的审批（请求、审批卡、决定）和效果日志、待我处理里属于项目的事项，用 21 号票的改写函数表按事件类型字段级改写，原话换成删除标记、状态不变（为此新登记了立项书、审批请求、待我处理事项的改写函数，审批卡的 `purge` 也把参数摘要换掉）。用户的话按原文副本留在素材库里（主切面有断言）。外部工作目录、项目列表频道上的项目事件（名字、一句话目标）不动。
  - **立项书**：只有筹备中、立项书还没确认的项目能交；确认之后不能再交——项目类型、外部路径绑定以后要改，归后续的票。同一个项目再交一版时上一张没处理的立项书卡过期。项目类型、工作目录绑定和工具包在两种确认时都立即生效。
  - **外部工作目录**：只有开发类能绑定；要写绝对路径；按真实路径（展开符号链接、目录联接和 8.3 短名）核对，两个方向都拒——它在数据目录或程序目录里，或者数据目录、程序目录在它里面。不要求已经存在（维护者按新装配拉起时建出来）。没有用目录联接：绑定关系写在项目档案的 `binding.json` 和 `charter.md` 里（11 号票恢复时据此认回）。
  - **首个建设任务完成**：任务以"已完成"结束、且不是"已转为项目"时，项目由建设中自动进入使用中（守护进程重启时补做）。本票的测试直接追加完成事件；13 号票的真实完成接上后照样生效。首个建设任务失败或取消时项目页给出"开工"，再发起一个建设任务接替它。首个建设任务的说明不写立项书正文（只说见项目档案里的立项书）。
  - **项目档案自动留旧版本**：接在守卫运行时的 `autoVersioning`（放行之前同步执行，复制失败就不执行这次调用）。只覆盖项目档案，不含工作目录（默认的 `workdir/` 也不含，靠 git 提交或备份，照 v1 模板）和历史区自己；`.history/` 只由运行时写，守卫把它当受保护区域（任何 agent 用任何方式写入或删除都是永不，删除包含它的整个项目档案也是），也不对它传"已备份"。历史区没有大小上限、也还不轮换清理。
  - **项目名**：没删掉的项目（含已归档）里不能重名，名字最长 40 字、目标 300 字。任务转为项目时项目名由用户定（界面预填任务标题，可以改），重名时明确提示换名。
  - **任务涉及的项目**：任务上新加了项目编号 `projectIds`（点"发起任务"时、计划提交时按当时的项目列表认），项目列表按编号数进行中的任务，不按名字。
  - **任务转为项目**：只有由自己的维护者执行的任务（不是某个项目的任务，共享协议包的 `hasOwnMaintainer`）能转，未结束的任何状态都能转；一句话目标取任务书里的目标，没有任务书时取任务的一句话说明。
  - **"新建项目"**：守护进程不建项目，只给秘书一条通知，写明不判断是不是项目、直接用"建议立项"工具出卡；faux 下只测运行时一侧。
  - **维护者的装配**：pi 工具 `read`、`write`、`edit`、`ls`，立项书确认且工具包带 bash 时加 `bash`；联网按工具包；skill、MCP 的装配留给 27 号票。立项问答按一条会话实现（16 号票再分段）。
  - **运行时**：`continueSession` 改成接着会话目录里最近的会话、不再按工作目录筛（pi 自带的 `continueRecent` 指定会话目录时按工作目录筛，任务转为项目、绑定外部路径后维护者的工作目录会变，接不上原来的会话）。加了契约测试。16 号票做会话分段和重置维护者时要明确指定接哪一个会话（docs/dev.md 里写了）。
  - **Web**：项目页上的定时作业（19）、工单流水线（16）、工具包修改（27）、范围记录（18）、重置维护者（16）只对原型的假项目显示；真项目的工具包只显示文字。项目列表的活动状态小圆点：活动状态频道有就显示（25 号票再细化）。维护者会话在打开时才订阅（`watchChannels`）。原型的假连接也照守护进程的规矩处理项目（状态迁移按共享协议包的 `projectActionTarget`）。
