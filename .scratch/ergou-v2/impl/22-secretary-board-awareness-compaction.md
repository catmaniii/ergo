## What to build

秘书的长期主线会话始终知道看板的现状：看板自上次以来有变化时，运行时在用户下一条消息之后追加一条"看板变化"上下文消息，系统提示不动；秘书还有一个只读的"查看板"工具，说进展时以看板为准，不靠回忆。用户问某个项目进展如何时，秘书用只读工具直接读这个项目的项目档案，不唤醒它的维护者。主线靠自动压缩控制长度，压缩时用秘书专用的压缩指令：丢掉任务的执行细节和已解决的问答，涉及的任务只留 ID 和一句话；保留进行中的话题、未回答的问题，以及刚说的、还没处理的指示。

用户在对话里说"暂停 / 继续 / 取消任务 X"时，秘书提议一个任务控制快速动作，按 21 号票的快速动作流程执行：用户这条消息里点明了是哪个任务的，直接执行，聊天里留"已执行"卡；秘书推断出来的任务控制动作一律先问。任务控制动作由用户的要求触发，算用户改的状态。秘书的承诺即任务：它只答应用户要它做的事，答应了就当场建任务（用户的要求就是授权）或简单提醒；要反复做的事，建一个任务，由计划里的定时作业定义落地；用户没要求的，只能给建议卡，不能口头答应。用户问"有什么要我处理的"时，秘书能列出待我处理里未处理的事项、加以解释，并把同一张卡放进聊天；但它不主动转述待我处理，也不能替用户在卡上做决定。

演示：让一个任务从执行中转为等我，然后在秘书页随便发一句话，看秘书的回复已经知道这个变化；问"项目 A 进展如何"，秘书读项目档案作答，项目列表上 A 的维护者小圆点一直是休眠；说"把任务 X 暂停"，聊天里出现"已执行"卡，看板上任务变为已暂停；问"现在有什么等我处理的"，秘书列出事项并把那张审批卡放进聊天，在聊天里点批准后，待我处理里的同一张卡也变成已处理。

## Acceptance criteria

- [x] 主切面（faux provider 记下收到的模型输入）：看板发生变化（比如某任务从执行中转为等我）后，用户发下一条消息时，秘书收到的模型输入在这条用户消息之后多一条"看板变化"上下文消息，列出自上次以来的变化；看板没变时不追加；系统提示与变化前逐字节相同。
- [x] 主切面：秘书的"查看板"只读工具返回任务看板派生视图的当前内容（任务、简单提醒、定时作业及其状态），与看板频道推给前端的一致。秘书的"读项目档案"只读工具按项目返回任意项目（含已归档）的项目档案内容；调用期间不拉起、不唤醒该项目的维护者，活动状态不变；没有对应的写工具。
- [x] 主切面：秘书主线触发压缩（自动触发，或测试里强制触发）时，传给模型的压缩指令是秘书专用的那一份，含第 7 节列出的丢弃和保留要求；压缩后仍是同一条主线会话，之后的看板变化消息照常追加。
- [x] 主切面：用户消息里原样出现了任务（名称或 ID）并说暂停、继续或取消时，任务控制快速动作直接执行，聊天里留"已执行"卡；任务状态按 13 号票的状态机迁移（执行中 → 已暂停、已暂停 → 执行中，名额已满时回到排队中；任何未结束的状态 → 已取消），迁移事件记为用户发起、按"谁能改"表里用户那一行校验；不合法的迁移（比如暂停一个已完成的任务）被拒绝且任务状态不变。
- [x] 主切面：秘书推断出的任务控制动作（用户消息里没有原样出现那个任务）一律先问——卡片带确认按钮、同时进待我处理，用户点确认后才执行，不论关注类别设置如何。经快速动作取消的任务照常产生"任务结局：取消"的素材事件（由 08 号票采集）。
- [x] 主切面：用户问到待我处理时，秘书用只读工具列出未处理的事项；秘书的回复带上某张卡的卡片引用，聊天里显示的就是同一张卡（同一 id、同一状态），在聊天里点按钮后，待我处理里这张卡同步变为已处理。待我处理新增事项本身不进入秘书的模型输入（不主动转述）；秘书会话的工具白名单里没有任何对卡片做动作的工具。
- [x] 主切面（faux 剧本）：用户要秘书去做一件需要任务的事时（比如"以后每天早上给我出一份简报"），秘书在同一轮里用 12 号票的建任务工具直接建出任务（规划中），看板频道推送，不出"建议发起任务"卡；秘书的工具里没有建定时作业的工具。秘书的固定系统提示写明承诺即任务的三条（只答应用户要它做的事；答应了当场建任务或简单提醒；没要求的只给建议卡、不口头答应），DeepSeek 手动冒烟做秘书分流时一并检查（不进自动测试）。
- [x] pi 契约测试里加上对应用例：在用户消息之后追加一条上下文消息、系统提示不变（13 号票已有"压缩之后注入上下文消息"的用例，挨着它加）；压缩时使用自定义的压缩指令。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：快速动作卡、执行器注册表、"已执行"卡、"明确点了"的运行时判定和操作记录归 21 号票，本票只往注册表里加"任务控制"这一种动作，并把它推断出来时的处置登记为先问。任务状态机、暂停 / 继续 / 取消落到维护者身上的效果（停下或唤起维护者）、名额满时回到排队中归 13 号票。给维护者的重注入块（每次唤起和压缩后注入）也归 13，本票的看板变化消息是秘书专用的另一件事。
- 任务的发起：用户要求时秘书直接建任务卡（规划中）并进入澄清、秘书自己发现时给"建议发起任务"卡、计划卡确认是执行前的闸，这些都归 12 号票；本票只在秘书的系统提示里落实"承诺即任务"。定时作业通过任务建：计划结构里的作业定义归 12，确认后登记和运行归 19。
- "读项目档案"工具读的是 15 号票建好的最小文档集（立项书、规格、术语表、ADR、进展、项目清单、范围记录）。它和秘书文件工具对项目档案的只读（03、07）是两回事：这个工具按项目取，不用秘书知道路径。
- 任务控制快速动作算用户改的状态（第 14 节），"谁能改"表不用改：秘书只是替用户提出动作，确认或"明确点了"都出自用户。
- 秘书常驻主线会话、流式和断线补发是 04 号票的；简单提醒工具是 06 号票的。
- DeepSeek 上中途插入上下文消息对前缀缓存的影响，按测试决定做一次手动冒烟，不进自动测试。
- 对应用户故事：8–15。

- 2026-10-08 实现（子 agent）。做法和取舍：
  - **看板变化消息**（`board/board-watch.ts`）：秘书"上次看到的样子"取上一条交到它手里的用户消息开始处理（`turn_start`）那一刻的看板；交给下一条用户消息时比较，新出现的、状态变了的（任务的状态，等我的带原因、失败的带原因；提醒的待触发 / 已触发 / 已取消）写成一条以"【看板变化】"开头的上下文消息，经宿主协议 5 的 `user_input.context` 跟在用户消息后面（pi 的 nextTurn 自定义消息），系统提示不动。比状态和第几阶段（评审后定：任务从第 N 阶段进到第 N+1 阶段报一行"任务 t-3「…」进入第 2/4 阶段"；刚开始执行、第一次有阶段的由状态那一行说明）。运行时给秘书的通知（系统消息）不带，变化攒到下一条用户消息。守护进程重启、秘书子进程意外退出后从事件日志对一遍（最后一条处理完、不是被打断的用户消息的 `turn_start` 之前的看板事件），所以停机时的变化照报、报过的不重报。
  - **"按天分段"**（主会话交接里提到）：规格里"秘书主线按天"是时间线全局层的着色（25 号票）。本票没有把主线拆成按天的会话或会话段（规格第 7 节是"一条长期主线会话"，整条一段 `SECRETARY_SEGMENT_ID`），只在秘书专用的压缩指令里要求摘要按日期分段写。
  - **压缩**：秘书专用的压缩指令（`SECRETARY_COMPACTION_INSTRUCTIONS`）经装配参数 `compactionInstructions` 交给子进程，子进程在 pi 的 `session_before_compact` 里用 pi 导出的 `compact` 按它写摘要（指令接在 pi 的摘要提示后面，"Additional focus: …"），自动（阈值、上下文溢出）和手动压缩都走它。发现 pi 的一个行为：二狗在每条输入前记的输入标记（自定义条目）让切点落在标记上，pi 把它当成"切在一轮中间"，那一轮用它自己的"半轮"提示另写（不带自定义指令）；扩展里认出这种其实没切开的情况，并回历史整段按指令写。**维护者会话（pi 默认的写法）同样有这个现象**：最后一轮前面的那一轮被当成"半轮"单独摘要，内容不丢，只是写法不同；18 号票（压缩时的范围审视）、24 号票（按上下文用量压缩）留意。秘书压缩之后不注入别的块（重注入块是维护者的），看板变化照常追加。
  - **任务控制快速动作**（`tasks/task-control.ts`）：三个登记 `pause_task` / `resume_task` / `cancel_task`，参数 `{ task }`（编号或名称）。规范化时按 `availableTaskActions(task, "user")` 查能不能做，不能做的提议直接被拒、不出卡（说法 `taskActRefusal`；快速动作模块对执行器抛的 `RequestRejected` 改成原样回给秘书"不能这样做：……"，别的错误仍是"参数不对"）。"点明了"（评审后收紧，照记忆命令的做法）：只看用户自己打的字，按句、按分句（逗号、顿号）看；问句不算（以问号结尾，或以"吗""么""呢""没有"这类收尾）；分句里有动作的说法（暂停；继续、恢复；取消），前面没有否定词，并且任务（编号作为一个词，或完整标题）出现在动作词后面到分句结束的那一段里；那一段只是指代时任务要在用户引用的卡片上；否则一律先问。另外认"把 X 暂停"的 X（票里演示的说法是"把任务 X 暂停"，评审的规则只说了动作词后面那一段，为了不让演示的说法变成先问，补了这一种；同样要不是问句、前面没有否定词）。执行走执行控制器新加的 `prepareAct`（和 `act` 同样的校验和迁移，只是先不落盘），任务事件和快速动作卡、操作记录同一事务追加；为此 `CardActionEffect`、`QuickActionOutcome` 各加了可选的 `afterCommit`（落盘之后叫一次：提示用户、把对应的通知记成处理过）。
