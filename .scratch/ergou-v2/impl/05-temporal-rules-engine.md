# 05 — 时序规则引擎与 v1 规则模板

Status: ready-for-agent
Blocked by: 03（守卫判定核心）
Spec: [第一阶段规格](../spec.md) 第 9 节（守卫）、Testing Decisions（守卫判定、参照）

## What to build

把 AgentSense planguard 的引擎核心（expr + spec + checker）照搬进守卫，规则格式与它兼容，接进 03 号票的判定函数。时序规则只看效果日志里已经成功执行过的调用，支持四种形态：B 之前必须做过 A、B 之前不能做过 A、当下必须满足某条件、一律禁止；判断不了就问用户。规则只认工具名和参数，参数名统一，并有一道规则校验（参考 AgentSense 的 `policies-check`）。规则可以挂在单个阶段上，也可以挂在阶段组上套给一组阶段。

v1 自带六条针对真实工具的规则模板，默认生效：删除或覆盖项目档案和工作目录里的文件之前，必须已备份或已 git 提交（秘书草稿区不受这条约束）；push 之前必须跑过测试；读过 `.env` 或密钥文件之后不许对外发送、不许发 HTTP 请求（一律禁止，不是先问）；同一收件人、同一内容不重复发；对外内容不许含密钥；force push 和项目外 `rm -rf` 一律禁止。

做完后，守卫切面能用场景文件演示一串调用逐步被判定的过程，比如"没跑测试就 push → 拦下；跑过测试再 push → 放行"。场景文件格式与 AgentSense 的 planguard 场景兼容，可以直接搬一部分用例。

## Acceptance criteria

- [ ] 引擎核心（expr + spec + checker）从 AgentSense planguard 移植，规则格式与它兼容；四种形态各有通过和违反的场景。
- [ ] 规则只看效果日志里执行成功的调用：被拦下或执行失败、没进效果日志的调用，既不能满足"B 之前必须做过 A"，也不会触发"B 之前不能做过 A"。
- [ ] 判断不了（缺少需要的环境事实、参数无法规范化、规则要的值取不到）时，判定为先问用户，既不放行也不拦下。
- [ ] 效果日志记录按规格第 9 节字段 `{序号, 任务, 阶段, agent, 工具或伪工具, 规范化参数, 效果摘要, 时间}`；参数名统一：带类型的工具和从通用 bash 拆出的伪工具调用规范化成同一种形式，同一条规则对两者都生效（例如带类型的 git 推送和 bash 里的 `git push` 都受"push 之前必须跑过测试"约束）。
- [ ] 规则校验：规则引用了注册表里没有的工具或参数名、或者形态写错时，校验报错并指出是哪条规则；校验是一个纯函数，存计划时可以直接调用。
- [ ] 六条 v1 模板各有至少一个违反场景和一个通过场景，覆盖带类型的工具和通用 bash 两种写法；模板默认生效，不需要写进计划。
- [ ] 模板的范围：v1 模板"删除或覆盖之前必须已备份或已提交"只管项目档案和工作目录里的文件，秘书在草稿区里删除或覆盖文件不受它约束（场景覆盖：秘书删草稿区里没提交过的文件仍为直接做只记录）；"读过 `.env` 或密钥文件之后对外发送或发 HTTP 请求"判为拦下，不是先问。
- [ ] 判定时把 v1 模板、当前阶段的规则和它所属阶段组的规则一起检查。违反时拦下，判定输出的"命中的时序规则"列出规则，给模型的说明写明违反了哪条、怎样才能满足；最终处置与关注类别的处置合并取最严。"当下必须满足某条件"用调用方传入的环境事实（文件元数据、git 状态）来判断，判定函数仍是纯函数。
- [ ] 守卫切面加上场景文件测试，格式与 AgentSense 的 `scenarios/*.planguard.json` 兼容，并搬入一部分它的用例（可参照它的 `scripts/planguard-*` 验证脚本）。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 和 03 的分工：参数名统一建在 03 号票工具注册表的参数规则之上；"对外内容不许含密钥"模板和 03 的底线（凭据写进对外内容为"永不"）用同一套密钥形态正则，避免两处说法不一。
- 和 07 的分工：效果日志作为派生视图落进 `ergou.db`、在工具执行成功后追加，是 07 号票接通运行时时做的；本票只定记录的形式和判定怎么用它。07 不依赖本票，若 07 先落地，按规格第 9 节的字段先建好效果日志，本票直接用。
- 和 13 的分工：读过 `.env` 或密钥文件之后的对外发送由本票的 v1 模板一律禁止。13 号票控制器里的硬检查是另一条——"某个对象被判过'永不'之后，再对它做对外动作要先问"，两条不重叠，本票不做那条。
- 和 28 的分工：带类型的特殊 bash 工具（git 状态和差异、提交、推送、建远端仓库、合并、跑测试、装依赖、启动构建）的执行实现在 28 号票，它和 v1 模板配合（push 前须跑过测试、删除前须已提交、禁止 force push）。本票的场景直接按工具名和参数构造调用，不依赖 28 落地。
- 不在本票：计划里时序规则的存储和在计划卡上的显示（12）；提交计划时调用本票的规则校验、执行中按当前阶段和阶段组取规则、授权只在所属阶段内有效、前置阶段须已验收（13）；拉回和偏离升级（14）；自定义关注类别（26）。
- 用户故事 64"我在对话里说的限制被编译成规则、显示在计划卡上"由 26 号票做：起草计划的维护者把对话里说的限制编译成时序规则或授权收窄；编译出的规则走本票的格式和规则校验。
