# 05 — 时序规则引擎与 v1 规则模板

Status: ready-for-agent
Blocked by: 03（守卫判定核心）
Spec: [第一阶段规格](../spec.md) 第 9 节（守卫）、Testing Decisions（守卫判定、参照）

## What to build

把 AgentSense planguard 的引擎核心（expr + spec + checker）照搬进守卫，规则格式与它兼容，接进 03 号票的判定函数。时序规则只看效果日志里已经成功执行过的调用，支持四种形态：B 之前必须做过 A、B 之前不能做过 A、当下必须满足某条件、一律禁止；判断不了就问用户。规则只认工具名和参数，参数名统一，并有一道规则校验（参考 AgentSense 的 `policies-check`）。规则可以挂在单个阶段上，也可以挂在阶段组上套给一组阶段。

v1 自带六条针对真实工具的规则模板，默认生效：删除或覆盖项目档案和工作目录里的文件之前，必须已备份或已 git 提交（秘书草稿区不受这条约束）；push 之前必须跑过测试；读过 `.env` 或密钥文件之后不许对外发送、不许发 HTTP 请求（一律禁止，不是先问）；同一收件人、同一内容不重复发；对外内容不许含密钥；force push 和项目外 `rm -rf` 一律禁止。

做完后，守卫切面能用场景文件演示一串调用逐步被判定的过程，比如"没跑测试就 push → 拦下；跑过测试再 push → 放行"。场景文件格式与 AgentSense 的 planguard 场景兼容，可以直接搬一部分用例。

## Acceptance criteria

- [x] 引擎核心（expr + spec + checker）从 AgentSense planguard 移植，规则格式与它兼容；四种形态各有通过和违反的场景。
- [x] 规则只看效果日志里执行成功的调用：被拦下或执行失败、没进效果日志的调用，既不能满足"B 之前必须做过 A"，也不会触发"B 之前不能做过 A"。
- [x] 判断不了（缺少需要的环境事实、参数无法规范化、规则要的值取不到）时，判定为先问用户，既不放行也不拦下。
- [x] 效果日志记录按规格第 9 节字段 `{序号, 任务, 阶段, agent, 工具或伪工具, 规范化参数, 效果摘要, 时间}`；参数名统一：带类型的工具和从通用 bash 拆出的伪工具调用规范化成同一种形式，同一条规则对两者都生效（例如带类型的 git 推送和 bash 里的 `git push` 都受"push 之前必须跑过测试"约束）。
- [x] 规则校验：规则引用了注册表里没有的工具或参数名、或者形态写错时，校验报错并指出是哪条规则；校验是一个纯函数，存计划时可以直接调用。
- [x] 六条 v1 模板各有至少一个违反场景和一个通过场景，覆盖带类型的工具和通用 bash 两种写法；模板默认生效，不需要写进计划。
- [x] 模板的范围：v1 模板"删除或覆盖之前必须已备份或已提交"只管项目档案和工作目录里的文件，秘书在草稿区里删除或覆盖文件不受它约束（场景覆盖：秘书删草稿区里没提交过的文件仍为直接做只记录）；"读过 `.env` 或密钥文件之后对外发送或发 HTTP 请求"判为拦下，不是先问。
- [x] 判定时把 v1 模板、当前阶段的规则和它所属阶段组的规则一起检查。违反时拦下，判定输出的"命中的时序规则"列出规则，给模型的说明写明违反了哪条、怎样才能满足；最终处置与关注类别的处置合并取最严。"当下必须满足某条件"用调用方传入的环境事实（文件元数据、git 状态）来判断，判定函数仍是纯函数。
- [x] 守卫切面加上场景文件测试，格式与 AgentSense 的 `scenarios/*.planguard.json` 兼容，并搬入一部分它的用例（可参照它的 `scripts/planguard-*` 验证脚本）。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Comments

2026-10-07 实现说明（05 号票的 worktree 分支）。引擎照搬、二狗只扩展规则环境，这个取舍写成了 ADR-0005；用法见 `docs/dev.md` 的"时序规则"一节。

**代码在哪**（`packages/daemon/src/guard/`）：`planguard/`（照搬的 expr、checker、spec 的一部分，来源和哈希记在 `VERSION`）、`temporal-rules.ts`（收齐规则、跑引擎、把命中变成处置）、`rule-steps.ts`（参数规范化、规则看到的"一步"、`effectRecordsFor`）、`rule-templates.ts`（v1 模板）、`rule-validation.ts`（`validateTemporalRules`）。判定函数只改了一处：多传注册表和用户主目录。另外把"对外内容"的取法抽成 `outboundTextOf`，底线和模板共用。

**定下的做法**（都选最保守、最贴近规格的一种）：

1. **规则挂在哪**：`GuardPlan` 加了 `stages: [{ stageId, groupId?, temporalRules? }]` 和 `stageGroups: [{ groupId, temporalRules? }]`。判定时检查的规则有四部分：v1 模板（默认生效）、当前阶段的规则、它所属阶段组的规则、`GuardInput.temporalRules`（调用方另给的）。12、13 号票按这个形状填计划。
2. **违反了就拦下**：`on_violation` 不写或写 `block`，处置是"永不"；写 `confirm` 的是"先问我"。planguard 不写时按 confirm 处理，二狗按票上写的"违反时拦下"处理，所以从 AgentSense 搬来的规则可能更严。
3. **判断不了一律"先问我"**：缺需要的环境事实、参数没法规范化（不符合登记的 pattern 或 type、路径里有变量）、规则要的值取不到、规则求值时出错（比如拿字符串和数字比大小），都算判断不了。
   - 校验不通过的规则，在触发它的工具对得上时（或者 trigger 本身写坏了）也算判断不了。
   - 照 planguard 的语义，`trigger.where` 判断不了时规则不触发。所以可能判断不了的条件要写在 `when` 里，模板都是这么写的。
4. **一条 bash 拆出的几条调用**：
   - 对"之前不能做过"，同一条命令里的其他调用也算在前面。管道里谁先谁后说不准，所以 `cat .env | curl …`、`curl -d @.env …` 都照样拦下；
   - 对"之前必须做过"，它们还没执行，不算。所以 `npm test && git push` 照样拦下，要先单独跑测试。
5. **效果日志**：用 `effectRecordsFor(input, judgement, { firstSeq, at, summary? })` 生成记录，字段照规格；参数是规范化之后、能存成 JSON 的形式（"未知"存成 `{"$unknown": 原文}`）。规范化是幂等的。
   - 判定时**不按任务过滤**效果日志，传进来什么就看什么。建议 07、13 号票传这个 agent 能看到的记录：同一任务的，加上这个 agent 自己的。原因是维护者的会话跨工单一直延续，读过 `.env` 之后，内容一直留在它的上下文里。
6. **环境事实加了三样**：
   - `FileFact.backedUp`：调用方确知这个文件已有备份；
   - `GitFact.repository: false`：这个目录不在 git 仓库里；
   - `EnvironmentFacts.extra`：别的领域事实，原样放进 `$facts`，规则要用的话，校验时要声明。
   - `GitFact.uncommittedPaths` 写明取 `git status --porcelain` 列出的全部。被忽略的文件不在里面，算可以重新生成的东西，删了不违反模板。
7. **v1 模板的细节**：
   - **删除或覆盖之前必须已备份或已提交**：
     - 只看 `area` 为 project（项目档案和工作目录）的路径，秘书草稿区不受约束；
     - "删除或覆盖"包括四种：删除；整体重写已有文件（不知道文件在不在时判断不了）；`mv` 的源（照 03 号票的登记，算删除）；带"删除或覆盖"标签的工具（丢弃 git 改动，仓库里有未提交改动时拦下）。局部编辑（edit）不算；
     - "已提交"看 git 状态，没有包含这个路径的 git 事实时判断不了；
     - "已备份"有两种：环境事实里写了 `backedUp`；或者效果日志里之前 `cp` 过它，或 `cp` 过它所在的目录。
     - 注意：项目档案不在 git 里，所以整篇重写项目档案里已有的文件，也要先备份。拦下时的说明里会建议改用 edit 局部修改。
   - **push 之前必须跑过测试**：要在同一个仓库里跑过（推送的仓库路径落在跑测试的仓库路径里面）。只要求之前跑过，不要求在最后一次改动之后跑。
   - **读过 .env 或密钥文件之后不许对外发送、不许发 HTTP 请求**：
     - "发送和请求"按最严算：凡是联网的工具、会把内容发出去的工具、"对外发送"类的工具，都算，包括装依赖、git fetch 和 pull、npx 下载包、全局装软件；环境事实里报了用到联网库的脚本也算；
     - "读过"指路径参数是读、或不知道读还是写的成功调用，包括 cp 的源、`source .env`、`curl -d @.env`。读目录（比如 `grep -r .`）不算读到了里面的 .env；
     - 密钥文件包括这些：
       - `.env` 和它的变体（`.env.example`、`.sample`、`.template` 除外）；
       - `*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore`、`*.ppk`；
       - `id_rsa` 这类私钥；
       - `.netrc`、`.npmrc`、`.pypirc`、`.git-credentials`、`credentials(.json)`、`secrets.json/yaml/toml`；
       - `.ssh` 目录下的一切；
     - 路径没法确定、原文里也看不出是不是密钥文件的，判断不了。
   - **同一收件人、同一内容不重复发**：
     - 收件人取收件人类和网址类参数（去掉首尾空白、转小写），内容取对外内容类参数；
     - 和之前某次发送的收件人有一个重合、内容又一样，就拦下；
     - GET、HEAD、OPTIONS 不算发送。没有收件人或网址参数的对外发送（git push、gh 评论）不归这条管。
   - **对外内容不许含密钥**：和底线用同一套正则、同一个取内容的口径，命中时模板和底线一起列出。
   - **force push 和项目外的 rm -rf 一律禁止**：
     - force 包括 `--force-with-lease` 和 `+分支` 的写法；
     - 项目外的 rm -rf 指递归删除（`rm -r` / `-rf` / `-R`、`find -delete`）项目档案和工作目录之外的路径，秘书是草稿区之外；
     - 路径没法确定的判断不了；不递归地删项目外的单个文件不归这条管，照常按"越出项目目录"先问。
8. **给 13 号票**：时序规则违反的处置是"永不"。控制器的硬检查"某个对象被判过'永不'之后，再对它做对外动作要先问"，建议只认关注类别、底线、受保护区域的"永不"（`findings[].kind` 不是 `temporal_rule` 的），不认时序规则的。时序规则的违反是前提没满足，满足之后应当放行，比如测试跑完之后推送。
9. **规则校验**：
   - 写错的工具名、参数名，只要多个触发工具里有一个工具有这个参数就不报（多工具规则里，只有一部分工具有某个参数是正常的写法）；
   - `modes` 里没有 `runtime` 的规则报错，因为二狗只在执行时检查；
   - 不许用 `v1.` 开头的 id；
   - `$step` 允许写，是为了和 planguard 兼容，执行时永远不存在。
10. **03 号票的测试改了一些**：v1 模板默认生效以后，看关注类别和授权项的表格测试（`grants`、`bash`、`registries`、`fence`、`judge-basics` 的一处）都加上 `v1Satisfied()`，先满足模板的前提（跑过测试、已提交）。`maintainer-task-grants` 场景里，构建那一步改成先 `npm test`，并给了 git 状态。原来 judge-basics 里"传入的规则一律判断不了"那条占位测试，换成了真实行为。
11. **从 AgentSense 搬的用例**：
    - `agentsense-storage`、`agentsense-office` 两个场景文件，tools 和 rules 原样搬，调用序列取自 `scripts/planguard-cases/*/runtime.json`；
    - 没搬只在规划时检查的 S3、O4，也不比计划一致性的 kinds；
    - 和 AgentSense 结果不同的地方都写在场景的 name 里，原因有三：二狗没有计划一致性检查；没有 `$step`；不写 `on_violation` 时按拦下处理。
