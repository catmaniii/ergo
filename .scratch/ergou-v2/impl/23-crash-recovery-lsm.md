## What to build

二狗的守护进程 `ergou-daemon` 从 04 号票起就在 Local Service Manager 里登记、由它启动（固定的 Node 22 LTS 绝对路径，指向主分支的构建产物）。本票在这个条目上补两件事：有任务在跑时经 LSM 的 link 协议心跳上报"忙"；条目开着 autoRestart，被 LSM 重启后按规则恢复。二狗自己不启动任何服务。

LSM 每次重启都会连带杀掉守护进程，Job 对象把所有子进程一起清掉。守护进程重新起来后，正在做的事按规则恢复，不乱、也不悄悄重做有副作用的操作：待审批的事项从审批表恢复，不重复通知；被打断的调用按工具注册表里的"只读或幂等"标记分两种——只读或幂等的告诉模型"这次调用被中断了"，由它决定要不要重做；有副作用、效果日志里又查不到成功记录的，任务里的让任务转为等我，原因写"中断：不确定 X 是否已执行"，秘书会话里的放一条同样写法的待我处理事项；输出到一半的回复丢掉中间片段，从会话文件里最后一个完整的回合续上；每个 agent 排着队的输入都在事件日志里，重启后按原顺序接着处理。

演示：主切面测试里，任务执行到一半时直接杀掉守护进程再起——一个正在等审批的调用重启后审批卡还在、没有多出一张；一个发到一半的"对外发送"调用让任务转为等我，看板上写着"中断：不确定 X 是否已执行"；秘书那条说到一半的回复不见了碎片，会话从上一个完整回合续上。

## Acceptance criteria

- [ ] 手动验证：在本机 LSM 里，`ergou-daemon` 条目开着 autoRestart；直接结束守护进程后由 LSM 拉起，`/healthz` 恢复健康，下面各条恢复规则在真实重启下照样成立；有任务执行中时，LSM 上能看到它报"忙"。
- [x] 主切面（测试里用替身接收 LSM link 心跳）：有任务处于执行中时，心跳上报"忙"；没有任务在执行时不报"忙"。
- [x] 主切面：直接杀掉守护进程后，所有 agent 子进程和孙进程随之结束（27 号票完成后，MCP 服务进程同样）；再起守护进程后没有遗留的旧进程。
- [x] 主切面：子进程正在等审批时守护进程被杀——重启后审批卡从审批表恢复、仍是待处理，不新建卡，也不再推送"新审批"事件，任务处于等我；这次调用不算"说不清做没做完"。用户事后批准后，按调用指纹记一条一次性授权，运行时唤起维护者并附"……已获批准，可以重试"，重试的那次调用直接放行，且只放行一次。
- [x] 主切面：被杀时正在执行、注册表里标了"只读或幂等"的工具调用，重启后运行时告诉模型"这次调用被中断了"，由模型决定是否重做；任务不转等我。
- [x] 主切面：任务里被杀时正在执行、有副作用（注册表里没标"只读或幂等"）、效果日志里又查不到成功记录的调用，重启后任务转为等我，原因写"中断：不确定 X 是否已执行"（X 为规范化后的调用摘要），待我处理出现一条"中断不确定"事项，任务看板的任务卡上能看到这个原因；运行时不自动重做这次调用。
- [x] 主切面：秘书会话里被杀时正在执行的有副作用调用（比如经用户批准、正在跑的草稿区外脚本），重启后待我处理出现一条"中断：不确定 X 是否已执行"事项（紧急度"不卡任务"），运行时不自动重做；秘书会话照常可用。
- [x] 主切面：被杀时正在流式输出的回复，重启后历史分页和会话文件里都没有半截内容，会话从最后一个完整回合续上；被杀时已经排队、还没处理的输入按原顺序处理，不丢也不重复。
- [x] pi 契约测试里加上对应用例：从末尾带半行、或带未完成工具调用的会话文件恢复会话，只保留完整回合，并能补上"被中断"的工具结果。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Comments

实现（分支 `worktree-agent-a02c26941fb2dad0b`）里定下的几件事（含两路评审后的修改）：

- **手动验证没做，由主会话合并后做**：按约定不碰用户正在跑的 `ergou-daemon`、不改 LSM 的登记目录。自动测试里 LSM 一端用替身（`test/helpers/lsm-stand-in.ts`）；测试底座起守护进程时都去掉 `LSM_*` 变量，在 LSM 拉起的终端里跑测试也不会连上真实的 LSM。主会话的步骤（`docs/dev.md`"LSM 登记"一节也写着）：
  1. 合并到 main 后在主检出目录 `npm ci`、`npm run build:web`。
  2. 改 LSM 登记目录里的真实条目 `registry/services/ergou-daemon.yaml`，照 `deploy/lsm/ergou-daemon.example.yaml` 改两处，其余不动：`probe.tier: linked`（保留 `probe.port` 和 `health.url`，接入层断开时降级回健康探针用），加 `link.enabled: true`。`autoRestart.enabled` 保持 true。在 LSM 目录跑 `node bin/lsm.mjs validate`，再 `lsm reload`。
  3. 在 LSM 里重启 `ergou-daemon`，按新代码起来：`/healthz` 转绿，LSM 上档位显示 linked（接入层连上了；守护进程日志里有"已接入 LSM（ergou-daemon）"），数据目录下有 `daemon.pid`。
  4. 看"忙"：发起一个任务，让它进入执行中（或者让秘书在草稿区外跑一个要批准的长脚本，比如 `sleep 120`，批准后它在跑），LSM WebUI 上这个服务显示"忙"，原因写着"正在执行 1 个任务：「…」"或"1 个有副作用的调用还没做完：…"。任务结束或调用结束后几秒内不再报忙。
  5. 看"等空闲再停"：忙的时候在 LSM 里点"等空闲再停"，守护进程照常、不停；调用做完、不忙了才停（`daemon.pid` 删掉）。再在 LSM 里启动。
  6. 看被杀后的恢复：再让一个有副作用的调用在执行（同 4），用 `taskkill /F /PID <daemon.pid 里的 pid>` 直接结束守护进程（不要用 LSM 的停止）。LSM 按 autoRestart 退避（约 5 秒）拉起，`/healthz` 恢复健康；任务里的那次调用让任务转为等我，看板任务卡写着"中断：不确定 X 是否已执行"，待我处理里一条卡着任务的"中断不确定"事项（秘书会话里的则是一条"不卡任务"的事项）；那个脚本没有被自动再跑一遍。点"已经执行了，继续"后任务接着执行。
  7. 看等审批：让维护者或秘书发起一个要审批的调用（比如读主目录里的文件），审批卡出来、不批，直接 `taskkill` 守护进程；LSM 拉起后审批卡还是那一张、仍待处理，没有新卡、没有再弹提示；批准后 agent 被唤起重试、放行一次。
  8. （可选，自动测试已覆盖）看单实例：守护进程在跑时，在另一个终端用同样的 `ERGOU_DATA_DIR` 手动跑一次 `<专用 Node 路径> packages/daemon/src/main.ts`，应立即以退出码 1 退出、说"已经有一个守护进程在运行"，正在跑的那个不受影响（没有任务转等我、没有"中断不确定"事项）。
  9. 都通过后勾上第一条验收标准。
- **link 协议**：照 LSM 的 `docs/link-protocol.md` v1 写在 `packages/daemon/src/lsm/link.ts`，WebSocket 用工作区已有的 `ws`（握手带 `Authorization` 头），没照搬参考客户端。**"忙" = 有任务处于执行中，或者任何 agent 有正在执行的有副作用的调用**（`lsm/busy.ts`），原因写明是哪些；"等空闲再停"因此会等它们做完。健康 = 秘书在不在运行（`ok` / `degraded`）。停机（立即、等空闲）走 `daemon.stop()`，停完删 pid 文件、断开接入层发 bye（只在停止流程的最后一处断），`main.ts` 再退出；管理器回 `conflict` 时退出。没有 LSM 注入的四个变量时什么都不连。stop 钩子保留，作为接入层断开时的兜底。
- **单实例**：`startDaemon` 一开始先看 pid 文件（进程还在、启动时间对得上）和本机端口，同一个数据目录已经有实例在跑就抛错、什么状态都不碰，`main.ts` 以退出码 1 退出——不然恢复会把正在跑的实例里正在执行的调用当成被杀时中断的。pid 文件改由 `startDaemon` 写（开好端口之后）、停完才删。
- **"有副作用、效果日志里查不到成功记录"的判定**：守卫接入在放行、开始执行有副作用的调用时记 `tool_call_started`，结束时记 `tool_call_finished`（成功与否、结果摘要；成功的和效果日志同一事务）。没结束的就是"查不到成功记录"的。只读或幂等的不记；bash 按判定拆出的伪工具算：每一条都标了"只读或幂等"才算只读。
- **同一批里先做完的调用不当成说不清**（评审指出的严重问题）：pi 并行执行一批工具调用、全部结束才把结果写进会话。结束记录因此留到这个 agent 又出了一条助手消息、或者这一轮结束（结果都写进会话了，记 `tool_calls_settled`）；被杀后重新拉起时，会话里缺结果的调用按结束记录补"已经执行完了（结果……），不要重做"（不算出错）或"执行失败了"，只有确实没有结束记录的才按"中断不确定"处理。宿主协议 7 的 `interruptedToolResults` 因此是 `{ text, isError }`。主切面有"同一批里一快一慢、杀在中间"的用例。
- **"宣布阶段完成"**：它跑验收脚本、改验收次数，不是只读或幂等，照旧标 `readOnlyOrIdempotent: false`；工具登记里另加"由执行控制器负责恢复"（`recoveredByController`），标了的不记执行记录——被杀时正在验收的阶段由 13 号票的控制器交回维护者再宣布一次，不多出一条"中断不确定"。
- **"最后一个完整回合"按 pi 的回合算**（一条助手消息加它要调用的工具的结果）：子进程接着会话时去掉末尾写到一半的一行，给最后一条助手消息里还没有结果的工具调用补上结果（等审批的"没有执行，批准后会通知你"；有副作用的按上一条；只读的用默认的"这次调用被中断了……需要的话再调用一次"）。pi 的流式增量本来就不落盘，半截回复只可能是末尾的半行。
- **被打断的任务维护者重启后被唤起**（`RESTART_WAKE_TEXT`），任务还在规划中、执行中、又没有别的输入等着它时才发；秘书和项目维护者不额外唤起（照 04 号票，被打断的那条不重送，排着的照常处理）。
- **"中断不确定"事项的动作**：任务里的卡着任务，动作"已经执行了，继续 / 没执行，重做这一步"，选了之后任务恢复执行、维护者照用户说的做；也能在任务详情里点"继续"或回话（"由用户定夺的等我原因"在协议包导出 `USER_DECIDES_WAIT_REASONS` / `userDecidesWait`，"谁能改"表的条件改名 `user_decides`）。秘书会话里的不卡任务，动作只有"知道了"。事项的数据在协议包定义成 `InterruptedNoticeData { toolCallId, agentId, taskId }`（`interruptedNoticeData` 取），调用摘要不放进数据，回答时从执行记录取。
- **子进程意外退出（守护进程没被杀）也按中断处理**：守卫接入看到子进程退出时还有开始执行没结束的有副作用调用，记成中断（任务转等我）。守护进程正常停止时（含 LSM 要求停机）不算，留到下次启动按被杀恢复；停止期间来的判定请求一律不放行。秘书为改写会话文件主动重启子进程（21 号票）只在闲着时做，不会碰上。
- **20 号票的子 agent 一样覆盖**：子 agent 经一次性子进程接守卫，它的有副作用调用照样记执行记录、执行期间算"忙"；被杀、子进程意外退出时记成中断，任务转为等我、待我处理里一条卡着任务的"中断不确定"，说明和交给维护者的确认里写明是哪个子 agent 在哪个阶段的调用。子 agent 重启后不重新拉起（20 号票交回维护者"被打断了"）；这条说明和随任务停下的说明里列出它停下时还在执行的调用，写明等用户确认、不要重做——不然维护者被这条说明唤起后可能自己把它重做一遍。主切面：`crash-recovery.test.ts` 里子 agent 的调用执行到一半被杀，`lsm-link.test.ts` 里任务本身在等我、只有子 agent 的调用在跑时报忙、等空闲再停等它做完。
- **31 号票的语音识别不用另做**：识别进程在它自己的 Job 对象里，守护进程被杀时随之结束；排队、识别中的语音在启动时由 `voice.start()` 接着识别（31 号票已做，`voice.test.ts` 的"守护进程重启后，上次排队、识别中的语音接着识别"）。等识别的那条消息还没交给 agent，重启后照常排在输入队列里。识别可以重做，不算"有副作用的调用"，也不报"忙"。
- **彻底删除、删除项目的口径一致**：执行记录（开始、结束、被中断）里的调用摘要、结果摘要登记了改写函数；彻底删除一次调用时，同一段调用摘要出现的地方一起改写——执行记录、任务和秘书两侧"中断不确定"事项的标题和正文、任务等我的说明（`waitNote`，新登记的任务事件改写函数只改这一项，别的字段被要求改写时照旧拒绝整个删除）、维护者会话里的系统说明和给它的通知（整条换成"已删除"）。删除项目时改写那个维护者的执行记录和他对话里的"中断不确定"事项。变基到 22 号票之后多了一处改不了的：秘书看任务看板时看到的等我原因（22 号票的看板变化消息进了秘书的会话文件、查看板的结果进了秘书对话的工具调用记录，都带着 `waitNote`，"中断不确定"的说明里有调用摘要）。这两处没有改写，`PURGE_LIMITS` 补了一句"和秘书看任务看板时看到过的等我原因"，ADR-0008 的后果一节、`docs/dev.md` 同步写明。规格第 14、15 节"删不掉的如实告诉用户"那句可能要主会话补上这一条。
