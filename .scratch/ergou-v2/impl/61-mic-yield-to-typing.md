# 61 — 麦克风让路：打字、分屏时放开，回来再预热；不发空白语音；麦克风诊断记录

Status: ready-for-agent
Blocked by: 44（麦克风不因闲置关闭）
Spec: [第一阶段规格](../spec.md) 第 22 节"麦克风预热"

## What to build

用户 2026-10-09 反馈：语音模式里麦克风一直被二狗占着，在"发起任务"等地方用系统输入法的语音输入时，输入法会提示"麦克风被占用"，观感不好。

调研见 `docs/research/16-voice-mic-hold-vs-instant.md`。

- **原因**：用户打字时，二狗还开着麦克风。
  - Android：Chrome 在前台占着麦克风，系统把输入法录到的声音换成静音。
  - 鸿蒙：华为浏览器的网页录音走通话通路，按"先到先得"拒掉后来的输入法。
  - iOS：系统听写会打断网页的录音，之后可能录不到声音。
- **关掉回声消除不管用**：用户的 Chrome 是 149，要 153 以上才不压别人；鸿蒙不看这个设置。
- **办法**：输入框获得焦点时，真正关掉麦克风。

本票照调研的"方案一"做，并加上诊断记录，方便在真机上看效果。

## Acceptance criteria

- [ ] **打字时让路**：页面里任何可输入的元素获得焦点时，立即停掉麦克风的所有音轨，这样系统输入法的语音就能用。可输入的元素包括：二狗自己的文字输入框、发起任务等对话框里的输入框、textarea、contenteditable。
- [ ] **焦点回来再预热**：焦点离开输入元素后，如果仍在语音模式、页面在前台，0.5 秒后重新预热（常量可调）。
- [ ] **分屏让路**：窗口失去焦点（页面仍可见，比如分屏切到另一边）也算让路；窗口回来后照上一条重新预热。
- [ ] **状态层**：以上规则写进 `state/voice-mic.ts` 的纯函数，有表格测试。`app/voice-session.ts` 用假的浏览器接口测：
  - 焦点进出时音轨确实停了、又重新打开；
  - 按住说话的过程中不会因为焦点变化被打断，"按住 说话"本身不是输入元素。
- [ ] **不发空白语音（一）：按下时检查**：按下时检查预热的音轨还活着没有（`readyState`、`muted`）。已经失效的，比如被 iOS 听写打断过，当作没预热，重新打开，照旧显示"准备中"。
- [ ] **不发空白语音（二）：录完时检查**：录完的一段如果整段是数字静音（全零，或者音量一直低于阈值），不发送，提示"没录到声音，再按一次试试"。
- [ ] **诊断记录**：随每条语音一起发给守护进程，存进语音对象的 `capture`，宽松、向后兼容，本机接口取得到。内容：
  - 这次开麦的原因：预热、按下、焦点回来……；
  - 冷启动耗时：`getUserMedia` 从调用到返回的毫秒数；
  - 最近 N 次（比如 10 次）麦克风开关的时刻和原因；
  - 浏览器 UA。

  `docs/dev.md` 写清楚在本机怎么看这些记录。
- [ ] **兜底开关保留**：`app/voice-fallbacks.ts` 的两个兜底开关保留，默认值不变。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。
