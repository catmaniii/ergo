# 118 — 附件一律显示在文字后面

Status: done
Blocked by: 无
Spec: [第一阶段规格](../spec.md) 第 19 节（会话区）；113 号票（附件卡片）、115 号票（任务做完时的附件）、117 号票（维护者也能发附件）

## What to build

用户 2026-10-13 原话："不管是秘书还是哪个 agent，现在是先给我发附件，然后再发一段文字，很多时候那个文字太多，就把那个附件挡住了，我建议你任何时候要给我发附件，要放在发的文字后面。"

现在：agent 在一轮里先调 `send_attachment`（附件马上成一条消息出现在会话里），再写回复的文字，所以附件在上、文字在下，文字长了附件被顶到屏幕外。115 号票的任务做完附件也在"任务做完"那一行下面、秘书回复的上面。

改成（**只改显示，不改事件和交给 agent 的内容**，旧消息也照新顺序）：

- 一轮里 agent 发的附件（只有文件 / 图片的那几条消息），显示时挪到这一轮**最后一段文字回复的后面**（语音气泡算回复）。这一轮没有文字的，附件照原位置。
- 115 号票任务做完时运行时放的附件：挪到秘书处理那条通知的那一轮回复后面（秘书还没回、正在回时先在原位置，回完挪过去）。
- 同一轮几个附件保持原来的先后，排成一排（113 号票：同一条消息里的排一排；挪到一起后连着的也排一排，能做就做）。
- 用户自己发的消息（文字 + 附件）不动。
- 正在出字时附件先不挪（免得跳来跳去），这一轮结束再挪；或者从一开始就把附件画在这一轮的末尾——挑不跳的做法。
- 105 号票的定位（`at`）、109 号票的已读 / 提醒、108 号票的跟着最新走不受影响。
- 秘书、任务维护者、项目维护者三种会话都一样；要点层 / 全局层跟着同样的顺序。

  - **和票面不一样的地方**：
    1. **挪的时机按"说完了的一段话"，不按"这一轮结束"**：正在出字的回复不算，定稿了才挪（正在出字时不跳，任务做完的附件在秘书还没回、正在回时也在原位置）。一轮里有两段话、附件在第一段前面的，第一段说完挪到它后面，第二段说完再挪到第二段后面（会跳两次）。协议里消息没有"属于哪一轮"的记号，回合开始只在实时收到时记着最近几个，旧消息认不出轮次。
    2. **"一轮"按会话里的先后认**，所以有两种认不准：附件不越过卡片（agent 先发附件、再出卡、再说话的，附件留在卡片前面）；排队的情况——agent 干活时用户又发了一句、或者任务做完的通知在秘书忙别的时候到——那一句排在上一轮回复的前面，上一轮的附件可能挪到下一轮的话后面，或者留在原位置。
    3. **连着的几条附件没合成一排**：两条消息各是一条条目（详情、定位、未读都按条目 id），挪到一起后照旧各占一行；同一条消息里的照旧一排（113 号票）。
    4. **多改了 109、108 号票的两处**（条目不全按序号排了，不改会出错）：109 的提醒说到的最后一条 `through` 取最大的序号（原来取排在最后的那条，附件排最后时文字的序号漏了）；108 的 ↓ 上的条数按停在底部时手里最大的序号算（`scroll-end.ts` 的 `maxSeq`、`newSince` / `jumpBadge` 多一个 `seenSeq`；原来按排在最后那条之后的算，附件挪到最后时，打开会话往上翻一点会把早就在的话算成 1 条新的，或者漏掉后来排到附件前面的话），`ZoomHistory` 的 ↓ 多记一个序号。"看到哪了"（`seenThrough`）照旧：看到文字就算到文字的序号，排在它后面、序号更小的附件也算看过（已读位置只是一个序号，表达不了"文字看了、附件还没看"；停在底部时都看过，和原来一样）。109 的提醒标题、"查看"现在是这一轮的文字，不再是"发来了附件"。
    5. **被附件隔开的发附件调用，挪走附件后连成一组**（"调用了 2 个工具：把文件作为附件发出 ×2"），组的 id 是第一次调用的；按原来的组 id、调用 id 照样找得到（`locateChatItem`）。
