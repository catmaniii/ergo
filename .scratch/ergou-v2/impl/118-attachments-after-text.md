# 118 — 附件一律显示在文字后面

Status: ready-for-agent
Blocked by: 无
Spec: [第一阶段规格](../spec.md) 第 19 节（会话区）；113 号票（附件卡片）、115 号票（任务做完时的附件）、117 号票（维护者也能发附件）

## What to build

用户 2026-10-13 原话："不管是秘书还是哪个 agent，现在是先给我发附件，然后再发一段文字，很多时候那个文字太多，就把那个附件挡住了，我建议你任何时候要给我发附件，要放在发的文字后面。"

现在：agent 在一轮里先调 `send_attachment`（附件马上成一条消息出现在会话里），再写回复的文字，所以附件在上、文字在下，文字长了附件被顶到屏幕外。115 号票的任务做完附件也在"任务做完"那一行下面、秘书回复的上面。

改成（**只改显示，不改事件和交给 agent 的内容**，旧消息也照新顺序）：

- 一轮里 agent 发的附件（只有文件 / 图片的那几条消息），显示时挪到这一轮**最后一段文字回复的后面**（语音气泡算回复）。这一轮没有文字的，附件照原位置。
- 115 号票任务做完时运行时放的附件：挪到秘书处理那条通知的那一轮回复后面（秘书还没回、正在回时先在原位置，回完挪过去）。
- 同一轮几个附件保持原来的先后，排成一排（113 号票：同一条消息里的排一排；挪到一起后连着的也排一排，能做就做）。
- 用户自己发的消息（文字 + 附件）不动。
- 正在出字时附件先不挪（免得跳来跳去），这一轮结束再挪；或者从一开始就把附件画在这一轮的末尾——挑不跳的做法。
- 105 号票的定位（`at`）、109 号票的已读 / 提醒、108 号票的跟着最新走不受影响。
- 秘书、任务维护者、项目维护者三种会话都一样；要点层 / 全局层跟着同样的顺序。

## Acceptance criteria

- [ ] 一轮里先发附件后写文字的，显示成文字在上、附件在下；任务做完的附件在秘书回复后面；用户消息不动；旧消息也照新顺序。状态层测试（会话条目层 `state/chat-items.ts` 一带，用现有录制回放或手写事件）。
- [ ] 截图：经典浅色 390（秘书会话里"文字在上、附件在下"），另一套风格一张。示例数据里不要出现日本相关的内容。
- [ ] 只动 Web：**不跑全量**，只跑相关测试文件 + typecheck + oxlint；`docs/dev.md` 一两句跟着改。
