# 111 — 任务自己生成的临时文件、脚本可以随便改、删，不问也不退回

Status: ready-for-agent
Blocked by: 无
Spec: [第一阶段规格](../spec.md) 第 9 节（"删除或覆盖"类别、v1 规则模板第 1 条"删除或覆盖前须已备份或已提交"、"删除或覆盖"的定义）；101 号票（对话审批关着时的安全范围）

## What to build

用户 2026-10-13 原话："覆盖和删除的限制，只对系统已有的资源、数据、配置以及项目阶段交付件。如果是任务中间的临时文件和脚本，以及为了生成每个项目阶段交付件临时生成的脚本和数据，默认可以修改或者删除，不要每次都问我或者拦住了，这种默认允许。"

现在：任务的 agent（维护者、子 agent、评审）删除或整体重写项目档案、工作目录里的文件时——
- 落入"删除或覆盖"关注类别（`guard/judge.ts` 的 `pathRule`、`categoryTagRule`）；
- 还要过 v1 规则模板第 1 条（`guard/rule-templates.ts` 的 `backupBeforeOverwrite`）：没有 git 提交、也没先 `cp` 备份的就**按规则退回**，计入拉回次数（累计被拒 5 次会暂停任务）。

agent 自己刚写的临时脚本、中间数据想重写或删掉，也要先备份一份，或者被退回——这就是用户说的"拦住了"。

改成：

- **任务自己的临时文件**不落入"删除或覆盖"类别，也不受 v1 第 1 条约束（不退回、不计拉回、不标敏感）。认法：
  1. 在这个任务的范围里（项目工作目录、任务的工作目录这些它本来就能写的地方）；
  2. **是这个任务开始之后才有的**：效果日志里有这个任务的 agent 新建它的记录（写入时它还不存在），或者文件的创建时间晚于任务开始（脚本里间接生成、守卫没看见的文件也认得出）；同一个任务的前几个阶段、定时任务的前几次运行建的也算这个任务的；
  3. **不是交付件**：任务产出区（`outputs/<任务>/`）里的文件、计划里各阶段交付件写到的路径，**一旦那个阶段交出去了**（提交验收 / 阶段完成）就算交付件，照旧受保护；还在做那个阶段时，agent 改自己正在写的交付件草稿不拦。项目档案（立项书、规格、进展……）一律不算临时文件。
- **照旧受保护的**："系统已有的"——任务开始之前就在的文件（不管是谁建的，包括以前别的任务做的）、配置、数据，和已经交出去的交付件：删除、整体重写照旧落入"删除或覆盖"、照旧要先备份或提交。认不出是不是临时的（比如路径没法确定、创建时间读不到又没有效果日志记录）的，按"已有的"算。
- 递归删除一个目录：里面全是这个任务的临时文件才放开；夹着已有的或交付件的，照旧。
- 不碰的：受保护区域、密钥区、子 agent 不能写项目档案、围栏、越出项目目录、项目外 `rm -rf` 一律禁止、三条硬底线；秘书（草稿区本来就不受约束，草稿区外照 101 号票）；没有任务的维护者直接对话照旧（写在 Comments）。
- 效果日志、时间线里照旧记下这些调用（能查），只是不标敏感、不算拉回。

## Acceptance criteria

- [ ] 守卫单元测试：任务里新建的脚本重写、删除不落类别、不退回；任务开始前就在的文件照旧落类别、照旧退回；已交出去的交付件照旧；还在做的阶段里改自己的交付件草稿不拦；认不出的按已有的；递归删除目录的两种情况；创建时间晚于任务开始的（脚本间接生成的）认作临时。
- [ ] 主切面测试：一个长程任务里维护者写脚本 → 改脚本 → 跑脚本生成交付件 → 删脚本和中间数据，全程没有退回、没有拉回计数、阶段照常推进；删上一个任务留下的文件照旧退回。可以照现有的 `deviation.test.ts`、`tasks.test.ts` 的剧本写法。
- [ ] 规格第 9 节（"删除或覆盖"的定义、v1 第 1 条、默认处置表那一行）跟着改；`docs/dev.md` 跟着改。
- [ ] 动了守护进程：全量测试一次，typecheck、oxlint 通过。
