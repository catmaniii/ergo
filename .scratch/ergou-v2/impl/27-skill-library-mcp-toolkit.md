# 27 — skill 库、MCP 登记与工具包调整

## What to build

二狗有了自己的 skill 库：框架自带的一批（第一阶段为空或只有示例），加上数据目录 skill 区里用户自己加的。它不自动读取 `~/.claude/skills`；intent-mining、reasoning-graph 这类现成的 skill，要用就在设置里的 skill 库页显式导入一份。MCP 先在二狗里登记（配置区），再写进项目或任务的工具包，授权给它。MCP 服务进程由守护进程拉起、放进 Job 对象，凭据由守护进程按登记注入；agent 经守护进程转发调用 MCP 工具，碰不到凭据；它们不是服务，不在 LSM 登记。每个维护者的会话都严格按工具包装配：只加载工具包里列的 skill，工具白名单按工具包来、有 skill 时含 `read`，不读 `~/.pi`、`~/.claude/skills` 和 CLI 认证。秘书还多了一种快速动作：调用一个已登记、并授权给秘书快速动作的 MCP 工具（参数固定）。

用户在项目页和任务详情里看、改工具包：skill 名单、MCP 名单、bash 开关、联网开关，扩大和减少都可以直接改，不用走计划变更。维护者可以自己增减 skill，每次增减记进时间线；开 bash、加 MCP、开联网要用户批准——在任务里走计划变更（卡上列出"工具包变更"），不在任务里时提交一张"工具包变更"卡；减少能力随时可以。工具包一变就立即生效：用户批准（或自己在项目页、任务详情里改）之后，以及维护者自己增减 skill 之后，守护进程等这个维护者做完手头这一步，就重启它的子进程，按新工具包重新装配会话，从会话文件接着干；代价是那一次的提示词前缀缓存失效。联网开关关着时，联网的工具和命令直接拒绝，脚本执行前先扫一遍、用到联网的库或函数就拒绝，脚本进程设一个无效的代理地址（和秘书一样是尽力而为）；开着时，只读的 GET 不落入关注类别，非 GET 的请求算"以我的名义对外发送"。

演示：在设置的 skill 库页导入一个 skill 目录，在项目页把它加进工具包，唤起维护者时会话里只有这一个 skill，`~/.claude/skills` 里的一个都没有；再让维护者在任务里要求开联网，待我处理出现带"工具包变更"的计划变更卡，只有受影响的阶段停下，批准后工具包里联网开关打开，维护者做完手头这一步后子进程重启、接着原会话干，这时已经能联网。

## Acceptance criteria

- [x] pi 契约测试里加上对应用例：按工具包装配的会话只含工具包列出的 skill（经 `additionalSkillPaths`，`noSkills: true`），工具白名单与工具包一致、有 skill 时含 `read`；测试机的 `~/.pi` 和 `~/.claude/skills` 里预先放了配置和 skill，装配出的会话里一个都没有，也不用 CLI 认证；同一个会话文件换一套工具包重新装配后能接着原来的对话继续，新加的 skill 和工具可用，去掉的不在。
- [x] 主切面：skill 库列出框架自带的和数据目录 skill 区里的 skill；经 skill 库页导入的 skill 复制一份进 skill 区，能被列出、能写进工具包；`~/.claude/skills` 里的不出现在 skill 库里。
- [x] 主切面 + 守卫切面：在配置区登记 MCP（每个 MCP 工具登记类别标签、参数规则和"只读或幂等"标记，进入工具注册表）后，只有工具包里授权了它的项目或任务，其维护者会话里才有这些工具。守护进程拉起 MCP 服务进程、放进 Job 对象、按登记注入凭据；agent 子进程和它的孙进程环境里都没有这些凭据；agent 的调用先过守卫、按登记的类别判定，再由守护进程转发给 MCP 服务进程；守护进程被杀时 MCP 服务进程一起结束；它们不在 LSM 登记。
- [x] 守卫切面 + 主切面：bash 开关关着时会话里没有 bash 工具（也没有 28 号票的带类型特殊 bash 工具），开着时有。联网开关关着时，会话里没有联网类工具，从 bash 拆出的联网命令（不论 GET 还是 POST）直接拒绝；脚本执行前扫到联网的库或函数就拒绝，给模型的说明里写明要联网须申请开联网；脚本进程的环境里设了无效的代理地址。联网开关开着时，只读的 GET 不落入关注类别，非 GET 的请求落入"以我的名义对外发送或发布"。
- [x] 主切面：维护者调用增减 skill 的工具，只能从 skill 库里选；每次增减写进工具包并记进时间线，任务详情或项目页的维护者会话里能看到这一条；这次调用结束后，守护进程重启它的子进程、按新名单重新装配会话，从原来的会话文件接着干，下一次模型调用里就是新的 skill 名单，不用等下一段会话。
- [x] 主切面：任务执行中维护者要开 bash、加 MCP 或开联网时，只能提交计划变更（沿用 14 号票），卡上的"工具包变更"一栏列出要加的能力；项目维护者不在任务里时要加这些能力，提交一张"工具包变更"卡进待我处理。两种情况下批准前工具包不变（任务里只有受影响的阶段停下），批准后工具包扩大并按下一条的做法立即重新装配，被拒绝则不变；批准、拒绝或收窄产生对应的素材事件（审批决定；由 08 号票采集）。
- [x] 主切面：用户在项目页或任务详情里直接扩大或减少工具包（增减 skill、MCP，开关 bash、联网），改完即写进工具包，不出计划变更卡；维护者减少能力也随时可以。改完后守卫的下一次判定就按新工具包，被去掉的能力用不到；维护者正在干活时，守护进程等它做完手头这一步就重启子进程、按新工具包重新装配会话并从会话文件接着干，新加的 skill、MCP 工具和 bash 在下一次模型调用里就可用、去掉的不再出现；子进程不在（维护者休眠）时不用重启，下次拉起即按新工具包装配。
- [x] 主切面：秘书提议"调用 MCP 工具"的快速动作时，只能选登记里标明授权给秘书快速动作的 MCP 工具，参数按登记固定；按 21 号票的确认规则执行，由守护进程转发调用，不拉起任何 agent，聊天里留"已执行"卡，执行事件进事件日志。
- [x] 界面：项目页和任务详情都有工具包区，显示 skill 名单、MCP 名单和 bash、联网两个开关，用户能在这里扩大或减少，改动即时显示；设置里有 skill 库页，列出全部 skill 并提供导入入口；待我处理里能处理"工具包变更"卡。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：立项时维护者提议的工具包随立项书一起确认、开发类项目默认带 bash 归 15 号票；计划卡上确认任务的工具包归 12；计划变更卡、"只停受影响阶段"归 14，本票给它加上"工具包变更"的内容和不在任务里时单独的那张卡；子 agent 的工具包不超过维护者归 20；评审子 agent 的固定只读工具包归 13；跨项目任务维护者的固定工具包（读项目档案、派工单、汇总回执）归 17；带类型的特殊 bash 工具本身归 28。秘书的工具是固定的，不走工具包。
- 联网开关关着时的做法和秘书不能联网（07 号票）是同一套：联网工具和命令直接拒绝、脚本先扫、无效代理地址，不是硬隔离，等以后加沙箱。联网命令在守卫里怎么判（关着拒绝，开着 GET 不落类别、非 GET 算对外发送）在 03 号票的判定函数里，本票把工具包的联网开关接进判定的输入，并给维护者的脚本加上扫描和代理设置。
- 快速动作的执行器注册表、"明确点了"的运行时判定和"已执行"卡归 21 号票；本票只往注册表里加"调用 MCP 工具"这一种动作。哪些 MCP 工具授权给秘书快速动作、参数固定成什么，写在配置区的 MCP 登记里。
- 配置模块只读：MCP 登记就是用户编辑数据目录配置区里的登记，二狗读取；配置区是受保护区域，agent 写不进去。
- bash、MCP 这类工具要进会话的工具白名单、skill 要经 `additionalSkillPaths` 进会话，都得在装配会话时给，所以工具包一变就重启子进程重新装配（第 21 节"工具包变了立即生效"）。"做完手头这一步"取插话的时机：当前的工具调用结束、下一次模型调用之前（13 号票）。重启沿用 12 号票闲置退出后重新拉起、接着原会话的做法；因为等这一步做完才重启，会话文件里没有做了一半的回合，不需要 23 号票被杀后的那套恢复。那一次的提示词前缀缓存失效是接受的代价。秘书的工具固定，不涉及这条。
- 重新装配时，固定上下文里的工具包说明随之更新，并追加一条"工具包已变更：……"消息告诉维护者；"做完手头这一步"指当前工具调用结束、下一次模型调用之前。
- 维护者的经验按项目存在项目档案里，不自动提炼；reasoning-graph 要等用户导入 skill 库后才能用。

## Comments

实现记录（2026-10-08，worktree 分支 `worktree-agent-a1e8e7a5f093698ce`，变基到 18 号票之后）。说明见 `docs/dev.md`"skill 库、MCP 登记与工具包"一节和 ADR-0018。规格第 20 节的"工具包的细则"（评审后补的）照做了。

**拿不准、按下面理解做了的地方：**

- **"做完手头这一步"的实现**：宿主协议升到 10（变基时 main 是 9），加命令 `yield` 和回合结局 `yielded`。子进程那一层包一层 pi 的 `agent.finishTurn`：收到 `yield` 后，这一轮模型那一步调了工具、结果都回来了，就在下一次模型调用之前结束回合；模型那一步已经不调工具（在写最后的回复）时照常结束，之后和闲着时一样。停下时排着、还没送进上下文的插话由子进程清掉队列并扣除，不算收下，守护进程照样留在队里。守护进程这一层是 `AgentSession.reassemble(notice)`：回合以 `yielded` 结束后按新装配拉起、接着同一个会话，把"工具包已变更：……"作为一条输入交过去，原来那条输入接着算在处理中（接着的这一轮结束时才记成处理完，`turn_end` 只有一个 `completed`）。闲着时停掉子进程、休眠时什么都不停，"工具包已变更"跟在下一条输入后面作上下文消息。
- **和范围审视（18 号票）配合**：审视在做时不换装配。闲着时的停子进程沿用 18 号票 `restartWhenIdle` 的检查；按 `yield` 停下后的重新拉起（`resumeTurn`）也等审视兑现之后才停旧的子进程，等的这段时间不送插话，再来的工具包变更并进同一句"工具包已变更"。
- **前缀缓存**：规格说"那一次的提示词前缀缓存失效是接受的代价"，照这个说。pi 接着已有会话、发现系统提示或工具变了时记一条系统消息（新的系统提示，加了、去掉了哪些工具）；faux 认会话中途的系统消息，照样追加，第一阶段的 deepseek-flash 不认，pi 发给它时把更新后的系统提示放回开头、工具列表整份重发，所以那一次缓存失效。契约测试只核对模型眼里现在的样子（新的 skill 段、加了去掉了哪些工具）。（第一版这里写成"开头的前缀照样命中"，是错的，评审后改回。）
- **MCP 服务进程什么时候拉起**：按需——会话装配时在后台拉起（拿服务进程报的参数说明），或者第一次调用时；登记改了下次用到时按新的重起。第一次装配时服务进程还没回话，模型看到的参数说明依次取登记里的 `inputSchema`、服务进程报的、宽松的 `{ type: "object" }`（下一次装配就是服务进程报的）。
- **每个 MCP 一个 Job 对象**（句柄关闭即结束），不放进 agent 管家的 Job（那里的孤儿回收会误杀）。闸门进程和带类型的 bash 工具共用（`process/gated-spawn.ts`、`process/gate-main.ts`）。客户端自己写（`initialize`、`tools/list`、`tools/call`、取消通知），不引入 MCP SDK。
- **凭据**：登记里写 `{ "fromEnv": "变量名" }`，从守护进程的环境里取（由 LSM 注入守护进程），登记文件里没有凭据本身；缺了照样拉起，日志写明缺了哪些。服务进程的环境是系统变量白名单加登记里的变量。注入的凭据值不出守护进程：服务进程的 stderr、不是 JSON 的输出、起不来的原因进日志之前，工具结果（含报错）交给 agent、写进事件日志之前，服务进程报的工具说明给模型看之前，都用 `redactSecretValues` 擦掉。
- **MCP 工具不写联网标记按要联网算**（规格已补）；联网关着时会话里没有要联网的 MCP 工具，也没有要联网的带类型 bash 工具（推送、建远端仓库、装依赖：`typedShell.toolsFor` 按开关过滤），调用也硬拒绝（说明里写"提交工具包变更申请开联网"）。带类型工具自己的联网检查留作第二道。pi 的 grep、find 联网关着时不给（07 号票就有）。
- **skill 不是权限**（规格已补）：执行时 skill 取项目工具包和任务的并集，bash、联网、MCP 取交集（`effectiveToolkit`）。项目的任务里维护者加 skill 只记在任务上，项目页的工具包不变；去掉 skill 只影响它所在那一层，项目工具包里也有的照样在（工具结果里写明）。
- **名字的检查**：skill 要在库里、MCP 要登记了。用户改工具包、维护者提交计划、自行调整计划、提交计划变更都查（`toolkits.nameProblems`），不在就拒绝并说明。
- **任务的工具包直接改**：任务结束了、计划还没确认时不能改。有计划变更卡在等时照样能收窄，扩大（开 bash、开联网、加 MCP）要等卡处理完；加 skill 不算扩大，也可以。之后确认这张卡时，卡上计划的基础版本和现在生效的只差工具包的，就把用户在这期间的增减补到卡上的计划里，作为最新的一版生效（卡上要加的和用户收窄的都在）；差别不只工具包的照旧算过时。改完现在生效的计划换一版（只改工具包，`task_plan` 推给前端）。
- **守卫用此刻的工具包**：每次判定把拉起时的守卫视角收窄到现在的工具包（`narrowedGuardAgent`：bash、联网取两边都开的，工具清单去掉现在不在工具包里的 MCP 的工具），子进程重新装配之前同一步里剩下的调用就被拒；正在等审批的调用被批准时也按此刻的重判，硬拒绝就不执行。加上的能力要等重新装配、会话里有了才算（会话里本来就没有那个工具）。项目维护者、任务维护者、子 agent 都这样。
- **工具包变更卡**：维护者一次申请里有减少也有增加时，减少的直接生效、增加的出卡；每个项目同时只有一张在等（再申请被拒、说明在等哪张）。批准时按**现在的**工具包加上要加的能力（期间用户改过的不被覆盖）。批准、拒绝都给维护者发一条通知；批准后的重新装配还会带一句"工具包已变更"，两句意思有重叠，可以接受。
- **直接改工具包也算审批决定素材**（情境 `toolkit:edited`），批准、拒绝的是 `card:toolkit_change`；减少能力（维护者自己减）不产生素材，只记时间线。
- **秘书的 MCP 快速动作**：类型 `mcp_call`，参数只有 `tool`（`<MCP 名>/<工具名>`），参数按登记固定。"点明"= 用户这一轮的原话里原样有登记写的快速动作说法（`quickAction.title`），否则按这个工具登记的类别判（给快速动作执行器加了可选的 `watchFor`，按动作给关注，和会话里 MCP 工具的登记同一份 `guardFieldsOf`）。快速动作的执行器改成二选一、类型上分开：当场做完的写 `execute`，要等外面回话的写异步的 `perform`。点明直接执行的等结果回来才出"已执行"卡（卡上写结果）；在卡上确认的，卡先记成已处理（"正在执行……"），结果回来后补上卡片的结果和操作记录（没做成的照样记，`ok: false`）。秘书的工具固定，快速动作只看登记里的授权，不看工具包。
- **导入 skill 的规矩**：绝对路径、是目录、不在数据目录里、`SKILL.md` 开头有 frontmatter（`name` 不写取目录名；只能小写字母、数字、短横线），有 `description`，库里不重名（和框架自带的同名也不行），不超过 2000 个文件或 20 MB；符号链接不复制。skill 库页没有"移除"（原型里有，规格没要求）：删掉 skill 区里的目录即可，工具包里引用了已不在库里的 skill 时装配跳过并记日志。
- **子 agent 不拿 skill 和 MCP**：20 号票的交集只取带类型的 bash 工具，没改。
