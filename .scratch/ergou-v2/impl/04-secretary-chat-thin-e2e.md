# 04 — 秘书聊天最薄端到端

Status: ready-for-agent
Blocked by: 01（工作区骨架与 agent 子进程 spike）, 02（Web UI 骨架与可点击原型）
Spec: [第一阶段规格](../spec.md) 第 1 节（工程与总体架构）、第 4 节（存储与事件）、第 5 节（前端协议）、第 6 节（访问与设备配对）、第 7 节（秘书）、Testing Decisions（守护进程对前端的协议）

## What to build

用户在 PC 上打开本机地址，进入秘书页，打一句话发出去，看到秘书逐字回复；刷新页面，历史还在；网断了再恢复，不用刷新就补上错过的内容；两个浏览器窗口同时开着，看到的一样。演示用的守护进程从本票起在 Local Service Manager 登记、由它启动：`ergou-daemon` 条目指向主分支的构建产物，开发期间的演示都经 LSM 启动。

这一刀纵向穿过整个系统：事件存储（事件日志是唯一真相，按频道编号，带幂等键，派生视图在追加事件的同一事务里更新）、网关的本机端口（只听 127.0.0.1，校验 Origin 和 Host）、WebSocket 上的三种帧、用 TypeBox 定义在共享协议包里的协议、常驻子进程里的秘书主线会话、流式（增量只推送不落盘）、断线按序号补发。02 号票的秘书页从这里起接真数据，其他页面仍是假数据。

同时搭好主切面（切面 1）的测试底座：用临时数据目录起一个真的守护进程，模型换成 faux provider 按剧本回话，测试扮演前端，通过 WebSocket 和 HTTP 收发并断言；agent 子进程真的拉起。之后的票都在这个底座上加场景。

## Acceptance criteria

- [ ] 事件存储：事件为 `{全局序号, 频道, 频道内序号, 类型, 负载, 时间, 幂等键}`，频道内序号连续；同一个幂等键追加两次只留一条，第二次拿到第一次的结果；派生视图和事件在同一事务里写，事务失败时两者都不落；清空派生视图后能从事件日志整体重建，结果和重建前一致。库为 `ergou.db`（WAL）。
- [ ] 本机端口只监听 127.0.0.1，端口号从配置读；HTTP 和 WebSocket 请求的 Origin 或 Host 不对时被拒（主切面覆盖 DNS 重绑定和跨站 WebSocket 两种情形）；本机信任只看从哪个端口进来，不看来源 IP。网关提供 Web UI 静态文件和健康探针 `/healthz`；页面脚本里没有任何私钥或令牌。
- [ ] 共享协议包用 TypeBox 定义：三种帧（请求 `{id, 方法, 参数, 幂等键?}`、响应 `{id, 成功与否, 结果或错误}`、事件 `{频道, 序号, 类型, 负载}`）、全部频道（秘书会话、维护者会话、任务看板、项目列表、待我处理、卡片、活动状态）、消息信封 `{id, 会话, 发言方, 时间, parts}` 和规格第 5 节的全部 part 类型（工具调用 part 带工具名、参数摘要、命中的关注类别、判定、是否授权内、是否通用 bash；本票用不到的先定义好）。守护进程和 Web 都用它生成的类型；格式不对的请求得到错误响应，连接不断。
- [ ] 秘书常驻：守护进程启动时拉起秘书的子进程，一条长期主线会话，模型 `deepseek-flash` 并显式设置思考档位（测试里换成 faux provider），系统提示固定，不含用户卡和记忆简报。主切面：前端发一条带幂等键的文本消息 → 收到用户消息事件 → 收到秘书回复的流式增量 → 收到定稿消息；同一幂等键重发，不会多出消息，也不会多一次回复。
- [ ] 流式：增量只推送、不落盘，每 100 毫秒最多推一次；事件日志和秘书会话的派生视图里只有定稿后的 part（文本；有推理时另有一个默认折叠的推理 part）。秘书正忙时连发两条消息，按顺序逐条处理，输入队列放在事件日志里，不放内存。
- [ ] 重连：前端带上每个频道最后收到的序号重连，服务端按序补发缺失的落盘事件，不重不漏，不补中间增量；前端乐观显示的尾巴被权威事件替换。主切面和前端状态层回放各有一条用例。
- [ ] 主切面测试底座：临时数据目录、真守护进程、faux provider 剧本、模拟前端（WebSocket + HTTP）、真拉起的子进程；测试里起的守护进程实例用完即销毁，不在 LSM 登记。能把一次场景收到的事件流录下来供前端状态层回放测试使用，并至少录一段秘书聊天，替换 02 号票里手写的事件序列。
- [ ] LSM 登记与演示（手动验证）：`ergou-daemon` 在本机 LSM 登记，指向主分支的构建产物，用固定的 Node 22 LTS 绝对路径启动，健康探针 `/healthz` 返回健康，条目开了 autoRestart；模型 key 由 LSM 从密钥目录注入（`env.from: file`），守护进程从注入的环境里取，再按 01 号票的做法显式交给秘书子进程。由 LSM 启动后在 PC 本机地址打开秘书页：发消息后看到逐字输出；刷新后历史还在；断网再恢复，不刷新就补上；两个窗口同时开着，内容一致。其他页面仍是假数据。
- [ ] 产生对应的素材事件：用户消息事件的负载里有会话、发言方、时间和原文，足够 08 号票采集为"用户发言"素材（08 尚未完成，本票保证事件类型和负载就绪）。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 秘书的另外四种回复形态都是只产生卡片的自定义工具，不在本票：简单提醒（06）、建议发起任务（12）、建议立项（15）、快速动作（21）。
- 不在本票：图片和文件、历史分页、发给模型前的投影（09）；卡片和待我处理（06）；工具调用 part 的实际产生和守卫（07）；外网端口和设备配对（10）；agent 管家的上限与超时（12）；秘书专用压缩指令（22）；被杀后丢掉半截回复、从最后一个完整回合续上，以及输入队列在重启后的恢复（23）；活动状态频道的内容（25，本票只定义频道）。
- 事件存储和主切面的测试底座在本票（规格 Further Notes 已按此写明）。
- 推理 part 随本票做：秘书显式设置了思考档位，回复里就会带推理。
- LSM 的分工：本票按规格第 1 节做 `ergou-daemon` 条目本身（固定 Node 22 LTS 绝对路径、`/healthz`、autoRestart、密钥注入、指向主分支的构建产物），从此开发期间的演示都经 LSM 启动，二狗自己不启动任何服务；link 协议在有任务执行时上报"忙"、autoRestart 重启之后的恢复（第 17 节）由 23 号票补上；`ergou-tunnel` 条目在 10。自动测试里在临时目录起的守护进程实例是测试的一部分，不算服务。
