## What to build

用户在 PC 上打开本机地址，进入秘书页，打一句话发出去，看到秘书逐字回复；刷新页面，历史还在；网断了再恢复，不用刷新就补上错过的内容；两个浏览器窗口同时开着，看到的一样。演示用的守护进程从本票起在 Local Service Manager 登记、由它启动：`ergou-daemon` 条目指向主分支的构建产物，开发期间的演示都经 LSM 启动。

这一刀纵向穿过整个系统：事件存储（事件日志是唯一真相，按频道编号，带幂等键，派生视图在追加事件的同一事务里更新）、网关的本机端口（只听 127.0.0.1，校验 Origin 和 Host）、WebSocket 上的三种帧、用 TypeBox 定义在共享协议包里的协议、常驻子进程里的秘书主线会话、流式（增量只推送不落盘）、断线按序号补发。02 号票的秘书页从这里起接真数据，其他页面仍是假数据。

同时搭好主切面（切面 1）的测试底座：用临时数据目录起一个真的守护进程，模型换成 faux provider 按剧本回话，测试扮演前端，通过 WebSocket 和 HTTP 收发并断言；agent 子进程真的拉起。之后的票都在这个底座上加场景。

## Acceptance criteria

- [x] 事件存储：事件为 `{全局序号, 频道, 频道内序号, 类型, 负载, 时间, 幂等键}`，频道内序号连续；同一个幂等键追加两次只留一条，第二次拿到第一次的结果；派生视图和事件在同一事务里写，事务失败时两者都不落；清空派生视图后能从事件日志整体重建，结果和重建前一致。库为 `ergou.db`（WAL）。
- [x] 本机端口只监听 127.0.0.1，端口号从配置读；HTTP 和 WebSocket 请求的 Origin 或 Host 不对时被拒（主切面覆盖 DNS 重绑定和跨站 WebSocket 两种情形）；本机信任只看从哪个端口进来，不看来源 IP。网关提供 Web UI 静态文件和健康探针 `/healthz`；页面脚本里没有任何私钥或令牌。
- [x] 共享协议包用 TypeBox 定义：三种帧（请求 `{id, 方法, 参数, 幂等键?}`、响应 `{id, 成功与否, 结果或错误}`、事件 `{频道, 序号, 类型, 负载}`）、全部频道（秘书会话、维护者会话、任务看板、项目列表、待我处理、卡片、活动状态）、消息信封 `{id, 会话, 发言方, 时间, parts}` 和规格第 5 节的全部 part 类型（工具调用 part 带工具名、参数摘要、命中的关注类别、判定、是否授权内、是否通用 bash；本票用不到的先定义好）。守护进程和 Web 都用它生成的类型；格式不对的请求得到错误响应，连接不断。
- [x] 秘书常驻：守护进程启动时拉起秘书的子进程，一条长期主线会话，模型 `deepseek-flash` 并显式设置思考档位（测试里换成 faux provider），系统提示固定，不含用户卡和记忆简报。主切面：前端发一条带幂等键的文本消息 → 收到用户消息事件 → 收到秘书回复的流式增量 → 收到定稿消息；同一幂等键重发，不会多出消息，也不会多一次回复。
- [x] 流式：增量只推送、不落盘，每 100 毫秒最多推一次；事件日志和秘书会话的派生视图里只有定稿后的 part（文本；有推理时另有一个默认折叠的推理 part）。秘书正忙时连发两条消息，按顺序逐条处理，输入队列放在事件日志里，不放内存。
- [x] 重连：前端带上每个频道最后收到的序号重连，服务端按序补发缺失的落盘事件，不重不漏，不补中间增量；前端乐观显示的尾巴被权威事件替换。主切面和前端状态层回放各有一条用例。
- [x] 主切面测试底座：临时数据目录、真守护进程、faux provider 剧本、模拟前端（WebSocket + HTTP）、真拉起的子进程；测试里起的守护进程实例用完即销毁，不在 LSM 登记。能把一次场景收到的事件流录下来供前端状态层回放测试使用，并至少录一段秘书聊天，替换 02 号票里手写的事件序列。
- [ ] LSM 登记与演示（手动验证）：`ergou-daemon` 在本机 LSM 登记，指向主分支的构建产物，用固定的 Node 22 LTS 绝对路径启动，健康探针 `/healthz` 返回健康，条目开了 autoRestart；模型 key 由 LSM 从密钥目录注入（`env.from: file`），守护进程从注入的环境里取，再按 01 号票的做法显式交给秘书子进程。由 LSM 启动后在 PC 本机地址打开秘书页：发消息后看到逐字输出；刷新后历史还在；断网再恢复，不刷新就补上；两个窗口同时开着，内容一致。其他页面仍是假数据。
- [x] 产生对应的素材事件：用户消息事件的负载里有会话、发言方、时间和原文，足够 08 号票采集为"用户发言"素材（08 尚未完成，本票保证事件类型和负载就绪）。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

  - 入口和 stop 钩子有自动测试（`test/main/entry.test.ts`）：只给 `ERGOU_DATA_DIR`、端口从配置读，起来后写 pid 文件，`/healthz` 报秘书闲着；stop 钩子核对 pid 文件后结束进程、端口放出，再停一次也成功；pid 文件里是别的进程、启动时间对不上、没有 pid 文件时什么也不做并说明原因。
  - 用临时数据目录、faux 秘书、真实的 Web 构建产物做过一次性的无头浏览器冒烟（脚本前台跑完即停，没留进程）：秘书页发消息 → 先显示折叠的推理和"正在回复…"→ 定稿；刷新后历史还在；第二轮照常。
- **协议的几处约定**（规格没写死的，取最贴近规格的做法）：
  1. 三种帧不加类型标记字段，按结构区分（事件帧有 `channel`，响应帧有 `id` 和 `ok`），和规格的形状一致。请求帧连 `id` 都读不出来时，错误响应的 `id` 为 `null`。
  2. **订阅即握手**：方法 `subscribe` 带协议版本和 `{频道: 最后收到的序号}`；版本不一致回 `protocol_mismatch`，前端提示刷新页面。服务端先回响应，再补发序号更大的落盘事件，之后实时推送。
  3. **重新同步**：前端带来的序号比某个频道的最后序号还大（比如数据目录恢复成了旧快照）时，订阅响应的 `resync` 点名这个频道，服务端从头补发；前端清掉这个频道的状态（还没确认的乐观显示留着）。主切面和前端回放（录制的 `secretary-resync`）各有用例。
  4. **流式增量是临时事件**：类型 `stream`，序号沿用所在频道当时最后一条落盘事件的序号（不占序号、不补发）；负载 `{ messageId, deltas: [{ part, type, offset, text }] }`，`messageId` 就是定稿消息的 id（守护进程生成 `m-<uuid>`），前端原地替换。每段增量带 part 下标和字符偏移，前端据此发现漏掉的增量，对不上就只显示"正在回复…"等定稿。节流按会话每 100 毫秒最多一帧，换了一条消息也一样；定稿时还没推出去的增量直接丢掉。
  5. **输入队列在事件日志里**：用户消息事件进队，交给秘书时追加 `turn_start`，处理完追加 `turn_end`（`{ inputMessageId, outcome, error? }`）出队；派生视图 `agent_inputs` 记着每条是等着、正在处理还是处理完。内存里只记"正在处理哪一条"。
  6. **处理到一半被打断的输入不重送**：秘书子进程崩溃、或守护进程重启时，有 `turn_start` 没 `turn_end` 的那条以 `interrupted` 结束出队，会话里追加一条系统说明"上一条消息「…」处理时中断了，秘书没有接着处理；需要的话请重发。"；排在它后面、还没开始的照常处理。从会话文件最后一个完整回合续上归 23 号票。
  7. 本票只收秘书会话的文本 part：发给维护者会话、带图片或文件的回 `not_implemented`（13/16、09 放开）；空白消息回 `bad_params`；`card_action` 回 `not_implemented`（06）。
  8. 时间格式只有一份：共享协议包的 `nowIso()`（带时区偏移的本地 ISO 时间，精确到毫秒），守护进程和 Web 都用它。
- **网关**：Host 只认 `127.0.0.1:<端口>` 和 `localhost:<端口>`；带了 Origin 就必须是这两个源（`null` 也拒）；不带 Origin 的本机程序（LSM 探针、命令行）放行。`/healthz` 返回 `{ ok, secretary, webUi, reasons }`：秘书不在运行超过阈值（默认 30 秒）或 Web UI 没构建时不健康、回 503 并写明原因。"页面里没有私钥或令牌"由主切面的一条用例现场构建真正的 Web UI、经本机端口取回来扫一遍，`npm run check` 一条命令就覆盖到。
- **秘书**：模型 `deepseek/deepseek-flash`，思考档位显式设为 `high`（pi 目录里这个模型支持 low / high / max）；没有工具（草稿区在 07）；系统提示固定（`secretary/system-prompt.ts`，替换掉 pi 默认的编程助手提示）；**每次拉起接着会话目录里最近的那个 pi 会话**（宿主协议的装配参数加了 `systemPrompt`、`continueSession`，pi 契约测试各加了用例），守护进程重启后还是同一条主线。子进程意外退出时按 1 秒起、翻倍、最多 30 秒的间隔重新拉起。
- **LSM 的 stop 钩子**：`packages/daemon/src/stop.ts` 和守护进程读同一份配置（数据目录、端口）；守护进程启动后在数据目录根下写 `daemon.pid`（pid、进程启动时间、端口），stop 钩子先核对"监听端口的就是这个进程、启动时间也对得上"（启动时间用 kernel32 的 `GetProcessTimes` 取）才结束它，否则什么也不做、说明原因、非零退出。没有 stop 钩子 LSM 拼不出 restart；守护进程按"随时可能被杀"设计，结束进程就是它的停机方式。
