# 24 — token 账本与消耗页

Status: done
Blocked by: 13（任务执行与阶段验收）
Spec: [第一阶段规格](../spec.md) 第 16 节（token 账本与消耗）、第 2 节（守护进程的模块）、第 3 节（agent 子进程与 pi 封装层）、第 10 节（范围审视）、第 19 节（Web UI）、第 21 节（实现细节补充）

## What to build

每次模型调用，运行时都从 pi 返回的用量里在 token 账本记一条：归属（任务、项目或定时作业）、agent、会话、模型、输入（缓存命中 / 未命中）、输出、时间。用户在任务看板的每张任务卡上看到这个任务的 token 总量；打开任务详情，看到按 agent（包括子 agent）细分的用量。范围审视的用量记在对应维护者的任务或项目名下，标"范围审视"；定时作业的用量记在作业名下。

"更多"里有一个全局"消耗"页：按天、按 agent 汇总用量，秘书单列为系统开销；选一个时间范围，页面用用量乘配置里的单价给出成本，并标明"粗估"。不做按时段计价。

演示：用 faux provider 跑一个任务，剧本里每次回话带固定的用量；看任务卡上的总量随每次调用增长，任务详情里维护者和评审子 agent 各占一行；打开消耗页，看到当天的汇总和单列的秘书系统开销，选今天这个时间范围，看到标着"粗估"的成本。

## Acceptance criteria

- [x] 主切面：秘书主线的调用也记账，归属为空、agent 为秘书；消耗页的数据按天、按 agent 汇总，秘书的用量单列为"系统开销"，不计入任何任务、项目或作业。
- [x] 主切面：范围审视那次模型调用（在维护者自己的子进程里另开一次，18 号票）照常经子进程上报用量，账本里记在该维护者当时所属的任务名下，不在任务里时记在项目名下，并标"范围审视"；任务详情里这部分单独可见，计入任务卡上的总量。
- [ ] 主切面（可注入时钟）：定时作业每次运行的用量（含执行它的项目维护者或作业自己的维护者）记在该作业名下，不算系统开销；看板上的作业卡和任务卡一样显示作业名下的总量。
- [x] 主切面 + 前端状态层回放：任务看板上每张任务卡显示该任务的 token 总量，每次新的模型调用后经看板频道更新；用录下的事件流回放，任务卡上的总量与账本一致。
- [x] 主切面：任务详情按 agent 细分该任务的用量，维护者、评审子 agent（以及 20 号票的并行子 agent）各占一行，各行之和等于任务卡上的总量。
- [x] 主切面：选一个时间范围，成本等于该范围内的用量乘配置里的单价，结果标明"粗估"；改配置里的单价后再算，结果随之变化；不按时段区分单价。
- [x] 界面：任务页的任务卡和作业卡显示 token 总量；任务详情显示按 agent 的细分；更多 → 消耗页显示按天、按 agent 的汇总、单列的系统开销、时间范围选择和标着"粗估"的成本。
- [x] pi 契约测试里加上对应用例：能拿到每次模型调用的用量，含缓存命中和未命中的输入 token（14 号票若已加了用量用例，在它上面补缓存命中、未命中的断言，不另写一份）。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：预算（token 加工具调用次数）超 1 倍让维护者说明、超 2 倍问用户归 14 号票；两边对同一任务的 token 计数应同源，都来自子进程上报的用量事件，不要各数一套。计划卡上的 token 粗估归 12 号票。
- 子 agent 的细分依赖 20 号票让子 agent 上报的用量带上子 agent 身份和所属任务；20 未完成时，至少 13 号票的评审子 agent 要能单独成行。
- 归属怎么定：执行某个任务工单的项目维护者（16、17 号票），用量按工单的所属任务记到该任务名下；项目维护者不在任务里时（立项问答、用户直接对话），记在项目名下；定时作业的一次运行，不论是作为工单交给项目维护者还是由作业自己的维护者执行，都记在作业名下（作业身份由 19 号票随用量事件带上；19 若后完成，本票先用构造的、带作业身份的用量事件验证，作业卡上的总量等 19 完成后接上）。
- 范围审视在维护者的子进程里跑（第 10 节），用量和其他调用走同一条上报路径，只多一个"范围审视"标记；18 号票若后完成，本票先用构造的、带这个标记的用量事件验证。
- 单价放在数据目录的配置区，配置模块只读。
- 对应用户故事：38、135–137。

## Comments

- **实现**（2026-10-08）：守护进程新模块 `ledger/`（`daemon.ledger`）；agent 管家收到子进程的 `usage` 连同会话 id 和拉起时给的归属（`SpawnAgentRequest.ledger`，现取）交给账本；记在任务、定时作业名下的同一事务在看板频道推 `token_totals`（最新合计，含按 agent、按阶段）；消耗页 `GET /api/usage?from=&to=`。查询接口（14 号票读 `totals` / `stageTokens` / `onRecorded`）写在 `docs/dev.md` 的"token 账本与消耗"。
- **缓存命中 / 未命中怎么算**：pi 的用量里输入分三块互不重叠（`cacheRead`、`input`、`cacheWrite`），账本里命中 = `cacheRead`，未命中 = `input + cacheWrite`（DeepSeek 不报 cacheWrite，是 0）。
- **归属怎么定**（规格没写细的部分，取最贴近规格的做法）：`AgentSession` 按正在处理（或刚处理完）的那条输入所属的定时作业、任务定（消息事件里的 `scheduledJobId`、`taskId`），其次项目，再按会话的 scope；所以项目维护者处理带任务的输入（项目的首个建设任务、16 号票的工单通知）记在任务名下，和用户直接对话时记在项目名下；工单结束时的范围审视（在回合之后）记在刚处理完的那条输入所属的任务名下。评审子 agent 记在任务名下、它评审的阶段。任务名下的调用记上调用时任务的当前阶段（`guardStageId`，和守卫一致），起草计划时、任务结束或全部验收之后的调用没有阶段。项目名下的用量只进账本和消耗页，不在看板上推。
- **范围审视（18）和定时作业（19）还没做**：按票里说的用构造的用量验证（测试接缝 `test/helpers/usage.ts` 的 `usageInjector`）。18 号票在子进程的 `usage` 里报 `purpose: "scope_review"`（宿主协议 5 加的可选字段，压缩那次已经用它报 `compaction`）；19 号票拉起作业自己的维护者时给 `ledger: () => ({ owner: { kind: "scheduled_job", id: 作业 id }, role: "maintainer" })`，把作业的一次运行交给项目维护者时，交过去的消息带上 `scheduledJobId`（`MessageScope` / `MessageEventPayload` 新加的可选字段），项目维护者处理它的用量就记在作业名下。
- **作业卡那条验收标准没勾**（评审后取消勾选）：作业名下的记账、看板上推的 `token_totals`（`owner.kind: "scheduled_job"`）、前端的 `jobTokenTotal` 都有了，但看板上真的作业卡归 19 号票，现在只有原型的假作业卡显示假数；19 号票接上真作业卡时用 `jobTokenTotal(state, 作业 id)` 显示总量，再勾这一条（界面那条里"作业卡显示 token 总量"同理）。
- **`SpawnAgentRequest.ledger` 是可选的**（免得并行开发的票新加的拉起点编译不过）：不给的记成"未归属"（`role: "unattributed"`，消耗页单列，不混进系统开销；账本日志里对每个这样的 agent 提醒一次）。20 号票的并行子 agent 要给 `{ owner: { kind: "task", id }, role: "sub_agent", stageId: 它被派去的阶段 }`，用量记到它自己的阶段。
- **评审后改的口径**（第二轮）：
  - 系统开销按角色判：秘书的用量不论输入带不带任务都是系统开销；
  - 压缩会话生成摘要的那次模型调用也记账（子进程在 pi 的 `compaction_end` 时报 `CompactionResult.usage`，`purpose: "compaction"`），记在同一归属下，任务详情里标"压缩"单独一行；
  - 评审子 agent 记在任务名下、带它评审的阶段、角色是评审；任务结束或全部阶段验收之后的收尾调用不带阶段。给 14 号票的预算比较用 `stageTokens(taskId, stageId, { budget: true })`（不算评审、范围审视；压缩算），看板上 `byStage[].budgetTokens` 和阶段抽屉显示的是同一个数；
  - 归属的优先次序：输入的定时作业 > 任务 > 项目 > 会话的 scope；输入的归属由输入队列（`agent_inputs` 的 `scope` 列、`QueuedInput.scope`）带着，不回读事件；
  - 合计只从派生视图的 SQL 聚合出；模型键统一用 `modelConfigKey`（faux 是 `faux`）；消耗页的日期用协议包的 `LocalDate` 校验（不存在的日期也回 400）；单价类型只留 `TokenPriceTable`（单价是协议包的 `TokenPrice`）；归属种类 `job` 改名 `scheduled_job`；
  - 契约测试加了真实 provider 的换算：pi 的 openai-completions 解析本机回放的录好的 DeepSeek 流式响应（不联网），断言命中 = `cacheRead`、未命中 = `input + cacheWrite`。
- **单价**放在数据目录配置区的 `config/ergou.json` 的 `tokenPrices`（每百万 token，命中、未命中、输出各一个，货币代码），每次算成本时现读（改了不用重启），启动时也校验。示例配置里 deepseek-flash 的单价（0.2 / 2 / 3 元）是照 DeepSeek 官网对 deepseek-chat 公布的价格写的示例值，V4.1 Flash 的实际价格用前要以官网为准。
- **按天**按记账时间的本地日期分（协议时间前 10 个字符，和简单提醒一样按本机时区），没按配置的 `timeZone`。
- **看板频道上多了 `token_totals`**：主切面里录看板频道的几段事件流重新录了（`task-execution`、`task-initiation`、`holiday-update-task`，`workday-calendar` 同一个文件跟着重录）。别的票如果也改了这几段，合并后重新录一次即可（命令见 `docs/dev.md`）。
- 宿主协议版本 5 → 6（22 号票先合并、占了 5；本票加的是 `usage.purpose`、faux 剧本的 `usage`、契约测试用的 `CatalogModelSpec.baseUrl`）。阶段抽屉的预算一行现在写"用了 / 预算 token"，工具调用次数仍只写预算（用了几次归 14 号票）。
- 删除项目时账本里这个项目名下的条目留着（只有数，没有原话），消耗页的历史照旧。
