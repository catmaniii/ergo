# 07 — 秘书草稿区、守卫接入与审批

Status: ready-for-agent
Blocked by: 03（守卫判定核心）, 06（卡片、待我处理与简单提醒）
Spec: [第一阶段规格](../spec.md) 第 3 节（agent 子进程与 pi 封装层）、第 4 节（存储与事件）、第 7 节（秘书）、第 9 节（守卫）、第 15 节（素材）、第 21 节（实现细节补充）

## What to build

秘书有了一块自己的草稿区，能动手了：用户让它算个东西，它在草稿区里写一个 Python 或 Node 脚本、用 Git Bash 跑出结果，再在聊天里回答。聊天里能看到每次工具调用、命中了哪些关注类别、守卫怎么判的、是否授权内、是不是通用 bash。草稿区里的写、改、删不落入任何关注类别，直接做、只记录。

秘书要跑草稿区外的现成脚本、或读用户给的本机文件时（用 bash 还是文件工具都一样），守卫判为"越出项目目录"，在对话里就是先问用户：守护进程先把审批写进审批表，再在聊天和待我处理里出一张审批卡，写明来源、要做什么、命中了哪个类别。用户 5 分钟内批准，这次调用接着执行；超时就以"已提交审批，等待用户"拦下；用户事后批准时，记成一条按调用指纹匹配的一次性授权，运行时告诉秘书"某某已获批准，可以重试"。判定为"交给我做"的，变成一个"交给我做"事项，用户亲手完成后点"已完成"。

秘书不能联网，这里是尽力而为、不是硬隔离：联网的工具和命令直接拒绝；草稿区里的脚本执行前先扫一遍，用到联网的库或函数就拒绝，并提示"联网请发起任务"；脚本进程设一个无效的代理地址，让常见的联网方式失败。真正挡死要等以后加系统级沙箱。

这张票把 03 号票的判定接进运行时：子进程里的二狗扩展在 pi 的 `tool_call` 钩子里把每次调用送给守护进程，按判定放行或拦截。以后维护者、子 agent 的工具调用都走同一条路。

## Acceptance criteria

- [ ] 守卫转发：子进程扩展在 `tool_call` 钩子里把每次工具调用经宿主协议的"守卫判定请求"送给守护进程，守护进程现取环境事实、用 03 号票的判定函数判定后回复；放行才执行，拦下的调用不执行，模型收到判定里的说明；守卫从不原地改参数。pi 契约测试里加上对应用例：`tool_call` 送到守护进程，等回复期间不执行，被拦截时真的不执行。
- [ ] 草稿区是临时区里秘书专用的一格。秘书的文件工具可以在里面写、改、删；bash 是 Git Bash，能用本机已有的 Node 和 Python，工作目录固定在草稿区。主切面（faux 剧本）：秘书写一个脚本、跑出结果、回答用户；这些调用不落入任何关注类别、直接执行，聊天里留有记录，bash 调用标"通用 bash"；秘书删除、覆盖草稿区里的文件同样直接做，不受"删除前须已备份或已提交"模板约束。
- [ ] 秘书的围栏（主切面）：文件工具写草稿区以外被直接拒绝，不出审批卡；项目档案只读；文件工具读草稿区和项目档案以外的文件、bash 碰到草稿区外的路径（跑用户某个目录里的现成脚本、读用户给的本机文件），落入"越出项目目录"，出审批卡；读密钥区一律拒绝；用文件工具或 bash 写受保护区域（配置区、密钥区、数据库区、二狗程序目录）判"永不"，不出审批卡。
- [ ] 秘书不能联网（主切面）：秘书的固定工具里没有联网工具；从 bash 拆出的发 HTTP 请求的伪工具调用（如 `curl`）直接拒绝；草稿区里的脚本执行前先扫，用到 Python 或 Node 里联网的库或函数就拒绝，说明里提示"联网请发起任务"，不用联网的脚本照常跑；bash 起的进程环境里代理地址设成无效值，也没有任何密钥（测试：子进程拿到的模型 key，在 bash 里查环境变量看不到）。扫描和无效代理按"联网开关关着"生效，不只认秘书。
- [ ] 审批：判定为"先问我"时，守护进程先写审批表、再建审批卡并通知前端（主切面断言：收到审批卡事件时审批表里已有这条记录）。审批卡写明来源（对话里写"秘书对话"，任务里写任务和阶段）、要做什么、命中了哪个类别；同一张卡出现在聊天和待我处理里，状态同步；对话里的审批卡紧急度为"不卡任务"。用户批准 → 这次调用继续执行；拒绝 → 调用被拦下，模型收到"用户拒绝"。
- [ ] 等待与挂起（时钟可注入）：子进程里的这次调用最多等 5 分钟（默认，可配置），超时以"已提交审批，等待用户"拦下，并产生一条带调用所属任务和阶段（对话里为空）的挂起事件。之后用户批准，记成一条一次性授权、按调用指纹匹配，运行时给秘书递一条"某某已获批准，可以重试"；重试时同一指纹放行一次，再来一次同样的调用重新走审批。
- [ ] "交给我做"：判定为"交给我做"的调用不执行，守护进程建一个"交给我做"事项进待我处理，带上 agent 准备好的内容（这次调用的规范化摘要）；用户点"已完成"后，agent 收到通知。主切面用测试里登记的、带"花钱"类别的工具驱动。
- [ ] 聊天里的工具调用 part 带工具名、参数摘要、命中的关注类别、判定、是否授权内和是否通用 bash。执行成功的调用追加进效果日志（`ergou.db` 的派生视图，字段按规格第 9 节），被拦下或执行失败的不追加。
- [ ] 产生对应的素材事件：审批决定（批准、拒绝；负载里留出收窄）的事件类型和负载就绪，由 08 号票采集为"审批决定"素材。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 任务一侧：本票只产生审批超时的"挂起"事件（带任务和阶段）。任务状态机在 12、13 才有，由 13 号票把挂起事件映射成任务转等我（原因"审批"）；"交给我做"让任务这一支转等我、任务里审批卡的紧急度，也在 13 接上。
- 脚本扫描是尽力而为：守卫只看得到命令这一层，扫描在执行前读脚本、把用到的联网库或函数作为环境事实传给 03 号票的判定函数；第一阶段没有系统级沙箱（Out of Scope），扫不出来的写法挡不住。联网开关关着的维护者同样适用，随 27 号票的联网开关接到维护者会话上。
- 不在本票：被杀重启后从审批表恢复、不重复通知、按同样的指纹匹配，以及按工具注册表的"只读或幂等"标记处理被打断的调用、秘书会话里说不清做没做完的有副作用调用放"中断：不确定 X 是否已执行"事项（23）；草稿区的产出作为附件发进聊天、存进媒体库（09）；草稿区 7 天清理（11）；单次工具调用超时（默认 10 分钟）和子进程资源限制（12）；快速动作的确认（21，不走审批卡）；时间线上被拦下、问过的样式（25）；维护者和子 agent 的围栏判定已在 03，接到他们的会话上随 12、13、16 的会话装配一起生效。
- 时序规则由 05 号票接进判定函数，接上后本票的转发不用改。效果日志若本票先落地，05 直接用它。
