# 14 — 偏离、阈值与计划变更

Status: done

Spec: [第一阶段规格](../spec.md) 第 8 节（任务、计划与阶段）、第 9 节（守卫）、第 13 节（调度）、第 5 节（前端协议）、第 15 节（素材）

## What to build

做完后，任务跑偏时，二狗打扰用户的程度和偏离的代价成正比。阈值（默认值，可配置）：调用不在所属阶段的授权、被拉回 3 次还不行；无进展被催促 3 次还不行；阶段验收退回 2 次、第 3 次还不过；预算超出 2 倍——这几种都要用户拍板，任务转"等我"，原因写"卡住求助"（前三种）或"超预算"（预算）。预算按 token 加工具调用次数计算，超出 1 倍只让维护者说明进展。agent 还活着、但 20 分钟内没有成功的工具调用也没有阶段推进，算无进展，触发一次催促。

偏离按级升级：计划外但在授权范围内的，只在时间线记一笔摘要；超出授权的（计划对这个类别有授权，但这次超出了对象范围或次数），先问用户；出现计划没预料到的类别（计划里完全没涉及这个类别），先问用户并暂停这一支；同一任务累计被用户拒绝 5 次，整个任务转"已暂停"。"先问我"类别的操作不在此列：计划里列了也照样当场问，"授权内只记一笔"只对"计划里列了才做"那一档成立。

维护者要扩大授权、加能力、加项目、改目标或验收时，提交一张计划变更卡进待我处理，只有受影响的阶段停下来等，其余阶段照常推进；被拒后，维护者在现有授权内重排受影响的阶段，做不到就标"做不了"、任务转等我。拆阶段、调顺序这类不扩大授权的调整，维护者自己改，记进时间线。授权项默认有效期 7 天，到期前一天待我处理里出现续期事项，过期的授权项不再生效。演示：用可注入时钟和 faux provider 剧本分别触发"20 分钟无进展 → 催促""预算超 2 倍 → 任务转等我（超预算）""提交计划变更 → 只有受影响的阶段停下 → 用户拒绝 → 维护者在现有授权内重排"，看待我处理和任务详情的变化。

## Acceptance criteria

- [x] 主切面：维护者用到不在当前阶段的授权时被拉回，满 3 次后再犯，这一支停下、任务转等我（原因"卡住求助"），待我处理出现卡住求助事项；阶段验收前 2 次退回只交回维护者，第 3 次仍不过时同样转等我（原因"卡住求助"）。
- [x] 主切面（可注入时钟）：维护者活着但 20 分钟内没有成功的工具调用、也没有阶段推进时，运行时催促它一次（正在干活时以插话送达）；同一次停滞里催满 3 次仍无进展，任务转等我（原因"卡住求助"）；中间出现成功的工具调用或阶段推进，催促计数清零。
- [x] 主切面：每个阶段按 token 加工具调用次数累计预算（token 取自子进程上报的用量）；超出 1 倍时运行时让维护者说明进展（一条消息进它的会话），任务状态不变；超出 2 倍时任务转等我（原因"超预算"），待我处理出现对应事项。pi 契约测试里要有"能拿到每次调用的用量"的用例（24 号票若还没加，在本票加上）。
- [x] 守卫切面 + 主切面：计划外但在授权范围内的调用放行，只在时间线记一条摘要；落在"先问我"类别的调用即使在授权范围内也当场问（"交给我做""永不"照旧）；计划对这个类别有授权项、但这次超出了对象范围或次数的，判为超出授权，先问用户（审批卡）；命中的类别在计划里没有任何对应的授权项的，判为没预料到的类别，先问用户并暂停这一支；同一任务累计被用户拒绝 5 次（默认）时，整个任务转已暂停，看板写明原因。
- [x] 主切面：维护者提交计划变更（扩大授权、加能力、加项目、改目标或验收）时，待我处理出现计划变更卡，卡上只列出相对当前计划新增或改动的部分；只有受影响的阶段停下等确认，其余阶段继续执行；用户确认后计划和授权项随之更新，受影响的阶段恢复。用户拒绝后，维护者在现有授权内重排受影响的阶段（重排记进时间线、不出卡）；做不到时把这些阶段标"做不了"，任务转等我。
- [x] 主切面：拆阶段、调顺序这类不扩大授权的调整，维护者直接改计划、不出卡，时间线记一笔；想借这条路扩大授权（新增授权项、放宽对象范围或次数、加工具包能力）的调整被拒，提示改走计划变更；运行中的授权项只能收窄。
- [x] 主切面（可注入时钟）：授权项默认有效期 7 天；到期前一天待我处理出现续期事项，用户续期后有效期延长；过期没续的授权项不再生效，相应操作执行到那一步时再问用户。
- [x] 主切面：产生对应的素材事件——用户在计划变更卡和续期事项上的批准、拒绝（审批决定）。由 08 号票采集；若 08 尚未完成，至少事件类型和负载就绪。
- [x] Web UI：待我处理里显示计划变更卡（只列变化部分）、续期事项、卡住求助和超预算事项；任务详情的时间线上能看到授权内偏离的摘要、催促、维护者自己调整或重排计划的记录；看板任务卡写明等我（卡住求助、超预算）或已暂停（累计被拒）的原因。前端状态层回放主切面录下的对应事件流，显示正确。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Comments

实现记录（2026-10-08，worktree 分支 `worktree-agent-a6eefb2751375ce81`；评审后改过一轮，变基到 20、23、16 号票之后）。说明见 `docs/dev.md`"偏离、阈值与计划变更"一节。

**拿不准、按下面理解做了的地方：**

- **术语**：维护者提交、用户在卡上确认的叫"计划变更"；维护者不扩大授权、直接改的叫"自行调整计划"；两者统称"计划变更和自行调整"（代码注释、工具说明、系统提示、CONTEXT.md 都这样写，不说"执行中改计划"）。
- **阈值的口径**："被拉回 3 次还不行"= 同一阶段拉回满 3 次后第 4 次；"催促 3 次还不行"= 同一次停滞里催满 3 次后再到点；"退回 2 次、第 3 次还不过"= 验收（脚本、评审）第 3 次没通过；预算按规格（2026-10-08 用户定的口径）：用量超过预算让维护者说明进展，用量超过预算的 2 倍问用户（超预算）。预算的两项（token、工具调用次数）各自算比值取大的，计划里写 0 的那一项不算（不然没写预算的阶段一开始就超）。阈值都可配（`tasks.thresholds`，字段名和配置键一致：`budgetExplainTimes`、`budgetAskTimes`……），默认值只在 `tasks/thresholds.ts`；系统提示、通知里的数字照阈值插值。
- **预算的计数**：token 从 24 号票的账本取（`ledger.stageTokens(taskId, stageId, { budget: true })`，子 agent 在这个阶段的用量也在里面），每记一条账（`onRecorded`）比一次；工具调用次数数维护者会话里的工具调用记录（维护者和子 agent 的都在那里，带调用时的阶段；被拦下的也算一次），`budget_used` 只记次数。追加预算继续 = 这个阶段从现在起重新给一整份（token 记下账本里这时的数作为起算点）。
- **阈值触发只停这一支**：照 13 号票的规矩，别的分支还能推进就只停这一支（阶段转 `waiting`，原因 `stuck` / `over_budget`），都在等才转等我。停下时待我处理里一条 `stuck_help` / `over_budget`（卡着任务），`data.stageIds` 写明哪几支；为什么停下是结构化的原因（`BranchStopReason`），说法只在 `execution-tools.ts`。用户点"继续执行""追加预算继续"（或者在任务会话里回话）时停下的几支一起接着走、计数清零。卡住求助、超预算和 23 号票的中断不确定放在一套里：协议包的 `USER_DECIDES_WAIT_REASONS` / `userDecidesWait`（"谁能改"表的 `user_decides`，点"继续"能接着执行）。会话里回话就接着执行的是它的子集 `RESUME_ON_REPLY_WAIT_REASONS`（卡住求助、中断不确定）：**超预算只有点"追加预算继续"（或任务详情里同一个按钮）才接着执行、重新给一整份预算**，用户在会话里说的话交给维护者回答，任务仍停在等我（2026-10-08 用户定的）。中断不确定是整个任务的，别的分支有了结论也不自己恢复。
- **无进展**：维护者的子进程在运行（agent 管家的 `live()`）才算"活着却没进展"，不在运行（闲置退出了）的到点不催，从那一刻重新计时；只在任务执行中、维护者手头的阶段在做时计时（它的当前阶段按 20 号票的 `stages.focus`，交给子 agent 的不算）；成功的工具调用 = 效果日志里有这个任务的记录（子 agent 的也算）；阶段推进 = 看板上任务的变化（计数本身、拉回不算），从那一刻重新计时，没在等用户的阶段催促计数清零。只有催促以插话送达；"这一支停下""说明进展"这几条通知排在手头这一条之后。计时挪进了 `tasks/stall.ts`，续期挪进了 `tasks/grant-renewal.ts`（`execution.ts` 太大）。
- **累计被拒**：审批卡上的拒绝和计划变更卡上的拒绝都算（交给我做不算）；满 5 次时任务从执行中、等我、排队中都能转已暂停（"谁能改"表加了排队中 → 已暂停 `system`），`pauseReason` 写明；用户继续时清零。
- **偏离的判定**：计划"对这个类别有授权项"= 计划里有同一个工具的授权项，或者授权项的工具登记在这个类别里（自定义类别按它的工具列表），或者授权项本身当成一次调用判也落在这个类别里（按路径判的越出项目目录）。授权项过期也算超出授权（先问，等）。没预料到的类别提交审批后不等，直接挂起这一支（`approval-waits.ts` 的 `suspendNow`）；**子 agent 的调用不先挂起**，照常等用户（它只做这一支，等的时候这一支就停着；挂起了它会接着往下做完、交回结果）——这是变基到 20 号票时定的，20 号票的主切面按这个口径照旧通过。
- **计划变更**：维护者交整份计划（`PlanDraft`：本任务的关注类别、用户的限制、定时作业、记忆范围沿用当前计划），运行时算出改动；"扩大"的口径是新增 / 放宽 / 挪动授权项、工具包加能力、加项目、改目标或任务的验收标准、改阶段的验收或交付件（整份计划里的多重集合，拆阶段挪过去不算）、加预算、删改原有的时序规则。每种改动的说法、对应的授权项、停哪些阶段在协议包 `PLAN_CHANGE_KINDS` 一张表里。没有扩大的不出卡（提示自行调整），扩大的不能自行调整（提示改走计划变更）。同一任务一次只有一张在等；已验收的阶段不能改，在等用户或在验收的阶段不能去掉。受影响的阶段按改动所在算，算不出时停维护者的当前阶段。确认和计划卡共用 `planConfirmation`；确认后任务的 `planCardId` 换成这张卡。
- **改目标、任务的验收标准**：计划变更工具多了 `acceptanceCriteria`（任务书里新的全部标准）。确认后任务书换成新的一版（`briefWritten`，版本加 1，不另交给维护者：确认的通知里写了改动），重注入块写新的目标和"任务的验收标准"，下一次提交跟新的任务书比。
