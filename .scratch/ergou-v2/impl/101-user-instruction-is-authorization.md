## What to build

用户 2026-10-12 先说："这些很多安全规则都是限制 agent 自主行为的，如果说我明确发的指令的要求的话，应该排除这些限制……"，主会话提了"用户在场直接下的指令就是授权"的做法；做到一半用户改了范围（原话）："现阶段安全不要搞得太敏感，超出了授权范围内的，如果是任务的 agent 的话先不管，因为他能访问到的数据有限，但是那个二狗秘书，稍微管一下特别敏感的操作，要我授权"。照新范围做，"用户在场才放开"的区分不要了（不认用户在不在场）。

对话审批开关（`guard.conversationApprovals`）开着时一切照原来（全部先问、按计划授权核对）；关着（默认）时：

1. **任务的 agent**（任务的维护者执行、定时 / 事件触发的运行、子 agent、评审子 agent、项目维护者的执行工单段——不分用户在不在场）：超出授权的一律不拦——计划授权项外的调用、关注类别处置为"计划里列了才做""先问我"的、计划外工单、`keepAsking` 那几种（密钥判断不了、路径没法确定、脚本写着受保护区域路径的未知写），都按"直接做、照常标出"（依据记新的说法"任务 agent 超出授权先不管，照常标出"），不出审批卡、不按规则退回（用到别的阶段的授权项不拉回）。
2. **秘书二狗**（秘书主线里的调用，不分用户在不在场）：大部分直接做、照常标出（含原来 `keepAsking` 的密钥判断不了、路径没法确定，越出项目目录的读，未知的写）。**特别敏感的要用户授权**（出审批卡，用户点了才做）：以我的名义对外发送或发布（`external_send`）、账户与安全（凭据、权限、全局装软件，`account_security`）、不可逆的提交（`irreversible_commit`）、删除或覆盖草稿区以外的文件；秘书写草稿区以外的地方原来是直接拒绝，改成这一档（问用户、批了才写），受保护区域照旧永不。
3. **不变的**：三条硬底线（写二狗自己的受保护区域、读密钥区、确定要把密钥内容往外送的）；"交给我做"（花钱、付款转账 / 建账户 / 改密码或两步验证——用户自己动手的事）和"永不"；判断出来确实违反的时序规则、流程的步骤先后和自动纠偏（保证照计划做事的，不是权限）照旧。主会话 2026-10-12 又定：任务的 agent 时序规则判断不了的、流程核对里计划外会改东西的和超出步骤写的对象，也直接做、照常标出；秘书删除或覆盖路径没法确定的文件算特别敏感，出审批卡。
4. 秘书提示里对话审批那几句、`docs/dev.md`、ADR-0026 的补充段跟着新范围写。

## Acceptance criteria

- [x] 三条硬底线、硬拒绝、交给我做、永不照旧；开着时一切照原样；有测试。
