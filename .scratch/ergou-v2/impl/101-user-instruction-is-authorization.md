# 101 — 用户明确下的指令就是授权：用户在场的那一轮不再"先问"，只留三条硬底线

Status: ready-for-agent
Blocked by: 无（和 100 同时做：100 动发语音和定时作业，本票动守卫；谁先做完谁先合并）
Spec: [第一阶段规格](../spec.md) 守卫一节；ADR-0026（功能先跑通、安全后接）、70 号票（对话审批的开关、`keepAsking`）

## What to build

用户 2026-10-12："这些很多安全规则都是限制 agent 自主行为的，如果说我明确发的指令的要求的话，应该排除这些限制，就是我明确说了的内容以及我授权的范围内 agent 去做应该都不需要再限制它，除非超出我说的范围或者我授权的范围。"主会话提了做法，用户回"先按你的思路做"：

1. **用户在场的那一轮**：agent 处理的是用户自己发的消息（打字、语音、插话）的那一轮——秘书主线、用户在任务详情里直接跟维护者说、用户在项目会话里直接跟项目维护者说——守卫判成"先问我"的一律按"直接做、照常标出"（关注类别照常命中、照常记进工具调用记录、效果日志），对话里不出审批卡。包括现在对话审批关着也"照旧先问"的那几种（`keepAsking`：要写或看不出读写的路径没法确定、牵涉密钥的 v1 模板"读过 .env 或密钥文件之后不许往外送""对外内容不许含密钥"判断不了、脚本里写着受保护区域路径的"未知的写操作"），也包括任务里超出计划授权本来要问的（用户在任务详情里直接说的就是新的授权）。依据记一个新的说法（比如"用户在场直接下的指令，按直接做"），说明里写明，事后详情里看得到。
2. **三条硬底线不变**（用户说了也不做）：① 写二狗自己的受保护区域（配置区、数据库区、程序目录）；② 读密钥区；③ 已经确定要把密钥内容往外送的（判断出来了，不是判断不了）。另外硬拒绝、"永不"、"交给我做"（用户自己在关注类别里设的处置）照旧。
3. **用户不在场的那一轮**（后台执行的任务、定时 / 事件触发的运行、运行时通知引起的一轮、秘书被任务做完通知唤起的那一轮）照旧：按计划授权核对、超出的照旧问或退回、`keepAsking` 照旧。事先给过的授权（计划里批准的授权项、100 号票的"跑完自动播报"）在范围内照旧放行。
4. 怎么认"用户在场的那一轮"：照现有的输入来源（用户消息 / 插话 vs 运行时通知、系统输入、定时运行的通知），守卫的判定输入里加一个标记；一轮里用户插话进来之后的调用也算。
5. "有没有超出用户说的范围"不自动判断（用户接受）：靠照常标出、事后在工具调用详情里看。
6. 秘书的系统提示里"对话审批"那几句跟着改：用户在场时照用户说的做，不用为了怕弹卡绕开；用户不在场时照旧。

## Acceptance criteria

- [ ] 用户在场的一轮：原来 `keepAsking` 的三种、超出计划授权的，直接做、照常标出、不出审批卡；有守卫切面测试和主切面测试（秘书主线、任务详情里用户直接说）。
- [ ] 三条硬底线、硬拒绝、永不、交给我做照旧；有测试。
- [ ] 用户不在场的一轮（后台执行、定时运行、运行时通知引起的）照旧问或退回；有测试。
- [ ] 全量测试一次，typecheck、oxlint 通过；`docs/dev.md` 守卫一节、ADR-0026 后面补一段。
