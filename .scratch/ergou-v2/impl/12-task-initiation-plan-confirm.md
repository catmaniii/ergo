## What to build

做完后，用户能从秘书聊天一路走到一张可以确认的计划卡。任务由用户发起，有三条路：点秘书页或任务页上的"发起任务"按钮；在消息里要秘书去做某件需要任务的事——这个要求本身就是授权，秘书直接建任务卡，不再出建议卡；或者点秘书给的"建议发起任务"卡上的"发起任务"——只有秘书自己发现、用户没要求的事，秘书才给这张建议卡。任务以"规划中"出现在任务看板上，秘书先说出它的理解（"我理解你要的是……，对吗？"），用提问卡成批提问（每题带推荐答案，可以一键"全按推荐"），对齐后写出任务书（目标、验收标准、约束、涉及的项目、记忆范围提议）。

运行时把任务书交给执行的维护者——本票里是任务建卡时产生的、任务自己的维护者。它被唤起后起草结构化的计划，用"提交计划"工具交出；代码从结构化数据生成计划卡，放进待我处理，任务转"待确认"。计划卡列出每个阶段的交付件、验收标准和由谁验收、授权项、时序规则、工具包、涉及的项目和改动、本任务要提醒的关注类别（默认取全局，只能加不能删）、可选的定时作业定义（时间表、每次要做的事、属于哪个项目）、假设栏、"授权后还会在 N 处停下来"和 token 粗估，细节默认折叠。用户可以逐行勾掉或收窄授权项后点唯一的"确认"按钮，任务转"排队中"；也可以附上意见打回，任务回到"规划中"，维护者重新起草。

同时把 agent 管家的资源限制补齐：同时存活的子进程上限（满了新的唤起排队）、维护者闲置退出、模型调用和工具调用超时、孤儿进程回收。演示：faux provider 按剧本回话——在秘书页说"帮我整理一份 X 的调研"，秘书直接建出任务（规划中）→ 提问卡"全按推荐" → 待我处理出现计划卡 → 收窄一行授权后确认 → 任务看板上任务进入"排队中"；再换一段剧本，用户只是聊到一件麻烦事、没让秘书去做，秘书给出"建议发起任务"卡，点"发起任务"后走同样的流程。

## Acceptance criteria

- [x] 主切面：三条发起路径都建出任务（规划中）并在任务看板频道推送——用户点页面上的"发起任务"按钮时不经秘书判断直接建出；秘书用建任务工具（用户在消息里要它去做时）直接建任务卡并进入澄清，这一轮不产生"建议发起任务"卡；秘书调用"建议发起任务"工具只产生一张卡、不建任务，用户点卡上的"发起任务"后才建出。秘书没有建定时作业的工具。
- [x] 主切面：提问卡成批提问、每题带推荐答案，"全按推荐"一次提交全部答案，答案作为消息交回秘书；秘书用任务书工具写出的任务书（目标、验收标准、约束、涉及的项目、记忆范围提议）存进二狗自己的存储，运行时把它作为输入交给该任务的维护者（新拉起的子进程、新的会话）。
- [x] 主切面：维护者用"提交计划"工具以结构化数据交出计划，字段齐全（阶段及其交付件、验收标准与方式、模式、前置阶段、授权项、时序规则、预算、所属阶段组；阶段组；工具包；涉及的项目和改动；记忆范围占位；本任务关注类别；可选的定时作业定义：时间表、每次要做的事、属于哪个项目；假设栏；预告的停点数；token 粗估），存在二狗的存储里而不在 pi 会话里；不符合 schema 的提交失败，原因返回给维护者，不出计划卡。本任务关注类别默认取全局设置、只能在其上增加：少了任何一个全局类别的提交失败并返回原因。
- [x] 主切面：计划卡由代码从结构化计划生成，卡上的授权项、关注类别和定时作业定义和存储里的逐条一致；勾掉或收窄某一行后确认，存储里的计划和授权项随之改变；附意见打回时，意见作为一条消息交回起草的维护者，它重新提交后出一张新的计划卡。
- [x] 主切面：任务状态按"规划中 →（维护者提交计划）待确认 →（用户确认）排队中""待确认 →（用户打回）规划中"迁移，每次迁移都是事件，并在任务模块里按"谁能改"表校验：只有用户能确认计划和打回，秘书或维护者发起的"确认计划"被拒；只有执行的维护者经"提交计划"把任务推进到待确认。
- [x] 主切面（把数值配小）：同时存活的子进程不超过上限（默认 8）；满了以后新的唤起不报错，而是排队，名额空出时按先后拉起，排队期间这个 agent 的活动状态是"排队"；维护者闲置到设定时间（默认 10 分钟）后子进程退出，再来输入时重新拉起、接着原会话；秘书常驻、不闲置退出；单次模型调用超时（默认 5 分钟）和单次工具调用超时（默认 10 分钟，工具可以声明更长）被中止并上报错误；孤儿进程按周期（默认每分钟）被回收。
- [x] 主切面：产生对应的素材事件——提问卡的回答（澄清问题的回答）；计划卡上的确认、勾掉或收窄、打回（审批决定）；"建议发起任务"卡、提问卡被关闭（回避信号）。由 08 号票采集；若 08 尚未完成，至少事件类型和负载就绪。
- [x] Web UI：秘书页显示"建议发起任务"卡和提问卡；秘书页和任务页都有"发起任务"按钮；任务页的看板接真数据，按五组显示：等我（等我、待确认）、进行中（规划中、排队中、执行中、已暂停）、运营中（简单提醒、定时作业）、最近结束（已完成、失败、已取消）、已归档；简单提醒显示为"运营中 · 待触发"；任务卡显示状态和"第 N/M 阶段"（M 取自计划）；待我处理里的计划卡细节默认折叠。前端状态层用主切面录下的这条流程的事件流回放，看板分组和计划卡状态正确；全部任务状态到分组的对应用构造的事件流逐一验证。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：
  - 本票只做不涉及项目的任务（任务自己的维护者）。单项目任务由项目维护者起草和执行归 16，多项目任务归 17；计划里"涉及的项目和改动"本票只存储和显示。
  - 排队中 → 执行中、全局并发、阶段执行、验收、暂停 / 继续 / 取消、任务详情页归 13。秘书的"查看板"工具、看板变化消息、"承诺即任务"（秘书只答应用户要它做的事、答应了就当场建任务或简单提醒，没要求的只能给建议卡）归 22，任务控制快速动作也归 22。看板上的活动状态小圆点和活动状态频道归 25（25 未完成时，本票至少让"排队"这个活动状态事件就绪），token 总量归 24。
  - 定时作业定义本票只存储、在计划卡上显示；确认计划后作业登记、进入运营中、在看板上显示归 19。秘书不能直接建定时作业，定时作业只通过任务的计划建。
  - 计划卡上增加本任务要提醒的关注类别的交互归 26；本票这个字段默认取全局，只显示，并在提交时保证不少于全局。对话里说的限制由起草计划的维护者编译成时序规则或授权收窄、显示在计划卡上，也归 26。记忆范围只占位（Out of Scope）。
  - 计划里的时序规则本票只作为数据保存、在卡上显示；规则校验和执行中生效归 13（依赖 05）。
- 审批卡、守卫接入来自 07 号票；维护者起草计划时的工具调用照常经守卫。
- 预告的停点数由维护者在计划里给出。想让任务少停几次，只能在计划里给对应操作预先授权，这只对"计划里列了才做"那一档有效；"先问我"类别的操作即使列进授权项，执行时也照样当场问（第 9 节），停点数要把它们算进去。
- 回避信号的"7 天没处理"计时归 08 号票，本票只保证卡片被关闭有事件。
- 秘书分辨"用户要它去做"还是"自己发现"、"先说出理解"、"已经确认过的不再问"都是秘书提示词的行为：faux provider 下只测运行时一侧，真实效果放进 DeepSeek 的手动冒烟（秘书分流、计划起草）。提问卡不设轮数和题数上限。计划卡的确认仍是执行前的闸，不管任务从哪条路发起。
- 对应用户故事：3、4、24–33、35–37、38（"第 N/M 阶段"部分）。
