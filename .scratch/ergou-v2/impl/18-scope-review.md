# 18 — 范围审视

Status: done
Blocked by: 16（工单与派单：单项目任务）
Spec: [第一阶段规格](../spec.md) 第 10 节（范围审视）、第 3 节（agent 子进程与 pi 封装层）、第 1 节（工程与总体架构）、第 11 节（项目与维护者）、第 5 节（前端协议）、第 19 节（Web UI）、第 21 节（实现细节补充）

## What to build

做完后，维护者做了范围外的事会被发现、记下来，但不会被卡死。审视有两个时点：维护者会话压缩时（扩展在 `session_before_compact` 里把待压缩的消息转成文本送审），以及每张工单结束时（运行时调用同一个审视函数）。守护进程不跑模型，所以审视的模型调用都在维护者自己的子进程里另开一次，不写进维护者的会话；工单结束的那次在子进程退出前做。审视用便宜模型（第一阶段也是 `deepseek-flash`），对照立项书、任务计划和用户给过的授权（包括用户在会话里直接说的话），产出范围记录，交给守护进程保存。

用户授权过的范围外工作记为范围变更，写进项目档案的范围记录；没授权的记为越界。压缩时的审视结果还用 `appendEntry` 存进会话。每张工单是一段新的 pi 会话，旧段里的 `appendEntry` 新段拿不到，所以 `before_agent_start` 从守护进程取最近 5 条范围记录，拼到维护者系统提示末尾，标题"近期范围记录"。发现越界时，待我处理里放一条不推送的通知，照常算未读。维护者不会因此被暂停——用户临时让它先做点别的，就是一次被授权的范围突破。不属于项目的任务没有项目档案，它的范围记录写进任务自己的产出区，在任务详情里显示。

简版项目页显示范围记录。演示：faux provider 剧本让维护者在一张工单里顺手改了立项书范围外的东西，工单结束时审视（faux provider 扮便宜模型）判为越界——待我处理出现越界通知、小红点亮起，项目页出现这条记录，下一张工单的会话里系统提示末尾有"近期范围记录"；再让用户在会话里说"先帮我做下 X"，审视把同类工作记为范围变更、写进项目档案。

## Acceptance criteria

- [x] 主切面：每张工单结束时、维护者子进程退出之前，子进程里另开一次模型调用做审视，输入包含这段工作的对话文本、立项书、任务计划和授权（含用户在会话里直接说的话）；输出是结构化的范围记录（范围变更或越界，附说明），交给守护进程保存；这次调用不出现在维护者的会话里。审视用规格定的便宜模型（代码常量），测试里由 faux provider 扮演。pi 契约测试里加上"子进程里能在会话之外另开一次模型调用并拿到用量"的用例。
- [x] 主切面：维护者会话压缩时，扩展在 `session_before_compact` 里拿到待压缩的消息、转成文本送审，审视结果用 `appendEntry` 存进会话，同时交给守护进程保存。pi 契约测试里加上"压缩前钩子能拿到待压缩的消息并 `appendEntry`"的用例。
- [x] 主切面：项目维护者的范围变更写进该项目档案的范围记录（文件内容可断言）；越界不写成范围变更，而是在待我处理放一条越界通知（不推送、不卡任务，照常算未读，待我处理的小红点亮起）；两种情况下维护者都不被暂停，当前工单照常继续。
- [x] 主切面：下一次唤起维护者时，`before_agent_start` 从守护进程取最近 5 条范围记录，拼到系统提示末尾，标题"近期范围记录"；超过 5 条时只取最近的 5 条；换了新的工单分段、旧段的 `appendEntry` 不在上下文里时也能拿到。pi 契约测试里加上"`before_agent_start` 能改系统提示"的用例。
- [x] 主切面：不属于项目的任务的维护者在压缩时同样被审视（对照任务计划和用户给过的授权），范围记录写进该任务的产出区（文件内容可断言），越界同样放不推送的通知。
- [x] 主切面：每条范围记录都作为事件出现在对应维护者会话的频道里，带上类型（范围变更 / 越界），供时间线标出。
- [x] Web UI：简版项目页显示范围记录，范围变更和越界分开标出；不属于项目的任务，范围记录显示在任务详情里；待我处理里能看到越界通知。前端状态层回放主切面录下的、含一条越界和一条范围变更的事件流，项目页和待我处理显示正确。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：工单结束的时点和按工单分段归 16，本票接上审视；项目档案里的范围记录文档由 15 号票建好；时间线要点层、全局层上范围变更和越界的标记样式归 25；审视那次模型调用的用量记进 token 账本归 24：记在对应维护者的任务或项目名下，标"范围审视"（24 先完成时直接记；没完成时至少把这条用量连同标记上报给守护进程）。
- 范围审视是软约束，和守卫是两道独立的闸：审视不拦任何工具调用，也不暂停维护者。
- 范围记录以守护进程保存的为准（第 3 节"业务状态不进 pi 会话"）；会话里的 `appendEntry` 只是副本，"最近 5 条"、项目页和任务详情的展示都从守护进程取。
- 工单结束的审视要在子进程退出前做完：闲置退出（12 号票）要等审视结果交给守护进程之后。
- 对应用户故事：82–85、105（范围记录部分）。

## Comments

- 2026-10-08（实现，18 号票的 agent，变基到 14 号票之后的 main 5d78061）：规格没写清、又必须定的地方，按最保守、最贴近规格的做法定了（难逆转的写进了 ADR-0016）：
  - **在哪跑、怎么跑**：审视在维护者自己的子进程里，用同一个 `ModelRuntime` 的 `completeSimple` 另开一次调用（不进维护者的会话，用量另报一条 `scope_review`）。审视用的模型是 `daemon.ts` 的常量 `SCOPE_REVIEW_MODEL`（`deepseek/deepseek-flash`，思考档位 `high`），和维护者、秘书的模型一样写在代码里，没放进配置文件；测试经 `startDaemon` 的 `scopeReviewModel` 换成 faux。宿主协议升到 9（装配参数 `scopeReview`、命令 `scope_context` / `scope_review`、报告 `scope_review_result`）。
  - **输出**：要模型只回约定的 JSON（`{"records":[…]}`），不用工具调用强制格式；取不出就当这次审视没做成：不卡工单、照常结束，维护者会话里一条说明（给用户看，不交给维护者）、日志里一行。子进程中途退出、超时（配置的单次模型调用超时加 30 秒）同样。
  - **对照物**：立项书（项目档案的 `charter.md`，最多 4000 字）、任务书（目标、验收标准、约束）、现在生效的计划（确认过的；还没确认过的用最新交上去的那版：阶段和交付件、授权项、工具包、用户说过的限制、假设）、用户在这个维护者会话里直接说的话（最近 20 条，跨会话分段：用户在对话段里同意的事，之后的工单里也算授权过）。审视的工作记录用 pi 压缩时的写法（`serializeConversation`）。
  - **哪些时候审视**：压缩会话时（项目维护者、任务自己的维护者都有）；项目维护者的**工单段**结束时——写回之后，以及催写回到了次数转用户拍板时（工单照样结束，工作照样要审视）。**对话段结束时不审视**（规格只说"每张工单结束时"；对话段多在维护者闲置退出时结束，那时子进程已经退了），**重置维护者时直接结束的段不审视**。任务自己的维护者没有工单，只在压缩时审视。工单结束时审视的是会话里还没审视过的部分（上次压缩留下的和之后的）。
  - **子进程退出之前**：子进程审视时排在后面的命令（含闲置退出的 `exit`）等它做完；agent 管家在有守护进程要的审视在做时不闲置退出（真模型审视可能超过 15 秒的退出宽限）。子进程已经不在了（闲置退出之后才收尾、守护进程重启后接着收尾）就按这一段的装配再拉起一个来审视。审视期间维护者又处理起这一段的输入（用户插话），这次的结果不用，这一轮结束后收尾时重新审视。
  - **存**：每条发现一条 `scope_record` 事件（项目维护者的在项目列表频道，不属于项目的任务的在看板频道——前端整条补发，项目页拿得全）、维护者会话频道上一条同种类的 `timeline_record`（25 号票的种类表里本来就有 `scope_change` / `out_of_scope`，没加新种类），越界另有一条待我处理的 `out_of_scope` 通知（`non_blocking`，动作"知道了"，**不调 `inbox.alert`**），都和工单的结束（或压缩时的那次追加）同一事务。项目档案的 `scope-records.md`（不属于项目的任务：`outputs/<任务>/scope-records.md`）是事件的投影：追加之后往文件里添一行，启动时按记录号补上没写进去的；**越界也写进文件**（种类写明，规格的"越界不写成范围变更"理解为不当成范围变更记）。范围记录以事件为准。
  - **近期范围记录**：按维护者取最近 5 条（范围变更和越界都算），越早的在前，以"## 近期范围记录"为标题拼到系统提示末尾；没有记录不拼。守护进程在拉起时放进装配、之后变了在下一条输入之前送过去（不让子进程回头问）。
  - **任务详情**：不属于项目的任务显示它自己的范围记录；项目的任务也显示项目维护者做它的工单时记下的（按任务认）。
  - **越界通知上不做"算范围变更（是我让它做的）"**（原型的假数据里有这个按钮）：规格没写，留给后续；用户可以直接和维护者说。
  - **活动状态**：审视在做时活动状态不另报"范围审视中"（说明的种类在协议包的 `ActivityDetail` 里，留给后续），按原来的算。
  - **删除项目**：项目的 `scope_record` 一起改写（摘要、说明、依据换成删除标记）；越界通知的数据里有项目编号，随待我处理里属于项目的事项改写。彻底删除某条素材时，范围记录里引着的同一段原话不跟着改（同 16 号票的工单内容），留给后续的票。
  - **测试底座**：faux 剧本加了 `reply_with_context`（回复里的 `{{context}}` 换成这次调用看到的上下文），主切面和契约测试借它核对审视的输入；`startTestDaemon` 加了 `scopeReviewer` 和 `scopeReviewerTokensPerSecond`，给的剧本后面总接上"都在范围之内"（`NO_SCOPE_FINDINGS`），别的用例不用管工单结束时的审视。
  - **24 号票的主切面**（`token-ledger.test.ts` 的"范围审视和压缩的用量"）：工单结束时的范围审视改成真的（审视剧本的一步带用量），断言不变；任务自己的维护者压缩时的、对话段里的仍用构造的用量。
  - **重新录的事件流**：工单结束时的审视记在任务名下，看板频道上多 `token_totals`：`work-orders-queue`（`token_totals` 18 → 22）、`project-lifecycle`（3 → 4），别的帧没变。新录了 `scope-review`（只录项目列表、待我处理、看板、卡片四个频道：维护者会话里有压缩用的一大段材料）。
- 2026-10-08（两轴评审后，18 号票的 agent，变基到 0a92920，宿主协议保持 9）：
  - **验收标准的措辞**：第一条里"审视用配置里的便宜模型"改成"规格定的便宜模型（代码常量）"——审视的模型是 `daemon.ts` 的常量 `SCOPE_REVIEW_MODEL`，和 `SECRETARY_MODEL`、`MAINTAINER_MODEL` 一样写在代码里（规格第 21 节"范围审视用的便宜模型也是它"），不在配置文件里。
  - **彻底删除**（规格第 12 节"范围审视的细则"）：审视的模型原样引了用户的话还是转述了，不去辨认——范围记录上记着这次审视看到的用户原话从哪来（`sources`：对照物里的消息和审批卡上的批准、会话里交给维护者的输入），彻底删除其中一条时，凡是看到过它的范围记录都改写（摘要、说明、依据换成删除标记，记录本身、种类、归属留着），连带时间线记录和越界通知，再追加一条改写后的新版本（项目页、项目档案里的文件据此换掉）；会话文件里审视结果的副本有彻底删除就整个换掉。宁可多改：一条消息在对照物里的那段时间里做的审视都会被改掉。开着的页面上时间线记录、越界通知要刷新才换（和别的被改写的事项一样）。
  - **工单内容**（16 号票）：工单的内容改写函数早已登记，但用户的话进工单内容只有一条路：打回计划时写的意见原样转进去，而计划卡上的决定（`plan_decided`）没有改写函数，彻底删除它整个被拒；17 号票起维护者派工单时还会转述。所以写进 `PURGE_LIMITS`："交给项目维护者的工单内容里转述的话"删不掉。
  - **重置**：工单段里干过活、还没审视就重置的（工单做到一半、写回中途、审视做到一半），时间线上记一笔"重置时这段没做范围审视"（新种类 `scope_review_missing`，"没做范围审视"，严重度"留意"，进要点层，同"没写回档案"）；对话段本来就只在压缩时审，重置时不记。审视做到一半的那次结果回来时这一段已经结束，不用。
  - **对照物**多了用户在审批卡上批准过的调用（这个维护者最近 20 条：工具的中文名和参数摘要），审视的说明里写明批准过的算授权过。
  - **越界通知上仍不做"算范围变更"按钮**；越界也写进项目档案、写回催满也审视、项目任务的任务详情显示范围记录，按评审保留（已补进规格）。
