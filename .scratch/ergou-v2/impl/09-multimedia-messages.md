# 09 — 多媒体消息

Status: done
Blocked by: 04（秘书聊天最薄端到端）
Spec: [第一阶段规格](../spec.md) 第 5 节（前端协议）、第 7 节（秘书）、第 18 节（数据目录与备份）、第 21 节（实现细节补充）

## What to build

用户在秘书页给秘书发图片和文件，秘书的回复也能带图片和文件（比如它在草稿区算好的表、生成的图）。大文件走分片续传：网断了接着传，不用从头来，收尾时用 sha256 校验原始上传的字节。媒体按 sha256 只存一份，下载支持 Range；图片入库时剥掉 EXIF，剥过的才是入库版本，消息和素材引用的都是它的哈希。秘书页往上滚动时按页加载更早的历史。

发给模型之前，消息经过一个带版本号的纯函数投影：卡片换成一行摘要；图片按模型能力投影，不支持视觉的模型看到"[图片：文件名]"；文本类文件（含 markdown、代码、CSV）内联前 32 KB，PDF 先抽取文本再同样处理，其他类型只给文件名、类型和大小；语音换成转写（第一阶段只预留）。投影规则固定，保证提示词前缀稳定。要读附件全文，agent 用"读取附件"工具，只能读自己会话里的附件。

## Acceptance criteria

- [x] 分片续传上传（自定义协议）：建上传 → 按偏移写分片 → 带 sha256 收尾，收尾校验的是原始上传字节的 sha256。主切面：上传到一半断开，重新连上后从服务端已收到的偏移继续，不重传已收到的字节；收尾的 sha256 不符时拒绝、不入库；超过单文件上限（默认 200 MB，可配置）在建上传时就被拒。
- [x] 媒体按入库版本的 sha256 存在数据目录的素材区，同样的内容只存一份；下载支持 Range（返回 206 和正确的字节段）；第一阶段不生成缩略图等派生物。
- [x] 图片入库时剥掉 EXIF：上传一张带 GPS 信息的 JPEG，下载回来的文件里没有 EXIF。剥过 EXIF 的是入库版本：收尾校验用原始字节的 sha256，入库和下载用剥过之后的内容，消息里的图片 part 和素材引用的都是入库版本的哈希（测试断言两个哈希不同、引用的是后者）。
- [x] 用户 → 秘书：秘书页能选图片和文件发送，显示上传进度，断网恢复后接着传，在手机竖屏宽度下可用；消息带图片 part 和文件 part；聊天里图片直接显示、文件可以下载；多个前端同步看到。
- [x] 秘书 → 用户：秘书能把草稿区里的文件作为附件发进聊天，文件复制进媒体库长期保留；之后删掉草稿区里的原文件，聊天里的附件照样能下载。
- [x] 发给模型前的投影是带版本号的纯函数：卡片引用 → 一行摘要；图片 → 模型支持视觉时作为图片输入，不支持时为"[图片：文件名]"（模型能力从配置读）；文本类文件（含 markdown、代码、CSV）→ 内联前 32 KB，超出的部分提示用"读取附件"工具读；PDF → 先抽取文本，再按文本类处理；其他类型 → 只给文件名、类型和大小；语音 → 转写（只预留）。同样的输入和版本，输出逐字节相同（快照测试，覆盖上面每一类）。
- [x] "读取附件"工具：agent 用它按附件引用读全文（文本类读原文，PDF 读抽出的文本），只能读自己会话里的附件；读别的会话的附件被拒并说明原因。主切面（faux 剧本）：用户发一个超过 32 KB 的文本文件，秘书看到前 32 KB，调用"读取附件"读到全文；伪造一个别的会话的附件引用去读，被拒。
- [x] 历史分页：HTTP 接口按页返回某个会话更早的消息；分页结果和 WebSocket 上的事件在交界处不重不漏。秘书页往上滚动时加载更早的历史。
- [x] 产生对应的素材事件：用户消息事件的负载里带附件引用（入库版本的 sha256、文件名、类型），够 08 号票把附件记为"外部、不可信"的引用加内容哈希。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 被素材引用的媒体永不回收；本票不做媒体回收。
- 草稿区和它的围栏在 07 号票，本票不依赖 07。07 未完成时，"秘书发附件"这条用例直接往草稿区目录放文件来测；07 落地后，这个发附件的工具照常经守卫。
- 附件存在素材区，在秘书的围栏（草稿区、只读项目档案）之外。agent 读附件只走"读取附件"工具，按附件引用读、不按路径读，所以不落入"越出项目目录"；它在工具注册表（03）里标"只读或幂等"、不落入任何类别，"只能读自己会话里的附件"由这个工具自己保证。

## Comments

2026-10-08 实现说明（子 agent，分支 `worktree-agent-a71a4f3271eb56a12`）。验收标准全部做到；下面是规格没写死、按最保守最贴近规格的做法定下的地方，和后面的票要知道的事。

- **媒体库**：`materials/media/<sha256>` 平铺存放，文件名就是入库版本的 sha256（**媒体 id = 入库版本的 sha256**，64 位小写十六进制），先写临时文件再改名。还没收尾的上传在临时区 `tmp/uploads/`（`<id>.json` 记文件名、类型、总字节数，`<id>.part` 是收到的字节，收尾后留一个 `<id>.done.json` 让重复收尾拿到同一个结果）；这些文件靠以后临时区的 7 天清理收掉，本票没做清理。
- **分片续传的细节**：服务端已收到的偏移就是 `.part` 的大小；一个分片的请求中途断了，已经写下的字节照样算数（不是按整片作数），前端查进度后从那里接着传。同一个上传同时只写一个分片（第二个回 409 `busy`），查进度会等正在写的分片收尾再报。收尾的 sha256 不符时这次上传作废（422，删掉 `.part`），前端从头再传。单文件上限是配置 `media.maxUploadBytes`（默认 200 MB），超了在建上传时就回 413。Web 一片 1 MB，sha256 在浏览器里分段算（WebCrypto 只能一次喂完整个文件，200 MB 要整个读进内存），只在收尾前算一遍。
- **剥 EXIF（规格将改为"去掉 GPS、相机等全部 EXIF，只留方向"）**：JPEG 原图的 EXIF 方向不是"正常"（1）时，入库版本补一个**只含方向这一项**的最小 EXIF——不然手机竖拍的照片在浏览器里会躺倒；GPS、相机、时间等一概不留。方向是 5–8（转了 90°）时，part 里的宽高按显示出来的方向对调。方向正常或没写方向时，入库版本里没有任何 EXIF（主切面"上传带 GPS 的 JPEG，下载回来没有 EXIF"用的就是这种；另有一条方向 6 的手机竖拍照片的主切面测试，断言只剩方向、没有 GPS）。另外 XMP、IPTC（APP13）、注释、多图索引（APP2 的 MPF）也去掉，**图像结束标记之后的数据一律截掉**（MPF 的第二张图、动态照片附带的视频等；为此剥元数据时走完整个文件的各段和各次扫描，不在第一个扫描处停下）；PNG 去掉 eXIf 和文字块（XMP 在 iTXt 里）；WebP 去掉 EXIF、XMP 块并清标志位。只认 JPEG、PNG、GIF、WebP 这几种浏览器能直接显示的为"图片"（按内容认，不看文件名和声明的类型）。**HEIC、TIFF（以及 SVG 等）本阶段按普通文件原样存，未剥元数据**，不当图片处理、不在聊天里直接显示——它们里面同样可能有 GPS，要剥得等以后的票。
- **下载**：只有认得的图片 `inline`，其他一律 `attachment` + `application/octet-stream`，并带 `Content-Security-Policy: sandbox`，免得用户上传的 HTML、SVG 在本机源下跑脚本；文件名经 `?name=` 带上（RFC 5987）。Range 只支持单个区间，多个区间时整个发（200）。
- **发消息时以服务端为准**：图片的类型和尺寸、文件的大小取入库的；文件的类型按扩展名认得的优先（浏览器常把 .md 报成空、把 .ts 报成视频），认不出才用前端声明的。前端按收尾响应里的 `kind` 决定发图片 part 还是文件 part（协议包的 `attachmentPartFrom`）；把不是图片的媒体当图片 part 发会被拒。"作为材料投喂"归 21 号票：输入框的附件菜单里先不出现，守护进程也不把 `asMaterial` 写进事件（前端带了也丢掉）。
- **用户消息事件就是素材事件的来源**：负载里的图片 part、文件 part 带 `mediaId`（入库版本的 sha256）、文件名和类型，08 号票据此把附件记成"外部、不可信"的引用加内容哈希，不另加事件类型。
- **投影第 1 版的格式**（`conversation/projection-v1.ts`，在 `model-projection.ts` 里按版本登记；期望输出是 `test/model-projection.test.ts` 里手写的字面量）。第 1 版用到的常量和小函数（文本扩展名表、附件分类、大小的说法、32 KB 上限、解码、时间标记）都归这个文件自己，不从会变的模块取；发消息、读取附件等日常判断用 `media/file-types.ts`（不随投影版本变）。调用方先问这一版要什么内容（`contentNeeded`：文本类的前 32 KB 原始字节、PDF 抽出的文本）再读文件：
  - 第一行是本地时间标记 `[YYYY-MM-DD 周X HH:mm ±HH:MM]`（主会话追加的需求：发送时间按配置 `timeZone` 换算，默认本机时区；秘书据此理解"明早""下周一"，标记只加在每条新消息上、不改系统提示）；之后各 part 空一行；
  - 文本类附件：`[附件：名字（类型，大小，附件引用 <sha256>）]` 加"附件内容开始/结束"两行夹住的内容；超过 32 KB 只放前 32 KB（按原始字节数，不切断字符），末尾提示用 `read_attachment` 读全文。文本先按 UTF-8 解，不是合法 UTF-8 再按 GB18030 解（Excel 导出的中文 CSV），都不行或含 NUL 就写"内容不是可读的文本"；
  - PDF 用 `unpdf` 1.8.1（自带 pdf.js 6.1.200、没有别的依赖，用到时才加载）抽文本，按抽出文本的 UTF-8 字节数截 32 KB；抽不出（扫描件）写一句说明。抽取在守护进程主线程里做、每次现抽（不存派生物），很大的 PDF 会短暂占住事件循环，真成问题再挪到 worker；
  - 卡片引用的一行摘要由调用方给：秘书按消息里的 `card_ref` 从卡片视图取卡片的纯文本降级 `text`（06 号票卡片类型注册表的 `toText` 生成），投影成 `[卡片：摘要]`；卡片找不到时只出 `[卡片 <id>]`；
  - 推理、工具调用、工单分隔各有固定写法，见代码注释。
- **模型能力**：配置 `models["provider/模型 id"].vision`，没配的一律不支持视觉。pi 的模型目录里 deepseek-flash 标着能收图片，但没实测过，示例配置里写成 `false`；要开得先手动冒烟。支持视觉时图片经宿主协议 `user_input.images`（base64）交给 pi 的 `prompt(text, { images })`，pi 会解码、缩放后再发给模型（契约测试 `host-tools.contract.test.ts` 验了图片到达模型）。
