## What to build

做完后，确认过的任务能自己跑完。排队中的任务在全局名额（默认 3 个，可调）空出时进入执行中，由它的维护者按计划逐阶段执行：计划与阶段控制器保管当前阶段，授权项只在所属阶段内有效，前置阶段没验收的阶段不能开始，当前阶段和它所属阶段组上的授权项、时序规则交给守卫检查。落在"计划里列了才做"类别里的操作（比如任务里越出项目目录），计划授权了就直接做；落在"先问我"类别里的操作，计划里写了、授权项里列了也照样在执行时当场问。某个对象被判过"永不"之后，再对它做对外动作要先问。每次唤起维护者、每次压缩之后，运行时注入一块"计划摘要 + 当前阶段 + 授权 + 边界"的上下文消息，维护者压缩后也不会忘掉约束。

维护者调用"宣布阶段完成"后，控制器跑这个阶段的验收：能写成脚本的标准由钩子在工作目录里运行；写不成脚本的派一个评审子 agent，只给固定的只读工具包，在新上下文里只看交付件和验收标准来判，结论卡上标"评审判定"；计划里标明"由你验收"的才进待我处理等用户。全部阶段验收通过，任务自动完成。维护者判失败必须说明原因，用户可以重试或取消；对已完成的任务，用户可以要求返工，只重开出问题的阶段和它的下游。用户随时能暂停、继续、取消任务。某一支在等用户（审批挂起、"交给我做"、由我验收）时，不依赖它的阶段继续推进，任务仍是执行中、占名额；所有能推进的分支都在等用户时，任务才转"等我"并写明原因。等我、已暂停的任务要恢复执行时名额已满，就回到排队中。维护者报告进展时，任务时间线上出现进度卡。

任务详情页可用：看维护者会话（和秘书聊天共用会话组件）、阶段抽屉和计划卡，还能在输入框里直接给维护者下指令；它正在干活时，这句话在它下一步之前插入，记进这个任务的时间线、不建新卡。演示：faux provider 剧本跑一个两阶段任务——第一阶段脚本验收通过，第二阶段评审判定通过，任务自动完成；再要求返工第二阶段，看到只有它被重开。

## Acceptance criteria

- [x] 主切面：全局最多 3 个任务（可配）处于执行中，多出的按排队先后留在排队中；等我、已暂停的任务不占名额，名额空出时排在最前的任务自动开始；等我或已暂停的任务要恢复执行（继续、批准后唤起）而名额已满时，回到排队中。某一支在等用户、其他阶段还能推进时，任务保持执行中并占名额；所有能推进的分支都在等用户时才转等我。07 号票产生的审批"挂起"事件让这一支停下，按上一条规则转等我（原因"审批"）；用户事后批准后，审批记成一条按调用指纹匹配的一次性授权，任务回到执行中（名额满则排队中），运行时唤起维护者并附一条"某某已获批准，可以重试"；"交给我做"事项同样让这一支停下，用户点"已完成"后这一支继续。任务里的审批卡和"交给我做"事项紧急度按卡住任务算。
- [x] 守卫切面 + 主切面：维护者用到不属于当前阶段的授权项时不按授权放行，而是返回把它拉回当前阶段的说明；前置阶段没验收时不能开始该阶段；守卫拿到的是当前阶段加所属阶段组的授权项和时序规则；维护者提交计划时，计划里的时序规则先过 05 号票的规则校验，不过的提交失败并返回原因。任务里落在"计划里列了才做"类别（包括越出项目目录）的调用，有对应授权项时直接放行、没有时先问；落在"先问我"类别的调用，即使授权项里列了也当场问。控制器的硬检查：某个对象被判过"永不"之后，再对它做对外动作要先问；读过 `.env` 或密钥文件后对外发送由 05 号票的规则模板一律禁止，不经这条硬检查重复判一遍。
- [x] 主切面：每次唤起维护者、每次压缩之后，会话里出现一条重注入块上下文消息（计划摘要、当前阶段、授权、边界），系统提示不变；计划、授权、阶段只存在二狗自己的存储里，不靠会话。
- [x] 主切面：维护者调用"宣布阶段完成"后——脚本方式的标准在工作目录里运行，按退出码和输出判定；评审方式的派一个评审子 agent（只读的固定工具包、新的上下文、输入只有交付件和验收标准），结论卡上标"评审判定"；用户方式的进待我处理，这个阶段停下等用户验收（原因"由我验收"，没有其他能推进的阶段时任务转等我）。只有维护者自检的阶段不算验收；不通过时把结果交回维护者，阶段不推进。评审子 agent 不占全局名额。
- [x] 主切面：全部阶段验收后任务自动转已完成。维护者判失败必须带原因，不带原因的失败被拒；失败后待我处理出现"失败后的抉择"事项，用户可以重试（回到执行中）或取消。用户对已完成的任务要求返工时，按依赖重开指定阶段和它的全部下游，其余阶段保持已验收，由同一个维护者接着做。用户能暂停、继续任务，能取消任何未结束的任务；维护者"转为等我"（卡住求助）时，任务卡和待我处理都写明原因；等我的事项永不自动批准。维护者"报告进展"时产生一张进度卡（所属任务、第 N/M 阶段、进展说明），进度卡在卡片类型注册表里登记（含纯文本降级版本）。
- [x] 主切面：用户在任务详情的输入框发话——维护者休眠时唤起它；正在干活时作为插话，在它下一步之前插入；这句话记进任务时间线，不建新卡。
- [x] pi 契约测试里加上对应用例：插话在下一步之前插入；压缩之后能注入一条上下文消息；工具白名单之外的工具不可用（评审子 agent 的只读工具包）。
- [x] 主切面：产生对应的素材事件——任务结局（完成、失败、取消）；用户对产出的反应（"由你验收"的结论、要求返工）；用户在维护者会话里的发言。由 08 号票采集；若 08 尚未完成，至少事件类型和负载就绪。
- [x] Web UI：任务详情页显示维护者会话、阶段抽屉（各阶段状态、验收方式和结果）、计划卡、进度卡和直接下指令的输入框；看板上的任务卡显示"第 N/M 阶段"和等我原因。前端状态层回放主切面录下的"两阶段任务到完成、再返工"事件流，阶段抽屉和看板状态正确。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

规格没写清、按最保守做法定下的：

- **执行状态全在任务里**：`Task.stages.list`（每个阶段的状态、等什么、验收结果、宣布完成的次数），每次变化是看板频道上的一条 `task` 事件（阶段的变化带 `stageId`），不另开频道、不放 pi 会话里。任务的变化用 `tasks.buildChange` 拿事件、照旧过 `TASK_TRANSITIONS`（加了：执行中 → 已完成 `system`、等我 → 已完成 `system`、失败 → 已取消 `user`）。排队先后在 `tasks` 视图加了 `queued_seq` 列（旧库启动时补列）。
- **控制器替维护者开始阶段**：开始执行、一个阶段验收通过、一支不用再等了时，自动开始下一个能开始的阶段（开始过的优先接着做），维护者收到写明交付件、验收标准、模式的通知；维护者也可以用 `start_stage` 换（前置阶段没验收的拒绝）。可并行的阶段由维护者依次做，真正并行在 20 号票。
- **一支在等用户**按阶段算：审批挂起、交给我做停的是调用所在的阶段（`origin.stageId`），由我验收停的是那个阶段；都在等时任务的等我原因取第一个在等的阶段的。批准或拒绝（`approval_decided` 且 `resumed: false`）都让这一支接着走（拒绝时维护者收到 07 号票的"已被用户拒绝"通知，自己决定怎么办）。
- **由我验收**：脚本和评审先跑，都过了才放进待我处理（`stage_acceptance`，卡着任务，动作"验收通过""退回"）；任务详情里也能做（`task_action` 的 `accept_stage` / `return_stage`，退回可附原因），做了待我处理里那条自动记成处理过。退回的原因只进"用户对产出的反应"事件（素材，彻底删除时改写）和交给维护者的通知，不写进阶段的验收结果和进度卡。
- **评审子 agent 交结论用代为执行的 `submit_review`**（每条标准按编号给通过与否和理由），没交就结束算评审出错、这几条没通过；脚本都过了才派评审（脚本没过时省一次评审）。评审的 agent id 是 `review-<任务>-<阶段>-<第几次>`，每次新会话。
- **脚本验收**用 Git Bash，在工作目录（任务的产出区）里跑，环境和 agent 子进程一样（系统变量白名单；联网开关关着时加无效代理），进 Job 对象，10 分钟超时；脚本是用户确认过的计划里的，不再经守卫。
- **失败、卡住、取消**：`fail_task` 原因必填（空白也拒）；`wait_for_user` 任务转等我（`stuck`），用户在任务详情里回话或点"继续执行"就接着执行；取消任务时它留下的卡着任务的事项改成不卡任务（不自动处理，等我的事项从不自动批准）。失败后的取消是用户的迁移（表里加了一行）。
- **暂停**中止维护者手头这一轮（排着的输入留着，继续后照常处理）；工具执行到一半被中止时 pi 报的是出错（"This operation was aborted"），子进程这一侧按"被要求中止过"改报 `aborted`。
- **维护者什么时候处理输入**看任务状态：规划中、待确认、执行中、等我时处理；排队中、已暂停、结束了的输入留在队里（恢复执行后处理）。起草计划和执行之间换装配时，等手头这一条处理完停掉子进程、下次按新的装配拉起（接着同一个会话）。执行装配：`read`、`write`、`edit`、`ls`、`grep`、`find`，工具包开了 bash 才给 bash，联网照计划显式给；系统提示还是同一段（起草和执行都写在里面），计划、阶段、授权只在重注入块里。skill、MCP 的装配在 27 号票。变基到合并了 28 号票的 main 后：执行时工具包开了 bash，带类型的 bash 工具随之出现（和起草时一样经 typedShell.toolsFor）；28 的测试用的 maintainerToolkit 只管起草计划时的工具包。
- **重注入块**：唤起后第一条输入之前作为一条上下文消息注入（pi 的 `sendCustomMessage`，不在回合里）；阶段、状态变了守护进程送 `context_block` 换成最新的，压缩之后（`session_compact`）由子进程里的扩展注入最新的那块。主切面验"每次唤起都注入、是最新的、系统提示不变"，压缩后注入在契约测试里验（主切面造不出真的压缩）。
- **插话**：维护者在处理一条输入时用户又说话，守护进程送 `interject`；子进程在回合结束时报出收下了哪几条（`turn_end.interjected`），这几条记成处理完（`turn_start` + `turn_end completed`），不另起一轮；回合已经结束、没收下的照常排队。
- **被判过永不的对象**：守卫运行时在任务里一次对外调用被判"永不"时记下对象（`never_recorded`，guard 频道；对象取规则步骤里的收件人、网址，推送是仓库、远端和分支），同一任务之后的判定带上 `neverObjects`，对它们的对外动作至少先问，说明里写"被判过永不"。只算"永不"的依据，按规则退回、写受保护区域这类不对外的不记。
- **用到别的阶段的授权**：判定函数发现授权项能覆盖、但属于别的阶段时按规则退回（`pullBack: ["grant_other_stage"]`），说明"属于阶段 sY，当前是阶段 sZ……"，不再只是改成先问。
- **任务完成后的回调** `taskExecution.onCompleted(fn)`：拿到任务、任务书、确认的计划、产出区路径；29 号票的节假日数据导入接在这里（`problems` 不空放一条 `holiday_import_problem` 说明，不卡任务；返工后再完成会再导入一次）。
- **用户在维护者会话里发话**：网关的 `messageScope` 决定能往哪个会话发、消息带哪个任务；已完成、已取消、已归档的任务不再收（要返工用"返工"），失败的还收（重试时维护者能看到）。15 号票合并后 `daemon.ts` 先问项目模块（项目维护者的会话带 `projectId`），再问 `userMessageScope`（任务维护者的会话带 `taskId`）；不是维护者的会话照 15 回 `not_implemented`，没有这个维护者回 `not_found`。
- **事件存储的通知顺序**：`appendBatch` 的一组事件整组排进通知队列。之前一个一个排，订阅者看到组里前面的事件（比如看板上的任务变化）就去处理会话里已经落盘、还没通知的输入时，前端会先收到 `turn_start` 再收到那条输入、把那条输入丢掉。加了一条事件存储的测试。
