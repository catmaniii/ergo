# 13 — 任务执行与阶段验收

Status: ready-for-agent
Blocked by: 05（时序规则引擎与 v1 规则模板）, 12（任务发起与计划确认）
Spec: [第一阶段规格](../spec.md) 第 8 节（任务、计划与阶段）、第 9 节（守卫）、第 3 节（agent 子进程与 pi 封装层）、第 5 节（前端协议）、第 11 节（项目与维护者）、第 15 节（素材）、第 19 节（Web UI）、第 21 节（实现细节补充）

## What to build

做完后，确认过的任务能自己跑完。排队中的任务在全局名额（默认 3 个，可调）空出时进入执行中，由它的维护者按计划逐阶段执行：计划与阶段控制器保管当前阶段，授权项只在所属阶段内有效，前置阶段没验收的阶段不能开始，当前阶段和它所属阶段组上的授权项、时序规则交给守卫检查。落在"计划里列了才做"类别里的操作（比如任务里越出项目目录），计划授权了就直接做；落在"先问我"类别里的操作，计划里写了、授权项里列了也照样在执行时当场问。某个对象被判过"永不"之后，再对它做对外动作要先问。每次唤起维护者、每次压缩之后，运行时注入一块"计划摘要 + 当前阶段 + 授权 + 边界"的上下文消息，维护者压缩后也不会忘掉约束。

维护者调用"宣布阶段完成"后，控制器跑这个阶段的验收：能写成脚本的标准由钩子在工作目录里运行；写不成脚本的派一个评审子 agent，只给固定的只读工具包，在新上下文里只看交付件和验收标准来判，结论卡上标"评审判定"；计划里标明"由你验收"的才进待我处理等用户。全部阶段验收通过，任务自动完成。维护者判失败必须说明原因，用户可以重试或取消；对已完成的任务，用户可以要求返工，只重开出问题的阶段和它的下游。用户随时能暂停、继续、取消任务。某一支在等用户（审批挂起、"交给我做"、由我验收）时，不依赖它的阶段继续推进，任务仍是执行中、占名额；所有能推进的分支都在等用户时，任务才转"等我"并写明原因。等我、已暂停的任务要恢复执行时名额已满，就回到排队中。维护者报告进展时，任务时间线上出现进度卡。

任务详情页可用：看维护者会话（和秘书聊天共用会话组件）、阶段抽屉和计划卡，还能在输入框里直接给维护者下指令；它正在干活时，这句话在它下一步之前插入，记进这个任务的时间线、不建新卡。演示：faux provider 剧本跑一个两阶段任务——第一阶段脚本验收通过，第二阶段评审判定通过，任务自动完成；再要求返工第二阶段，看到只有它被重开。

## Acceptance criteria

- [ ] 主切面：全局最多 3 个任务（可配）处于执行中，多出的按排队先后留在排队中；等我、已暂停的任务不占名额，名额空出时排在最前的任务自动开始；等我或已暂停的任务要恢复执行（继续、批准后唤起）而名额已满时，回到排队中。某一支在等用户、其他阶段还能推进时，任务保持执行中并占名额；所有能推进的分支都在等用户时才转等我。07 号票产生的审批"挂起"事件让这一支停下，按上一条规则转等我（原因"审批"）；用户事后批准后，审批记成一条按调用指纹匹配的一次性授权，任务回到执行中（名额满则排队中），运行时唤起维护者并附一条"某某已获批准，可以重试"；"交给我做"事项同样让这一支停下，用户点"已完成"后这一支继续。任务里的审批卡和"交给我做"事项紧急度按卡住任务算。
- [ ] 守卫切面 + 主切面：维护者用到不属于当前阶段的授权项时不按授权放行，而是返回把它拉回当前阶段的说明；前置阶段没验收时不能开始该阶段；守卫拿到的是当前阶段加所属阶段组的授权项和时序规则；维护者提交计划时，计划里的时序规则先过 05 号票的规则校验，不过的提交失败并返回原因。任务里落在"计划里列了才做"类别（包括越出项目目录）的调用，有对应授权项时直接放行、没有时先问；落在"先问我"类别的调用，即使授权项里列了也当场问。控制器的硬检查：某个对象被判过"永不"之后，再对它做对外动作要先问；读过 `.env` 或密钥文件后对外发送由 05 号票的规则模板一律禁止，不经这条硬检查重复判一遍。
- [ ] 主切面：每次唤起维护者、每次压缩之后，会话里出现一条重注入块上下文消息（计划摘要、当前阶段、授权、边界），系统提示不变；计划、授权、阶段只存在二狗自己的存储里，不靠会话。
- [ ] 主切面：维护者调用"宣布阶段完成"后——脚本方式的标准在工作目录里运行，按退出码和输出判定；评审方式的派一个评审子 agent（只读的固定工具包、新的上下文、输入只有交付件和验收标准），结论卡上标"评审判定"；用户方式的进待我处理，这个阶段停下等用户验收（原因"由我验收"，没有其他能推进的阶段时任务转等我）。只有维护者自检的阶段不算验收；不通过时把结果交回维护者，阶段不推进。评审子 agent 不占全局名额。
- [ ] 主切面：全部阶段验收后任务自动转已完成。维护者判失败必须带原因，不带原因的失败被拒；失败后待我处理出现"失败后的抉择"事项，用户可以重试（回到执行中）或取消。用户对已完成的任务要求返工时，按依赖重开指定阶段和它的全部下游，其余阶段保持已验收，由同一个维护者接着做。用户能暂停、继续任务，能取消任何未结束的任务；维护者"转为等我"（卡住求助）时，任务卡和待我处理都写明原因；等我的事项永不自动批准。维护者"报告进展"时产生一张进度卡（所属任务、第 N/M 阶段、进展说明），进度卡在卡片类型注册表里登记（含纯文本降级版本）。
- [ ] 主切面：用户在任务详情的输入框发话——维护者休眠时唤起它；正在干活时作为插话，在它下一步之前插入；这句话记进任务时间线，不建新卡。
- [ ] pi 契约测试里加上对应用例：插话在下一步之前插入；压缩之后能注入一条上下文消息；工具白名单之外的工具不可用（评审子 agent 的只读工具包）。
- [ ] 主切面：产生对应的素材事件——任务结局（完成、失败、取消）；用户对产出的反应（"由你验收"的结论、要求返工）；用户在维护者会话里的发言。由 08 号票采集；若 08 尚未完成，至少事件类型和负载就绪。
- [ ] Web UI：任务详情页显示维护者会话、阶段抽屉（各阶段状态、验收方式和结果）、计划卡、进度卡和直接下指令的输入框；看板上的任务卡显示"第 N/M 阶段"和等我原因。前端状态层回放主切面录下的"两阶段任务到完成、再返工"事件流，阶段抽屉和看板状态正确。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：
  - 阈值和升级（拉回 3 次、催促、验收退回 2 次第 3 次找用户、预算、无进展 20 分钟）、偏离的逐级升级、累计被拒 5 次暂停任务、计划变更、授权有效期归 14；本票只做"拉回"和"验收退回"本身，不计数。
  - 可并行的阶段在本票由维护者依次执行（不依赖等待中阶段的，可以先做）；用户确认后派子 agent 真正并行归 20。评审子 agent 是验收的一部分，在本票做，不需要用户确认。
  - 单项目任务由项目维护者执行、会话按工单分段归 16；多项目工单的阶段验收（回执齐了再跑）和任务详情里的工单列表归 17；工具包的查看和修改归 27；token 总量归 24；活动状态小圆点和时间线缩放归 25；"中断：不确定 X 是否已执行"这个等我原因归 23；秘书经快速动作暂停 / 继续 / 取消任务归 22。
- 和 07 号票的分工：07 只产生带任务和阶段的审批"挂起"事件、按调用指纹的一次性放行和"交给我做"事项本身；它们在任务一侧的效果（这一支停下、任务转等我、批准后回到执行中或排队中并唤起维护者、紧急度）在本票接上，并加主切面用例。
- 和 03、05 号票的分工：默认处置表（任务里"越出项目目录"是"计划里列了才做"）和"先问我"一定当场问的判定在 03 的判定函数里；本票负责把计划、当前阶段和授权项交给判定函数，并在控制器里做三条硬检查（授权只在所属阶段内有效、前置阶段必须已验收、被判过"永不"的对象再做对外动作要先问）。读过 `.env` 或密钥文件后对外发送归 05 的规则模板（一律禁止），两条不重叠。
- 进度卡在本票登记和产生；它在聊天里的出现方式沿用 06 号票的卡片引用。
- 不属于项目的任务，脚本验收在数据目录里该任务的产出区运行（第 18 节）。
- 用户在维护者会话里直接说的小指令不建新卡（用户故事 47）；时间线的要点层、全局层样式归 25。
- 对应用户故事：38（阶段部分）、39–42、44–51、61、63、79、100、153（维护者会话、阶段抽屉、计划卡部分）。
