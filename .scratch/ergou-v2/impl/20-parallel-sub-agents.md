## What to build

维护者执行任务时，遇到阶段图里可以并行的阶段或步骤，可以用"提议并行"工具提议派子 agent 同时做。运行时据此生成一张并行确认卡放进待我处理，写明是哪个任务、要并行哪些阶段或步骤、派几个子 agent、各做什么；只有用户点了确认，运行时才真正拉起子 agent；用户拒绝，维护者照常一件一件做。做什么由维护者决定；每个子 agent 占自己的子进程，工具包和授权不超过它的维护者，不能写项目档案，做完即解散，结果作为一条消息回到维护者的会话里，维护者接着用。子 agent 不占全局 3 个任务的并发名额。

开发类项目里，维护者先在工作目录里为每个子 agent 建一个 git worktree，子 agent 各在自己的 worktree 里改动，彼此互不覆盖；最后维护者用 28 号票的带类型 git 合并工具，把各条改动合并回工作目录。

演示：faux provider 剧本里，维护者对两个互不依赖的阶段提议并行，待我处理出现并行确认卡；点确认后两个子 agent 被拉起，各自在自己的 worktree 里改动并结束，任务详情的维护者会话里出现两条结果；维护者调用合并工具后，工作目录里两边的改动都在。

## Acceptance criteria

- [x] 主切面：维护者调用"提议并行"后，待我处理出现一张并行确认卡（在卡片类型注册表里登记，带纯文本降级），写明任务、要并行的阶段或步骤、子 agent 个数和各自的工作说明；用户确认前不拉起任何子 agent 进程，可并行的阶段仍按顺序执行。
- [x] 主切面：用户确认后，运行时为每个子 agent 拉起独立的子进程，递送维护者给它的工作说明；用户拒绝则不拉起任何子 agent，维护者收到拒绝后照常串行执行。并行确认卡的按钮闭环沿用 06 号票（按版本条件更新，两个前端同时点时后到的得到"已被处理"）。
- [x] 守卫切面 + 主切面：子 agent 的工具包是其维护者工具包的子集，维护者没有的工具子 agent 的会话里也没有；子 agent 的每次工具调用照常送守卫，按其维护者所属任务的计划、当前阶段和授权项判定，用不到维护者没有的授权。
- [x] 守卫切面：子 agent 的文件工具写项目档案一律拒绝（不问），写工作目录（含自己的 worktree）照常判定；写受保护区域（配置区、密钥区、数据库区、二狗程序目录）一律"永不"；读密钥区照常拒绝。
- [x] 主切面：子 agent 做完后进程退出，结果作为一条消息出现在维护者的会话里，维护者下一回合能用到；在任务详情的维护者会话里能看到这条结果。
- [x] 主切面：全局并发上限为 3、已有 3 个任务处于执行中时，其中一个任务派出子 agent 不受并发名额限制，排队中的任务也不会因此提前开工；子 agent 仍受同时存活子进程上限（默认 8）约束，满了时新的子 agent 按 12 号票排队，活动状态显示"排队"。
- [x] 主切面（临时 git 仓库作工作目录）：维护者在工作目录内为两个子 agent 各建一个 git worktree；两个子 agent 各在自己的 worktree 里改动并提交，主工作目录看不到这些改动；维护者用带类型的 git 合并工具合并后，工作目录里同时有两边的改动，合并调用在时间线上是一次带类型工具调用、不带"通用 bash"标记。
- [x] 用户对并行确认卡的确认或拒绝产生对应的素材事件（审批决定；由 08 号票采集，若 08 尚未完成，至少事件类型和负载就绪）。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：13 号票的评审子 agent（固定只读工具包、新上下文、只看交付件和验收标准）不需要用户确认，也不走本票的并行确认卡；本票只管为并行而派的子 agent。子 agent 的活动状态小圆点归 25；子 agent 的 token 用量按 agent 细分归 24——本票要保证子 agent 上报的用量事件带上子 agent 身份和所属任务，供 24 使用。
- 同时存活子进程的上限、满了排队、超时、闲置退出、孤儿回收是 12 号票 agent 管家的事，本票只是它的又一个使用者。
- 子 agent 不能写项目档案，所以 16 号票"每段结束检查进展文档是否写回"只针对维护者，不针对子 agent。
- **worktree 和合并**：worktree 由维护者建在工作目录内（绑定了外部路径的，就建在那个外部路径里），这样子 agent 的文件工具都落在路径围栏之内。建 worktree 没有带类型的工具，维护者用 bash 建，照常过守卫、标"通用 bash"。合并用 28 号票的带类型 git 合并工具（合并有冲突时的行为见 28）。本票的依赖里没有 28：若本票先做，合并那一步的主切面用例先用通用 bash 的 `git merge` 驱动，28 完成后改用带类型的合并工具。
- 子 agent 在自己的 worktree 里提交，用的是 28 号票的带类型提交工具，前提是维护者的工具包里有它。

## Comments

实现概要（2026-10-08）：新模块 `packages/daemon/src/sub-agents/`（`createSubAgents`，`daemon.subAgents`）：维护者的"提议并行"工具 `propose_parallel`（`tools.ts`）、并行确认卡（`card.ts`，负载 `ParallelCardPayload` 在协议包 `parallel-schema.ts`）、提议 / 用户决定 / 拉起子 agent / 结果交回维护者（`sub-agents.ts`）、子 agent 的装配从维护者收窄（`assembly.ts`，纯函数）、`sub_agents` 频道上的事件（`events.ts`）和派生视图（`views.ts`）、"审批决定"素材和彻底删除的改写（`material-source.ts`）、子 agent 的系统提示（`system-prompt.ts`）。任务执行控制器加了 `checkParallel`、`parallelStartEvents` 和 `subAgentsOn` 选项；维护者模块加了 `assemblyOf`、`subAgentTools`；`MessageScope` 和消息事件的负载加了可选的 `stageId`、`agentId`。Web 的并行确认卡换成协议负载。接口写在 `docs/dev.md` 的"子 agent 并行"和"任务执行与阶段验收"的"并行"一条。

规格没写清、按最保守做法定下的：

- **并行确认卡不卡任务**（`non_blocking`）：用户处理之前维护者照常一件一件做（这是 AC 的"确认前可并行的阶段仍按顺序执行"）。同一任务再提议时，上一张没处理的卡过期；任务结束（完成、失败、取消、归档）时没处理的卡过期。卡上的两个动作用协议里早就留好的 `parallel`（同意并行）、`sequential`（不并行，按顺序做）。
- **同意时阶段怎么变**：没开始的阶段随卡片更新一起开始（`stage_started`，`by: user`），几个阶段同时是"进行中"；维护者手上那个阶段本来就在做的不变。提议之后维护者按顺序做到了别处（阶段已验收、在验收、在等用户，或者子 agent 的目录被删了），同意被拒（`not_allowed`，说明原因），卡仍待处理，用户可以改点"不并行"。
- **有子 agent 在做的阶段**：维护者不能宣布完成（要等结果回来、合并之后）、不能切过去；换阶段时不放下它；在做的阶段全是子 agent 的时候，控制器看下一步时替维护者开始一个能开始的阶段（"做不依赖它的阶段"）。阶段的状态本身没有加"谁在做"的字段，子 agent 在做哪个阶段记在 `sub_agents` 派生视图里（控制器经 `subAgentsOn` 取）。
- **维护者的当前阶段**（评审后改）：是它自己最后一次开始的那个，记在任务里（`Task.stages.focus`：维护者 `start_stage` 的、运行时替它开始的；用户同意并行时交给子 agent 的不算），由事件推出，暂停、继续、重启后都对；守卫、重注入块、进展卡、看板上的第 N 阶段都按它（`stages.ts` 的 `currentStage`），不按计划里的顺序取。子 agent 交回结果后它的阶段交还维护者：维护者对一个在做、但没有活着的子 agent 的阶段调 `start_stage` 就切过去（手头在做的那个放下），不再回"已经在做了"。
- **子 agent 的目录**：`workDir` 要已经存在、在维护者的工作目录里（相对路径相对维护者的工作目录）；几个子 agent 自己的目录彼此不重叠；不写就和维护者共用工作目录（只限不是开发类的）。**开发类强制各自的 worktree**（评审后加）：开发类的每个子 agent 必须有自己的目录，而且是建在工作目录里的这个仓库的 git worktree（看目录里的 `.git` 文件指向 `<工作目录>/.git/worktrees/`），不满足就拒绝提议并说明原因。"开发类"怎么认：任务自己的维护者没有项目类型，按最保守的——工作目录是 git 仓库就算；项目维护者按立项书的项目类型，16 号票接（`MaintainerAssembly.development`）。worktree 由维护者用 bash 建（通用 bash），本票不加建 worktree 的带类型工具。
- **子 agent 的工具包**：pi 工具、bash 和联网开关照维护者此刻的；代为执行的工具只给带类型的 bash 工具（维护者开了 bash 时，工作目录是子 agent 自己的，用它在自己的 worktree 里提交），维护者推进任务的工具（宣布阶段完成、报告进展、提议并行……）都不给。是维护者的子集这件事在纯函数里保证（评审后改）：维护者的代为执行的工具名放进 `MaintainerAssembly.hostTools`，`subAgentAssembly` 拿候选和它取交集、再去掉维护者专用的，守卫切面有表格用例。skill、MCP 归 27 号票，到时候也从维护者的工具包收窄。
- **工具包变了**（评审后加）：`daemon.subAgents.reassemble(taskId)`，14 号票改计划、27 号票接 MCP 改了维护者的工具包之后调。活着的子 agent 按新的交集重算，变了的照规格"工具包变了立即生效"等它做完手头这一步（当前的工具调用结束、下一次模型调用之前）就结束子进程、按新的装配重新拉起，接着原来的会话，交给它一条"工具包已变更"；还没开始的直接重拉；这一步之后这一轮就做完了的照常交回结果（子 agent 只活一轮，不选"等这一轮结束再重拉"——那时它已经解散了）。只改授权项不用调：守卫每次调用现取任务的计划。
- **结果**：子 agent 这一轮最后一段回复的文字就是结果；这一轮结束就结束进程（做完即解散）。每个子 agent 的结果各是维护者会话里的一条系统消息（交给维护者的输入，带所属任务、阶段、子 agent），维护者下一回合用到；出错写原因。任务暂停、取消、失败、完成时它的子 agent 随之结束，交回一条"停下了"；守护进程重启前没结束的，启动时交回一条"被打断了"（不重新拉起，维护者自己接着做或再提议）。
- **子 agent 的会话和工具调用记录**：pi 会话在会话区 `sessions/sa-<n>/`（每次新会话）；工具调用记录、审批卡引用、交回的结果都进维护者的会话，消息负载带 `stageId`、`agentId`，时间线据此归到所属任务和阶段（25 号票按它着色、区分子 agent）。子 agent 的流式回复不推给前端。
- **审批**：子 agent 的调用照常经守卫，"先问我"的出审批卡（来源写"任务「…」阶段 sX 的子 agent sa-N"），等待期间用户批准就接着执行。等审批超时挂起后用户才批准的（评审后改）：通知进维护者的会话，写明"……是子 agent sa-N 在阶段 X 的调用，用户事后批准了；子 agent 已结束，这次批准用不上了。还要做的话请在阶段 X 里自己重新调用，会再问一次用户"，不说"原样再调用一次会直接放行"（守卫接入运行时加了 `lateNotice` 钩子，由子 agent 模块给说法）；控制器也不再对子 agent 的调用发"先切回 sX 再原样重试"。
- **素材**：`parallel_decided`（协议包登记为 `EVENT_TYPES.parallelDecided`）记成"审批决定"，同意、不同意都是用户在 agent 先提出的提议上的选择，用户附的话是本人打的字；彻底删除只改写用户写的话。
- **名额**：子 agent 经 agent 管家拉起，占子进程名额、满了排队（活动状态"排队"由管家照常报）；它不是任务，不占任务的执行名额。主切面用 `tasks.maxRunning: 1`、`agents.maxLive: 4` 验证（规则和默认的 3、8 一样）。
- **用量（24 号票的账本，变基到 24 之后接上）**：子 agent 的 id 是 `sa-<n>`，拉起时照 24 号票的约定给 `SpawnAgentRequest.ledger`：`{ owner: { kind: "task", id }, role: "sub_agent", stageId: 它被派去的阶段 }`，用量记在它**自己的**阶段（不看维护者此刻在哪个阶段），算进那个阶段的预算（`ledger.stageTokens(taskId, stageId, { budget: true })`），不另数一套。维护者自己的用量记在它的当前阶段：账本的 `currentStage` 照 25 号票取 `taskMessageScope(task).stageId`，它改按任务里记的 `focus` 算（和守卫一致），不再按计划里的顺序取第一个在做的。主切面"维护者的当前阶段"用例验证两边各记在各自的阶段。`daemon.subAgents.ownerOf(agentId)`（或 `sub_agents` 视图的 `getSubAgent`，重启后也在）仍可查它属于哪个任务、哪个阶段、哪个维护者。
