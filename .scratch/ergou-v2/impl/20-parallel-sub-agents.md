# 20 — 子 agent 并行

Status: ready-for-agent
Blocked by: 13（任务执行与阶段验收）
Spec: [第一阶段规格](../spec.md) 第 8 节（任务、计划与阶段）、第 11 节（项目与维护者）、第 3 节（agent 子进程与 pi 封装层）、第 9 节（守卫）、第 5 节（前端协议）、第 21 节（实现细节补充）

## What to build

维护者执行任务时，遇到阶段图里可以并行的阶段或步骤，可以用"提议并行"工具提议派子 agent 同时做。运行时据此生成一张并行确认卡放进待我处理，写明是哪个任务、要并行哪些阶段或步骤、派几个子 agent、各做什么；只有用户点了确认，运行时才真正拉起子 agent；用户拒绝，维护者照常一件一件做。做什么由维护者决定；每个子 agent 占自己的子进程，工具包和授权不超过它的维护者，不能写项目档案，做完即解散，结果作为一条消息回到维护者的会话里，维护者接着用。子 agent 不占全局 3 个任务的并发名额。

开发类项目里，维护者先在工作目录里为每个子 agent 建一个 git worktree，子 agent 各在自己的 worktree 里改动，彼此互不覆盖；最后维护者用 28 号票的带类型 git 合并工具，把各条改动合并回工作目录。

演示：faux provider 剧本里，维护者对两个互不依赖的阶段提议并行，待我处理出现并行确认卡；点确认后两个子 agent 被拉起，各自在自己的 worktree 里改动并结束，任务详情的维护者会话里出现两条结果；维护者调用合并工具后，工作目录里两边的改动都在。

## Acceptance criteria

- [ ] 主切面：维护者调用"提议并行"后，待我处理出现一张并行确认卡（在卡片类型注册表里登记，带纯文本降级），写明任务、要并行的阶段或步骤、子 agent 个数和各自的工作说明；用户确认前不拉起任何子 agent 进程，可并行的阶段仍按顺序执行。
- [ ] 主切面：用户确认后，运行时为每个子 agent 拉起独立的子进程，递送维护者给它的工作说明；用户拒绝则不拉起任何子 agent，维护者收到拒绝后照常串行执行。并行确认卡的按钮闭环沿用 06 号票（按版本条件更新，两个前端同时点时后到的得到"已被处理"）。
- [ ] 守卫切面 + 主切面：子 agent 的工具包是其维护者工具包的子集，维护者没有的工具子 agent 的会话里也没有；子 agent 的每次工具调用照常送守卫，按其维护者所属任务的计划、当前阶段和授权项判定，用不到维护者没有的授权。
- [ ] 守卫切面：子 agent 的文件工具写项目档案一律拒绝（不问），写工作目录（含自己的 worktree）照常判定；写受保护区域（配置区、密钥区、数据库区、二狗程序目录）一律"永不"；读密钥区照常拒绝。
- [ ] 主切面：子 agent 做完后进程退出，结果作为一条消息出现在维护者的会话里，维护者下一回合能用到；在任务详情的维护者会话里能看到这条结果。
- [ ] 主切面：全局并发上限为 3、已有 3 个任务处于执行中时，其中一个任务派出子 agent 不受并发名额限制，排队中的任务也不会因此提前开工；子 agent 仍受同时存活子进程上限（默认 8）约束，满了时新的子 agent 按 12 号票排队，活动状态显示"排队"。
- [ ] 主切面（临时 git 仓库作工作目录）：维护者在工作目录内为两个子 agent 各建一个 git worktree；两个子 agent 各在自己的 worktree 里改动并提交，主工作目录看不到这些改动；维护者用带类型的 git 合并工具合并后，工作目录里同时有两边的改动，合并调用在时间线上是一次带类型工具调用、不带"通用 bash"标记。
- [ ] 用户对并行确认卡的确认或拒绝产生对应的素材事件（审批决定；由 08 号票采集，若 08 尚未完成，至少事件类型和负载就绪）。
- [ ] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- **不在本票**：13 号票的评审子 agent（固定只读工具包、新上下文、只看交付件和验收标准）不需要用户确认，也不走本票的并行确认卡；本票只管为并行而派的子 agent。子 agent 的活动状态小圆点归 25；子 agent 的 token 用量按 agent 细分归 24——本票要保证子 agent 上报的用量事件带上子 agent 身份和所属任务，供 24 使用。
- 同时存活子进程的上限、满了排队、超时、闲置退出、孤儿回收是 12 号票 agent 管家的事，本票只是它的又一个使用者。
- 子 agent 不能写项目档案，所以 16 号票"每段结束检查进展文档是否写回"只针对维护者，不针对子 agent。
- **worktree 和合并**：worktree 由维护者建在工作目录内（绑定了外部路径的，就建在那个外部路径里），这样子 agent 的文件工具都落在路径围栏之内。建 worktree 没有带类型的工具，维护者用 bash 建，照常过守卫、标"通用 bash"。合并用 28 号票的带类型 git 合并工具（合并有冲突时的行为见 28）。本票的依赖里没有 28：若本票先做，合并那一步的主切面用例先用通用 bash 的 `git merge` 驱动，28 完成后改用带类型的合并工具。
- 子 agent 在自己的 worktree 里提交，用的是 28 号票的带类型提交工具，前提是维护者的工具包里有它。
- 对应用户故事：52、53。
