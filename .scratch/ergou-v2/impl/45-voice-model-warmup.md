# 45 — 语音模型预热：二狗启动后提前加载合成和识别模型

Status: done
Blocked by: 31（语音识别）, 32（agent 用语音回复）, 38（分段合成）
Spec: [第一阶段规格](../spec.md) 第 22 节（语音消息）

## What to build

用户真机实测：二狗重启后的第一条语音，识别用了 36 秒（要先把 large-v3 加载进显卡），之后的都不到 1 秒。合成那边也一样：audio.cpp 按需加载模型（`lazy_load`），第一次请求才加载，加载后一直留到它自己退出。

用户 2026-10-09 定：**二狗启动后，看语音合成模型有没有加载好，没有就提前加载；语音识别模型也提前加载好。**

audio.cpp 没有"模型加载了没有"的接口（`/health` 只报就绪和配置了几个模型，`/v1/models` 只列 id），所以合成的预热就是发一条极短的试合成：模型没加载时会顺势加载，已经加载时很快返回。这台机器显卡 12 GB，现在用了约 7 GB；large-v3（int8_float16）约 2 GB，放得下，所以识别模型改成常驻，不再闲置 5 分钟就退出。

## Acceptance criteria

- [x] **识别预热**：守护进程启动后在后台拉起识别进程并加载模型，不等第一条语音，也不挡启动。
  - 识别进程协议加一个"加载"消息，加载好了回报用的模型、设备、加载耗时；加载失败按现有规则退回 CPU 的 small，记下原因。
  - 默认常驻：`voice.recognizer.idleMinutes` 默认改成 0，表示不因闲置退出；配了正数的照旧闲置退出。
  - 识别进程意外退出（崩溃、被杀）后，马上在后台重新拉起并加载，不等下一条语音。连续失败按退避重试，不刷屏。
- [x] **合成预热**：守护进程启动后，在后台给 audio.cpp 发一条极短的试合成，用实际会用的模型和参考音色，确保模型加载好；结果不进任何会话、不留文件。
  - audio.cpp 没开时不报错，记下"没开"。
  - 它从连不上变成连得上时（比如被 LSM 重新拉起），再预热一次。用低频探活发现，比如每分钟看一次 `/health`，只在状态变了的时候动作。
  - 按这次试合成的耗时，判断模型之前是不是已经加载好，记进日志。
- [x] **顺序**：两个预热依次做（先识别、后合成），不同时往显卡里加载。预热期间来了真的识别或合成请求，照常处理，不被预热挡住太久：真请求排在预热后面，或者预热让路，选一种写进 Comments。
- [x] **状态可见**：设置 · 语音里显示两个模型的状态，实时更新：加载中、已就绪（模型、设备、加载耗时）、没开、出错（原因）。本机接口取得到同样的状态。
- [x] **测试**：用假的识别进程和假的合成服务，不碰本机 8090、不拉真的 Python。覆盖：
  - 启动后两个都预热；
  - 识别加载失败退回 CPU；
  - 识别进程被杀后重新加载；
  - audio.cpp 先没开、后来开了时补一次预热；
  - 预热期间来真请求。
- [x] **自动播放开关挪进设置 · 语音**（用户 2026-10-09 加，规格第 22 节"设置 · 语音"）："自动播放 agent 的语音"开关从外观下面挪到语音这一栏，外观下面那一项去掉。只挪位置，行为不变：默认开、按设备记住，存储键沿用 `ergou-voice-autoplay`，已存的值照常生效。
- [x] **识别引擎显示成一个选项**（同上）：设置 · 语音里显示成选择控件（单选或下拉），只有"faster-whisper"一项且选中；旁边带上本票的状态：用的模型（large-v3，或者退回的 small）、设备、加载中 / 已就绪 / 出错。
  - 引擎清单由守护进程给（现在只有一项），不在前端写死。
  - 先不做持久化和切换，也不为将来的引擎预先搭配置项或抽象；这一栏怎么排写进 Comments。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Comments

- **预热和真请求撞上：真请求排在同一个模型的预热后面，不排在另一个模型的预热后面**（没选"预热让路"：预热做的就是真请求要等的那次加载，让路也省不下时间）。
  - 识别：识别进程拉起后先收到"加载"，按到达顺序一条一条处理，真的识别排在加载后面，加载好就识别，不另起进程。
  - 合成：语音回复用的合成由预热包一层（`VoiceWarmup.speech`），试合成在做时等它做完再发。同时发过去也只是在 audio.cpp 的模型锁上排队，等过它的 `busy_timeout_ms` 还会被回 503、退回只发文字。
  - 真的合成等试合成的那段时间不算进它自己的超时：最坏要多等一次试合成的超时，默认约 107 秒（余量 15 + 冷启动 90 + 1 秒语音 × 2）。
  - 合成的预热排在识别的后面（不同时往显卡里加载），但真的合成不等识别的预热：识别加载期间来了语音回复照常合成，之后轮到合成的预热时试合成很快回来，记成"之前已经加载好了"。
- **识别进程拉起后总是马上加载**（不只是预热时）：闲置退出后来了语音、意外退出后重拉，都是先加载再识别，状态里都有加载耗时。加载出错一律按致命算；加载最多等识别超时配置里的余量加冷启动（默认 90 秒），超了结束进程、记成出错。
- **意外退出后的重拉**（评审后改）：识别进程宿主经 `onLifecycle` 明确报"加载好了"和"没了"（没加载起来、加载好之后意外没了、闲置退出），预热据此决定，不从状态跳变倒推。加载好之后 60 秒没崩才算稳定，稳定了才把连续失败清零：稳定之后意外没了（崩溃、被杀、识别超时被结束、识别时报致命错误）马上重拉；没加载起来、加载好了还没稳定就又没了（"加载好就崩"）都算连续失败，按 5 秒、30 秒、2 分钟、之后每 10 分钟再试，每次一行日志，"没加载起来"和"加载好后很快又退出了"分开写。配置里的 Python 还是占位符时不预热（状态是出错，带原因）。
- **合成预热也在导入参考音色后做**：启动时还没有参考音色（没法用实际会用的音色试合成）时状态是"等待"，导入了第一个参考音色再预热。语音回复的合成成功了也把合成模型记成已就绪，连不上记成没开（探活之外的补充）。
- **合成服务忙**（评审后加）：试合成碰上 503（显卡在给别的任务用，和 drama 共用时启动时常见）时，状态记"忙"（模型状态多了 `busy`），按探活的间隔（`probeSeconds`）再试，状态一直是"忙"，只在开始忙时记一行日志；成了就是已就绪。
- **探活**：新配置项 `voice.speech.probeSeconds`（默认 60）。只在"连不上 ↔ 连得上"变了的时候动作。已知的空子：audio.cpp 在两次探活之间被重启（没被看到"连不上"）时不会补预热，下一条语音回复照常冷启动；audio.cpp 没有能看出它重启过的接口（`/health` 只有 status、backend、models）。
- **状态的推送**：两个模型的状态变了推一条临时事件 `voice_models`，放在活动状态频道上（前端一直订阅它，不用加新频道）；负载和 `GET /api/voice-models` 一样（`VoiceModelsView`），带 `startedAt`、`revision`，前端并进状态层时留新的（接口晚到的旧结果不盖掉推来的新状态）。宿主协议没改。
- **设置 · 语音的排法**：识别、合成、播放三块。识别：识别引擎的单选（清单由守护进程给，现在只有 faster-whisper、选中），旁边是识别模型的状态（用的模型、设备、计算精度、加载耗时、退回的原因，或者加载中 / 出错的原因）。合成：audio.cpp 那一行的状态（模型、试合成耗时、之前是否已加载；没开 / 出错的原因），下面是参考音色（导入按钮挪到这一块的标题栏）。播放："自动播放 agent 的语音"开关，从设置列表的外观下面挪过来，存储键和行为不变。以后加识别引擎时再加切换和存储。
- **测试的副作用**：每个测试守护进程启动时都会拉起假的识别进程预热；假的合成服务把试合成单独记、单独回，所以原有的语音回复测试不用改。`recognizer-py.test.ts` 加了两条"加载"的用例：它用的是本机的 Python 加替身模块（不加载真模型），和原来的用例一样本机没有 Python 时跳过。
- **不经 `startTestDaemon` 起守护进程的测试**：守护进程一起来就预热，所以独立进程里的守护进程（`fixtures/daemon-host.ts`、`fixtures/killable-daemon.ts`）改成给假的识别进程和连不上的合成服务，像 LSM 那样拉起 `main.ts` 的测试（`entry`、`restore-cli`）在配置里写 `helpers/ports.ts` 的 `NO_VOICE_SERVICES_CONFIG`（占位的 Python、连不上的合成服务地址）。以后新加这类测试照这个来。
