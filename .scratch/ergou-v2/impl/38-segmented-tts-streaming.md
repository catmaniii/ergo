# 38 — 语音回复分段合成、边合成边推送、前端无缝播放

Status: done

## What to build

用户真机实测：一段 309 字的口语总结合成出 56 秒的语音，用了 51 秒，要等它整段合成完才听得到。用户要求（2026-10-08）：长的语音分段合成，由系统无缝拼接、边合成边推送。

audio.cpp 的原生流式输出只对标了 streaming 的模型可用（比如 VoxCPM2），我们用的 Fish-Audio S2 Pro 不在其列，所以由守护进程分段：把送进 TTS 的稿子按句子切成若干段，依次合成，每合成好一段就推给前端；前端把各段在时间上首尾相接地排好播放，听起来是连着的一段。全部合成完后拼成一条完整的音频存进语音对象，之后重播、下载都用这一条。合成大约比实时快一点（1 秒语音约 0.85 秒），所以第一段出来以后，后面的段一般赶在前一段播完之前就好。

## Acceptance criteria

- [x] 主切面：送进 TTS 的稿子按句切段（句号、问号、叹号、分号、换行等），太短的并到相邻句、太长的再按逗号切，第一段尽量短以缩短第一声的等待；依次合成，每段合成好就经频道推一次 agent 语音的更新（这一段的音频、时长、在整段里的位置）。全部完成后拼成一条完整音频（同样的采样率和格式，段间留一个自然的短停顿），语音对象记完整音频、总时长，状态"完成"；中间段的音频不留成没人引用的孤儿文件，彻底删除时连同处理（沿用 21、32 号票的口径）。测试里 TTS 用假的（按段返回）。
- [x] 合成到一半失败或超时：已经推出去的段照常可以播；语音对象记"只合成了一部分"，会话里一条说明，回复的文字照常显示出来（短回复原本只出语音的，这时把文字补出来）。服务忙（503）时同样处理。合成到一半守护进程被杀，重启后按 32 号票的做法重做整条。
- [x] 前端：第一段到了就出现 agent 的语音气泡（时长随已到的段增长、标"合成中"），开着自动播放时（36 号票）立刻开始播，后面的段到了接着排，段与段之间不出现明显的空白或爆音（用 Web Audio 按时间排程，或同等效果的做法）；全部完成后气泡显示总时长，点一下重播用完整音频。用户中途点暂停、点别的语音时停掉整条。前端状态层用主切面录下的事件流回放（含"合成到一半失败"的流程）。
- [x] 计时记录：语音对象记"第一段出来用了多久"和"整条合成用了多久"，本机接口取得到，方便真机上看。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Notes

- 合成和语音对象在 `packages/daemon/src/voice/`（`speech.ts`、`voice-reply.ts`、`agent-voice-views.ts`、`wav.ts`）；前端的 agent 语音气泡和自动播放在 36 号票之后的版本里。
- 段的大小影响音色连贯和等待：句子太碎，段间语气容易不连；第一段太长，等待又变长。按句切、首段短，是平衡点，具体数字写进 Comments。
- 真机冒烟：用户发一条语音、让秘书回一段长的，记录第一声的等待和整条耗时，写进 Comments。

规格没写清、按最保守做法定下的：

- **切段的数字**（字数按估时长同一套：汉字一个算一个，英文单词、数字串一个算两个；每秒约念 4.5 个）：按句切（。！？!?；;…和换行，英文句点后面跟空白才算），一句一段；**不到 8 字**的句子并到下一句（最后一句并到前一句）；**第一段最多 16 字**（约 3.5 秒）；之后每段的上限是前一段的 **1.25 倍**（16、20、25、31、39），**最多 40 字**（约 9 秒）；超过上限的句子按逗号切开（，、：和英文逗号；英文冒号只在后面跟空白时才算，`15:30`、`3:2`、`https://` 不切）、小句凑到上限以内，切下来剩的不到 8 字就不切，一个小句本身就超长的不再切。上限逐段放大而不是一下放开，是因为合成只比实时快一点（票里说 1 秒语音约 0.85 秒，用户实测 56 秒语音 51 秒，约 0.91）：后一段比前一段长太多，就赶不上前一段播完。按 0.9 的速度和每次请求约 0.3 秒的额外开销估，1.25 倍的增长在开头几段可能各有零点几秒的空当，之后越来越宽裕；真机上看 `firstSegmentMs` 和听感再调这几个数（只在 `SPEECH_SEGMENT_RULES` 一处）。
- **段间停顿 200 毫秒**（拼成完整音频时留，前端边收边播按各段的 `offsetMs` 排，听起来一样），接缝两边 5 毫秒淡出淡入（守护进程拼接和前端 Web Audio 都做，常量 `AGENT_VOICE_SEGMENT_FADE_MS` 在协议包里共用），免得段的头尾不在零点上时出爆音。各段格式（采样率、声道、位深）对不上算这一段没合成下去。
- **只有一段的不推段**：合成好直接 `done`（和 32 号票一样，不多一个版本），`segmentCount: 1`，没有 `segments`，`firstSegmentMs` 等于 `elapsedMs`。不止一段的，最后一段不单独推，随 `done` 一起（`done` 带全部的段，正在边收边播的接着排最后一段）。
- **"只合成了一部分"是新状态 `partial`**（不是 `failed` 加标记）：推出去的段拼成一条入库，和语音消息、系统说明"语音只合成了前面一部分（原因），回复的文字照常显示。"同一事务；协议包的 `agentVoiceCoversReply` 对它不收文字，所以整段合成的短回复把文字补出来。一段都没推出去就失败的照旧 `failed`（没有语音消息）。拼好的那条存不进去时退成 `failed`。服务忙（503）、超时、出错、回的不是 WAV 都一样处理。
- **段的音频不进媒体库**，放在临时区 `tts-segments/<语音 id>/<第几段>.wav`，经 `GET /api/agent-voices/<id>/segments/<n>`（不缓存）取：媒体库按内容哈希去重，同样的一段可能正好是别的语音的完整音频（合成是确定性的时候），删的时候会误删；也不让中间段在媒体库里留成没人引用的文件。删的时机：一条语音有了结局（完整音频入库了，或者失败了）之后再留 5 分钟才删它的段（前端可能还在取最后一段；按守护进程的时钟，停的时候没到点的不删），守护进程启动时全删。临时区 7 天一清也兜着底。彻底删除：agent 的语音消息本来就不在彻底删除的范围里（21 号票按素材删，agent 的回复不是素材；32 号票没加），拼好的完整音频和以前一样在媒体库里；段不在媒体库，不用跟着处理。
