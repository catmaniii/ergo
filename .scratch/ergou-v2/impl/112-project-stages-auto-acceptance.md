# 112 — 项目里的阶段不再找用户验收：立项时定好验收标准，之后自动验收；只在项目状态变更时找用户

Status: done
Blocked by: 无
Spec: [第一阶段规格](../spec.md) 第 7 节（计划、阶段、验收：script / review / user 三种验收方式）、项目一节（立项、建设任务、项目状态）；13 号票（等你验收）、15 / 16 号票（项目生命周期）

## What to build

用户 2026-10-13 原话："一个项目的各个阶段，不要每个阶段都让我来验收通过吧，应该在项目规划的时候就把每个阶段的验收标准定好啊，到了那个验收交付件有了之后拿你的验收方法去验收啊，你要么是有一些测试脚本再加一些 prompt 去综合评估……你应该是在项目立项阶段，每个阶段的交付件和验收标准你定下来找我确认，我确认完你就自动验收就行了，你不用每个阶段找我验收……你要做的就是整个项目做完之后让我看一眼决定要不要转运营或者其他的，就项目状态变更时找我确认，项目内部阶段不要找我确认。"

现在：计划里每个阶段的每条验收标准有三种验收方式（`ACCEPTANCE_METHODS`：`script` 脚本、`review` 独立评审、`user` 由用户验收）。维护者起草建设任务的计划时常写 `user`——比如项目「AI 情报站」的建设任务 t-6 九个阶段里七个带 `user`，用户一上午被叫去验收了好几次（"等你验收"事项）。另外首个建设任务做完时，项目自动从"建设中"进入"使用中"（`projects.ts` 的 `taskCompleted`，不出卡、不等用户）。

改成：

### 1. 项目里的任务，阶段一律自动验收

- **范围**：属于项目的任务——项目的建设任务、项目内部任务、派到项目的工单。项目外的长程任务照旧可以写"由你验收"（用户这次只说了项目；写在 Comments，问用户要不要扩到全部）。
- **起草计划时**：维护者给每个阶段写清交付件和验收标准，验收方式只能是 `script`（能跑的检查：测试脚本、校验命令，附命令和期望）和 `review`（独立评审 agent 按标准综合评估，评审能读交付件、能跑命令）；鼓励每个阶段"能脚本查的先脚本查，再加一条评审综合看"。维护者的提示词、`propose_plan` 的说明跟着改；计划检查拒收项目任务里的 `user`，退回时说明"项目里的阶段自动验收，改成 script 或 review"。
- **用户只确认一次**：建设任务的计划卡（立项后起草的那份）就是用户确认"每个阶段的交付件和验收标准"的地方，卡上照旧逐阶段列出交付件、标准、验收方式。确认后各阶段做完就自动验收，不再出"等你验收"。
- **已经在跑的项目任务**（比如 t-6）：升级后，还没验收的阶段里写着 `user` 的标准**改由评审验收**（照这条标准的原文判）；已经在等用户验收的（待办里"等你验收"还没处理的），交给评审去验、那条事项标为已处理（写明"项目里的阶段改成自动验收，交给评审了"）。进展卡、时间线上写明这一条原定由你验收、按新规矩改由评审。
- **例外照旧找用户**：评审连续不通过到上限（现有的"验收第 3 次"那套）、卡住求助、失败后的抉择、超出授权这类异常——这些不是例行验收，照现有规矩。计划变更（`propose_plan_change`）改了用户确认过的交付件、验收标准或授权的，照旧要用户确认（改的是用户拍过板的东西；写在 Comments）。

### 2. 项目状态变更时找用户

- 首个建设任务做完时**不再自动进入"使用中"**，改成给用户一张"项目「X」首版做完了"的卡（进待办，来源是项目，105 的"去项目 ›"能跳）：写明做成了什么（建设任务的最后总结、每个阶段的验收结果一行一个、交付件在哪）。选项：
  - **转入使用**（项目进入"使用中"，以后有运营态的东西就从这里接上——第二期的"项目转运营"）；
  - **继续建设**（项目留在"建设中"，维护者按用户写的一句话起草下一轮建设任务的计划，照常找用户确认计划）；
  - **放弃并归档**（照现有 `abandon`）。
  不选就一直挂在待办里，项目停在"建设中"。
- 其余项目状态变更（停用、重新启用、归档、取消归档、删除）本来就是用户在项目页上点的，不变。
- 秘书拿到这张卡的待办摘要（照现有的待办工具），用户问"情报站做得怎么样了"能答。
