# 16 — 工单与派单：单项目任务

Status: done

Spec: [第一阶段规格](../spec.md) 第 12 节（工单与派单）、第 11 节（项目与维护者）、第 8 节（任务、计划与阶段）、第 4 节（存储与事件）、第 5 节（前端协议）、第 19 节（Web UI）、第 21 节（实现细节补充）

## What to build

做完后，只涉及一个项目的任务（包括立项后的首个建设任务）由这个项目的维护者起草计划并执行，维护者要做的事都以工单的形式送达。工单写进事件日志时注明收件项目，派单器把它放进项目维护者的工单队列：维护者休眠就唤起，正忙就排队，一次只做一件、先来先做；被挡住的任务留在排队中，看板上标"等项目 X"。发给已归档项目的工单直接退回并说明原因；已停用的项目照常接单。任务的执行权限是任务授权和项目权限的交集。维护者干活中遇到要问的，工单转"等澄清"，由派单方回答——用户发起的单项目任务就问用户。

维护者会话分段，每段是一个新的 pi 会话，从固定上下文重新开始：工具包说明、项目规范（第一阶段是一段内置的简短说明）、项目档案快照（规格摘要、进展、术语表）、上一段的摘要、这次的工单（对话段没有），再加上重注入块；更早的分段不进上下文。段有两种：每张工单一段；用户在维护者手上没有进行中的工单时直接和它说话（包括立项问答），开一个"对话段"。维护者干活时用户发来的话作为插话进当前段。每段结束时，维护者把新的理解写回项目档案，并一并写一段摘要，作为下一段的"上一段摘要"；运行时检查进展文档的内容哈希变没变、摘要有没有写，没写回就催维护者，这段不算完成。用户可以在项目页上重置维护者：新开一段会话，只凭项目档案重建理解，旧会话保留可查。

前端把各段拼成一条连续的聊天，用工单分隔线隔开；简版项目页出现工单流水线（排队中、进行中、已结束），每张工单显示来源、所属任务和当前阶段。演示：给同一个项目连发两个单项目任务，第二个标"等项目 X"，第一个结束后它自动开始；项目页流水线随之流动，维护者会话里出现工单分隔线。

## Acceptance criteria

- [x] 主切面：只涉及一个项目的任务，起草计划和执行都由该项目的维护者做，不新建任务自己的维护者；任务的执行权限是任务授权和项目权限的交集——项目工具包里没有的能力，任务授权也放不开。
- [x] 主切面：工单按"待接 → 进行中 ⇄ 等澄清 → 已结束（完成、退回、做不了）"迁移，每次迁移都是事件；派单器把工单送进收件项目维护者的队列，维护者休眠时唤起、正忙时排队；同一项目同一时刻只有一张进行中的工单，先来先做。
- [x] 主切面：项目正忙时，后到的任务留在排队中，看板上的任务卡标"等项目 X"；前一张工单结束后它自动开始。工单不在看板上单独占卡。
- [x] 主切面：每张工单开一段新的 pi 会话（新的会话文件），开头的固定上下文包含工具包说明、内置的项目规范说明、项目档案快照（规格摘要、进展、术语表）、上一段的摘要、这次的工单和重注入块；更早分段的内容不在这段的上下文里。维护者手上没有进行中的工单时，用户直接对它说话开一个对话段（同样的固定上下文，没有工单）；对话段在维护者闲置退出或下一张工单开始之前结束。维护者干活时用户发来的话作为插话进当前段，不另开段。
- [x] 主切面：一段（工单段或对话段）结束时，进展文档的内容哈希没变、或维护者没写这一段的摘要，运行时催促维护者写回，这段不算完成、工单不结束；写回之后才结束，下一段固定上下文里的"上一段摘要"就是它写的这段摘要。
- [x] 主切面：用户重置维护者后新开一段会话，上下文只来自项目档案（没有上一段的摘要）；旧会话文件原样保留，前端仍能查看。
- [x] 主切面：用户发起的单项目任务里，维护者提问时工单转等澄清，问题以提问卡进待我处理；没有其他能推进的阶段时任务转等我（原因"澄清"）；用户回答后回答交回维护者，工单回到进行中、任务回到执行中（名额满则排队中）。回答照常作为"澄清问题的回答"产生素材事件（由 08 号票采集）。
- [x] 主切面：发给已归档项目的工单直接以"退回"结束并附原因，维护者不被唤起；发给已停用项目的工单照常执行。
- [x] Web UI：维护者会话把各段拼成一条连续聊天，用工单分隔线（工单分隔 part）隔开，对话段也有分隔；简版项目页显示工单流水线（排队中、进行中、已结束），每张工单显示来源、所属任务和当前阶段；项目页上有重置维护者的入口。前端状态层回放主切面录下的"两个任务排进同一项目"事件流，流水线和"等项目 X"标记正确。
- [x] 主切面（端到端）：项目的首个建设任务由项目维护者自己经计划提交和执行工具走完、在守卫下执行，全部阶段验收后任务以已完成结束，项目自动进入使用中（13 号票只验了执行控制器和项目模块之间的接口衔接）。
- [x] 所有测试通过（vitest），lint（oxlint）无报错。

## Comments

- 2026-10-08（实现，16 号票的 agent）：规格没写清、又必须定的地方，按最保守、最贴近规格的做法定了（ADR-0012 记了会话分段那部分）：
  - **单项目任务**：点"发起任务"时只选了一个项目的任务，执行的维护者就是这个项目的维护者（`Task.maintainerId`），不新建任务自己的维护者；项目的任务的计划提交时，涉及的项目里总有这个项目（计划里没写也补上）。选了多个项目的仍归 17。
  - **两种工单**：起草计划（`plan`）和执行（`execute`）各是一张工单。秘书写任务书、用户打回计划、项目开工建出首个建设任务时派起草计划的工单（打回时工单的内容是打回意见加任务书，因为新的一段会话里没有上一版的对话）；任务排队中（确认了计划、重试、返工）还没有执行工单时补派一张执行工单。首个建设任务的工单内容是一份指向立项书的任务书（不写立项书正文，同 15）。
  - **一次只做一件**："维护者正忙" = 手上有进行中或等澄清的工单，或者有在进行、收尾中的会话段。**等澄清的工单仍占着维护者**（不趁等回答时做别的工单：一段会话只属于一张工单）。执行工单的开始和任务进入执行中同一事务（执行控制器问派单器 `admit`），全局执行名额另算。
  - **工单的结局**：任务取消 → 退回（"任务取消了"）；任务失败 → 做不了（原因是失败原因）；任务结束时还排着的工单退回。起草计划的工单在计划交了（任务离开规划中）时、执行的在任务完成时先让这一段收尾，写回之后才以"完成"结束。
  - **已归档**：派出时就以"退回"结束（同一事务，附原因），项目归档时还排着的也退回；**项目归档时正在做的工单不处理**（继续占着，等用户取消任务或取消归档），留给后续的票。
  - **写回检查**：只看 `progress.md` 的内容哈希变没变、有没有用 `write_segment_summary` 写摘要，不判断写得好不好。催写回最多 3 次，之后会话里留一条说明、这一段一直收尾中（用户和它说话、或者重置维护者）；运行时不替它写，也不自动跳过。重置维护者时当前这段直接结束、不催写回；正在做的工单在新的一段里接着做。
  - **对话段**：维护者手上没有在进行的段时，用户直接说话开一段（段和分隔线排在用户这句话之前，同一事务）；运行时给它一条不属于任务的通知时也开一段。对话段在闲置退出时、或者有工单在等时收尾（同样要写回）。第一段对话段接着这个维护者以前的会话文件（任务转为项目、本票之前就有的项目），之后每段一个新文件。**接哪个会话都是显式指定的**：段里记着会话文件名，拉起时按它打开；唯一要"挑"的是第一段对话段开段那一刻，从会话目录里取修改时间最近的那个（只有任务转来的、本票之前的项目才有旧文件），取到的名字记进这一段，之后不再挑。没有在进行的段时不会拉起维护者（只处理当前段的输入）；万一拉起也开新会话（`continueSession: false`），不去猜。
  - **用户的话**：维护者干活时用户说的话总进当前这一段（插话），哪怕这段的任务这时暂停了或已经结束（项目维护者是用户直接对话的对象，和任务详情里"已结束的任务不收消息"不同）；运行时交给它的、属于别的任务的通知留在队里，等那个任务的工单段。
  - **固定上下文**：拼在系统提示后面，每次拉起现算（同一段里闲置退出再唤起时，项目档案快照可能比开段时新）。快照里每份文档最多 3000 字，超出的提示用 read 读全文。项目规范是一段内置的简短说明（`PROJECT_STANDARD`）。
  - **执行权限的交集**：skill、MCP 取交集，bash、联网都开才开；验收脚本的联网同样取交集；重注入块和交给维护者的阶段边界里写的是交集之后的工具包。**起草计划的工单段**：读写项目档案和工作目录，不带 bash、不联网（"确认之前不动手做任务本身"靠系统提示，文件工具守卫没另外卡——起草时要往项目档案写进展；和任务自己的维护者起草时只能读不同）。
  - **等澄清**：项目维护者为工单提问时用 `ask_clarification`（只在工单段里能用；对话段直接问），提问卡记着是谁为哪张工单问的（卡片类型 `questions` 升到版本 2），回答交回它、不交给秘书；关掉提问卡也让工单回到进行中，通知维护者按自己的理解接着做。起草计划的工单也能问（任务还在规划中，不转等我）。
  - **消息的范围**：维护者会话里的消息带当前这一段的项目和任务（`AgentSession` 的 `scope` 给函数），任务那部分（含当时的阶段）取 25 号票的 `taskMessageScope`。顺手让审批卡引用、审批结果的通知带上调用所在会话的范围（`CallOrigin.messageScope`：守卫判定那一刻的，和工具调用记录同一份；没有时按 `taskId`、`stageId`），项目维护者的也带项目。**已知的顺序瑕疵**：项目正忙时任务重试、返工的通知先进会话（排在那张工单的分隔线之前），工单开始时才被处理。
  - **删除项目**：项目的工单的内容（任务书、打回意见）一起改写成删除标记（登记了 `work_order` 的改写函数）；段的事件在维护者会话频道上，随整条会话换成标记。彻底删除（21）某条素材时，工单内容里引用的同一段原话不跟着改（和 12、13 号票交给维护者的通知一样，原话的副本留在工单里），留给后续的票。
  - **宿主协议**升到 8（22 号票用了 5、24 号票用了 6、23 号票用了 7）：装配参数可选的 `sessionFile`。agent 管家只认 `名字.jsonl` 这种文件名。
  - **13 号票的"首个建设任务：接口衔接"用例**换成了本票的端到端用例（`work-orders.test.ts` 的"项目的首个建设任务（端到端）"）；15 号票的立项问答、开工的用例按会话分段改了剧本（维护者写回进展、写摘要），`project-lifecycle` 重新录了。

  - **秘书发起的单项目任务**：`create_task`、`suggest_task`（卡片版本 2）可以写涉及的项目，恰好一个时由这个项目的维护者起草并执行（任务模块的 `buildCreate` 统一按涉及的项目定执行的维护者，点按钮、秘书建卡、建议卡都走它）。建卡时没写、**第一版**任务书只涉及一个项目列表里的项目的，任务书交出时改由这个项目的维护者起草（看板上的任务事件 `handed_to_project`，状态不变）；只在第一版换（任务自己的维护者那时还没接过任何输入），之后的任务书、涉及零个或多个项目的都不换——最保守的做法。

  - **有工单没结束不能归档**（规格第 12 节）：放弃、归档都算；被拒的说法和项目页按钮旁的说明是同一句 `archiveBlockedText`（列出任务编号和标题）。上面"项目归档时正在做的工单不处理"一条作废；派单器里"归档时退回还排着的工单"也删了（这时不会有）。15 号票"放弃 → … → 删除"的用例跟着改：开工之后先确认放弃被拒，取消首个建设任务、工单随之退回之后再放弃。
  - **写回中途重置**：照常算完成，段和工单标 `unwritten: "reset"`，时间线记一笔（`write_back_missing`，"重置时这段没写回档案"），项目页的工单状态同样写出来；处理过输入、没写回就被重置的进行中的段也标（工单在新的一段接着做，不结束）。重置时有没有写回同样按内容哈希和摘要判断。
  - **催写回升级**：最多催 `tasks.thresholds.nudges` 次（默认 3，同第 8 节的催促阈值；14 号票合并时已从写死的 `WRITE_BACK_NUDGES` 改成读配置），还没写回就转为用户拍板：待我处理里一条"卡住求助"（`stuck_help`，不卡任务，动作"知道了"），会话里一条说明，这一段以 `unwritten: "nudged"` 结束，工单照常结束并标出来，时间线记一笔，项目的队列接着走。**"工单所属任务转等我"做不到**：工单段收尾时它的任务已经离开了执行中（计划交了是待确认——本来就在看板的"等我"组；执行的已完成、失败或取消），任务状态机只许执行中转等我，所以任务状态不改；"卡住求助"的数据里也不记任务编号（任务那一套"卡住求助"按任务编号认事项、用户回话即恢复执行，这条不是那种）。要真让任务转等我，得让执行的工单在写回之后才判任务完成，改动执行控制器的完成流程，留给用户定。
  - **"等项目 X"**：只在真被项目挡住时标（前端）：任务有一张排着的、它正等着的工单（起草计划的任务在规划中，执行的在排队中），而项目的维护者手上有别的工单。全局执行名额满了、任务暂停了都不标。前端看不到对话段，对话段挡着时不标。
  - **起草计划的工单段只读**：pi 工具只有 `read`、`ls`（和任务自己的维护者起草计划时同一份 `PLANNING_PI_TOOLS`），写回进展用新的 `write_progress`（整份换掉 `progress.md`，旧版本先留进历史区），摘要用 `write_segment_summary`；固定上下文、系统提示、催写回的通知都按这一套说。上面"起草计划的工单段读写项目档案和工作目录"一条作废。
  - **开发类的工作目录**：二狗给的默认工作目录在立项书确认时 `git init`（项目模块建工作目录时做，不做第一次提交）；用户绑定的外部目录不动，不是 git 仓库的，提议并行时先拒绝并说明办法（初始化成 git 仓库、提交一次，再用 git worktree 建子 agent 的目录）。
  - **关掉提问卡**：保留"按自己的理解接着做"，另在时间线记一笔（`own_judgement`）。
