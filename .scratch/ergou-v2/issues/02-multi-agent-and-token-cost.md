# 多 agent 架构与 token 成本

Type: grilling
Status: resolved

## Question

二狗的执行层到底用多少个 agent？需要回答：
- 一个任务交给单个执行者，还是一个 agent 集群？
- 在什么条件下才需要：
  - 多个 agent 并发；
  - 项目经理（PM）；
  - 独立的审查者？
- 派遣时怎样控制 token：
  - 用引用代替转述；
  - 保持前缀稳定，提高缓存命中；
  - 把能推迟的任务放到空闲时段。
- 每个任务、每个 agent 的 token 消耗怎么记账，在 UI 上怎么展示？

## Context

- 用户担心多 agent 太费 token，希望单独讨论（立项 grilling Q11、Q21）。
- `docs/research/04-multi-agent-teams.md`：星形协调的收益与代价、PM 失效模式、单写者原则。
- `docs/research/09-chat-multimedia.md` §5：基于 DeepSeek Flash 价格的成本估算。缓存命中价和未命中价相差 50 倍。

## Answer

2026-10-07，用户在立项会话中直接拍板。

1. **固定绑定一个维护者。** 每个任务、每个项目都绑定一个**维护者** agent，它的会话长期保存、由系统管理好。任务完成后，无论转入运营还是要继续修改、维护，秘书都唤起这个维护者来做。
2. **默认单 agent 串行。** 维护者自己按计划一步步做。v1 架构从简。
3. **并行由维护者提议、用户确认。** 如果计划里有能并行的阶段，维护者向用户提议"派几个 agent 并行做哪几步"，用户确认后才并行；否则就串行。
4. **维护者的权限受任务限制。** 它的工具、沙箱、可见的记忆和文件范围，都由所属任务限定。
5. **用户可以绕过秘书。**
   - 用户能像在 AgentSense 里一样查看所有任务及其状态，并打开任意维护者的会话历史。
   - 用户可以直接在维护者的会话里给它下指令，维护者直接向用户汇报。
   - 相关进展同时由秘书收集。

**移交到其他票的细节：**
- token 的记账与展示 → 「任务生命周期与任务看板」。
- 省 token 的手段（用引用代替转述、保持前缀稳定、利用空闲时段）→ 「运行时架构」。
- v1 是否还设"只管不干"的独立 PM → 「角色模型」。
