# 意图澄清与规划交互

Type: grilling
Status: resolved
Phase: 1
Blocked by: 03, 05

## Question

秘书从收到指令到交出计划请用户确认，中间的交互流程是什么？需要定下：

1. **分流**：什么时候直接执行，什么时候先澄清，什么时候做规划。
2. **少问**：怎样借助记忆和动机假设，把提问次数降到最少。可选做法：
   - 先说出自己的假设，再请用户确认；
   - 把问题攒成一批一起问；
   - 每个问题都附上推荐答案。
3. **提问预算**：允许用户调整。
4. **两种提问的分工**："了解你"问题箱，和在对话里顺口问一句，各管什么。
5. **合并确认**：确认计划和给出授权，怎样合成一次交互。

## Answer

2026-10-07 定稿。

### 1. 分流

- 秘书的每次回复只落在五种形态之一：
  1. 直接回答；
  2. 快速动作卡；
  3. "建议发起任务"卡；
  4. "建议立项"卡；
  5. 简单提醒。
- **由秘书在同一轮里判断**，用结构化输出给出形态，不另加分类器。建议卡判错的代价很低（用户不点就行），不值得多一层。
- 用户在消息里明说要发起任务、要立项，或者点了"发起任务""新建项目"按钮时，跳过判断。

### 2. 少问

- **不设轮数和题数上限**。问几轮都以把目标问清楚为准。
- "少问"是二狗的长期目标，要在使用中探索：靠对用户意图的理解和挖掘（记忆、动机假设）来减少提问，而不是靠硬性配额。
- 现在就采用的做法：
  - **先说假设**："我理解你要的是……，对吗？"
  - **成批问**：问题攒成一批，每题带推荐答案，可以一键"全按推荐"。
  - **不问已知的事**：记忆里已经确认的不问。只在指令和动机假设冲突、或者缺关键信息时才问。
  - **假设栏**：规划时还拿不准的地方，写进计划的"假设"栏，用户确认计划时一起改，不必为它们单独再问一轮。

### 3. 两种提问的分工

- **澄清问题**：为了把当前这件事做对而问，由秘书（或起草计划的维护者）在对话里问。不设上限，见上节。
- **"了解你"问题**：记忆管理者为了了解用户本人而形成的问题，随记忆简报附带，秘书顺口问。每天上限默认 3 次，可调（「记忆边界」已定）。
- 两种问题的回答都是素材（「记忆边界」七类素材里的"澄清问题的回答"）。

### 4. 计划由谁起草

1. **秘书负责对齐意图**，写一份**任务书**：目标、验收标准、约束、涉及哪些项目、记忆范围提议。
2. **执行任务的维护者据此起草阶段计划**：
   - 单项目任务（包括项目的建设任务）由项目维护者起草；
   - 其他任务由任务维护者起草，它在建任务卡时就产生。
3. 多项目任务在规划时只读各项目的档案，不发工单。各项目的改动在计划里逐项列出，用户确认计划后才变成工单。

立项走另一条路（「项目生命周期、工作空间与维护者」已定）：秘书收口，维护者做立项问答，交出立项书。

### 5. 计划确认卡

一张卡、一个"确认"按钮，同时确认计划和授权。卡上包括：

- 阶段列表：每个阶段的交付件、验收标准、由谁验收（系统检查、评审子 agent，或用户）；
- 涉及的项目，以及每个项目改什么，逐行列出；
- **工具包**：执行的维护者要用哪些 skill、外部工具（MCP），能不能用 bash、能不能联网。由维护者提议，用户确认。立项书上同样列出项目维护者的工具包；
- 记忆范围：引用了哪些记忆、执行中可以调用的范围，证据可以点开看；
- 本任务要提醒的关注类别：默认取全局设置，可以增删；
- 预先授权的操作和边界；
- 假设栏；
- token 粗估。

用户可以整体确认，也可以逐行勾掉或收窄，或者附上意见打回重做。细节默认折叠。

### 6. 执行中改计划

- **不用问用户的调整**：拆阶段、调顺序这类不扩大授权、不加项目、不改交付件和验收的调整，维护者自己改，记进时间线。
- **工具包的调整**：
  - skill 的增减，维护者自己做，记进时间线。skill 只是说明书，不增加权限；
  - 开 bash、加 MCP、开联网这类能力的增加，算扩大授权，走"计划变更"；
  - 减少能力随时可以。
- **要问用户的调整**：扩大授权、加项目、改目标或验收，提交一份"计划变更"进"待我处理"。只有受影响的阶段停下来等，其余阶段照常进行。

### 留给规格

- 秘书结构化输出的字段；五种形态各自的卡片内容。
- 任务书模板；"假设"栏的格式。
- 缺关键信息时的提示词写法。
- 计划卡的折叠方式；逐行勾掉和收窄怎样回写到计划和授权。
- 打回意见怎样回传给起草计划的维护者。
- 计划变更的记录格式。
