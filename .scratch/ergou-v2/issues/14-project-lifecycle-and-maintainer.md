# 项目生命周期、工作空间与维护者

Type: grilling
Status: resolved
Phase: 1
Blocked by: 02, 03, 05

## Question

1. **项目状态机**：草案是 筹备 → 进行中 → 目标完成（待用户判定）→ 运营 / 归档；运营中可以接新目标。具体要定：
   - "目标"是否作为项目的子实体；
   - 怎样转入运营、怎样归档。
2. **立项**：用意图澄清（类似 grill-with-docs）产出项目的规格、`CONTEXT.md` 和 ADR。
3. **隔离**：
   - 工作空间隔离：目录或 git 仓库、会话、文档；
   - 可选的沙箱运行环境；
   - 项目能看到哪部分记忆，由用户授权。
4. **维护者**：
   - 怎样长期保有对项目的理解；
   - 怎样休眠、怎样被拉起；
   - 怎样拉起其他 agent 配合。
5. **项目群组 UI**：移交「项目管理界面」。

- 「记忆边界」已定：立项时授予项目级的记忆范围；维护者每次被唤起时都在这个范围内取用，超出范围要提醒用户临时授权。维护者看不到动机假设。

- 「任务生命周期与任务看板」已定：
  - 项目是原子的、可运营的功能模块，和任务分开管理，在项目管理界面里，不上看板。

  - 开发新项目：立项问答 → 建项目 → 开发工作作为任务，由新项目的维护者执行。
  - 任务转为项目：先走立项问答，原任务的维护者成为项目维护者。

## Answer

2026-10-07 定稿。

> **2026-10-07 写规格时修订**（用户决定）：项目状态不再区分"运营中"和"已完成"，合并为"使用中"。新状态机：筹备中 → 建设中 →（首个建设任务完成，自动）使用中 ⇄ 已停用，可归档。不再有运营判定和"转运营"；项目页直接显示背后的服务在不在线、有哪些定时作业。下文 §1 里关于运营中、已完成的内容以此为准。

### 1. 项目状态

```
筹备中 ─确认并开工→ 建设中 ─首版做完，你判定─┬→ 运营中 ⇄ 已停用
                                            └→ 已完成 ─加了服务或定时作业→ 运营中
放弃：  筹备中 / 建设中 → 已归档
你手动：已完成 / 已停用 → 已归档（取消归档回到原状态）
```

- **筹备中**：立项问答进行中。立项书确认了但还没开工，仍是筹备中，标"立项书已确认"。
- **建设中**：首个建设任务发起后进入。叫"建设中"而不叫"开发态"，对非开发类项目也成立。
- **运营中 / 已完成**：建设任务完成后，维护者提议，用户在"待我处理"里判定。
  - 区别只看项目有没有在 LSM 注册的服务、公网入口或定时作业，不管它们此刻在不在线。有就是运营中，没有就是已完成。
  - 已完成的项目后来加了服务或定时作业，走一次"转运营"，进入运营中。
- **已停用**：项目不再使用，服务撤出 LSM，公网入口收回。可以"重新启用"。停用和重新启用都有副作用，作为任务由维护者执行。
- **已归档**：只能由用户手动触发，可以从已完成、已停用，或放弃了的筹备中、建设中进入。归档时记住原状态，取消归档就回到原状态。
- **删除**：只能从已归档发起，要二次确认。删除项目档案和维护者会话；由它产生的素材不跟着删，要删得去记忆 Web UI。
- **项目状态不随任务变**：运营中或已完成的项目上有任务在做时，状态不变，项目卡上显示"有 N 个进行中的任务"。
- **服务在不在线不是项目状态**：服务的在线、离线、按需拉起，由服务层单独监控；项目页只把背后服务的在线情况显示出来。服务层怎样监控，交「运营态项目的服务托管与公网入口」。
- **不设"目标"实体**：阶段只挂在任务上，每个阶段有交付件、验收标准，以及本阶段的授权和安全策略。"一期、二期"这类长线规划写在项目的规格和进展文档里，真要做某一期时再发起一个任务。
- 内置项目"记忆管理"常驻运营中，不能停用或归档（「记忆边界」已定）。

### 2. 立项

- **三个入口**：
  - 用户明说要开项目，或在项目管理界面点"新建项目"；
  - 秘书在对话中给出"建议立项"卡，用户点了才算；
  - 任务转为项目。
- **两步走**：
  1. **秘书收口**：确认这是项目而不是任务，定名字和一句话目标，提议项目的记忆范围。用户确认后项目立刻诞生（筹备中），维护者随之产生。
  2. **维护者立项问答**：维护者在自己的会话里和用户做 grill-with-docs 式的问答，把规格、术语表、ADR 写进项目档案，最后交出**立项书**（范围、目标、首版要做到什么程度），放进"待我处理"。
- **立项书卡上有两个按钮**：
  - "确认并开工"：确认立项书，同时发起首个建设任务，项目进入建设中；
  - "只确认，稍后开工"：项目留在筹备中。以后用户发起建设任务时才进入建设中。
- **任务转为项目**：不新建维护者，原任务的维护者接着做立项问答。
- 建设任务的阶段计划由谁起草，交「意图澄清与规划交互」。倾向由项目维护者起草。

### 3. 文件与隔离

- **项目档案**：立项书、规格、术语表、ADR、进展、项目清单，以及维护者会话。固定放在数据目录的 `projects/<项目名>/` 下，随数据目录备份，永远不放进外部仓库。
- **工作目录**：项目的实际产物，比如代码仓库或数据。默认在项目档案里面；开发类项目立项时可以改为绑定一个外部路径。
- **二狗仓库**：项目都不在二狗自己的 GitHub 仓库里。某个项目的仓库要推到 GitHub 时，用户和它的维护者商量，由维护者单独建仓库。建仓库和推送都算对外发布，要用户明确确认。
- **文件边界**：维护者和它的子 agent，文件工具只能碰项目档案和工作目录这两处。
- **沙箱**：v1 不做系统级沙箱。隔离靠两层：文件工具的路径白名单，以及 bash 等命令经过的 AgentSense 式 hook 守卫。Windows 原生沙箱的调研留作将来加固时的参考。
- **记忆**：项目的记忆范围由秘书在立项时提议、用户确认。执行工单时，维护者能看到的是项目的记忆范围，加上工单里引用的、属于该任务记忆范围的条目。

### 4. 维护者

- **理解靠项目档案，不靠会话。**
  - 每个项目一条维护者会话，界面上是一条连续的聊天，按工单分段。
  - 每次唤起，上下文都从固定内容重新开始：工具包说明、项目规范、项目档案快照（规格摘要、进展、术语表）、上一段的摘要、这次的工单。更早的分段不进上下文，只留着给用户查看。
  - 每段结束前，维护者必须把新的理解写回项目档案，否则这段不算完成。具体写哪些文档，交「项目规范」。
  - 可以**重置维护者**：新开一段会话，只凭项目档案重建理解，旧会话保留可查。
- **平时休眠**，只是磁盘上的一条会话。两种情况会唤起它：
  - 工单到达；
  - 用户在它的会话里直接说话。
- **一次只做一件事**：同一个项目的工单排队，先来先做。被挡住的任务留在"排队中"，标"等项目 X"。
- **用户插话**：维护者干活时用户直接发给它的话，在它下一步之前插进去。
- **秘书查项目进展**不唤起维护者，直接读项目档案。
- **运营告警**（比如 LSM 报服务挂了）先只进"待我处理"。要不要自动唤起维护者诊断，交「运营态项目的服务托管与公网入口」。
- **停用和归档以后**：已停用项目的维护者照常可以对话、接工单。已归档项目的维护者会话只读，要用先取消归档；派单器碰到发给已归档项目的工单，直接退回并说明原因。
- **子 agent**：做什么、怎么分工，由维护者决定（并行仍要用户确认）。两条默认规则：
  - 项目档案只有维护者能写；
  - 开发类项目的并行改动，各自在独立的 git worktree 里做，由维护者合并。

### 5. 工单与派单

- **工单**是交给某个维护者的一份工作。维护者要做的所有事都是工单，来源有三种：
  1. 用户发起的、只涉及这个项目的任务；
  2. 别的任务的维护者派来的（多项目任务的一部分）；
  3. 定时作业的一次运行。

  用户在会话里直接跟维护者聊天不算工单。
- **派单器**是运行时的一部分，不是 agent。工单写进事件日志时注明收件项目；派单器把它放进这个项目维护者的工单队列，维护者在休眠就唤起，正忙就排队。维护者不用自己去领或去查。
- **工单的状态**：待你确认（只有计划外的工单才有这一步）→ 待接 → 进行中 ⇄ 等澄清 → 已结束（完成、退回、做不了）。
  - 项目维护者可以退回会伤害自己项目的改动，并说明理由。这时由任务维护者调整，或者转为"等我"问用户。
- **授权随计划一次确认**：多项目任务的计划要逐项列出动哪些项目、每个项目改什么，用户确认计划就确认了这些工单。计划外要动别的项目，或改动超出计划写的范围，才进"待我处理"再确认。
- **执行权限**：任务授权和项目权限的交集。
- **agent 之间只有工单这一种通信**：星形，不做 agent 群聊，全部记在任务时间线上。
- **可视化**：
  - 项目页上有维护者的**工单流水线**，分排队中、进行中、已结束三栏。每张工单显示来源（用户、哪个任务、哪个定时作业）、所属任务和当前阶段，点开跳到任务或会话。
  - 任务详情里列出这个任务派出的所有工单。
  - 工单不在任务看板上单独占卡。

### 6. 定时

- **调度器做在二狗守护进程里**，和 OpenClaw 的做法一样：
  - 守护进程本来就由 LSM 托管，不新增服务；
  - 不用 Windows 计划任务，因为 LSM 的 ADR-0005 不允许项目自带自启机制；
  - 简单提醒和定时作业共用这一个调度器。
- 本机插电和用电池时都从不睡眠、从不休眠（实测），不需要靠计划任务唤醒电脑。
- **错过的触发在启动时补**（电脑重启、关机，或者 LSM 重启把守护进程一起带走）：
  - 提醒晚了照发，标明"晚了 N 分钟"；晚得太久就改放进"待我处理"，作为"错过的提醒"；
  - 定时作业只补跑一次。
  - 具体阈值交「运行时架构」。
- 电脑关机期间提醒发不出去，v1 接受。
- **属于项目的定时作业由项目维护者执行**，每次运行是它的一张工单。只有不属于任何项目的定时作业才配自己的维护者。

### 7. agent 活动状态与全景

- 运行时实时上报每个 agent 的**活动状态**：
  - **休眠**：没在运行；
  - **干活中**：附带在干什么，比如任务 X 第 N 阶段、定时作业、和用户对话；
  - **等你**：在等用户批准、回答或验收；
  - **排队**：有活，但在等并发名额，或者在等项目维护者空出来。
- 第一阶段：任务看板和项目列表上用小圆点显示每个 agent 的活动状态。
- 第二阶段：做**全景**页，拟人化、带动画，一眼看到所有 agent 在干什么，点一个就进入它的会话。见新票「全景视图」。
- 读记忆不经过记忆管理者：每轮的简报和深查都是运行时的检索，不调用记忆管理者。所以在全景里，读记忆不会让它"动起来"。
