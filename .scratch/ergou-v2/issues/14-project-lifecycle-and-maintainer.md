# 项目生命周期、工作空间与维护者

Type: grilling
Status: open
Blocked by: 02, 03, 05

## Question

1. **项目状态机**：草案是 筹备 → 进行中 → 目标完成（待用户判定）→ 运营 / 归档；运营中可以接新目标。具体要定：
   - "目标"是否作为项目的子实体；
   - 怎样转入运营、怎样归档。
2. **立项**：用意图澄清（类似 grill-with-docs）产出项目的规格、`CONTEXT.md` 和 ADR。
3. **隔离**：
   - 工作空间隔离：目录或 git 仓库、会话、文档；
   - 可选的沙箱运行环境；
   - 项目能看到哪部分记忆，由用户授权。
4. **维护者**：
   - 怎样长期保有对项目的理解；
   - 怎样休眠、怎样被拉起；
   - 怎样拉起其他 agent 配合。
5. **项目群组 UI**：移交「项目管理界面」。

## Context

- 立项 grilling Q6、Q12：
  - 项目另起独立空间，可以用 grill-with-docs 规划；
  - 用户判定目标完成之后，项目可能归档，也可能转运营；
  - 每个项目必须有一个维护者，平时不拉起。
- 和「多 agent 架构与 token 成本」强相关（用户原话："这和是否一定要多 agent 架构有关系"）。
- 「多 agent 架构与 token 成本」已定：
  - 每个项目和任务绑定一个常驻维护者；
  - 默认串行执行，要并行时由维护者提议、用户确认；
  - 用户可以绕过秘书直接和维护者对话。

  本票只需要定下：项目状态机、立项、隔离，以及维护者怎样休眠、怎样被拉起。
- 「记忆边界」已定：立项时授予项目级的记忆范围；维护者每次被唤起时都在这个范围内取用，超出范围要提醒用户临时授权。维护者看不到动机假设。
- 用户 2026-10-07 补充（见「项目规范：默认工作流程与文档模板」）：
  - 用户心目中的项目状态有：开发态、已完成、运营态、已下线。本票要把它们和上面的草案对齐。
  - 要注意区分"已下线"（运营过、后来停掉）和"归档"（目标完成后没有转运营）是否是两个状态。
  - "开发态"这个叫法只适合开发类项目；二狗的项目覆盖所有日常事务，状态名要对非开发项目也成立。
  - 状态机定下来后，「项目规范：默认工作流程与文档模板」在它之上定每个状态的流程和文档。
- 「任务生命周期与任务看板」已定：
  - 项目是原子的、可运营的功能模块，和任务分开管理，在项目管理界面里，不上看板。
  - 任务和项目多对多。**只有项目的维护者能改它的项目**：单项目任务由项目维护者执行；多项目任务由任务自己的维护者统筹，把各项目的部分交给各项目的维护者。本票要定维护者之间怎样交接。
  - 开发新项目：立项问答 → 建项目 → 开发工作作为任务，由新项目的维护者执行。
  - 任务转为项目：先走立项问答，原任务的维护者成为项目维护者。
