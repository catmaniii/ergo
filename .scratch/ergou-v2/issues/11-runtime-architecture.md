# 运行时架构：守护进程、pi 封装层与持久化

Type: grilling
Status: open
Blocked by: 01, 02

## Question

1. **部件组成**：守护进程内部由哪些部件组成？候选部件：
   - 网关；
   - 秘书运行时；
   - 任务调度器；
   - 执行者运行时；
   - 记忆管理者；
   - 通知服务；
   - 定时器。
2. **pi 封装层**：边界划在哪里？
3. **持久化**：事件日志、任务状态机、审批表、会话存储，分别用什么实现？
4. **可靠性**：崩溃后怎样恢复？有副作用的操作怎样保证幂等？

产出 ADR。

## Context

- `docs/research/06-long-tasks-hitl-interruptions.md` §3：pi 的审批对话阻塞在进程内，进程一死审批就丢；需要自补事件日志、审批表、心跳。
- 「pi 1.0 各层能力映射」和「多 agent 架构与 token 成本」的结论。
- 「多 agent 架构与 token 成本」移交过来的：
  - 每个任务和项目都有一个常驻维护者会话；
  - 默认串行执行，并行要经用户确认后才拉起临时 agent；
  - 省 token 的手段（用引用代替转述、保持前缀稳定、利用空闲时段调度）由本票落实。
- 「pi 1.0 各层能力映射」的结论：
  - 推荐用 pi-ai + pi-durable，外面包一层薄封装；
  - 需要自建：审批表、强制守卫、回退摘要、事件续传、成本账本；
  - 每个会话固定一个模型；
  - 版本要精确锁定。

  详见 `docs/research/10-pi-layer-mapping.md`。
- 2026-10-07 用户修正：**排除 pi-durable**（实验性）。底座在下面两者中选，崩溃续跑、待审批恢复、子 agent 父子关系都要自建：
  - (A) `pi-agent-core` 的 `Agent`；
  - (B) `pi-coding-agent` 的 SDK。
- **2026-10-07 用户已定**：底座用 `pi-coding-agent` 的 SDK，见 `docs/adr/0001-pi-coding-agent-sdk-as-runtime.md`。本票不再讨论选层，只讨论部件、封装边界、持久化和恢复。
- 「记忆边界」已定，本票需要落实：
  - 用户卡放在秘书的 system 段，每天最多刷新一次；
  - 记忆简报和"看板变化"作为持久化的上下文消息追加在对话尾部，不改 system 段；
  - 素材事件由运行时自动、确定性地产生（七类，统一信封），agent 不能挑选；
  - 秘书只有一条主线会话，要配专用的压缩指令：丢掉任务执行细节和已解决的问答，任务只留 ID；保留进行中的话题、未回答的问题、还没被记忆管理者处理的指示；
  - 部件里要有提醒调度器：简单提醒到点直接发通知，不拉起 agent。
- 「任务生命周期与任务看板」已定，本票需要落实：
  - 所有状态变化写入事件日志，看板由事件推导；
  - 全局最多同时 3 个任务在执行（可调），其余排队；子 agent 不占名额；
  - 快速动作执行器：用户确认后由运行时直接执行，不拉起 agent；
  - 维护者之间的交接通道（多项目任务把各项目的部分交给项目维护者）；
  - token 记账：从 pi 每次调用的用量里记任务、agent、会话、模型、输入（缓存命中 / 未命中）、输出。
