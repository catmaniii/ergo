## 讨论稿 v0（2026-10-07，供讨论用，尚未定案）

### 1. 看板上放什么

- **看板的单位是任务**，形态有：一次性任务（包括长程任务）、简单提醒、定时作业。
- **项目不作为卡片**，列在「项目管理界面」里。项目里的每一件工作，作为一张任务卡出现在看板上，标明所属项目，由项目维护者来做。
- **对话不上看板**。但有副作用的事一律成为任务（地图 Notes）。
- **快速动作**（待定）：一步就能做完、不需要 agent 判断的副作用操作（比如把秘书已经写好的一段话发出去），是否像简单提醒一样不配维护者，由运行时在用户确认后直接执行？

### 2. 状态

```
规划中 → 待确认 → 排队中 → 执行中 → 已完成 → 已归档
                            │  ↑ ↓            │
                            │  等我 / 已暂停   └→ 返工 → 执行中
                            ├→ 失败 ─(重试)→ 执行中
任何未结束的状态 ──────────→ 已取消
```

- **等我**：带原因——运行时审批、任务澄清、卡住求助。
- **已暂停**：用户手动暂停，或系统因超预算、卡住而暂停。
- **失败**：维护者判断做不下去，并说明原因。用户可以重试或取消。系统不会悄悄判失败。
- **已完成**：维护者交付并通过验收。用户可以要求返工，由同一个维护者接着做。
- **已归档**：已完成、失败、已取消的任务，若干天没有动作后自动归档，也可以手动归档。
- **简单提醒**：待触发 → 已触发（一次性的），或者继续待触发（重复的）。
- **定时作业**：运营中 ⇄ 已暂停；每次运行留一条运行记录，记录自己的结果。

看板分组：**等我**（包括待确认）→ **进行中**（规划中、排队中、执行中）→ **运营中**（提醒、定时作业）→ **最近结束**（已完成、失败、已取消）→ 已归档。

### 3. 谁能改状态

| 谁 | 能做什么 |
|---|---|
| 秘书 | 建任务、规划；用户要求时取消 |
| 维护者 | 开始、报告进展、转为等我、完成、失败 |
| 用户（在看板上） | 确认计划、暂停 / 继续、取消、批准、回答、返工、归档、把任务转为项目 |
| 系统 | 排队调度；卡住或超预算时暂停；到点触发提醒 |

所有变化都是事件，写入事件日志，看板由事件推导出来。

### 4. 任务、agent 与会话

- 一次性任务：一个维护者，维护者有自己的长期会话。项目里的任务由项目维护者来做。
- 子 agent：挂在任务下面，各有会话，在任务详情里能看到。
- 定时作业：一个维护者，每次运行一条运行记录，会话按运行分段查看。
- 简单提醒、快速动作：没有 agent。

### 5. token 记账

- 每次调用模型记一条：任务、agent、会话、模型、缓存命中、缓存未命中、输出。
- 任务卡上显示该任务的总量；任务详情里按 agent 细分。
- 秘书和记忆管理者的消耗单列为"系统开销"。
- 全局"消耗"页按天、按 agent 汇总。金额只作粗估，并标明是粗估。

### 6. 秘书从看板得到什么

"看板变化"消息只包括：别人新建的任务（用户直接建、维护者登记）、转为等我、完成、失败、取消、提醒已触发。日常进展不推给秘书。

## Answer

2026-10-07 定稿。

> **2026-10-07「项目生命周期、工作空间与维护者」修订**：
> - 属于项目的定时作业由项目维护者执行，只有不属于任何项目的定时作业才有自己的维护者（改 §6）。
> - 维护者要做的所有事都是**工单**，经派单器送进它的工单队列；单项目任务也生成一张工单给项目维护者（补充 §2）。
> - 多项目任务的交接：计划里逐项列出各项目的改动，用户确认计划即确认这些工单（补充 §2）。

### 1. 三种工作形态与看板

| 形态 | 是什么 | 在哪里管 |
|---|---|---|
| **对话** | 和秘书一问一答；可以包含快速动作，秘书也可以在对话里建简单提醒 | 聊天 |
| **任务** | 用户明确发起、分阶段规划、一次授权后执行到底的综合性工作。原先的"长程任务"就是它，二者合并为一个词 | **任务看板** |
| **项目** | 原子的、可以长期运营的功能模块 | **项目管理界面** |

- **看板上只有**：任务、简单提醒、定时作业。对话、快速动作和项目都不上看板。
- **任务必须由用户明确发起**：在消息里明说，或者点"发起任务"按钮。秘书在对话中发现要多步干活时，只能给出一张"建议发起任务"的卡，用户点了才算发起。
- **快速动作**：一步就能做完、不需要 agent 判断的副作用操作（比如把秘书已经写好的话发出去）。
  - 秘书把动作写清楚：做什么、对谁做。
  - 用户确认后（或者在已有授权范围内），由运行时直接执行，不拉起 agent。
  - 是否需要确认，由「关注类别与打扰策略」决定。
  - 聊天里留一张"已执行"的动作卡，并记入操作记录。
  - 秘书仍然没有执行权，只能提议。
- **转为项目**：先经过立项问答（确认范围和目标），之前的对话和任务作为上下文；原任务的维护者就是新项目的维护者。

### 2. 任务和项目的关系，谁来动手

- 一个任务可以涉及 0 个或多个项目。任务卡上标出它涉及的项目，项目页列出所有涉及它的任务。
- **只有项目的维护者能改它的项目。**
  - **只涉及一个项目**（比如"给项目 X 加个功能"）：由 X 的维护者直接执行，不另起 agent。
  - **涉及多个项目或不涉及项目**：任务有自己的维护者，负责统筹。要改哪个项目，就把那部分交给那个项目的维护者，最后自己汇总。
  - **只是查看**多个项目的进展：直接读各项目按「项目规范」提供的统一入口。
  - **开发新项目**：立项问答 → 建项目 → 开发工作作为一个任务，由新项目的维护者执行。
- 用户直接在维护者会话里下的小指令，记进原任务的时间线，不建新卡。新的成块工作，由用户明确发起新任务。

### 3. 任务的状态

```
规划中 → 待确认 → 排队中 → 执行中 → 已完成 ──(用户手动)──→ 已归档
                            │  ↑ ↓            │
                            │  等我 / 已暂停   └→ 返工 → 执行中
                            ├→ 失败 ─(重试)→ 执行中
任何未结束的状态 ──────────→ 已取消
```

- **内外两层**：上图是任务这一层，看板显示的就是它。"执行中"里面运行 AgentSense 式的阶段计划，每个阶段有交付件、验收标准、本阶段的授权和安全策略。卡片上显示"第 N/M 阶段"。阶段层的机制交给「长程任务机制泛化」。
- **等我**带原因：运行时审批、任务澄清、计划里标明"由你验收"的阶段、卡住求助（拉回超限、某阶段 3 次未通过）。
- **已暂停**：用户手动暂停，或系统因超预算、卡住而暂停。
- **失败**：由维护者判定并说明原因，系统不会悄悄判失败。用户可以重试或取消。
- **已完成**：自动进入，不需要用户验收。用户可以要求**返工**，沿用 AgentSense 的"按依赖重开"：只重开出问题的阶段和它的下游，由同一个维护者接着做。
- **已归档：只能由用户手动触发。**已完成、失败、已取消的任务，用户不归档就一直留着。每周把结束超过 7 天、还没归档的汇总成一条"归档清单"放进"待我处理"，每一项可以选：归档、继续改（返工）、先留着（下周再问）。
- **简单提醒**：待触发 → 已触发（一次性的），或者一直待触发（重复的）。
- **定时作业**：运营中 ⇄ 已暂停。每次运行留一条运行记录。某次失败就记一条失败的运行记录，作业卡上标"最近一次失败"；连续失败 3 次自动暂停，并进"待我处理"。

### 4. 谁能改状态

| 谁 | 能做什么 |
|---|---|
| 用户 | 发起任务、确认计划、暂停 / 继续、取消、批准、回答、验收、返工、归档、转为项目 |
| 秘书 | 按用户的发起建任务卡、做规划；用户要求时取消；建、改、取消简单提醒 |
| 维护者 | 开始、报告进展、转为等我、完成、失败 |
| 系统 | 排队调度；卡住或超预算时暂停；到点触发提醒和定时作业 |

所有变化都是事件，写入事件日志，看板由事件推导出来。

### 5. 并发

- 全局最多同时 **3 个任务**在执行，可调。多出来的进"排队中"。
- "等我"和"已暂停"的任务不占名额，简单提醒和快速动作也不占。
- 名额按任务算，不按 agent 算。任务经用户确认后派出的子 agent 不占名额，所以同时在跑的 agent 可能超过 3 个。

### 6. 任务、agent 与会话

- 每个任务的执行者是一个维护者：只涉及一个项目的，是项目维护者；否则是任务自己的维护者。维护者有自己的长期会话，看板上能打开它的会话历史，也能在会话里直接给它下指令。
- 子 agent 挂在任务下面，各有会话，在任务详情里能看到。
- 定时作业：一个维护者，会话按运行分段查看。
- 简单提醒、快速动作：没有 agent。

### 7. 待我处理

- Web UI 主界面上的一个 tab，**汇集所有需要用户注意或确认的事项**。竖屏时点进去是一个单独的页面。
- **事项种类**：待确认的计划、运行时审批、任务澄清、阶段验收、卡住求助和失败后的抉择、定时作业被自动暂停、每周的归档清单。
- **"了解你"问题不放进来**，留在记忆 Web UI 的问题箱里，不亮红点。
- **小红点**：有未读事项时亮，全部已读就不亮。看过还没处理的事项留在列表里，tab 上用灰色数字显示还剩几件。
- **管理**：每一项可以标已读、归档、删除。还卡着任务的事项（比如待批的审批）不能直接删除或归档，要先处理掉，免得任务悄悄卡死。纯通知类的事项可以随意删除、归档。
- **秘书不转述**：进了"待我处理"的事，秘书不在对话里主动提。用户主动问时，秘书能看到所有未处理的事项，在对话里列出来、解释，并把同一张事项卡放进聊天。用户在卡上点按钮才算处理，秘书不能代替用户做决定。
- 手机上：卡住任务的事项按「推送与远程审批通道」的规则推送，点开推送直接进到对应的那一项。

### 8. token 记账

- 运行时封装层从 pi 每次调用模型返回的用量里记一条：任务、agent、会话、模型、输入（缓存命中 / 未命中）、输出。
- **展示**：
  - 任务卡上显示该任务的总量；
  - 任务详情里按 agent 细分，包括子 agent；
  - 全局"消耗"页按天、按 agent 汇总，秘书和记忆管理者单列为"系统开销"。
- **粗估成本**：选一个时间范围，用量乘单价，页面上标明"粗估"。
