Type: grilling
Status: resolved

## Question

用户怎样为长程任务和项目指定"哪些操作要提醒我"？需要定下来的问题：

1. **关注类别注册表**：结构是什么（匹配条件、属性、处置档位）？
2. **默认值**：默认带哪些类别？哪些底线不允许用户放宽？
3. **授权与确认**：计划期给出的、带边界的授权（grant），和运行时的确认是什么关系？
4. **打扰控制**：打扰预算、汇总推送、免打扰时段，以及超时后的默认处理。
5. **呈现**：这些类别在全局层和要点层视图上怎样展示？

  - 计划卡上要展示两件事：这份计划引用了哪些记忆，以及执行中可能调用的记忆范围。

  - 计划外的工单（计划没列的项目，或超出计划写的改动范围）要进"待我处理"确认。
  - 项目建 GitHub 仓库、推送，算对外发布。
  - **v1 不做系统级沙箱**，隔离只靠文件工具的路径白名单和 AgentSense 式 hook 守卫，所以守卫要能识别 bash 等命令越出项目目录（项目档案和工作目录）。
  - 按需服务的拉起要不要确认，和「运营态项目的服务托管与公网入口」一起定。

## Answer

2026-10-07 定稿。

### 1. 关注类别是什么

- 关注类别是给**工具调用**分的类。agent 每次调用工具之前，守卫先判断"这次调用落在哪些类别里"，再按那个类别的处置档位决定：放行、记一笔，还是问用户。
- 判断分三层：
  - **看工具本身**：每个工具带类别标签。比如"发消息"永远算"以我名义对外发送"；`read` 一般什么类别都不算。
  - **看参数**：`write` 的路径在项目目录外，算"越出项目目录"；覆盖一个已有文件，算"删除或覆盖"。
  - **拆开 bash 命令看**：`git push` 算对外发布，`rm` 算删除，`npm install` 算装软件。见第 5 节。
- 一次调用可以同时落在多个类别里，取其中最严的档位。

### 2. 类别注册表

- 类别做成数据，放在数据目录里 agent 写不到的地方。
- **v1 内置这些类别**：
  - 花钱；
  - 以我的名义对外发送或发布（包括建 GitHub 仓库、推送）；
  - 删除或覆盖；
  - 不可逆的提交；
  - 账户与安全（凭据、权限、装软件）；
  - 越出项目目录；
  - 使用授权范围外的记忆；
  - 计划外工单；
  - 未知的写操作。
- **内置类别和自定义类别都靠确定的规则判断**，结果可预期。用户自定义类别也只能写规则：匹配工具、路径、收件人、金额。比如"往 xx@company.com 发邮件""动 `D:\财务` 目录"。
- "写一句话、由模型判断算不算"以后再加。加的时候，这个模型只能把处置往严里改。

### 3. 处置档位：六档

按打扰程度从低到高：

| 档位 | 含义 | 例子 |
|---|---|---|
| 1. 直接做，只记录 | 不打扰，事后可查 | 在项目目录里读写文件 |
| 2. 做完告诉我 | 不拦，但写进任务摘要，在时间线上标出 | 做了一次 git commit |
| 3. 计划里列了才做 | 确认计划时一次批准，执行时不再问；计划外才问。对话模式没有计划，等同"先问我" | 计划里写明要推送到某个仓库 |
| 4. 先问我 | 停下来，等用户点 | 计划外的对外发送 |
| 5. 交给我做 | agent 把东西准备好，最后一步用户亲手做 | 付款 |
| 6. 永不 | 不问，直接拒绝 | 把密钥写进对外内容 |

- **为什么不是 AgentSense 的三档**：红线、拦截、确认三档只覆盖"不许做"和"问你"这一侧，结果大部分操作要么完全静默，要么打断用户，缺了"可以做，但你想知道"的中间档。AgentSense 的红线大致对应第 6 档，拦截对应第 5 档，确认对应第 4 档；第 1–3 档是新加的。第 3 档是长程任务"规划一次、授权一次"的核心。
- 每个类别分"对话"和"任务"两套默认档位。用户只能往严里调。
- **两条底线，不能放宽**：
  - 付款转账、创建账户、改密码或两步验证：固定为"交给我做"；
  - 把凭据写进对外内容：固定为"永不"。

### 4. 授权与确认

- **照搬 AgentSense 的授权项**：
  - 一个授权项 = 操作种类 + 对象范围 + 次数 + 所属阶段。次数按实际生效的效果计算。
  - 计划卡上没勾选的操作，执行到那一步再问。
  - 不在所属阶段内的调用会被拉回。
- **新增两项**：
  - 授权有**有效期**，过期要续；
  - **记忆范围**也算一种授权项，在用户确认计划时一并授予（「记忆边界」已定）。
- **计划卡上的授权由代码生成**：从结构化数据生成，不用模型写的摘要。
- **运行中授权只能收窄**，要放宽一律回来问用户。重新规划时只问新增的部分。
- **偏离计划时逐级升级**：
  1. 计划外、但在授权范围内：只记一条摘要；
  2. 超出授权：先问用户；
  3. 出现计划没预料到的类别：先问用户，并暂停这一支；
  4. 累计被用户拒绝太多次：暂停整个任务。
- **时序规则**（hook 上的"B 之前必须做过 A"这类检查）也要。引擎、规则模板和"阶段组"策略，见「长程任务机制泛化」。

### 5. bash 与"通用 bash"

- **能用专用工具的就不用 bash**：读写文件、git、HTTP 都走带类别标签的专用工具。
- **常用的特殊 bash 操作封装成带类型的工具或特殊调用**，比如 git 提交和推送、跑测试、装依赖、启动构建。它们有确定的类别，规则可以直接套用。
- 其余的 bash 调用叫**通用 bash**，也就是没有事先规定类型的命令：
  - 照常受守卫检查：拆开管道和子命令，查路径是否越出项目目录，查有没有删除、联网、推送、装软件。拆出来落在某个类别的，按那个类别的档位处置。
  - 拆不开的（`eval`、内联脚本、编码过的命令），按"未知的写操作"先问用户。
  - 拆得开、也没落在任何类别里的，不打断，但**必须显式标出**：任务时间线的要点层和全局层都要能看到"这里调了一个没有事先规定类型的通用 bash"。
- **bash 由工具包决定**，不再"只给工程师角色"（「角色模型」已取消角色）。开发类项目默认带 bash。
- v1 只开放一种 shell。

### 6. 快速动作与推送分级

- **快速动作**：
  - 用户这一轮明确点了对象和内容的（比如"把这段发给张三"），卡片只展示规范化后的动作，不再确认；
  - 秘书自己推断出来的副作用，按类别处置（通常是先问）。
- **"待我处理"里的事项分三档紧急度**：
  - 卡住了任务、而且有时限：立即推送；
  - 卡住了任务：推送，可以合并，免打扰时段先攒着；
  - 不卡任务：不推送。比如维护者的越界通知（「角色模型」）。
- "了解你"问题不进"待我处理"、永远不推送；任务澄清走审批和推送通道（「记忆边界」已定）。
- v1 不设每日打扰上限，改为在计划卡上预告"授权后还会在 N 处停下来"。

### 7. 呈现

- 要点层和全局层上，落在关注类别里的调用标出类别。
- 通用 bash 单独标出（第 5 节）。
- 授权内的操作、做完告诉我的操作、被拦下或问过的操作，用不同的样式区分。
