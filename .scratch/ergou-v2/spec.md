# 二狗 v2 第一阶段规格：骨架

Status: ready-for-agent

来源：地图 [二狗 v2](map.md) 第一阶段的全部决策票、记忆子地图的「素材管理」、ADR-0001（pi-coding-agent SDK 作运行时）、ADR-0002（每个 agent 一个子进程）、ADR-0003（不设角色，按项目或任务配工具包），以及根目录 `CONTEXT.md` 术语表。本规格汇总这些决定；票里写明"留给规格"的细节，在这里给出默认做法，并在 Further Notes 里列出请用户过目的几项。

## Problem Statement

我要一个真正为自己干活的个人助理。现有的做法（直接套用 OpenClaw 的二狗 v1）有几个问题：

- 一个 agent 什么都干，上下文越堆越乱，干长活时忘了计划、忘了我说过的边界。
- 要么事事都问我，要么悄悄做了我不想让它做的事。没有"可以做，但我想知道"的中间档，也没法事先一次说清楚这件事里哪些操作要提醒我。
- 我说过的话、我的反应散落在各个会话里，没有攒起来。以后想让它真正理解我，得从第一天起就把这些原始素材留好。
- 多个长期在做的事情（项目）没有固定的负责者，每次都要重新交代背景。
- 我在手机和电脑上都要用，审批和进展要能随时看到，断线了也不能丢东西。
- 电脑会重启、守护进程会被重启，正在做的事不能因此乱掉或悄悄重做有副作用的操作。

## Solution

二狗 v2 第一阶段先搭一副能用的骨架：

- **秘书是唯一的默认对话入口**。它理解我的话，每次回复只落在五种形态之一：直接回答、快速动作卡、"建议发起任务"卡、"建议立项"卡、简单提醒。它不碰项目、不对外，只有一块自己的草稿区，可以写文件、跑脚本做计算；对项目或对外有副作用的操作，走快速动作或任务。
- **任务**由我发起：直接点"发起任务"，或者让秘书去发起（我的要求就是授权）。秘书先和我对齐意图、写出任务书，执行的维护者据此起草分阶段的计划。我在一张计划卡上一次确认阶段、工具包和授权，之后它按计划执行到底，尽量不打扰我。
- **项目**是可以长期使用的功能模块，有自己的项目档案、工作目录和固定的维护者。维护者要做的所有事都是工单，由派单器送进它的队列，一次做一件。
- **守卫**在每次工具调用之前判断它落在哪些关注类别里，按六档处置决定直接做、做完告诉我、计划里列了才做、先问我、交给我做还是永不。时序规则持续检查"B 之前必须做过 A"这类约束。
- **范围审视**作为软约束，在压缩时和每张工单结束时检查维护者有没有做范围外的事，越界的记下来、提醒我，但不卡死。
- **待我处理**汇集所有要我注意或确认的事。同一张卡在聊天、待我处理和时间线里状态同步。
- **从第一天起积累素材**：我说过的每句话、对产出和审批的每个反应都作为素材入库，"本人"的原话另存一份不可修改的副本，建好关键词和向量索引。第一阶段只积累，不推断。
- **Web UI** 按手机竖屏优先设计，宽屏换布局；PC 本机直接用，其他设备经 VPS 的 HTTPS 域名、配对后使用。
- **运行时**：常驻守护进程由 Local Service Manager 托管，只当管家；每个 agent 跑在自己的子进程里，状态都在磁盘上，被杀后能按规则恢复。每晚备份到华为家庭存储的同步目录。

## User Stories

**秘书与对话**

1. 作为用户，我希望有一个默认的对话入口（秘书），以便不用记住该找哪个 agent。
2. 作为用户，我希望秘书对简单问题直接回答，以便日常问答像普通聊天一样快。
3. 作为用户，我希望秘书发现一件事需要多步干活时，只给我一张"建议发起任务"卡，以便由我决定要不要正式发起任务。
4. 作为用户，我希望在消息里让秘书去做某件需要任务的事、或点"发起任务"按钮时，秘书直接发起任务（我的要求就是授权），以便不被多余的确认打断。
5. 作为用户，我希望秘书发现一件事更像一个长期模块时，给我一张"建议立项"卡，以便由我决定要不要立项。
6. 作为用户，我希望说"明早 9 点提醒我交报告"时，秘书直接建好简单提醒，并给我一张能改、能取消的提醒卡，以便不用另开日历。
7. 作为用户，我希望秘书能改和取消已有的简单提醒，以便在对话里随口调整。
8. 作为用户，我希望秘书答应"以后、到点做某事"时当场在任务看板上建出对应的任务或提醒，以便承诺不会只活在对话里而被忘掉。
9. 作为用户，我希望秘书掌握任务靠查看板而不是靠回忆，以便它说的进展总是准的。
10. 作为用户，我希望看板有变化时，秘书在我下一条消息之后自动得知变化，以便它不会拿着过时的情况回答我。
11. 作为用户，我希望秘书查项目进展时直接读项目档案、不去唤醒维护者，以便查询又快又不打扰正在干活的 agent。
12. 作为用户，我希望秘书只有一条长期主线会话，靠自动压缩控制长度，以便我不用管理一堆会话。
13. 作为用户，我希望压缩时丢掉的只是任务执行细节和已解决的问答，进行中的话题和我刚说的还没处理的指示一定保留，以便压缩后秘书不会失忆。
14. 作为用户，我希望秘书不主动转述"待我处理"里的事，但我问的时候它能列出来、解释，并把同一张卡放进聊天，以便对话不被通知淹没、需要时又能就地处理。
15. 作为用户，我希望秘书不能替我在卡片上做决定，以便所有确认都出自我亲手点击。
16. 作为用户，我希望发给秘书的消息可以带图片和文件，秘书的回复也可以带图片和文件，以便处理日常材料。
17. 作为用户，我希望秘书有一块自己的草稿区，能写文件、跑脚本做简单计算，以便它为了理解我的需求能动手算一算、试一试。
18. 作为用户，我希望秘书要跑草稿区外的现成脚本或读我给的本机文件时，先给我一张审批卡，以便点一下就能跑、又不越界。
19. 作为用户，我希望秘书不能联网，要联网就派一个任务出去，以便读得到我全部记忆的 agent 不会把东西往外发。

**快速动作**

20. 作为用户，我希望"把这段发给张三"这种我点明了对象和内容的一步操作，卡片只展示规范化后的动作、不再让我确认，以便明确的指令立即生效。
21. 作为用户，我希望秘书自己推断出来的副作用按关注类别处置（通常先问我），以便它不会擅自行动。
22. 作为用户，我希望快速动作由运行时直接执行、不拉起 agent，并在聊天里留一张"已执行"的动作卡，以便又快又有记录。
23. 作为用户，我希望快速动作不上任务看板、不占并发名额，以便看板只放真正的工作。

**任务**

24. 作为用户，我希望发起任务后秘书先说出它的理解（"我理解你要的是……，对吗？"），以便尽早纠正误解。
25. 作为用户，我希望秘书的澄清问题攒成一批，每题带推荐答案，可以一键"全按推荐"，以便少花时间回答。
26. 作为用户，我希望已经确认过的事秘书不再问，以便不重复回答。
27. 作为用户，我希望规划时拿不准的地方写进计划的"假设"栏，确认计划时一起改，以便不必为它们单独再问一轮。
28. 作为用户，我希望秘书把对齐后的意图写成一份任务书（目标、验收标准、约束、涉及哪些项目），交给执行的维护者起草计划，以便规划由最了解执行的 agent 来做。
29. 作为用户，我希望只用一张计划卡、一个"确认"按钮，同时确认阶段、工具包和授权，以便一次授权后不再被打扰。
30. 作为用户，我希望计划卡上列出每个阶段的交付件、验收标准和由谁验收，以便知道什么算做完。
31. 作为用户，我希望计划卡上逐行列出涉及哪些项目、每个项目改什么，以便确认计划时就确认了对各项目的改动。
32. 作为用户，我希望计划卡上的授权是由代码从结构化数据生成的，而不是模型写的摘要，以便我看到的就是实际生效的。
33. 作为用户，我希望能在计划卡上逐行勾掉或收窄授权，或附上意见打回重做，以便按我的意思调整计划。
34. 作为用户，我希望计划卡上能增加本任务要提醒的关注类别（默认取全局设置，只能加不能删），以便每个任务按需提醒，不局限于安全。
35. 作为用户，我希望计划卡预告"授权后还会在 N 处停下来"，并给出 token 粗估，以便心里有数。
36. 作为用户，我希望计划卡的细节默认折叠，以便一眼看清要点。
37. 作为用户，我希望在任务看板上看到所有任务、简单提醒和定时作业及其状态，按"等我 → 进行中 → 运营中 → 最近结束 → 已归档"分组，以便一眼知道哪些需要我。
38. 作为用户，我希望任务卡上显示"第 N/M 阶段"、活动状态小圆点和 token 总量，以便不点开也知道进展。
39. 作为用户，我希望"等我"状态写明原因（审批、澄清、由我验收、卡住求助、中断不确定），以便知道要做什么。
40. 作为用户，我希望能暂停、继续、取消任何任务，以便随时掌控。
41. 作为用户，我希望任务完成是自动的，但我能要求返工，只重开出问题的阶段和它的下游，以便不重做没问题的部分。
42. 作为用户，我希望维护者判定失败时必须说明原因，系统不会悄悄判失败，我可以重试或取消，以便失败有交代。
43. 作为用户，我希望归档只能由我手动触发，并且每周把结束超过 7 天还没归档的任务汇总成一条归档清单，每项可选归档、继续改或先留着，以便看板不乱又不丢东西。
44. 作为用户，我希望全局最多同时执行 3 个任务（可调），多出来的排队，以便机器和费用可控。
45. 作为用户，我希望等我和已暂停的任务不占并发名额，以便卡住的任务不挡别人。
46. 作为用户，我希望能打开任意任务的维护者会话，直接给它下指令，以便绕过秘书处理细节。
47. 作为用户，我希望我在维护者会话里直接说的小指令记进原任务的时间线、不建新卡，以便看板不被碎事填满。

**阶段执行、验收与偏离**

48. 作为用户，我希望每个阶段的验收标准能写成脚本的都写成脚本，在维护者宣布阶段完成时由系统运行，以便验收不靠维护者自说自话。
49. 作为用户，我希望写不成脚本的标准由一个只读的评审子 agent 在新上下文里只看交付件和标准来判，卡片上标"评审判定"，以便有独立的第二双眼睛。
50. 作为用户，我希望只有计划里标明"由你验收"的阶段才停下来等我，以便验收不成为打扰。
51. 作为用户，我希望维护者自检不能单独算验收，以便"做完了"是可信的。
52. 作为用户，我希望阶段图允许并行，但只有我确认后才真正派子 agent 并行，以便并行的成本由我决定。
53. 作为用户，我希望子 agent 的结果一定回到维护者的会话里，以便维护者能接着用。
54. 作为用户，我希望维护者不扩大授权的调整（拆阶段、调顺序）自己改并记进时间线，以便不为小事问我。
55. 作为用户，我希望要扩大授权、加项目、加能力、改目标或验收时，维护者提交一份计划变更进待我处理，只有受影响的阶段停下来，以便其余工作照常推进。
56. 作为用户，我希望维护者偏离计划时按级升级：授权内只记一笔、超出授权先问我、出现没预料到的类别先问我并暂停这一支、累计被拒太多次暂停整个任务，以便偏离的代价和打扰成正比。
57. 作为用户，我希望调用不在所属阶段的授权时被拉回，拉回 3 次还不行就找我，以便维护者不会乱跳阶段。
58. 作为用户，我希望阶段验收退回 2 次、第 3 次还不过就找我，以便不无限重试。
59. 作为用户，我希望预算按 token 加工具调用次数计算，用量超过预算让维护者说明进展、超过预算的 2 倍问我，以便及时发现跑偏。
60. 作为用户，我希望 agent 还活着但很久没有进展时系统催促它，催 3 次还不行就找我，以便卡死的任务不会静悄悄地耗着。
61. 作为用户，我希望我长时间不在时，"等我"的事项永不自动批准，不依赖它的阶段继续推进，以便安全和进度兼顾。
62. 作为用户，我希望授权有有效期，过期要续，以便旧授权不会永远有效。
63. 作为用户，我希望计划、授权、当前阶段和我说过的边界由运行时保管，每次唤起和压缩之后重新注入，以便维护者压缩后不会忘掉约束。
64. 作为用户，我希望我在对话里说的限制被编译成规则、显示在计划卡上，以便限制真的生效而不只留在对话里。

**守卫与打扰**

65. 作为用户，我希望每次工具调用之前，守卫按工具本身、参数和拆开的 bash 命令确定性地判断它落在哪些关注类别里，以便结果可预期。
66. 作为用户，我希望一次调用落在多个类别时取最严的处置，以便不会因为分类重叠而漏网。
67. 作为用户，我希望内置花钱、对外发送或发布、删除或覆盖、不可逆的提交、账户与安全、越出项目目录、使用授权范围外的记忆、计划外工单、未知的写操作这几类，以便开箱就有合理的保护。
68. 作为用户，我希望能用确定的规则自定义关注类别（匹配工具、路径、收件人、金额），比如"往某个邮箱发邮件"或"动某个目录"，以便提醒我关心的任何事，不限于安全。
69. 作为用户，我希望每个类别在对话和任务里各有一套默认处置，我只能往严里调，以便设置不会意外放松保护。
70. 作为用户，我希望付款转账、创建账户、改密码或两步验证永远是"交给我做"，把凭据写进对外内容永远是"永不"，以便这两条底线谁也放宽不了。
71. 作为用户，我希望"做完告诉我"的操作不拦，但写进任务摘要并在时间线上标出，以便知道却不被打断。
72. 作为用户，我希望常用的特殊 bash 操作（git 提交和推送、跑测试、装依赖、启动构建）有专门的带类型工具，以便规则可以直接套用。
73. 作为用户，我希望拆不开的 bash（`eval`、内联脚本、编码过的命令）先问我，以便看不懂的命令不会悄悄执行。
74. 作为用户，我希望每个通用 bash 调用在时间线的要点层和全局层都单独标出，以便一眼看到"这里调了一个没有事先规定类型的 bash"。
75. 作为用户，我希望维护者的文件工具只能碰项目档案和工作目录，越界写入直接被拦下，以便没有沙箱也有一道硬边界。
76. 作为用户，我希望守卫拒绝任何 agent 读取密钥目录，agent 子进程只拿到它需要的模型 key、它起的孙进程拿不到任何密钥，以便密钥不会被 agent 带出去。
77. 作为用户，我希望 v1 自带一套针对真实工具的时序规则模板（删除前必须已备份或已提交、push 前必须跑过测试、读过密钥文件后不许对外发送、同一收件人同一内容不重复发、对外内容不许含密钥、禁止 force push 和项目外 `rm -rf`），以便常见的坑默认就被挡住。
78. 作为用户，我希望时序规则判断不了的时候问我，以便不确定时不冒险。
79. 作为用户，我希望策略可以挂在单个阶段上，也可以定义一次套给一组阶段，以便同类阶段共用一套约束。
80. 作为用户，我希望审批卡说清楚是哪个任务、哪个阶段、要做什么、命中了哪个类别，以便我能快速判断。
81. 作为用户，我希望要点层和全局层上，授权内的、做完告诉我的、被拦下或问过的操作样式不同，以便扫一眼就知道发生了什么。

**范围审视**

82. 作为用户，我希望维护者的做事范围不被硬卡死，我可以临时让它先做点别的，以便范围能被我突破。
83. 作为用户，我希望维护者会话压缩时和每张工单结束时，另一个便宜模型对照立项书、计划和我给过的授权检查它做了哪些范围外的事，以便越界能被发现。
84. 作为用户，我希望我授权过的范围外工作记为范围变更、写进项目档案，以便项目的实际范围有据可查。
85. 作为用户，我希望没授权的记为越界，写进维护者系统提示末尾的"近期范围记录"，并在待我处理里放一条不推送的通知，以便维护者自我约束、我也知情，但不被打断。

**项目与维护者**

## Implementation Decisions

### 1. 工程与总体架构

- **语言与栈**：TypeScript + Node（≥22.19），固定一个专用的 Node 22 LTS，在 LSM 条目里写绝对路径。npm workspaces，三个包：**守护进程**、**Web**、**共享协议**。测试用 vitest，lint 用 oxlint。
- **pi**：用 `@earendil-works/pi-coding-agent` 的 SDK（ADR-0001）。二狗在自己的工作区里装一份，开工时取最新稳定版，不用本机全局那份。所有 `@earendil-works/*` 包精确锁定，配合 npm `overrides` 和 lockfile。pi 的类型只出现在运行时封装层里。
- **进程模型**（ADR-0002）：守护进程只当管家，自己不跑模型；每个 agent（秘书、维护者、子 agent）各占一个子进程，子进程里是一个 pi 会话。子进程之间不直接通信，agent 之间只有工单，全部经守护进程转交。
- **模型**：第一阶段全部用 DeepSeek V4.1 Flash（`deepseek-flash`），显式设置思考档位。模型在服务端（守护进程这台电脑）调用，目前只支持 DeepSeek；设置里能按角色选模型和思考档位（73 号票）。以后可以扩展别的服务商（用户 2026-10-10 记下，暂不实现）。一个会话固定一个模型；换模型就新开会话，附一份交接摘要。范围审视用的"便宜模型"也是它。
- **服务登记**：LSM 里只登记两个服务：
  - **`ergou-daemon`**：健康探针 `/healthz`；接入 LSM 的 link 协议，有任务在跑时心跳上报"忙"；开 autoRestart；密钥由 LSM 从密钥目录注入（`env.from: file`）；对 `audiocpp`（语音合成，和 drama 共用）是弱依赖（soft），二狗不等它、也不起它。
  - **`ergou-tunnel`**：照抄现有的 `agentsense-tunnel`，换端口；只连守护进程的外网端口。
- **`ergou-daemon` 从 04 号实现票起就在 LSM 登记**，指向主分支的构建产物；开发期间的演示也经 LSM 启动。自动测试里在临时目录起的守护进程实例是测试的一部分，用完即销毁，不算服务。
- **agent 子进程和 MCP 服务进程都不是服务**：不对外监听端口，不在 LSM 登记，由守护进程按需拉起，放进 Job 对象。

### 2. 守护进程的模块

每个模块对外只暴露一个小接口，内部可以很深。

| 模块 | 职责 | 对外接口（概念） |
|---|---|---|
| 事件存储 | 事件日志是唯一真相；按频道编号；派生视图在追加事件的同一事务里更新，可以从日志整体重建 | 追加事件（带幂等键）、按频道从某个序号订阅、读派生视图 |
| 网关 | 两个监听端口，提供 HTTP API、WebSocket 和 Web UI 静态文件；鉴权 | 帧的收发；历史分页；媒体上传下载 |
| 设备配对 | 配对请求、批准、发凭证、吊销 | 发起请求、批准、吊销、校验凭证 |
| agent 管家 | 拉起、监控、回收子进程；注入环境；Job 对象；数量上限、超时、闲置退出；转发会话事件；上报活动状态 | 唤起某个 agent 并递送输入、插话、中止、查询活动状态 |
| 守卫 | 每次工具调用的判定 | 判定函数：调用 + 上下文 → 判定（见第 9 节） |
| 审批 | 审批表、审批卡、等待与挂起、恢复 | 发起审批、用户裁决、按调用指纹查已有裁决 |
| 计划与阶段控制器 | 计划存储、阶段状态、验收钩子、阈值、预算、无进展检测、重注入块、计划变更、返工 | 确认计划、推进阶段、宣布阶段完成、提交计划变更、重开阶段 |
| 任务 | 任务状态机、看板派生 | 发起、状态迁移（按"谁能改"表校验） |
| 项目 | 项目状态机、立项、项目档案、重置维护者 | 建项目、立项书确认、状态迁移、归档、删除 |
| 派单器 | 工单、每个维护者的工单队列、全局并发名额 | 开工单、接单、交回执、退回 |
| 调度器 | 简单提醒、定时作业、内部作业（备份、校验、清理、归档清单、回避信号计时）、错过补发 | 建、改、取消、暂停、恢复 |
| 快速动作执行器 | 执行已确认的快速动作 | 按动作类型注册的执行函数 |

### 3. agent 子进程与 pi 封装层

- **第一个 spike**：验证 pi 的 RPC 模式（stdin/stdout JSON）能不能当守护进程和子进程之间的通信层；不合适就在子进程里用 SDK，自己写一层 stdio 上按行分帧的 JSON IPC。不管哪种，都包在运行时封装层里，上层只看到下面的"agent 宿主协议"。
- **agent 宿主协议**（守护进程 ⇄ 子进程，概念上的消息类型）：
  - 守护进程 → 子进程：启动（会话装配参数）、用户输入、工单、插话（在下一步之前插入）、守卫判定回复、中止、退出。
  - 子进程 → 守护进程：就绪、流式增量、消息定稿、工具调用开始和结束、守卫判定请求、用量、回合结束和闲置、范围审视结果、错误、心跳。
  - **守护进程代为执行的工具**（06 号票加）：会话装配时声明一组由守护进程执行的工具；子进程调用时发"代执行工具调用"，守护进程执行后回"代执行工具结果"。秘书只产生卡片的工具、读取附件等都走这条路，工具的实现和数据留在守护进程一侧。
- **会话按工具包装配**：
  - 每个会话用 `DefaultResourceLoader`，`noSkills: true`，只通过 `additionalSkillPaths` 加载工具包里列出的 skill；不读 `~/.pi`、`~/.claude/skills` 和 CLI 认证。
  - 工具白名单按工具包来，有 skill 时必须含 `read`。
  - 挂上二狗的扩展：守卫转发、范围审视。
- **守卫转发**：子进程里的扩展在 `tool_call` 钩子里把每次调用送给守护进程，按判定放行或拦截。硬限制一律用拦截实现，不原地改参数（改完不会重新校验）。drama_maker 的路径守卫扩展可以当样板。
- **环境注入**：每次拉起子进程都显式注入它需要的模型 key 和环境变量，不继承守护进程的环境；工具起的孙进程环境里剥掉所有密钥。
- **资源限制**（默认值，可配置）：同时存活的子进程最多 8 个；维护者闲置 10 分钟退出，秘书常驻；单次模型调用超时 5 分钟；单次工具调用默认超时 10 分钟（工具可以声明更长）；每分钟回收一次孤儿进程。
- **Job 对象**：所有子进程和孙进程放进二狗自建、不允许脱离的 Job 对象。
- **进行中的回合持续写盘**；同一个 agent 的输入串行排队，队列放在事件日志里，不放内存。
- **业务状态不进 pi 会话**：计划、授权、阶段、工单、审批都存在二狗自己的存储里。

### 4. 存储与事件

- **数据库**：`ergou.db`（SQLite，WAL）放事件日志和派生视图（看板、待我处理、审批表、工单、提醒、计划与阶段、效果日志、token 账本、已配对设备）；`memory.db` 放素材和索引，只由素材模块写。
- **SQLite 驱动**：优先用 `node:sqlite`，接受它的 ExperimentalWarning（只屏蔽这一条警告）；地基票先验证 FTS5 的 trigram 分词器可用，不可用就换 better-sqlite3。存储访问包在一层薄接口后面，换驱动只改这一层。
- **事件**：`{全局序号, 频道, 频道内序号, 类型, 负载, 时间, 幂等键}`。有副作用的请求带幂等键，重发不会做两次。审批记录先写库、再通知前端。
- **pi 会话文件**：每个 agent 一组 JSONL，放在数据目录的会话区。维护者会话按工单分段，每段一个 pi 会话；界面上把各段拼成一条连续的聊天，用工单分隔线隔开。

### 5. 前端协议

- **传输**：每个前端一条 WebSocket，帧分三种：请求 `{id, 方法, 参数, 幂等键?}`、响应 `{id, 成功与否, 结果或错误}`、事件 `{频道, 序号, 类型, 负载}`。SSE 不做主通道。
- **频道**：秘书会话、某个维护者会话（看哪个订哪个）、任务看板、项目列表、待我处理、卡片、活动状态、已配对设备。
- **重连**：前端带上每个频道最后收到的序号，服务端补发缺失的事件。前端乐观显示的尾巴，收到权威事件后被替换。
- **流式**：中间增量只推送、不落盘，只存最终的 part。进度事件节流到每 100 毫秒最多一次。
- **HTTP**：历史分页；媒体按 sha256 存，支持 Range 下载；上传分片续传（自定义协议：建上传 → 按偏移写分片 → 带 sha256 收尾），单个文件默认上限 200 MB；图片入库时剥掉 EXIF；第一阶段不生成缩略图等派生物。被素材引用的媒体永不回收。
- **schema**：用 TypeBox 定义，放在共享协议包里，守护进程和 Web 共用生成的类型。
- **消息** = 信封 + 若干 part。信封 `{id, 会话, 发言方, 时间, parts}`。part 的形状对齐 AI SDK 的 UIMessage parts，但类型自己定义，不依赖 `ai` 包：文本、推理（默认折叠）、图片、文件、语音（用户发的，附识别文字，31 号票定形）、agent 语音（送进 TTS 的原文等，32 号票定形）、视频（预留）、工具调用（工具名、参数摘要、命中的关注类别、判定、是否授权内、是否通用 bash）、卡片引用、工单分隔。
- **发给模型前的投影**：用带版本号的纯函数把界面视图投影成模型输入：卡片换成一行摘要；图片按模型能力投影（不支持视觉的模型换成"[图片：文件名]"）；语音换成转写。投影规则固定，保证提示词前缀稳定。
- **卡片**是独立实体 `{id, 类型, 版本, 状态, 负载, 紧急度?, 创建和处理时间, 处理结果}`，消息里只放引用。
  - **按钮闭环**：前端发"对卡片做动作"`{卡片 id, 动作, 期望版本, 幂等键}` → 服务端按版本条件更新（先到先得）→ 回 ack → 在卡片频道推送更新事件。后到的请求得到"已被处理"。
  - **卡片类型注册表**：每种卡登记类型、schema、版本和纯文本降级版本。不认识的前端显示文字加"去 Web 处理"的链接。
  - **第一阶段的卡片**：计划确认卡、审批卡、提问卡（成批问题，每题带推荐，可一键全按推荐）、进度卡、快速动作卡（含"已执行"）、"建议发起任务"卡、"建议立项"卡（含名字、一句话目标）、简单提醒卡、立项书卡（"确认并开工" / "只确认，稍后开工"）、工单卡、计划变更卡（含"工具包变更"）、并行确认卡、记忆删除卡、配对请求卡。
  - **待我处理事项**：以上需要处理的卡，加上通知类事项：错过的提醒、中断不确定、越界通知、备份失败、快照校验失败、定时作业被自动暂停、归档清单、授权到期续期、卡住求助和失败后的抉择。
- **紧急度**三档：卡住任务且有时限、卡住任务、不卡任务。第一阶段只在 Web 内显示（小红点和排序），手机推送是第二阶段。
- **卡片被关闭、长期不处理**要产生事件，供回避信号使用。

### 6. 访问与设备配对

- **两个监听端口**：
  - **本机端口**只监听 127.0.0.1，自动信任；校验 Origin 和 Host，防 DNS 重绑定和跨站 WebSocket。
  - **外网端口**是隧道的唯一目标，永远不享受本机信任，每个请求都要带有效的设备凭证。
  - 本机信任只看从哪个端口进来，不看来源 IP。端口号从配置读，默认值在地基票里查过本机已登记的端口后选定。
- **配对**：
  1. 新设备打开页面，显示配对请求：设备名、6 位短码、8 位十六进制短指纹。
  2. 在已信任的设备或 PC 本机上，待我处理里出现配对请求卡，显示同样的设备名和短指纹，供核对后批准。
  3. 批准后服务端发 HttpOnly、Secure、SameSite=Strict 的 cookie：256 位随机值，服务端只存哈希；有效期 365 天，每次使用时续期。
  4. 设置里列出已配对设备，可以随时吊销。
- 待批请求 5 分钟过期；同一来源 10 分钟内最多 5 个请求。
- **配对的补充**（10 号票评审后定）：凭证在新设备来领时才生成，批准后 5 分钟内不领就作废；配对请求卡有"拒绝"按钮；外网端口要求 Origin 与 Host 一致，cookie 用 `__Host-` 前缀；已配对设备走前端频道"已配对设备"，可以吊销包括自己在内的任何设备；吊销后浏览器记住"本设备已被吊销"，不自动重新申请；设备在第一次带凭证的请求成功前算未启用，24 小时内没用就作废。经前门转发、看不到真实来源时，卡片上的来源写"经前门转发，无法识别"。
- 网页脚本里不放私钥，也不放令牌。
- **nginx 站点**：二狗生成配置（支持 WebSocket、放大 `client_max_body_size`、加长 `proxy_read_timeout`、每个 location 都覆盖写 `X-Forwarded-For` 和 `X-Real-IP`、加 HSTS）；VPS 上的隧道端口只绑本机地址。部署是一次 ssh 上 VPS 的动作，按"对外发送或发布"先问用户。证书沿用 VPS 上现有的 Let's Encrypt 做法。域名按现有惯例 `ergou.<VPS>.sslip.io`。

### 7. 秘书

- **一条长期主线会话**，常驻子进程，靠自动压缩控制长度。
- **系统提示固定**，第一阶段不含用户卡，不做每轮记忆简报（都属第二阶段）。
- **五种回复形态**：直接回答是普通文本；其余四种各是一个只产生卡片的自定义工具（提议快速动作、建议发起任务、建议立项、建、改、取消简单提醒）。秘书在同一轮里自己选，不另加分类器。用户明说要发起任务或立项、或点了按钮时，跳过判断。
- **任务的发起**（2026-10-09 用户定，ADR 0019，取代原来"要求即授权"）：只有用户点明了才发起——消息里说了"发起任务""长程任务""按流程做"之类、输入 `/流程` `/任务`、或在发起对话框里先选了种类；点明的种类决定是流程（`start_workflow`）还是长程任务（`create_task`），说"发起任务"没说种类的按长程任务。没点明的一律按普通对话处理；秘书觉得该发起时最多给一张"建议发起任务"卡，卡上两个按钮"作为流程""作为长程任务"。点明后建任务卡（规划中）并进入澄清；计划卡的确认仍是执行前的闸。
- **意图澄清**：先说假设；提问用提问卡成批问；不设轮数和题数上限；回答作为素材。
- **任务书工具**：澄清完成后写任务书（目标、验收标准、约束、涉及的项目、记忆范围提议），由运行时交给执行的维护者起草计划。
- **只读工具**：查看板、读任意项目的项目档案、列出待我处理里未处理的事项、检索素材（关键词 + 向量，用于执行显式记忆命令）。
- **草稿区**：临时区里秘书专用的一格，和其他临时文件一样 7 天后清理。
  - 秘书可以用文件工具在里面写、改、删，用 bash（Git Bash，加本机已有的 Node 和 Python）跑脚本、做计算，工作目录固定在草稿区。
  - 草稿区里的写、改、删不落入任何关注类别，直接做，只记录；守卫照常检查，通用 bash 照常标出。
  - 要给用户看的产出（算好的表、生成的图或文档）作为附件发进聊天，存进媒体库长期保留，清理草稿区不会丢。
- **不能联网**：秘书读得到全部记忆，不给它往外发东西的口子。要联网就发起任务（或给出"建议发起任务"卡），由任务的维护者按工具包和授权去做。
  - 第一阶段没有系统级沙箱，这里是尽力而为，不是硬隔离：联网的工具和命令直接拒绝；草稿区里的脚本执行前先扫一遍，用到联网的库或函数就拒绝，并提示"联网请发起任务"；脚本进程设一个无效的代理地址，让常见的联网方式失败。真正挡死要等以后加沙箱。
  - 关掉联网开关的维护者同样按这几条处理。
- **看板变化消息**：看板自上次以来有变化时，运行时在下一条用户消息后追加一条"看板变化"上下文消息，不改系统提示。
- **专用压缩指令**：丢掉任务的执行细节和已解决的问答，涉及的任务只留 ID 和一句话；保留进行中的话题、未回答的问题，以及刚说的、还没处理的指示。
- **承诺即任务**：秘书只答应用户要它做的事，答应了就当场建任务或简单提醒；用户没要求的，只能给建议卡，不能口头答应。

### 8. 任务、计划与阶段

- **两种任务**（2026-10-09 用户定，ADR 0019，推翻 issue 12"只有一种计划"）：任务分流程和长程任务，建卡时定下、不能换。**长程任务**就是下面写的阶段、验收、计划变更这一套，原有任务都算这一种。**流程**照搬 AgentSense 的固定计划：维护者按任务书把要做的事排成一串步骤，每步是一次工具调用（工具和参数）和它要满足的条件（用时序规则写：之前必须做过、之前不能做过、当下必须满足、一律禁止）；计划先过审查修补（参照 AgentSense 的 planguard 审查），再由用户在计划卡上一次授权；执行时守卫把每次调用和计划比对（计划外、超范围、顺序错、重复、禁止），能修的自动修回（改回参数、引回前置步骤，每步最多 2 次），修不了的问用户；一轮要收工时还有没做的步骤提醒一次；不逐步验收，执行中不能改步骤（要改就重新发起）。流程的进度是做完的步骤数 / 总步数。下面讲阶段、验收、计划变更的条目只对长程任务。
- **项目内部任务**（2026-10-09 用户定）：项目维护者也能在自己项目里用流程或长程任务做代码维护，由它自己执行；发起的规矩和秘书一样（用户在项目会话里点明，或维护者给建议卡、用户点了才发起）；不上全局看板，只在项目页和项目会话里看得到，但计划卡、审批、卡住求助照常进待办。
- **任务状态**：规划中 → 待确认 → 排队中 → 执行中 → 已完成 → （用户手动）已归档；执行中 ⇄ 等我 / 已暂停；执行中 → 失败 →（重试）执行中；已完成 → 返工 → 执行中；任何未结束的状态 → 已取消。（13 号票评审后补）因"卡住求助"转等我的任务，用户在它的会话里回话即恢复执行。（12 号票评审后补）排队中也可以被用户暂停（→ 已暂停）；任务转为项目时以"已完成 · 已转为项目"结束。计划卡上维护者可以把全局类别的处置调严，不能调松。
- **谁能改**：

  | 谁 | 能做什么 |
  |---|---|
  | 用户 | 发起任务、确认计划、暂停 / 继续、取消、批准、回答、验收、返工、归档、转为项目 |
  | 秘书 | 按用户的发起建任务卡、写任务书；用户要求时取消；建、改、取消简单提醒 |
  | 维护者 | 开始、报告进展、转为等我、完成、失败 |
  | 系统 | 排队调度；卡住或超预算时转等我，累计被拒太多次时暂停；到点触发提醒和定时作业 |

  所有变化都是事件；状态迁移在任务模块里按此表校验。
- **执行者**：只涉及一个项目的任务由该项目的维护者执行；涉及多个项目或不涉及项目的任务在建卡时产生自己的维护者。任务涉及几个项目在建卡时定下，之后不随计划改动重新判断；单项目任务的计划不能写进别的项目，不涉及项目的任务的计划不能写项目行（要涉及项目就重新发起任务）（17 号票评审后定）。起草计划的就是执行的维护者。多项目任务规划时只读各项目档案、不发工单。
- **计划**（结构化存储，计划卡由代码从它生成）：
  - 阶段列表，每个阶段：交付件、验收标准（每条注明方式：脚本 / 评审 / 用户，脚本方式附脚本）、模式（定步附步骤 / 开放）、前置阶段、授权项、时序规则、预算（token + 工具调用次数）、所属阶段组。
  - 阶段组：一组阶段 + 共用的授权项和时序规则。
  - 工具包：skill 名单、MCP 名单、bash 开关、联网开关。
  - 涉及的项目和每个项目的改动（确认后变成工单）。
  - 记忆范围（第一阶段只占位，见 Out of Scope）。
  - 本任务要提醒的关注类别（默认取全局，只能增加不能删；想让任务少停几次，就在计划里给对应操作预先授权，这只对"计划里列了才做"那一档有效）。
  - 定时作业定义（可选）：时间表、每次要做的事、属于哪个项目。
  - 假设栏；预告的停点数；token 粗估。
- **提交计划**：维护者起草完，调用"提交计划"工具交出，运行时据此生成计划卡，任务进入待确认；打回后任务回到规划中。
- **计划卡**：一个确认按钮；可逐行勾掉或收窄授权、附意见打回；细节默认折叠。勾掉和收窄回写到计划和授权；打回意见作为一条消息交回起草的维护者。
- **阶段执行**：控制器保管当前阶段；授权只在所属阶段内有效；前置阶段必须已验收；并行阶段只有用户确认派子 agent 时才真正并行。
- **重注入块**：每次唤起和每次压缩之后，运行时注入一块固定内容"计划摘要 + 当前阶段 + 授权 + 边界"，作为上下文消息，不改系统提示。
- **验收**：维护者调用"宣布阶段完成"后，控制器运行该阶段的验收：
  - 脚本：由钩子在工作目录里运行，看退出码和输出；
  - 评审：派一个评审子 agent，固定的只读工具包，新的上下文里只给交付件和验收标准；
  - 用户：进待我处理等用户验收。
  
  维护者自检不能单独算验收。
- **包含多项目工单的阶段**：每张工单带自己的验收标准，项目维护者完成后交回执；回执全部到齐后，任务维护者再跑一遍本阶段的验收。任何一张工单被退回或做不了，本阶段不通过；任务维护者可以调整方案（算一次退回），或转为等我。按依赖重开某个阶段时，向相关项目重新派工单。
- **阈值**（默认值，可配置）：拉回 3 次；催促 3 次；验收退回 2 次，第 3 次还不过就找用户；预算用完（用量超过预算）让维护者说明进展，用量超过预算的 2 倍问用户（预算按 token 和工具调用次数各算一个比值、取大的；2026-10-08 用户定的口径）；无进展判定为 agent 活着但 20 分钟内没有成功的工具调用、没有阶段推进，触发一次催促。需要用户拍板的（拉回超限、催促超限、验收第 3 次不过、预算超 2 倍）任务转等我，原因写"卡住求助"或"超预算"。卡住求助时用户在任务会话里回话就算让它接着做；超预算只有点"追加预算继续"才接着做并重给一整份预算，会话里的话交给维护者回答、任务仍等我（2026-10-08 用户定）。
- **偏离的逐级升级**：计划外但在授权范围内只记摘要；超出授权先问用户；出现计划没预料到的类别先问用户并暂停这一支；同一任务累计被用户拒绝 5 次（默认）暂停整个任务（转已暂停）。"超出授权"指计划里对这个类别有授权，但超出了对象范围或次数；"没预料到的类别"指计划里完全没涉及的类别。
- **计划变更**：扩大授权、加能力、加项目、改目标或验收时提交，进待我处理；只有受影响的阶段停下来；被拒后，维护者在现有授权内重排受影响的阶段，做不到就标做不了、任务转等我。拆阶段、调顺序这类不扩大授权的调整，维护者自己改，记进时间线，阶段抽屉显示调整后当前生效的计划。同一任务一次只能有一张计划变更卡在等；已验收的阶段不能再改；用户点"追加预算继续"后，这个阶段重新给一整份预算（从这时起算）。改目标或验收标准的计划变更被确认后，任务书和重注入给维护者的内容都换成新的。
- **返工**：按依赖重开出问题的阶段和它的下游，由同一个维护者接着做。
- **归档清单**：每周一次，把结束超过 7 天、还没归档的任务汇总成一条待我处理事项，每项可选归档、继续改（返工）、先留着。
- **并发**：全局最多 3 个任务处于执行中（可调），多出的排队；等我、已暂停、简单提醒、快速动作不占名额；子 agent 不占名额。
- **状态补充**：
  - 要恢复执行（继续、批准后唤起）而名额已满的任务，回到排队中。
  - 部分阶段在等用户、其他阶段还在推进时，任务仍是执行中、占名额；所有能推进的分支都在等用户时，才转等我。
  - 任务转为项目后，原任务以"已完成 · 已转为项目"结束。
  - 计划里带定时作业定义的，确认计划后作业登记、进入运营中（第 13 节）。
- **看板分组**：等我（等我、待确认）；进行中（规划中、排队中、执行中、已暂停）；运营中（简单提醒、定时作业）；最近结束（已完成、失败、已取消，以及已触发的一次性简单提醒）；已归档。
- **长时间不在**：等我的事项永不自动批准；不依赖它的阶段继续推进；授权项默认有效期 7 天，到期前一天放一条续期事项。

### 9. 守卫

- **判定函数**：输入是一次工具调用（真实工具或从 bash 拆出的伪工具调用）、发起的 agent 及其工具包、所属任务的计划、当前阶段和授权项、效果日志、全局与本任务的关注类别设置；输出是：处置、命中的关注类别、是否通用 bash、命中的时序规则、是否属于授权内、给模型的说明。纯函数，环境事实（文件元数据、git 状态）由调用方现取后传入。
- **工具注册表**：每个工具（内置、特殊 bash 操作、MCP 工具）登记类别标签、参数规则（比如路径参数、收件人参数），以及可选的"做完告诉我"标记（没有类别、但值得一提的操作，比如 git 提交、在工作目录里装依赖）。
- **关注类别注册表**：内置类别和默认处置随框架代码提供；用户的调整和自定义类别是数据，放在数据目录的配置区，agent 写不到。内置类别见下表；自定义类别只能写确定的规则（匹配工具、路径、收件人、金额）。用户自己加的类别，在设置里随时可以改规则、改处置或删除；内置类别只能往严里调，两条底线不能动。用模型判断的类别以后再加。
- **默认处置**（用户只能往严里调）：

  | 关注类别 | 对话里 | 任务里 |
  |---|---|---|
  | 花钱 | 交给我做 | 交给我做 |
  | 以我的名义对外发送或发布（含建 GitHub 仓库、推送） | 先问我 | 计划里列了才做 |
  | 删除或覆盖（项目档案和工作目录内） | 先问我 | 做完告诉我 |
  | 不可逆的提交 | 先问我 | 计划里列了才做 |
  | 账户与安全（凭据、权限、全局装软件） | 先问我 | 先问我 |
  | 越出项目目录 | 先问我 | 计划里列了才做 |
  | 使用授权范围外的记忆 | 先问我 | 先问我 |
  | 计划外工单 | — | 先问我 |
  | 未知的写操作 | 先问我 | 先问我 |

  不落在任何类别里的调用：直接做只记录；带"做完告诉我"标记的：做完告诉我。对话里没有计划，"计划里列了才做"等同"先问我"。

  **"先问我"的意思是执行时一定当场问**，计划里写了、授权项里列了也照样问；"计划里列了才做"才是靠计划一次授权。
- **两条底线**：付款转账、创建账户、改密码或两步验证固定为"交给我做"；把凭据写进对外内容固定为"永不"（用正则检查对外内容里的密钥形态）。
- **授权项**：操作种类 + 对象范围 + 次数 + 所属阶段 + 有效期，次数按实际生效的效果计算。计划卡上没勾的操作，执行到那一步再问。运行中授权只能收窄；重新规划时只问新增的部分。
- **快速动作的确认**：用户这一轮明确点了对象和内容的，卡片只展示规范化后的动作，不再确认；秘书自己推断的，按类别处置。"明确点了"由运行时判定，不由秘书自报：动作的对象和内容必须原样出现在用户这条消息里（或用户引用的卡片里），否则一律按推断处理；推断出来的任务控制动作一律先问。（21 号票评审后定）每个执行器自己声明"点明"的判定：记忆命令要求用户这条消息里有该动作的触发词、前面没有否定词，并且提议的内容和触发词后面到句末的那一段一致；推断出来的"记住"也一律先问。快速动作作为一个伪工具调用交给关注类别匹配，用户的自定义类别同样适用。聊天里的卡片可以"引用"到输入框。
- **时序规则**：照搬 AgentSense planguard 的引擎核心（expr + spec + checker），规则格式与它兼容。四种形态：B 之前必须做过 A、B 之前不能做过 A、当下必须满足某条件、一律禁止。只看效果日志里已经成功执行过的调用；判断不了就问用户。规则只认工具名和参数，参数名统一，并加一道规则校验（参考 AgentSense 的 `policies-check`）。
- **v1 规则模板**：删除或覆盖项目档案和工作目录里的文件之前，必须已备份或已 git 提交（秘书草稿区不受这条约束）；push 之前必须跑过测试；读过 `.env` 或密钥文件之后不许往外送（用户 2026-10-08 定：只拦往外送——非 GET 的 HTTP 请求、带数据或上传的请求、发消息、推送、发布、建远端仓库、看不出方向的联网脚本；只往下拉的照常——GET、装依赖、`git pull` / `fetch` / `clone`；"对外内容不许含密钥"同时扩展到 GET 的网址和命令参数）；同一收件人、同一内容不重复发；对外内容不许含密钥；force push 和项目外 `rm -rf` 一律禁止。
- **违反时序规则的结果**（2026-10-07 评审后定）：
  - 前提没满足、agent 自己能补救的（删除或覆盖前须已备份或已提交、push 前须跑过测试）：**按规则退回**——这次调用不执行，说明怎么补救；它不是一档处置，计入拉回次数。
  - 一律禁止的（force push、项目外 `rm -rf`）和对外内容含密钥：永不。
  - 同一收件人、同一内容不重复发：先问我（重复可能是正常需求）。没有收件人参数的发送，以目标对象（仓库加 issue 或 PR 号、URL）当收件人。
  - 用户的规则或编译出的规则没写违反时怎么办的，按先问我。
  - 规则的条件算不出结果，按判断不了处理，先问。
  - "之前"只算真正先执行的：`a && b` 里 a 在 b 之前，同一条管道里的各段互相算之前；"之后"只在同一个任务内算，不属于任务的只在同一段会话内算。
- **控制器里的硬检查**：授权只在所属阶段内有效；前置阶段必须已验收；某个对象被判过"永不"（关注类别的永不，或一律禁止类规则的永不，不含按规则退回）之后，再对它做对外动作要先问。（读过 `.env` 或密钥文件之后对外发送，由上面的规则模板一律禁止，不走这条。）
- **效果日志**：只有执行成功的调用才追加：`{序号, 任务, 阶段, agent, 工具或伪工具, 规范化参数, 效果摘要, 时间}`。
- **bash**：
  - v1 只开放一种 shell：Git Bash。
  - 特殊 bash 操作封装成带类型的工具：git 状态和差异（只读）、git 提交、git 推送、建远端仓库、跑测试、在工作目录里装依赖、启动构建。
  - 其余是通用 bash：用现成的 POSIX shell 语法解析库拆开管道和子命令，映射成伪工具调用（比如 `rm` → 删除、`git push` → 推送、`npm install -g` → 全局装软件、带 POST 的 `curl` → 对外发送），查路径是否越出项目目录，再逐个套类别和规则。
  - 拆不开的（`eval`、内联脚本、编码过的命令）按"未知的写操作"先问用户。
  - 拆得开、也没落在任何类别里的，不打断，但打上"通用 bash"标记。
  - bash 由工具包决定；开发类项目默认带 bash。
- **硬拒绝**：越出能力或边界的调用直接拒绝，不问用户，用户批准和授权项都改变不了：文件工具写围栏外、工具包联网关着时联网、读密钥区、工具包没给的工具（包括没开 bash 时调 bash）、子 agent 写项目档案（文件工具和 bash 一样）。硬拒绝不是处置的一档；它和两条底线同时命中时，以底线为准（给模型的说明按底线写），其余情况硬拒绝优先。
- **"删除或覆盖"**指删除文件或整体重写已有文件；对已有文件的局部编辑不算。
- **授权项按类别覆盖**：一次调用命中的每个关注类别都要各自被授权项覆盖（操作种类和对象范围都对得上），没被覆盖的类别按它自己的处置走，最后取最严。
- **路径围栏**：
  - 维护者和子 agent 的文件工具：项目档案和工作目录之外，写一律拒绝（不问），读落入"越出项目目录"、按处置走；bash 命令碰到项目外路径同样落入"越出项目目录"。
  - 秘书的围栏是草稿区：文件工具只能写草稿区、只读项目档案；草稿区外的读，以及 bash 碰到草稿区外的路径（比如跑用户某个目录里的现成脚本、读用户给的本机文件），落入"越出项目目录"，在对话里就是先问用户。
  - **受保护区域**：数据目录里的配置区、密钥区、数据库区和二狗程序目录，任何 agent 用任何方式（文件工具、bash、脚本）写入都是"永不"，用户批准也不行；密钥区连读都拒绝。
- **联网开关**：工具包里联网关着时，任何联网的工具或命令直接拒绝（秘书一律视为关着，见第 7 节的尽力而为做法）；开着时，只读的 GET 不落入关注类别，非 GET 的请求算"以我的名义对外发送"。
- **审批流程**：判定为"先问我"时，守护进程写审批表、建审批卡；子进程里的这次调用最多等 5 分钟（默认）。期间用户批准就继续执行；超时就以"已提交审批，等待用户"拦下，这一支停下，任务转等我。用户事后批准时，审批记成一条一次性授权，按调用指纹匹配，运行时唤起维护者，附一条"某某已获批准，可以重试"的消息。被杀重启后也按同样的指纹匹配。
- **"交给我做"**：agent 把东西准备好（比如填好的付款信息摘要、要点的链接），建一个"交给我做"事项，任务这一支转等我，用户亲手完成后点"已完成"。

### 10. 范围审视

- **两个时点**：维护者会话压缩时（扩展在 `session_before_compact` 里把待压缩的消息转成文本送审），以及每张工单结束时（运行时直接调用同一个审视函数）。
- **对照物**：立项书、任务计划，以及用户给过的授权（包括用户在会话里直接说的话）。
- **结果**：用户授权过的记为范围变更，写进项目档案；没授权的记为越界。审视结果用 `appendEntry` 存进会话；`before_agent_start` 把最近 5 条范围记录拼到维护者系统提示末尾，标题"近期范围记录"。发现越界时，在待我处理放一条不推送的通知（照常算未读）。不暂停维护者。
- **在哪跑**：审视的模型调用在维护者自己的子进程里另开一次（守护进程不跑模型）；工单结束的那次在子进程退出前做。结果交给守护进程保存；因为每张工单是一段新的 pi 会话，下一段的"近期范围记录"从守护进程取，不靠旧会话里的 `appendEntry`。
- **不属于项目的任务**：范围记录写进任务自己的产出区，在任务详情里显示。

### 11. 项目与维护者

- **项目状态**：筹备中 →（确认并开工）建设中 →（首个建设任务完成，自动）使用中 ⇄ 已停用；筹备中、建设中可以放弃 → 已归档；使用中、已停用 →（用户手动）已归档；取消归档回到原状态。删除只能从已归档发起，要二次确认。首个建设任务完成时自动进入使用中，是"项目状态不随任务变"的唯一例外；首个建设任务失败或取消时项目留在建设中，用户可以再发起一个建设任务，或者放弃归档。（用户 2026-10-07 定：不再区分"运营中"和"已完成"。）
- 项目页直接显示它背后的服务在不在线（项目自己的服务属第二阶段）、有哪些定时作业及各自状态；第一阶段只显示定时作业。停用在第一阶段只做暂停该项目的定时作业，重新启用时恢复。
- **立项**：
  1. 三个入口：用户明说或点"新建项目"；秘书给出"建议立项"卡、用户点了；任务转为项目。
  2. 秘书收口：建议立项卡上写名字和一句话目标，用户点"立项"后项目立刻诞生（筹备中），维护者随之产生。
  3. 维护者立项问答：在维护者会话里做 grill-with-docs 式的问答，把规格、术语表、ADR 写进项目档案，交出立项书和它提议的工具包，放进待我处理。
  4. 立项书卡两个按钮：确认并开工（同时发起首个建设任务）；只确认，稍后开工（留在筹备中，标"立项书已确认"）。
  5. 任务转为项目时不新建维护者，原任务的维护者接着做立项问答。
- **项目档案**：立项书、规格、术语表、ADR、进展、项目清单、范围记录，以及维护者会话。固定放在数据目录的项目区，随数据目录备份，永不进外部仓库。第一阶段只建这套最小文档；完整的项目规范模板是第二阶段。 项目档案里的文件被整体重写或删除前，运行时自动留一份旧版本，所以"删除或覆盖前须已备份"对项目档案总是满足。
- **工作目录**：默认在项目档案里面；开发类项目立项时可以改为绑定一个外部路径（外部路径不随二狗备份，靠项目自己的 git 远端）。
- **维护者唤起时的固定上下文**：工具包说明、项目规范（第一阶段是一段内置的简短说明）、项目档案快照（规格摘要、进展、术语表）、上一段的摘要、这次的工单，再加上重注入块和近期范围记录。更早的分段不进上下文。
- **写回档案**：每段工作结束时，运行时检查进展文档是否被更新（内容哈希变了）；没更新就催促维护者写回，这段不算完成。
- **唤起**：工单到达，或用户在它的会话里直接说话。干活时用户直接发来的话作为插话，在它下一步之前插入。
- **一次只做一件**：同一个项目的工单排队、先来先做；被挡住的任务留在排队中，标"等项目 X"。
- **重置维护者**：新开一段会话，只凭项目档案重建理解，旧会话保留可查。写回档案中途重置的，这张工单照常算完成，时间线和项目页如实写"重置时这段没写回档案"（2026-10-08 用户定）。
- **已停用**的项目，维护者照常对话、接工单；**已归档**的项目，维护者会话只读，派单器把发给它的工单直接退回并说明原因。项目还有正在做或排队的工单时不能归档：归档按钮写明先完成或取消哪几个任务（2026-10-08 用户定）。
- **写回催促**：每段结束时催写回最多 3 次（同第 8 节的催促阈值），还没写回就转为用户拍板：待我处理里一条"卡住求助"，这一段标"催了还没写回档案"后结束；工单所属任务这时通常已离开执行中，任务状态不改；项目队列不因此一直卡住。
- **范围审视的细则**（18 号票评审后定）：审视时点是会话压缩时和每张工单结束时（写回催满结束的段也审；对话段只在压缩时审）；对照物含立项书、任务书、现在生效的计划、用户在会话里说的话和审批卡上的批准；授权过的记为范围变更、没授权的记为越界，两种都写进项目档案的范围记录（越界标明），项目页和项目任务的任务详情都能看到；审视没做成不卡工单，会话里留一条说明；重置时没审视的那段工作在时间线上如实写明。范围记录里引用的用户原话随彻底删除一起改写。
- **子 agent**：做什么由维护者决定，并行要用户确认；权限不超过维护者；不能写项目档案；开发类项目的并行改动各自在独立的 git worktree 里做，由维护者合并；结果回到维护者的会话。
- **固定工具包**：跨项目任务的维护者只有读项目档案、派工单、汇总回执三样；评审子 agent 只读。
- **工具包的调整**：skill 的增减维护者自己做、记进时间线；开 bash、加 MCP、开联网走计划变更；减少能力随时可以。
- **经验**：按项目存在项目档案里，不自动提炼。用户要求时用推理图谱（reasoning-graph）skill 沉淀领域知识，前提是用户把它导入 skill 库。

### 12. 工单与派单

- **工单来源**：用户发起的单项目任务；别的任务的维护者派来的部分；定时作业的一次运行。用户和维护者直接聊天不算工单。
- **工单状态**：等阶段开始（多项目任务计划内的工单，确认计划时建出）/ 待你确认（只有计划外的工单）→ 待接 → 进行中 ⇄ 等澄清 → 已结束（完成、退回、做不了；计划外工单被用户拒绝的记"没派出"）。计划外工单交给守卫判定（"计划外工单"类别），要确认的只出工单卡（确认派出 / 拒绝），不另出审批卡。等阶段开始、待你确认的工单也挡项目归档（17 号票评审后定）。
- **派单器**：工单写进事件日志时注明收件项目；派单器把它放进该项目维护者的工单队列，维护者休眠就唤起，正忙就排队。
- **执行权限**：任务授权和项目权限的交集。
- **回执**：项目维护者完成或退回时交回执，回执进任务维护者的会话。
- **星形通信**：agent 之间只有工单，全部记在任务时间线上，不做 agent 群聊。
- **可视化**：项目页的工单流水线（排队中、进行中、已结束）；任务详情里列出该任务派出的所有工单；工单不在看板上单独占卡。

### 13. 调度

- **调度器**在守护进程里，简单提醒、定时作业和内部作业共用。不用 Windows 计划任务。
- **简单提醒**：到点直接通知前端，不拉起 agent。一次性的：待触发 → 已触发；重复的：一直待触发。在看板上显示为"运营中 · 待触发"。
- **定时作业通过任务建**：比如"每天早上出简报"是一个任务，计划里写明作业的时间表和内容，用户确认计划后作业登记生效；属于项目的作业，就是对那个项目发起的任务。秘书不能直接建定时作业。
- **定时作业**：运营中 ⇄ 已暂停；每次运行留一条运行记录；属于项目的作为一张工单交给项目维护者，不属于项目的有自己的维护者；失败记一条失败的运行记录并在作业卡上标"最近一次失败"；连续失败 3 次自动暂停并进待我处理。每次运行占一个全局并发名额（运行真正开始时才占，在项目队列里排着不占）。项目停用或归档时它的作业暂停，重新启用或取消归档时恢复因此暂停的。用户可以暂停、恢复、取消作业；暂停时已经排着的运行一并丢掉；同一个作业上一次还没跑完的，这一次跳过。审批超时被拦下等没做成的运行记为失败；停机打断的那次记为"中断"、不算进连续失败。
- **定时作业的授权**（2026-10-08 用户定）：作业定义在计划卡上列出每次运行要的授权项和用户说的限制（编成时序规则），随计划卡一起确认；作业在就一直有效，不按 7 天续期，用户暂停或取消作业即收回。运行时超出这些授权的照常先问用户。
- **错过的触发**：启动时补。提醒晚了 60 分钟以内照发，标明晚了多久；更晚的改放进待我处理（错过的提醒）；定时作业只补跑一次。重复提醒错过多次，只按最近一次处理。错过的内部作业（如当晚的备份）开机后补一次。
- **内部作业**：每晚备份（默认 03:30）；每周校验最新快照；每天清理临时区里 7 天前的文件；每周归档清单；回避信号计时；授权到期提醒。

### 14. 快速动作

- 秘书写清动作（做什么、对谁做），用户确认后（或在已有授权内）由执行器直接执行，不拉起 agent，聊天里留一张"已执行"的动作卡；执行本身是事件日志里的一条事件，也就是"操作记录"，在时间线上可见。任务控制动作由用户的要求触发，算用户改的状态。
- 彻底删除的范围（21 号票评审后定）：消息事件整条换成删除标记，其他事件只改写带原话的文本字段、保留状态；会话文件里的消息、相关工具调用的参数和结果、覆盖了被删消息的压缩摘要一起改写；没有别的消息引用的附件媒体文件一起删。删不掉的如实告诉用户：秘书回复里的转述、秘书看任务看板时看到过的等我原因（23 号票加："中断不确定"的说明里有调用摘要），以及备份快照里的副本（随快照轮换消失）。记忆删除卡可以换删法、去掉几条，一张最多 50 条；设置里的批量删除走 HTTP。
- 执行器按动作类型注册。第一阶段内置：记忆命令（记住、忘掉、彻底删除、别推断）、任务控制（按用户要求暂停、继续、取消）、调用一个已登记并授权给秘书快速动作的 MCP 工具（参数固定）。

### 15. 素材

- **采集**：由守护进程从事件日志确定性地产生，agent 不能挑选。七类素材事件：用户发言（任何会话，包括维护者会话和附件引用）、用户对产出的反应（采纳、修改附 diff、要求返工、放弃）、审批决定（批准、拒绝、收窄）、澄清问题的回答、用户主动投喂的材料、显式记忆命令、任务结局（完成、失败、取消）。另加**回避信号**：卡片被关闭，或建议卡、提问卡 7 天（默认）没处理。agent 之间的内部往来、从记忆召回的内容都不算素材。
- **信封**：`{id, 类型, 说或做, 时间, 来源会话, 任务或项目, 来源等级（本人 / agent / 外部不可信 / 系统）, 指向原始记录的引用, 情境标签, 切段, 原文副本（仅本人）}`。
- **原文副本**：来源为"本人"的素材另存一份原文副本，不可修改、只追加、只有用户能删。agent 的产出、附件和外部内容只存引用加内容哈希。
- **切段与来源标记**（确定的规则）：引用块、附件、抓取的网页标"外部、不可信"；用户自己打的字标"本人"；用户接受了 agent 的提议算用户的选择，注明"agent 先提出"；语音转写标"本人"并注明"转写"；判断不了的纯文本默认"本人"。
- **索引**：
  - 关键词：SQLite FTS5，trigram 分词器。
  - 向量：守护进程里用 CPU 跑量化版 bge-m3（transformers.js 加 ONNX 模型），模型文件放在数据目录里。素材入库后后台异步补算，不卡写入和对话；每条向量旁记下模型名，换模型时整批重算。第一阶段用暴力扫描做相似度检索，量大了再换。
- **删除**：
  - **忘掉**（默认）：从素材库删除，顺着证据边删掉由它推出的判断（第一阶段还没有派生内容）；聊天记录里仍看得到原话。
  - **彻底删除**：连会话原文一起删。事件日志和会话文件里对应的原文改写成删除标记。事件日志不可修改，例外只有三个：彻底删除；删除项目时改写属于这个项目的原话和读出去的内容（15 号票评审后补，66 号票补齐：维护者会话、立项书，属于项目的审批、工单、范围记录、待我处理的事项、调用的完整内容和项目内部任务，以及项目之外读过这个项目的调用——秘书会话里的、跨项目任务的维护者和评审的；结构字段和状态保留，用户说过的话照样作为素材保留）；工具调用的完整内容过了保留期或超出总量上限时换成摘要（65 号票，用户 2026-10-09 定保留 90 天、上限 2 GB，每天凌晨清一次，"现在就清理"只清已到期或超上限的）。
  - **别推断**：素材保留，标记为不参与推断。
  - 入口：对话里的显式记忆命令（秘书检索出匹配的素材，生成记忆删除卡供核对）；按会话或按时间段删除（设置里）。
- 第一阶段只积累和建索引，不做抽取、推断，也不产出任何记忆。

### 16. token 账本与消耗

- 运行时从 pi 每次调用返回的用量里记一条：任务、agent、会话、模型、输入（缓存命中 / 未命中）、输出、时间。
- 任务卡显示总量；任务详情按 agent（含子 agent）细分；"消耗"页按天、按 agent 汇总，秘书单列为系统开销。
- 粗估成本：选一个时间范围，用量乘配置里的单价，页面标明"粗估"。不做按时段计价。

### 17. 被杀后的恢复

LSM 每次重启都会连带杀掉守护进程，Job 对象把所有子进程一起清掉。重启后：

- 待审批的事项从审批表恢复，不重复通知。
- 只读或幂等的工具调用：告诉模型"这次调用被中断了"，由它决定要不要重做。
- 有副作用、又说不清做没做完的：任务转等我，原因写"中断：不确定 X 是否已执行"，放一条待我处理事项。
- 输出到一半的回复：丢掉中间片段，从会话文件里最后一个完整的回合续上。
- 错过的定时触发：按第 13 节补。
- 重启后没人登录时，二狗不在线，等用户登录后由 LSM 拉起再补。
- （23 号票评审后补）agent 子进程意外退出（守护进程没被杀）也按上面的规则处理。并行执行的工具里，已经有成功记录的不重做，只有确实没有结束记录的才算"不确定"。"中断不确定"由用户定夺：已执行就继续，没执行就重做这一步；也可以在任务详情里点继续或直接回话。同一数据目录已有实例在跑时，新起的实例立即退出，不碰任何状态。有任务在执行、或有 agent 正在执行有副作用的调用时，向 LSM 报"忙"；停机期间守卫拒绝新的调用。

### 18. 数据目录与备份

- **数据目录**由环境变量 `ERGOU_DATA_DIR` 指定（LSM 条目里设置；配置文件本身在数据目录里，所以数据目录的位置不能再放进配置），不设时默认用户主目录下的 `.ergou`，不写死。各区：配置（含 MCP 登记、关注类别注册表）、密钥（只由 LSM 注入，agent 读不到）、数据库（`ergou.db`、`memory.db`）、会话、项目、不属于任何项目的任务的产出、素材（原文和按内容哈希存的媒体）、skill（用户自己加的）、参考音色（`voices`，每个音色一个英文 id 命名的目录）、临时区（含秘书草稿区）、本机备份、日志。
- **落盘规矩**：每类要记下来的东西有固定归宿（任务看板、素材库、项目档案、配置）；任何 agent 只能写分配给它的那一格，不能自己建顶层目录；临时文件只能放临时区。
- **备份**：
  1. 每晚在本机做一致性快照到本机备份区的日期目录：SQLite 用 `VACUUM INTO`；其他文件增量复制（pi 会话 JSONL 是追加写，复制时容忍最后半行）；媒体按内容哈希只存一份。本机保留最近 7 份。
  2. 把快照复制到配置里的同步目录（本机配置为华为家庭存储同步目录下的 Ergou_projects）的日期子目录，由华为客户端同步。同步目录保留每日 7 份、每周 4 份。不加密。
  3. 不进备份：密钥目录、临时区、外部工作目录。
  4. 写入失败（目录不在、空间不够、复制出错）放一条待我处理事项。二狗只确认"已写进同步目录"。
- **校验与恢复**：每周打开最新快照的数据库做完整性检查，失败进待我处理；一条恢复命令从指定日期的快照恢复（恢复前守护进程须停止）。

### 19. Web UI

- **技术**：React 19 + Vite + TypeScript，手写 CSS，不用组件库和状态管理库。从 AgentSense 复制 `web/src`，之后各自演进；视觉 token 沿用它的 `look.css`。UI 由守护进程提供。
- **主框架**：竖屏底部 5 个 tab（秘书、任务、项目、待我处理、更多）；更多里有消耗、记忆入口（第二阶段）、设置。

### 21. 实现细节补充

写实现票时发现的缺口，按下面的默认做法补齐（2026-10-07）：

- **带类型的特殊 bash 工具**单列一张实现票：git 状态和差异、提交、推送、建远端仓库、合并、跑测试、在工作目录里装依赖、启动构建。
- **工具注册表**标明每个工具是否"只读或幂等"，供被杀后的恢复使用。秘书会话里被打断、说不清做没做完的有副作用调用，放一条"中断：不确定 X 是否已执行"事项。
- **子进程满 8 个时**，新的唤起排队，活动状态显示"排队"。
- **立项**：立项书写明项目类型（开发类 / 其他）和是否绑定外部工作目录，确认立项书即生效；开发类的默认工具包带 bash。
- **维护者会话分段**：除了工单段，用户直接和维护者对话（包括立项问答）时开一个"对话段"；维护者干活时的插话进当前段。每段结束时，维护者写回档案时一并写一段摘要，作为下一段的"上一段摘要"。重置维护者的入口在项目页。
- **工单的"等澄清"**由派单方回答：用户发起的问用户；任务维护者派的问任务维护者，它可以再转问用户。用户关掉工单的提问卡，算"按你自己的理解接着做"，维护者照常推进并在时间线上记下（16 号票评审后保留）。多项目任务的工单在计划确认时建出，所属阶段开始时派出。
- **并行**：维护者用"提议并行"工具出并行确认卡；git worktree 由维护者建在工作目录内，用带类型的 git 合并工具合并。（20 号票评审后补）并行确认卡不卡任务，用户处理前维护者照常串行做；再次提议时上一张没处理的卡过期；开发类项目的每个子 agent 必须有自己的、建在工作目录里的 git worktree；有子 agent 在做的阶段不能宣布完成，子 agent 交回结果后阶段交还维护者；任务暂停时子 agent 随之停下，继续后不自动重拉；子 agent 的工具包和授权永远是维护者的子集，维护者被收窄时子 agent 跟着重新装配。
- **工具包变更**：用户自己在项目页或任务详情里扩大能力，不用走计划变更；维护者不在任务里时要加能力，提交一张"工具包变更"卡（计划变更的一种）。导入 skill 的入口在设置里的 skill 库页。
- **工具包的细则**（27 号票评审后定）：skill 不是权限，执行时 skill 取项目工具包和任务的并集，bash、联网、MCP 这些能力取交集；任务里加的 skill 只记在任务上，不改项目工具包。工具包里的 skill 只能从 skill 库里选、MCP 只能选已登记的（提交计划、计划变更、自行调整都检查）。联网开关关着时，会话里没有任何要联网的工具（包括带类型 bash 工具里的推送、建远端仓库、装依赖）；MCP 工具没写联网标记的按要联网算。有计划变更卡在等时，用户仍可直接收窄任务的工具包，扩大要等卡处理完。工具包一改，守卫的下一次判定就按新的。
- **工具包变了立即生效**：用户批准（或自己在项目页、任务详情里改）之后，守护进程等这个 agent 做完手头这一步，就重启它的子进程，按新工具包重新装配会话（固定上下文里的工具包说明随之更新），从会话文件接着干，并追加一条"工具包已变更：……"消息告诉它；skill 的增减同样立即重载。"做完手头这一步"指当前工具调用结束、下一次模型调用之前。代价是那一次的提示词前缀缓存失效。
- **GitHub**：推送、建远端仓库直接用本机已登录的 git 和 GitHub 命令行，二狗不另外管密钥；仍算"以我的名义对外发送或发布"。
- **附件**：文本类文件（含 markdown、代码、CSV）发给模型时内联前 32 KB，并提供"读取附件"工具读全文；PDF 先抽取文本再同样处理；其他类型只给文件名、类型和大小。agent 只能读自己会话里的附件。剥掉 EXIF 后的图片是入库版本，消息和素材引用入库版本的哈希；上传收尾时校验的 sha256 是原始上传字节的。
- **素材检索**：FTS5 trigram 查不了 3 个字以下的词，这类查询退回子串扫描。bge-m3 模型文件不存在时，守护进程提示用户运行一条下载命令，文件放进数据目录的模型区。
- **主动投喂材料**：聊天的附件菜单里有"作为材料投喂"，用户这样发的内容记为"用户主动投喂的材料"。
- **对话里说的限制**由起草计划的维护者编译成时序规则或授权收窄，显示在计划卡上。
- **简单提醒到点**：在待我处理里放一条置顶的提醒事项，页面内提示，用户允许时再发浏览器通知。重复规则支持每天、每周几、每月几号、按我的工作日。
- **工作日历**：用户个人的上班日 = 新加坡工作日（周一到周五、去掉新加坡公众假期，含补假）∪ 国内工作日（周一到周五、去掉法定假日，加上调休补班的周末）∪ 用户自定的额外上班规则（比如"每月最后一个周六"）和手动标记的上班日期 − 手动标记的休息日期。新加坡放假、国内上班的撞日因此算上班。
  - 节假日数据是框架自带的公开数据，来源和已公布年份见 `docs/research/13-holidays-sg-cn.md`；每年 12 月一个内部作业检查下一年的数据，缺了就在待我处理里提醒，用户点一下发起一个联网任务去更新（秘书不能联网）。
  - 额外规则和手动标记是个人数据，放在数据目录的配置里。入口：主导航的日历页（按月看，每天标明上班或休息及原因，点某天在当天详情里改；额外规则在设置的工作日规则页里加）；也可以对秘书说"下周一我不上班"，秘书出一张快速动作卡，确认后由运行时改配置。
  - 简单提醒和定时作业的重复规则都可以选"按我的工作日"。
- **设备配对**：设备名默认取浏览器和系统信息，新设备上可改；批准卡上显示短码和短指纹供核对。经隧道来的请求，以 nginx 覆盖写的 `X-Real-IP` 作为来源。nginx 部署由用户在本机运行一条命令完成，运行命令即为确认。批准配对不算素材。
- **备份**：同步目录里每周留的那一份取周日的快照。
- **token 记账**：范围审视的用量记在对应维护者的任务或项目名下，标"范围审视"；定时作业的用量记在作业名下。
- **时间线全局层**：任务按阶段着色，项目维护者会话按工单段着色，秘书主线按天着色。
- **语音识别**（2026-10-08 实测后用户定）：faster-whisper large-v3，显卡上用 int8_float16（显存约 2.1GB，15 秒中文约 1.2 秒，冷启动多约 4 秒），用时拉起、闲置 5 分钟退出释放显存；显卡不可用或显存不够时退回 CPU 跑 small。实测 CPU 跑 large-v3 约 4–5 倍于语音时长、small 错字多，所以不默认用 CPU。
- **语音合成**（同上）：共用本机 LSM 托管的 audio.cpp 服务（drama 的 TTS 引擎，Fish-Audio S2 Pro，第一次用到时加载，显存约 7.3GB，已加载时合成一句 4 秒的话约 3.3 秒），经它的 HTTP 接口用参考音色（WAV 和逐字稿）克隆；二狗在 LSM 里对它声明弱依赖，它没开时语音回复退回只发文字。两者同时在显卡上合计约 10.2GB / 12GB。audio.cpp 读不了带中文的路径，导入的参考音色在数据目录里用英文文件名存。

### 22. 语音消息

（用户 2026-10-08 加入第一阶段，取代"Out of Scope"里的"语音服务"。）

- **语音输入模式**（照微信）：输入栏右侧一个按钮在"文字 / 语音"之间切换；左边的加号（附件菜单）不变。语音模式下整个输入框变成"按住 说话"。按住时弹出录音面板，实时显示当前音量和最近一小段波形（滚动，只显示最新的几秒）；抬手直接发送；按住时手指（或鼠标）上划超过一段距离就进入"松开取消"，抬手不发送。触屏和鼠标都支持。单条最长 60 秒，最后 10 秒倒计时，到 60 秒自动发送；不到 1 秒的提示"说话时间太短"、不发送。没有麦克风权限时提示怎么开。界面参考 vibecraft 的语音输入（只参考界面）：vibecraft 是边说边在服务器识别、客户端实时显示文字，效果不好；二狗只在本地录音，抬手后整段上传，**上传完成后由服务器识别**。
- **语音气泡**：语音消息在聊天里显示成和文字类似的气泡，带播放图标和时长，宽度随时长变；点一下播放或暂停（同一时间只播一条）；用户发的语音，识别出的文字默认直接显示在气泡下方（识别中显示"识别中"），这段文字就算用户对识别结果的确认；长按（桌面上右键）弹出菜单，至少有"复制文字"，失败的有"重新识别"，以及消息通用的菜单项（引用等，等消息有了通用菜单再加）。agent 发的语音也显示成气泡，长按"转文字"展开送进 TTS 的原文。（用户 2026-10-08 改：去掉大模型修正，识别文字默认直接显示。）
- **一条语音 = 一个数据对象**：服务器端把语音和它的文字绑在一起，作为同一个对象保存，方便以后用。
  - 用户发的语音：音频（入库的媒体，按内容哈希）、时长、格式、波形摘要（画气泡用）；faster-whisper 直接识别的结果（原文、分段时间、语言、模型名）；识别状态（排队、识别中、完成、失败）。
  - agent 发的语音：音频、时长；送进 TTS 的原文；所用的参考音色、TTS 模型；这条语音对应的完整回复（文字、图片、视频等）在哪条消息里。
- **识别**：上传完成后，守护进程用 faster-whisper 识别出文字（第一阶段不再用大模型修正）。识别是运行时自动做的：agent 收到的是识别出的文字（注明"语音转写"），识别完成之前这条输入在 agent 的输入队列里等着；识别失败时 agent 收到"[语音，识别失败]"，用户在气泡菜单里可以重新识别。
- **识别的运行方式**：faster-whisper 由守护进程按需拉起的 Python 识别进程运行（放进 Job 对象，闲置一段时间自动退出），Python 路径、设备（显卡 / CPU）、模型都在配置里。默认值见第 21 节"语音识别"一条（按实测定）。
- **素材**：用户的语音算用户发言（本人），素材文字取识别出的文字，信封标"语音转写"；原文副本里同时存识别文字和音频的引用。
- **快速动作的点明**：语音转写和用户打的字一样参与"点明"判定（气泡下直接显示的识别文字就算确认）；长程任务本来就有计划确认。
- **agent 用语音回复**：只要用户这条消息是语音，agent 就用语音回复（秘书和维护者的会话都一样）。
  - 回复短的，整段合成语音；回复长的，不全文合成：agent 先写一段适合听的口语总结来合成语音，详细内容用文字、图片、视频等照常发到聊天里。是否用语音、什么算"长"由运行时判定和兜底，不只靠提示词。秘书和维护者的会话都有"口语总结"工具（`spoken_summary`）。
  - **模型预热**（2026-10-09 用户定）：二狗启动后在后台提前加载识别模型和合成模型（合成用一条极短的试合成让 audio.cpp 把模型加载好；audio.cpp 后来才开的，开了再预热），识别模型常驻、不因闲置卸掉；设置 · 语音里看得到两个模型的状态。
  - **设置 · 语音**（2026-10-09 用户定）："自动播放 agent 的语音"开关放在语音这一栏（不在外观下面）；语音识别引擎在这里显示成一个选项，目前只有 faster-whisper 这一个（同时显示用的模型、设备和状态），以后加了别的引擎再能选。
  - **麦克风预热**（2026-10-08 用户定，取代"只在按住时开麦"）：进入语音模式就打开麦克风流、备好音量分析，但不录；按下才开始录，所以开头不丢。语音模式期间麦克风指示灯亮着；切回文字模式、离开会话页、页面切到后台就关掉麦克风，闲置不关（用户 2026-10-09 定）。页面里任何输入框获得焦点、窗口失去焦点（分屏切到另一边）时也立即关掉，让系统输入法的语音能用，焦点回来 0.5 秒后再预热（用户 2026-10-09 反馈"麦克风被占用"，调研见 docs/research/16）；按下时预热的音轨已失效就重新打开，录到的是一段静音就不发。
  - **分段合成**（2026-10-08 用户定）：送进 TTS 的稿子按句切段依次合成，合成好一段就推给前端，前端无缝接着播；全部完成后拼成一条完整音频存下。第一声只等第一段。
  - **气泡和自动播放**（2026-10-08 用户定）：语音和它的文字在同一个气泡框里（播放条和时长在上、文字在下），用户和 agent 两侧都这样；用户的语音识别完成就显示文字，agent 的语音长按"转文字"才显示。agent 的语音到了前端自动播放，设置里有开关、默认开（按设备记住）；翻历史、重连补发的不自动播。
  - **显示**（2026-10-08 用户定）：用户发语音的这一轮，回复文字不流式显示，先显示"正在回复…"；长回复照常出文字和附件，口语总结的语音合成好再加一个语音气泡；短回复先显示"正在合成语音…"，合成好只出 agent 的语音气泡，文字在长按"转文字"时才展开；合成失败才显示文字并说明。
  - **总结兜底**（2026-10-08 用户定）：回复长、agent 没写口语总结时，运行时追问它一次；还没有才截取回复开头几句，加一句"详细内容我发在聊天里了"。
  - TTS 经本机 LSM 托管的 audio.cpp 服务（和 drama 共用，地址在配置里；二狗不自己启动它），用参考音色做声音克隆。
  - **参考音色**是个人数据，放在数据目录里：设置里可以导入参考音色（一段干净的 WAV 加它的逐字稿）、试听、选当前用哪一个。不直接列出或引用 audio.cpp 自带的音色库；用户想用其中某个，就手动导入。
  - TTS 失败、服务没开、超时或显卡忙（服务回忙）时，退回只发文字，并在会话里说明；没有任何参考音色时只发文字，并在待我处理里提示去导入。

## Testing Decisions

- **好测试的标准**：只测外部行为，不测实现细节。测试从切面的入口驱动、在切面的出口断言；换掉内部实现、只要行为不变，测试就不该改。每条用户故事尽量能落到某个切面上的一个场景。
- **三个切面**（用户已确认）：
  1. **守护进程对前端的协议（主切面）**：用临时数据目录起一个真的守护进程，模型换成 pi 的 faux provider 按剧本回话；测试扮演一个前端，通过 WebSocket 和 HTTP 发消息、点卡片按钮，断言收到的事件、卡片、看板、待我处理和数据目录里的文件。agent 子进程真的拉起。覆盖：秘书五种形态、快速动作、简单提醒、任务从发起到完成、计划卡确认、工单派发与回执、守卫问用户与批准、阶段验收（脚本和评审）、返工、范围审视、被杀后恢复（测试里直接杀守护进程再起）、素材入库与删除、设备配对与吊销、重连补发、调度和错过补发（用可注入的时钟）、备份与恢复。
  2. **守卫判定**：把判定当纯函数测，表格驱动加场景文件。覆盖关注类别 × 处置 × 对话或任务、底线、授权项（次数、阶段、有效期、收窄）、时序规则四种形态和 v1 模板、bash 拆解和伪工具映射、拆不开的 bash、通用 bash 标记、路径围栏、密钥目录。
  3. **pi 契约测试（升级闸门，ADR-0001）**：单独拉起一个 agent 子进程，接 faux provider，只验二狗依赖的 pi 行为：按工具包装配会话（工具白名单、只注入指定 skill、不读用户目录配置）；`tool_call` 送到守护进程、被拦截时真的不执行；压缩前钩子能拿到待压缩的消息并 `appendEntry`；`before_agent_start` 能改系统提示；能拿到每次调用的用量；插话在下一步之前插入。升级 pi 前先跑这套。
- **Web UI**：不单设切面。前端状态层用切面 1 录下来的真实事件流回放来测；页面主要靠用户评审第一个可点击切片。
- **真实模型**：DeepSeek 只做少量手动冒烟（秘书分流、计划起草、DeepSeek 上中途插入系统消息对前缀缓存的影响），不进自动测试。
- **参照**：
  - AgentSense 的 planguard 场景文件（`scenarios/*.planguard.json`）和 `scripts/planguard-*` 验证脚本：守卫切面的场景文件格式与它兼容，可以直接搬一部分用例。
  - drama_maker 的 `tests/unit/*.test.mjs` 和 `pi-extensions/drama-path-guard`：路径守卫和 pi 扩展的测试写法。
  - pi 自带的 faux provider：切面 1 和切面 3 的模型替身。

## Out of Scope

第一阶段不做，属于第二阶段或更后：

- **记忆的使用**：记忆管理者和内置项目"记忆管理"、做梦阶段、用户卡、每轮记忆简报、深查工具、`request_memory`、记忆范围的实际授予和检查、"了解你"问题、记忆 Web UI、动机挖掘。计划里的记忆范围字段第一阶段只占位；"使用授权范围外的记忆"类别存在但不会触发。
- **推送与远程审批通道**：手机系统级推送、高危审批的原生密钥签名（Keystore / HUKS）。第一阶段紧急度只在 Web 内体现。
- **安卓 App**：第一阶段手机用浏览器访问，鸿蒙 App 已提前做（用户 2026-10-09 加，见第 19 节"鸿蒙 App"）；安卓的 `frontend/android/` 先留空。
- **项目规范**：完整的默认工作流程和文档模板、停用和重新启用的检查清单。
- **运营态项目的服务托管与公网入口**：项目自己的服务在 LSM 注册、项目的公网入口、服务在线监控、运营告警。
- **完整的项目管理界面**、**全景**页。
- **系统级沙箱**（AppContainer 等）。
- **内置 skill 库**的内容。
- **外部连接器**：邮件、IM、日历等对外发送渠道（快速动作和工具只覆盖已登记的 MCP）。
- 用模型判断的自定义关注类别、批准率监测、规则建议、影子运行。
